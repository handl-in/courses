Section 1 — The 20-Line Agent (≈4 pages)

We start with the textbook ReAct loop. Everyone has seen this. We reproduce it with no apologies.

from anthropic import Anthropic

client = Anthropic()
tools = [...]  # defined elsewhere

def agent(query: str) -> str:
    messages = [{"role": "user", "content": query}]
    while True:
        resp = client.messages.create(
            model="claude-sonnet-4-6",
            max_tokens=4096,
            tools=tools,
            messages=messages,
        )
        if resp.stop_reason == "end_turn":
            return resp.content[0].text
        messages.append({"role": "assistant", "content": resp.content})
        tool_results = []
        for block in resp.content:
            if block.type == "tool_use":
                result = dispatch_tool(block.name, block.input)
                tool_results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,
                    "content": str(result),
                })
        messages.append({"role": "user", "content": tool_results})

Walk through it line-by-line. stop_reason == "end_turn" is the agent's way of saying "I'm done." Tool results come back as a user message. The model sees them on the next turn.

Q: Why does the tool result get a user role?

That's the API's convention. Tool results are content that wasn't generated by the model, so it's wrapped in a user turn. Mentally, model the conversation as: user asks → assistant decides + maybe asks tools → "user" returns tool results → assistant continues.

Q: What if the model returns text AND a tool_use in the same response?

It can. resp.content is a list of blocks. Iterate through. Show the text to the user (or log it as the model's "thinking"), execute the tools, return results. The next response will continue the chain.

Section 2 — Five Ways It Breaks (≈6 pages)

We deploy the naive loop and watch it explode. Each failure mode gets a Watch It! block, a reproduction case, and the fix-preview (full fixes come in Section 3).

Failure 1: Infinite loop. Model keeps calling tools without ever ending. The 20-line version has no max-iteration guard. Real example: agent tasked with "find a recent article on X" keeps calling search with slight query variations because the first results don't match its preconception. 47 search calls, $4.20, no answer.

Failure 2: Token exhaustion. Conversation grows unbounded. Around turn 30, the message history is 80K tokens. Around turn 50, you hit context window. The 20-line version has no compression. We don't fix this here (that's Module 8) but we add the detection.

Failure 3: Tool hallucination. Model calls a tool that doesn't exist (get_user_email_v2 instead of get_user_email). Naive code crashes. Production code returns the error to the model so it can retry.

Failure 4: Malformed tool input. Model calls the right tool with wrong-shaped JSON. Same fix family: catch, return error to model.

Failure 5: Transient API errors. 529 overloaded, 500 internal, network blip. Naive code crashes the whole task. Production code retries with backoff.

The Loop That Cost $1,400 in 90 Minutes

A team's "research agent" was deployed Friday afternoon. By Monday, finance had flagged unusual spend on the Anthropic account. The agent had been called once Friday at 4:50pm — the user asked about a topic the model didn't know well. The model called web_search. Results were partial. Model called web_search again. Same results. Again. Again. 1,847 search calls before the customer's session timeout (60 minutes wall-clock) finally killed it.

The fix took five minutes: if turn > 25: break. The lesson took longer.

Section 3 — Hardening Pass 1: Safety Rails (≈5 pages)

We add the cheap, must-have guards.

Max iterations. A hard cap on turns. We default to 25; configurable per task.

Token accounting. Track input + output tokens per turn, cumulative for the whole loop. Print a running tally. (Foreshadows Module 17 observability.)

Cost ceiling. Convert tokens to dollars per turn. Abort if cumulative cost crosses a per-task budget.

Wall-clock timeout. start_time plus a max duration (default 5 minutes for a single agent task).

class AgentBudget:
    def __init__(self, max_turns=25, max_cost_usd=1.0, max_seconds=300):
        self.max_turns = max_turns
        self.max_cost = max_cost_usd
        self.max_seconds = max_seconds
        self.turns = 0
        self.cost = 0.0
        self.start = time.time()

    def check(self):
        if self.turns >= self.max_turns:
            raise BudgetExceeded("turn cap")
        if self.cost >= self.max_cost:
            raise BudgetExceeded(f"cost cap (${self.cost:.4f})")
        if time.time() - self.start >= self.max_seconds:
            raise BudgetExceeded("wall-clock cap")

    def record(self, usage, model_pricing):
        self.turns += 1
        self.cost += (
            usage.input_tokens * model_pricing.input_per_token
            + usage.output_tokens * model_pricing.output_per_token
        )

Section 4 — Hardening Pass 2: Tool Dispatch (≈6 pages)

The tool dispatcher is the most accident-prone surface. We build it properly.

Registration: tools register their schema and handler in one place. No drift between "what we told the model" and "what we actually run."

@dataclass
class Tool:
    name: str
    description: str
    input_schema: dict
    handler: Callable[[dict], str]

class ToolRegistry:
    def __init__(self):
        self._tools: dict[str, Tool] = {}

    def register(self, tool: Tool):
        self._tools[tool.name] = tool

    def schemas(self) -> list[dict]:
        return [
            {"name": t.name, "description": t.description, "input_schema": t.input_schema}
            for t in self._tools.values()
        ]

    def dispatch(self, name: str, input: dict) -> str:
        tool = self._tools.get(name)
        if tool is None:
            return f"ERROR: unknown tool '{name}'. Available: {list(self._tools.keys())}"
        try:
            return tool.handler(input)
        except Exception as e:
            return f"ERROR executing {name}: {type(e).__name__}: {e}"

Error returns vs. exceptions. Errors come back to the model as tool_result content. Exceptions abort the loop. Get this wrong and you'll either crash on every typo or hide real bugs. Rule: anything the model could fix by calling differently is an error-result. Anything indicating system failure (DB down, OOM) is an exception.

Schema validation. Use jsonschema to validate the model's input against the declared schema before dispatch. Saves you from "the model hallucinated a field and your handler exploded."

Don't return str(exception) blindly. Stack traces leak internals. PII in error messages becomes part of the conversation history. Sanitize before returning to the model.

Section 5 — Hardening Pass 3: Retries and Resilience (≈4 pages)

API errors happen. We classify and handle.

Retryable: 429 (rate limit), 500 (server), 502/503/504 (gateway), 529 (Anthropic-specific overloaded), connection errors.

Non-retryable: 400 (bad request), 401 (auth), 403 (forbidden), 404 (model not found).

Exponential backoff with jitter. Cap retries (default 3). Different backoff for rate limits (longer) vs. transient (shorter).

@retry(
    retry=retry_if_exception_type((
        anthropic.RateLimitError,
        anthropic.APITimeoutError,
        anthropic.InternalServerError,
        anthropic.APIConnectionError,
    )),
    wait=wait_exponential_jitter(initial=1, max=60),
    stop=stop_after_attempt(3),
    reraise=True,
)
def call_model(self, **kwargs):
    return self.client.messages.create(**kwargs)

We use tenacity here; reader can adapt.

Q: Why retry inside the loop instead of letting the whole task fail and retry from outside?

Both have a place. Retry-inside is for transient blips during a task — the user shouldn't see the agent restart from scratch. Retry-outside is for persistent failures (downstream services down for hours). Different triggers, different timeframes.

Section 6 — Hardening Pass 4: Streaming and Backpressure (≈4 pages)

For interactive agents, streaming changes UX. The Anthropic SDK supports client.messages.stream(...). We adapt the loop:

  • Stream text deltas to the user as they arrive.
  • Hold tool_use blocks until they're complete (you can't dispatch a half-formed tool call).
  • Yield events to a callback so the UI can show "thinking..." vs "calling tool X..." vs "got result."
with client.messages.stream(...) as stream:
    for event in stream:
        if event.type == "content_block_delta" and event.delta.type == "text_delta":
            yield TextChunk(event.delta.text)
        elif event.type == "content_block_stop":
            block = stream.current_message_snapshot.content[event.index]
            if block.type == "tool_use":
                yield ToolStart(block.name, block.input)

The hardened version exposes events: TextChunk, ToolStart, ToolResult, TurnComplete, LoopComplete, BudgetExceeded. Downstream code can do anything with them — print to terminal, push to WebSocket, log to traces.

Why can't you start dispatching a tool the moment you see tool_use start in the stream, even though you have its name?

Because the input is built incrementally. You'd dispatch with empty arguments. Wait for content_block_stop for that block.

Section 7 — Hardening Pass 5: Observability Hooks (≈4 pages)

Tracing for free if you build it right. We hook every interesting event:

  • on_turn_start(turn_num, message_count)
  • on_model_request(model, message_count, tool_count)
  • on_model_response(usage, stop_reason)
  • on_tool_call(name, input)
  • on_tool_result(name, result_or_error)
  • on_turn_end(turn_num, cost)
  • on_loop_end(reason, total_cost, total_turns)

Default implementation logs to stdout. Easy to swap with OpenTelemetry, Langfuse, or your own collector. We don't go deep here — Module 17 is the full observability module — but the hooks need to exist now so we can use them later.

The Agent That Worked In Dev

Sam shipped the hardened loop. Worked fine in dev. In prod, occasionally an agent would just... stop responding. No error. No exception. The loop variable just stopped advancing.

Cause: the on_tool_call hook was synchronously logging to a metrics service. The metrics service occasionally took 30 seconds to ack. The async Python framework had a 10-second timeout on the surrounding request. The framework gave up before the hook returned. The agent loop never received the response. No error fired because nothing actually crashed — the request just got dropped.

Fix: hooks are async, fire-and-forget, never block the loop.

Section 9 — Sync vs. Async (≈2 pages)

The hardened loop above is synchronous. For real workloads, you want async. We show the diff:

  • Anthropic → AsyncAnthropic
  • client.messages.create → await client.messages.create
  • Tool dispatch can be async def (and probably should be, for I/O tools)
  • Hook callbacks become async

We don't rewrite the whole thing — just the pieces that change. Reader has both versions in the repo.

If your tools mix sync and async, the dispatcher has to handle both. Use inspect.iscoroutinefunction(handler) to decide whether to await. Or just declare a convention: all tools are async, sync handlers wrap with asyncio.to_thread.
