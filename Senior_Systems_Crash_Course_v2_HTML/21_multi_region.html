MODULE 21

Multi-Region Architecture

Latency budgets, edge POPs, anycast, regional data residency, and the patterns for active-active across continents

Your CEO says: "We just landed a customer in Tokyo. They say our app is slow. Can we put a server in Tokyo?"

That sentence triggers six months of engineering work, three architectural decisions that can't be undone, and a permanent increase in operational complexity. Or, done well, three weeks of work and a clean activation.

The difference is whether you understand the multi-region landscape before the question gets asked. Latency physics, data residency law, consistency vs availability tradeoffs at planet scale, the difference between a CDN, an edge POP, and a region — these aren't optional knowledge for senior engineers. They're the conversation you'll have at every growth stage from "first international customer" to "we serve 40 countries."

This chapter is that landscape, the patterns that work, and the failure modes that have brought down companies you've heard of.

Sam wants to "just put a server in Tokyo"

Sam The Tokyo customer is complaining. Latency is 250ms. We need to put a server there. I'll spin up an EC2 instance in ap-northeast-1, deploy our service, and route Tokyo users to it. Done by Friday?

Maya Done by Friday means broken by Monday. What does that Tokyo server talk to? Your database is in us-east-1. Every database query from Tokyo to us-east-1 is 150ms round trip. If your service makes 5 DB queries per request, you've turned 250ms into 750ms. Worse.

Sam OK so we replicate the database to Tokyo too.

Maya Read replica or write master? If it's a read replica, what happens when the Tokyo customer writes? Reads from Tokyo, writes to us-east-1, see your own write back from Tokyo's stale replica? Hello, customer escalation.

Sam So multi-master?

Maya Now you have write conflicts to resolve, distributed transactions to invent, and possible data divergence. And Japan has data residency laws — some customer data is allowed to leave Japan, some isn't. You haven't even started thinking about that. So no, we are not putting a server in Tokyo by Friday. We're going to spend two days figuring out what kind of multi-region architecture matches our actual constraints.

Sam What kinds are there?

Maya Five patterns, increasing in complexity and decreasing in latency. Most companies start at pattern two and never need pattern five. Let me walk you through them.

There is no "just add a region" operation. Multi-region architecture is a spectrum of patterns trading complexity for latency. The senior skill is choosing the right pattern for your actual constraints — read/write ratios, consistency needs, data residency requirements, and customer SLA tolerance — and resisting the urge to over-engineer.

The physics: latency floors you cannot beat

Everything in multi-region design starts with the speed of light. You cannot make light travel faster. You can only put computation closer to users. This is the foundational reality.

Real-world inter-region latencies (round-trip).

These are typical AWS / GCP / Azure values. Other clouds and on-prem are similar within ~20%.

From To Distance RTT
us-east-1 (Virginia) us-west-2 (Oregon) 3,800 km 60-70ms
us-east-1 eu-west-1 (Ireland) 5,500 km 75-90ms
us-east-1 ap-northeast-1 (Tokyo) 11,000 km 140-160ms
us-east-1 ap-southeast-1 (Singapore) 15,500 km 200-230ms
eu-west-1 ap-northeast-1 9,500 km 220-260ms
Same region, cross-AZ — 50-100 km 0.5-2ms
Same AZ — <10 km 0.1-0.5ms

Theoretical minimum (light in fiber): roughly 5ms per 1,000 km round-trip. Real networks add ~30-50% overhead from routing, equipment, and TCP retransmits. So 11,000 km = 110ms theoretical floor, 140-160ms typical reality.

The latency budget is fixed by physics, not engineering effort. You cannot reduce Tokyo↔Virginia from 150ms to 50ms by buying better servers, hiring better engineers, or paying AWS more money. You can only put compute and data closer to users.

The 5-query trap. A "simple" web request makes 5 database queries (auth check, user lookup, fetch product, fetch inventory, log analytics). Each is a fast 5ms query within a region. Total: 25ms, plus 50ms of app processing = 75ms total. Fast.

Now imagine the user is in Tokyo and the database is in Virginia. Each query becomes 150ms RTT instead of 5ms. Total: 5 × 150ms + 50ms = 800ms. The user sees a 10x slowdown — not because anything is broken, but because physics is happening 5 times.

Lesson: minimize cross-region round trips per request, not just total latency. Batching queries, denormalizing data, using async patterns — these become survival techniques across regions.

Senior framing. Latency budgets are like a financial budget. You have ~200ms total to keep customers happy. Cross-region RTT eats 150ms of that. You have 50ms left for everything — database lookups, business logic, serialization, network within the region. If your app makes synchronous cross-region calls, you've already overspent and can't afford the rest. The architecture must eliminate synchronous cross-region calls on the hot path, not just minimize them.

The five patterns of multi-region architecture

Understand these five. Know which one fits which problem. Senior interviews ask you to name them, contrast them, and pick the right one for a scenario.

Pattern 1: Single region with CDN

Pattern 1 — Single region with CDN. Your application lives in one region (e.g., us-east-1). Static assets (images, CSS, JS, video) are served from a CDN with edge POPs worldwide. Dynamic API calls all go to the single region.

Strengths - Simplest possible architecture. - No data consistency challenges — single source of truth. - CDN handles 80% of byte-volume traffic at the edge for free. - Static-asset latency drops from 200ms to 20ms globally.

Weaknesses - API/dynamic latency still suffers globally. - Single region failure = global outage. - Limited compliance flexibility.

When to use Pattern 1: when your app is mostly static (content sites, marketing pages, video streaming, e-commerce browsing). When dynamic API calls are infrequent or tolerant of 100-300ms latency. When all your customers are in one continent. Most startups should start here. Don't over-engineer.

Tools: CloudFront, Cloudflare, Fastly, Akamai, Cloudflare Workers (for edge compute).

Pattern 2: Single-region writes, multi-region reads

Pattern 2 — Single-region writes, multi-region reads. All writes go to one primary region. Read-only replicas live in other regions. Most user requests hit local replicas; writes pay the cross-region latency cost.

                ┌─────────────────────┐
                │   us-east-1 PRIMARY │
                │   (writes go here)  │
                │                     │
                │   ┌──────────────┐  │
                │   │  PostgreSQL  │  │
                │   │   PRIMARY    │  │
                │   └───────┬──────┘  │
                └───────────┼─────────┘
                            │ async replication
              ┌─────────────┼──────────────┐
              ▼                            ▼
    ┌─────────────────┐         ┌─────────────────┐
    │   eu-west-1     │         │ ap-northeast-1  │
    │   READ REPLICA  │         │   READ REPLICA  │
    │   (Ireland)     │         │   (Tokyo)       │
    │                 │         │                 │
    │   reads local   │         │   reads local   │
    │   writes → US   │         │   writes → US   │
    └─────────────────┘         └─────────────────┘

Strengths - Reads are fast everywhere (~5-20ms). - Single writer = no conflict resolution. - Simple operational model. - Works well for read-heavy workloads (95%+ reads, like most consumer products).

Weaknesses - Writes are slow for non-primary-region users (150ms+). - Read-after-write inconsistency: user writes in Tokyo, replica is 100ms behind, user re-reads, sees stale data. - Primary region failure = no writes globally.

When to use Pattern 2: read-heavy workloads (95%+ reads), users tolerate occasional slow writes, single-writer is OK from a business perspective. Most SaaS products fit here for years.

Common implementations: - PostgreSQL with read replicas across regions (logical or physical replication). - MySQL with read replicas via async replication. - Aurora Global Database — managed AWS solution with cross-region replicas, ~1 second lag. - Spanner if you need stronger consistency on reads (but it's a different beast — see Pattern 5).

Read-after-write inconsistency in Pattern 2. User in Tokyo writes "update profile photo" → goes to us-east-1 primary → succeeds → user immediately reloads → request goes to Tokyo replica → replica hasn't received the change yet → user sees old photo.

Mitigations: 1. Read-your-writes routing. After a write, route subsequent reads from that user to the primary for N seconds (typically 5-30s). Tradeoff: some reads pay cross-region cost. 2. Sticky sessions to primary for write-heavy operations. 3. Optimistic UI — show the new photo immediately, sync with replica eventually. 4. Wait-for-replication — after write, return a "replication position" token; read with that token; wait until replica catches up. Postgres has pg_wait_for_replay_lsn.

Senior teams pick mitigation per-feature, not globally.

Pattern 3: Active-active with conflict resolution

Pattern 3 — Active-active multi-master. Multiple regions accept writes. Conflicts are resolved by some strategy: last-write-wins, vector clocks, CRDTs, or application-level merge.

    ┌─────────────────┐         ┌─────────────────┐
    │   us-east-1     │◄───────►│   eu-west-1     │
    │   READ + WRITE  │  bidir  │   READ + WRITE  │
    │   (Virginia)    │  sync   │   (Ireland)     │
    │                 │         │                 │
    └────────┬────────┘         └────────┬────────┘
             │       conflicts           │
             │       resolved            │
             │       per-strategy        │
             │                           │
             ▼                           ▼
       ┌─────────────────────────────────┐
       │  Conflict resolution layer:     │
       │  - Last-write-wins (timestamps) │
       │  - Vector clocks                │
       │  - CRDTs                        │
       │  - App-level merge              │
       └─────────────────────────────────┘

Strengths - Local writes everywhere (~5-20ms). - Region failure tolerated (other regions keep writing). - Geographic load distribution. - Best customer-facing latency.

Weaknesses - Conflict resolution complexity. - Possible data divergence if conflict resolution is buggy. - Harder to reason about correctness. - Eventual consistency, not strong.

Conflict resolution strategies:

  1. Last-write-wins (LWW). Each write has a timestamp. The latest timestamp wins. Lose-data-if-clocks-skew. Simplest, weakest. Cassandra default.
  2. Vector clocks. Each write tracks a version vector across nodes. Conflicts are detected, not auto-resolved — usually surfaced to the application. Riak, DynamoDB Streams.
  3. CRDTs (Conflict-free Replicated Data Types). Data structures that mathematically merge without conflict (counters, sets, registers). Powerful but constraint-laden — you can't make any data type a CRDT.
  4. Application-level merge. Detect conflicts, apply business logic to resolve. Most flexible, most code.
  5. Operation-based replication (OT, ot.js). Used in collaborative editing (Google Docs). Operations transformed against each other. Specialized.

The classic LWW disaster. Two users update the same document at "the same time" (within 100ms). User A in Tokyo, User B in London. Tokyo's write lands at timestamp 12:00:00.150, London's at 12:00:00.140. London's write is "earlier" by 10ms — but actually User B clicked save after seeing User A's name in the document. The wall-clock-earlier write was the semantically-later one. LWW silently discards User A's edits.

This is why LWW is fine for caches, awful for collaboration data. Senior engineers know LWW is a weak conflict resolution and use it only when data loss on conflict is acceptable.

Pattern 3 in practice. Used by: - DynamoDB Global Tables (multi-region multi-master, LWW resolution). - Cassandra with multi-DC replication (LWW with timestamp-based resolution). - Couchbase XDCR. - CockroachDB in multi-region active-active mode (uses Raft for stronger consistency — a hybrid).

Most companies that successfully run Pattern 3 are running it with very specific data shapes that conflict-resolve cleanly: append-only events, key-value caches, idempotent state. Few succeed at Pattern 3 with general relational data.

Pattern 4: Region-pinned data (sharded by user/tenant)

Pattern 4 — Region-pinned data. Each user or tenant is assigned to a "home region." Their data lives there primarily. Requests are routed to the user's home region. Cross-region access is rare and explicit.

              ┌─────────────────────────┐
              │   Routing layer (DNS,   │
              │   GeoDNS, or smart LB)  │
              │   "where is this user?" │
              └────────────┬────────────┘
                           │
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
  ┌──────────┐      ┌──────────┐      ┌──────────┐
  │us-east-1 │      │eu-west-1 │      │ap-tokyo  │
  │          │      │          │      │          │
  │US users' │      │EU users' │      │JP users' │
  │data lives│      │data lives│      │data lives│
  │HERE      │      │HERE      │      │HERE      │
  └──────────┘      └──────────┘      └──────────┘

  Each region is the SOURCE OF TRUTH for its users.
  Cross-region queries are rare/explicit.

Strengths - Local reads AND writes for each user (everyone is fast). - Natural data residency compliance (German user's data stays in Frankfurt). - Regional fault isolation (US outage doesn't affect EU users). - No cross-region conflict resolution — each user has one home.

Weaknesses - Cross-user queries get harder (analytics, social features). - "User moves to a new country" is a data migration. - Per-region capacity planning (one region might be hot). - Identity/auth services usually still need to be global.

When to use Pattern 4: SaaS B2B (each customer is a tenant), social products (group users by primary geography), regulatory data residency requirements (GDPR, China, India, healthcare), low-write-volume "user profile" type data.

Implementations: - Application-layer routing (your service knows the user→region mapping). - DNS-based routing (api-eu.yourapp.com vs api-us.yourapp.com). - AWS Route 53 with geolocation routing. - Cloudflare with regional services. - Some databases support this directly (CockroachDB regional-by-row tables, MongoDB zone sharding).

Real Pattern 4 example. A B2B SaaS serves companies in US, EU, and APAC. Each customer's data is fully contained in their region. Cross-customer features (admin dashboards, billing) are global services that aggregate from regional sources async. New customer signs up: their region is determined by company HQ; data lives there permanently.

When the customer wants to migrate (acquired by a US parent company, moves to US), it's a planned migration: dump from EU, import to US, switch routing. Hours-to-days of work, but rare and explicit.

This is the pattern that scales cleanly to 50+ regions and survives regulatory changes.

Pattern 5: Globally consistent (Spanner / CockroachDB / FoundationDB)

Pattern 5 — Globally consistent active-active. Multiple regions accept writes. Strong consistency (often serializability or external consistency) is preserved across regions via consensus protocols. Achieves strong consistency at the cost of cross-region latency on writes.

Strengths - Strong consistency globally — no app-level conflict resolution. - ACID transactions across regions. - Reads can still be local (if using "follower reads" or "stale reads"). - Single mental model for developers.

Weaknesses - Cross-region writes pay full RTT cost (consensus needs majority of regions to agree). - Significantly more expensive than other patterns. - Operational complexity is real (Spanner runs on TrueTime, CockroachDB on hybrid logical clocks). - Regulatory compliance still requires careful zone configuration.

When to use Pattern 5: financial systems (banking, exchanges) where strong global consistency is non-negotiable; inventory systems with global SKUs; scenarios where conflict resolution complexity is itself unacceptable. Read-after-write must be globally true.

Implementations: - Google Cloud Spanner. Uses TrueTime (atomic clocks + GPS). Five-9s SLA at multi-region. - CockroachDB. Uses Raft per-range; configurable consistency vs latency. - YugabyteDB. Postgres-compatible distributed SQL. - FoundationDB. Different model — single-region usually, multi-region adds complexity. - TiDB. MySQL-compatible distributed SQL.

Senior nuance: Spanner is external consistency, not just serializability. External consistency means: if transaction T1 commits before T2 starts (in real wall-clock time), then T1 will appear before T2 in the global serialization order. This is stronger than serializability — it's called "linearizability for transactions." Achieved via TrueTime, which provides bounded clock uncertainty (Google's claim: ε < 7ms typically).

Most distributed databases offer serializability but not external consistency. Spanner is unique in providing it. CockroachDB approximates it with hybrid logical clocks (HLC).

If an interviewer asks about Spanner specifically, drop "external consistency via TrueTime." That's the senior signal.

Choosing a pattern: the decision tree

Step-by-step pattern selection.

  1. Are most of your users in one region currently? Yes → start with Pattern 1 (single region + CDN). Don't over-engineer.

  2. Is your workload >90% reads? Yes → Pattern 2 (single-region write, multi-region reads) is the right next step. Cheap, simple, effective for SaaS.

  3. Do you have data residency requirements (GDPR, China, India)? Yes → Pattern 4 (region-pinned data) is mandatory regardless of other choices. You'll need to combine it with another pattern for cross-region features.

  4. Do you need globally strong consistency? Yes → Pattern 5 (Spanner-class). Expensive, but necessary for finance/inventory/exchanges. Most companies don't actually need this — interrogate the requirement carefully.

  5. Do you need writes from every region with low latency, and can your data tolerate eventual consistency? Yes → Pattern 3 (active-active with conflict resolution). Pick conflict resolution per data type — LWW for caches, CRDTs for counters, app-level for business logic.

  6. Most likely real answer for senior teams: a hybrid. Pattern 4 for user-owned data (residency compliance), Pattern 2 for catalog/reference data (read-heavy global), Pattern 5 only for the few datasets that genuinely need global strong consistency (e.g., billing).

"There is no single multi-region architecture. Senior systems use different patterns for different data types — region-pinned for user data, replicated for catalog, globally consistent for billing — composed thoughtfully."

Edge POPs vs regions vs availability zones

These three concepts are constantly conflated. Senior engineers distinguish them precisely.

Availability Zone (AZ) A single data center (or small cluster) within a region. AZs are connected by fast, dedicated fiber (1-2ms RTT). Failures of an AZ are independent (different power, different network paths).

Region A geographic area containing 2-6 AZs (e.g., us-east-1 has 6 AZs in northern Virginia). Regions are isolated — failures don't propagate. A region failure is rare but possible (entire AWS us-east-1 has had multi-hour outages).

Edge POP / Edge Location A small presence-of-network in a city, intended for caching, TLS termination, and latency-critical compute. CDNs have hundreds (Cloudflare claims 300+ POPs). They have limited compute and storage — not full region capabilities.

Edge compute Running application logic at edge POPs. Examples: Cloudflare Workers, AWS Lambda@Edge, Fastly Compute@Edge. Limited language support, limited execution time, no persistent state. Best for filtering, routing, lightweight transforms.

The hierarchy: Edge POP (latency, caching, light compute) → Region (full compute and storage, most workloads live here) → Multi-region (multiple regions for residency, redundancy, geo-distribution). Each layer has different capabilities and costs. Senior architecture uses each appropriately: static and lightweight stuff at edge, heavyweight at region, distributed where needed.

Edge POPs done right. Authentication: TLS terminates at edge. Token validation happens at edge (cached JWTs). Cookie inspection at edge. Result: 50-80% of unauthenticated traffic gets blocked at edge (DDoS protection, abuse blocking) before it ever hits the region. The 20% that's authenticated proceeds to the region for actual processing.

Result: region traffic is reduced 5x, regions handle real work, edge handles network garbage. This is what edge POPs are good at.

Edge POPs are not databases. A common mistake: treating edge POPs as regional database mirrors. They're not. Edge POPs have limited storage (often KV stores with 25MB-100MB limits per key, eventually consistent across the network), no transactions, and slow writes. Use them for caching and routing, not as primary data stores.

Routing traffic across regions

You have multiple regions. How does a user in Tokyo find the right one? Three main approaches.

DNS-based routing (GeoDNS)

How GeoDNS works. A user's resolver queries api.yourapp.com. The DNS server inspects the resolver's IP, infers geographic location, returns the IP of the nearest region's load balancer.

Strengths: simple, works everywhere, no client changes needed, supports any protocol.

Weaknesses: DNS caching (stale routing for minutes-to-hours), resolver IP ≠ user IP (a user in Tokyo using a DNS resolver in California gets misdirected), DNS-level routing can't react to application-level health (DNS doesn't know your service in Tokyo is failing).

Tools: AWS Route 53 (geolocation/latency-based routing), Cloudflare DNS, NS1, GCP Cloud DNS.

Anycast routing

Anycast advertises the same IP address from multiple regions. The internet's routing protocol (BGP) automatically directs traffic to the closest region by network distance. No DNS lookup needed; routing is at the IP layer.

Strengths of anycast - Routing is automatic and reactive (BGP convergence takes seconds, not DNS TTLs). - No DNS-resolver-IP confusion. - Failover is fast — if a region disappears, BGP routes around it automatically. - Works under DDoS — attack traffic is distributed across all regions.

Weaknesses of anycast - Requires owning IP space and BGP capability (cloud providers handle this for you). - TCP connections can break if BGP re-routes mid-connection. - Limited control over which region serves which user.

Cloudflare's edge network is anycast. When you point DNS at Cloudflare, you get one IP that resolves to the closest Cloudflare POP via BGP. AWS Global Accelerator and GCP Cloud Load Balancing also use anycast. This is how modern CDNs achieve millisecond-level global routing.

Application-layer routing

How it works. A first-tier service (could be at edge) inspects the request — JWT claim, header, cookie, query parameter — and decides which region to route to. The user's "home region" is encoded in their identity, not derived from their network location.

Strengths: precise control, easy to override (testing, migration, regulatory exceptions), works with stateful sessions.

Weaknesses: adds a hop, requires the routing layer itself to be globally distributed (often via anycast).

Tools: Cloudflare Workers, Fastly Compute@Edge, AWS Lambda@Edge — all of these can do app-layer routing at edge POPs.

Senior pattern: combine routing layers. Anycast or GeoDNS gets the user to some region's edge. Edge logic inspects the user's identity and routes to the correct home region for their data (Pattern 4). This combines fast network routing with precise data routing.

Data residency: the requirement that overrides everything

Data residency laws are not negotiable. GDPR, China's PIPL, India's DPDP Act, Russia's data localization law, and many others require certain customer data to be stored and processed within specific jurisdictions. Senior architects know this before they design — retrofitting residency is expensive and slow.

What residency means in practice

Residency requirements you might encounter:

  1. EU GDPR. EU residents' personal data must remain in adequate jurisdictions (EU + a list of approved countries). Schrems II ruling complicated US transfers significantly. Many EU enterprises now require data does not leave EU.

  2. China (PIPL). Personal information of Chinese residents must be stored in China. Cross-border transfer requires regulatory approval. Most non-Chinese cloud providers operate via partnerships (AWS via Sinnet, Microsoft via 21Vianet).

  3. India (DPDP). Personal data must be stored in India for "significant" platforms. Sectoral rules (banking, telecom) have stricter local-only requirements.

  4. Russia. Personal data of Russian citizens must be processed on servers in Russia.

  5. Healthcare (HIPAA, etc). Sectoral, not geographic, but often pushes for regional compliance.

  6. Financial services. Many regulators require core records to remain in-country.

The retrofit nightmare. A SaaS expanded into Germany without explicitly designing for GDPR. Six months later, an enterprise customer demanded data-stays-in-EU contractual guarantees. Engineering had to: stand up an EU region, migrate German customer data, modify auth and billing services to support per-region data routing, audit every log/cache/backup that might contain EU PII, and prove all of it to the customer's compliance team. Result: 9 months of engineering work to retrofit something that would have been 6 weeks if designed for from day one.

Lesson: if you might serve EU customers, design Pattern 4 (region-pinned) from the start.

Senior compliance moves: - Tag every data store with a "residency class" (none / EU-only / US-only / customer-controlled). - Design auth and routing so each user is associated with a residency region from signup. - Log analysis: any PII in logs is "data" for residency purposes. Most companies forget this. - Backups: backup encryption keys and storage location are subject to residency. EU data backed up to US S3 is a residency violation regardless of encryption. - AI/ML pipelines: moving customer data to a model-training region is a transfer event.

The compliance theme: data leaves the residency region every time it's processed, not just when it's stored. Caches, queues, function memory, log aggregators — all of these "process" data.

Three exercises

Exercise 1: The "we just got a Tokyo customer" question.

Your CEO tells you: "We just signed a Tokyo enterprise customer doing $2M ARR. They say our app is too slow. They want a 100ms p99 SLA. Right now from Tokyo, p99 is 800ms. What's your plan?"

There's no one right answer. The senior approach interrogates the requirement, presents options, and recommends a staged plan.

Senior answer:

"Three things first. (1) What does the customer actually mean by 'slow'? Page load? API call? Specific operation? (2) Is the 100ms p99 a contractual SLA or a stated preference? (3) What's the current architecture — single region, where, what's the read/write ratio for this customer's use case?

Assuming this is a typical SaaS app with reads >> writes, here's my recommendation, staged:

Phase 1 (2-3 weeks): Pattern 1+ ('CDN-everything'). - Move all static assets behind a global CDN. - Enable HTTP/2, compression, connection reuse, image optimization. - Aggressive HTTP caching where possible. - Move TLS termination and authentication to edge. - This typically gets perceived load times down 30-50%, even with API still in us-east-1. May satisfy the customer for asset-heavy operations.

Phase 2 (4-8 weeks): Pattern 2 ('read replicas in Tokyo'). - Stand up read replica in ap-northeast-1. - Route Tokyo customer's reads to local replica. - Writes still go to us-east-1 (acceptable if customer's workload is read-heavy). - Implement read-your-writes routing so the Tokyo user sees their own writes immediately (route their reads to primary for 5s after a write). - This typically gets read p99 to <50ms, write p99 to ~150-200ms.

Phase 3 (3-6 months) IF needed: Pattern 4 ('Tokyo home region'). - If write latency is still unacceptable, region-pin this customer's data to Tokyo. - Route their full traffic (reads and writes) to a Tokyo deployment. - This is real engineering investment — only do it if the customer's $2M ARR justifies it.

My recommendation: start Phase 1 immediately. Commit to Phase 2 within 2 months. Don't promise Phase 3 in the contract — gate it on actual measured customer experience.

The thing I'd push back on: the 100ms p99 SLA. Across global multi-region, 100ms p99 is achievable for reads, very hard for writes. I'd negotiate to 150-200ms p99 for writes specifically, with a stronger commitment on read latency. Pretending we can hit 100ms on writes from Tokyo with a US database is a future support escalation.

What this signals to the CEO: I have a phased plan, I respect the customer, I'm honest about what's hard, and I'm not going to overcommit to a number we can't hit."

Exercise 2: Active-active conflict resolution.

You're designing a multi-region active-active deployment for a collaborative document editing product. Two users in different regions edit the same document at the same time. What conflict resolution strategy do you choose, and why?

LWW will be tempting. It will also be wrong here. Think about what kind of data this is.

Senior answer:

LWW is wrong for collaborative editing. If User A's cursor adds "important note" at position 100, and User B's cursor adds "delete this paragraph" at position 95, LWW based on timestamps would silently discard one of the operations. That's the worst possible outcome — silent data loss in collaboration.

The right answers are operation-based:

Operational Transformation (OT), used historically by Google Docs. Each edit is an operation (insert, delete, format). Concurrent operations are transformed against each other so they can be applied in any order with the same final result. Complex, well-studied, requires a server to coordinate.

CRDTs for text (Y.js, Automerge, RGA, LSEQ). Modern approach. Each character has a unique ID; insertions and deletions are commutative through clever ordering. Can be peer-to-peer, no central coordinator needed.

My recommendation for a multi-region product: - Use a CRDT-based text representation (Y.js or Automerge). - Replicate operations across regions, not state. Each region applies operations as they arrive — eventual convergence is mathematically guaranteed. - Persist the operation log per region; regions catch up on each other's logs asynchronously. - For features that aren't text (comments, share permissions, document metadata), use simpler conflict resolution: app-level merge for permissions (union of grants), LWW with audit trail for permissions (since data loss on simultaneous permission changes is recoverable from audit log).

What this signals: named specific algorithms (OT, CRDTs), distinguished text from non-text, picked CRDTs as the modern answer, addressed how non-text fields would resolve, and noted the recoverability tradeoff.

The non-senior answer is "use last-write-wins with timestamps." Do not give that answer — it shows you don't understand collaborative data.

Exercise 3: The residency/compliance scenario.

A US-based startup grows to 50K customers. About 30% are in EU. The legal team raises GDPR concerns. The CTO wants to "add an EU region." Walk through what actually needs to happen.

"Add an EU region" is shorthand for a multi-month workstream. Senior engineers know that, name it, and scope it.

Senior breakdown of the actual work:

Step 1: Define what data is regulated. - Customer PII (name, email, phone, address) — clearly regulated. - Customer business data (their content) — usually customer-controlled, often regulated. - Logs and analytics that contain user IDs or IPs — regulated. - ML training data derived from customer interactions — regulated. - Backups of all the above — regulated.

Step 2: Tag every data store. - Primary databases: which contain EU customer data? - Secondary stores: caches, queues, search indices, analytics warehouses. - Operational stores: log aggregators, APM systems, error trackers. - Backups: where are backups stored, and where can they be restored?

Step 3: Architecture decision — Pattern 4 home regions. - New EU customers: signup creates an "EU home region" association from day one. - Existing EU customers: planned migration. Communicate timeline. Migrate per-customer. - Routing: auth tokens carry residency claim. Edge layer routes EU customers to EU stack.

Step 4: Per-service compliance audit. - For each service in the request path, ask: does it process or store data? If yes, does it need an EU deployment? If yes, how do we ensure EU-routed traffic stays EU? - Common gotchas: Stripe (uses US for payment processing — Schrems II concerns), email providers (SendGrid in US), error tracking (Sentry US), analytics (Segment, Mixpanel US destinations).

Step 5: Backup and DR strategy. - EU data backed up to EU storage (EU-region S3/GCS). - Disaster recovery: if EU region fails, can you fail over without violating residency? (Usually no — DR must be within EU; multiple EU regions or multiple EU AZs.)

Step 6: Documentation and customer-facing assurances. - Updated DPA (Data Processing Agreement). - Subprocessor list (every third party that touches data). - Audit and ISO 27001/SOC 2 certification often required.

Realistic timeline: 4-9 months from "let's add EU region" to "we can sell to GDPR-strict enterprises with confidence." Engineering work is the smallest part — most time is spent on auditing the full data flow, including third parties.

What this signals: treats residency as a system property, not a region deployment. Names specific audit areas. Acknowledges third-party dependencies (Stripe, Sentry, etc.) as compliance gates. Realistic about timeline.

No dumb questions

Q: How do I know if I actually need multi-region?

Three real triggers: (1) a customer demands an SLA your single region can't meet, (2) regulatory residency requires it, (3) your single-region failure tolerance is unacceptable for the business. If none of these are true, multi-region is premature optimization. Most companies can serve global users from one region with a CDN for years.

Q: AWS Aurora Global Database — what pattern is that?

Pattern 2 with managed plumbing. One primary region, up to 5 read-only secondary regions, ~1 second replication lag. AWS handles the replication; you handle the application logic for read-your-writes. Good fit when your workload matches Pattern 2 and you don't want to operate replication yourself.

Q: What about CockroachDB? Pattern 3 or Pattern 5?

Pattern 5 (globally consistent) with knobs that let you tune toward Pattern 4 (regional locality). Each table can be configured: regional-by-row (data lives in user's home region), regional-by-table (whole table in one region), global (replicated everywhere). It's the most flexible — and most operationally complex — option.

Q: How do I handle caching in multi-region?

Per-region cache, never global. Don't try to invalidate a cache across regions synchronously — too slow. Either use TTL-based eventual consistency (stale data for 1-60 seconds) or invalidate via async messages (cache region listens for invalidation events). Senior pattern: cache-by-region, accept eventual consistency, design TTLs to match business tolerance.

Q: What about session storage across regions?

Three options: (1) sticky sessions to home region (user always lands in same region), (2) session in JWT/cookie (no server-side state), (3) globally replicated session store (Redis/DynamoDB Global Table). Senior teams default to option 2 (stateless via JWT) — it's the cleanest. Sticky sessions are fine for some workloads. Globally replicated session stores have all the consistency challenges of multi-region data.

Q: How do I test multi-region behavior?

Three layers: (1) integration tests that use real multi-region infrastructure (slow, expensive — run nightly, not per-PR), (2) latency injection in test environments (simulate cross-region RTT in single-region test setups), (3) chaos experiments that disable a region in production-shaped staging. The latency injection is underused — your single-region tests don't catch the "5x DB queries from Tokyo" trap.

Q: When does it make sense to have more than 3 regions?

When customer concentration justifies it. The marginal value of region 4-5-6 drops fast: most users are within 100ms of some major region already. Consider 4+ regions when: regulatory (EU + China + India + US is realistic for global SaaS), latency-critical workloads (gaming, trading), or extreme reliability requirements (telco-grade). Most products do well with 2-3 regions.

Q: What's the cost premium for multi-region?

Rough rule: 2 regions ≈ 1.6-1.8x single-region cost (some sharing of fixed costs). 3 regions ≈ 2.5-2.8x. 5+ regions ≈ 4-5x. The non-linear scaling comes from cross-region data transfer (egress is expensive — AWS charges $0.02-0.09/GB for inter-region transfer), redundant infrastructure, and operational overhead.

Three myths

MYTH: "Multi-region equals high availability."

Multi-region enables HA but doesn't guarantee it. A poorly-designed multi-region system can fail in more ways than a well-designed single-region one — split-brain scenarios, cross-region cascade failures, replication lag during regional outage. Companies have caused outages by adding a second region (e.g., a misconfigured cross-region replication amplifying load). Multi-region requires more operational discipline, not less.

MYTH: "We just need to put a database in each region."

Database is the easy part. The hard parts are: routing logic, cross-region transactions, identity/auth coordination, configuration consistency, deploy coordination across regions, observability across regions, and dependency management (third parties may not be multi-region). Companies that focus only on the database typically rebuild their architecture twice — once for "we have multiple databases" and once for "everything else also needs to be multi-region."

MYTH: "CDN solves all our latency problems."

CDN solves static asset latency. It does not solve API latency. Most modern apps are dynamic — interactive APIs, personalized data, real-time updates. A CDN reduces page-load time but doesn't reduce the latency of "save document" or "place order." Senior architects know what fraction of their latency budget goes to dynamic API vs static assets, and choose patterns accordingly.

Five gotchas

GOTCHA 1: Replication lag amplifies during incidents.

Normal cross-region replication: 100-500ms lag. During a primary-region incident (load spike, failure recovery), lag can grow to seconds or minutes. Applications that ignore replication lag silently — assuming reads are fresh — show stale data during incidents, exactly when customers are most attentive to errors. Always check replication lag before serving from replica; have a "lag threshold" beyond which you fall back to primary or error.

GOTCHA 2: Cross-region data transfer is expensive.

AWS inter-region data transfer: $0.02-0.09 per GB. For a system replicating 10 TB/day cross-region, that's $200-900/day = $6K-27K/month just for data transfer. Senior architects: minimize cross-region traffic, use compression, batch operations, leverage cloud-provider-managed replication (which is often cheaper than DIY).

GOTCHA 3: DNS TTLs control your failover speed.

If your DNS TTL is 300 seconds (5 minutes), a regional outage means at minimum 5 minutes of broken routing for users whose DNS is cached. Most public resolvers respect TTLs reasonably; many corporate resolvers cache for hours. Senior pattern: low TTLs (60s) for routing-critical records, with the understanding that some clients ignore TTLs anyway. Anycast bypasses DNS TTL entirely — another reason to use it.

GOTCHA 4: Configuration drift between regions.

Each region's services have config files, feature flags, environment variables. Over time, regions drift. A bug fix deployed only to us-east-1, a feature flag enabled only in eu-west-1, a database tuning param adjusted only in Tokyo. Eventually, a routing change exposes the drift catastrophically. Senior teams enforce config-as-code, region-parameterized only where strictly required, and audit drift periodically.

GOTCHA 5: Time zones and date handling get worse multi-region.

A "yesterday" in Tokyo is not "yesterday" in San Francisco. Reports computed in one region show different numbers than the same query from another region. Cron jobs at "midnight" run at midnight local time — different times in different regions. Senior code stores everything in UTC, performs business logic in UTC, displays in user-local timezone — but cron schedules and analytics aggregations need explicit attention. This is one of the most common bug sources in multi-region systems.

Mock interview

Interviewer: "Walk me through how you'd architect a globally distributed e-commerce platform."

You: "I'd decompose the data first. E-commerce has at least four distinct data domains, and each one wants a different multi-region pattern.

Catalog data — products, descriptions, prices, images. Read-heavy by 100:1, writes are infrequent (hourly catalog updates from suppliers). I'd use Pattern 2: single primary region for writes, replicas in every region. Cache aggressively. CDN for product images. This data benefits from being everywhere.

User data — accounts, addresses, payment methods. Privacy-sensitive, often regulated. Pattern 4: region-pinned. EU customers' user data in EU, US in US, etc. Authentication carries the residency claim.

Cart data — short-lived, per-user. Pattern 4 (in user's home region) is fine. Could also be edge-cacheable since it's user-specific and low-write-volume — Pattern 1+ with edge KV for sessions works.

Order data — the interesting one. Orders touch inventory (which is global) and payments (which are regulated). I'd use Pattern 5 (globally consistent) for just the inventory part — Spanner or CockroachDB for product inventory tracking — because over-selling is a business-critical correctness issue. The rest of the order record stays in user's home region (Pattern 4) for residency.

Routing layer: anycast for getting users to some region's edge. Edge logic inspects user identity, routes to home region for user-data operations, routes to nearest region for catalog reads.

Caches: per-region, never global. TTL-based for catalog. Per-user for cart.

Analytics: async aggregation from all regions to a central analytics warehouse — eventually consistent, hours behind, fine.

The senior framing: different data, different pattern. Not 'we use Pattern X for everything.' That's the senior call."

What makes this senior: decomposed by data type before talking architecture, named specific patterns (1, 2, 4, 5) for different domains, identified the one place global consistency matters (inventory) rather than applying it everywhere, addressed routing/caching/analytics as separate concerns. The composition — multiple patterns in one system — is the senior signal interviewers look for.

Interviewer: "Your active-active deployment in two regions is showing data divergence. The same record has different values in us-east and eu-west. Walk me through how you'd diagnose and fix it."

You: "Diagnosis first, then fix. Don't reach for the fix prematurely.

Diagnosis steps:

  1. Confirm divergence is real. Pull the record from both regions, compare. Check if it's actually different or if you're hitting different replicas at different replication positions. Use the primary of each region for the comparison.

  2. Check replication health. Is replication actively running? What's the replication lag? Are there errors in replication logs? A replication that stopped a week ago is the simplest cause of divergence — a buildup of unreplicated changes.

  3. Find the divergence timestamp. When did the values first differ? This narrows the search dramatically. Look at audit logs / change history if you have them.

  4. Check for conflicts in the conflict resolution layer. If you're using LWW: was there a clock skew? Two writes with overlapping timestamps where the LWW arbitrator picked the 'wrong' winner? If using vector clocks: are there unreconciled conflicts surfacing as 'divergent' values that should have been resolved by app code?

  5. Audit recent code changes. Did someone deploy a change to one region that didn't deploy to another? Configuration drift?

Most common root causes ranked: - Replication paused/broken without alerting (I'd estimate 40% of cases). - Application bug writing different values to different regions (intentionally or not) — 25%. - Clock skew + LWW losing data — 15%. - Schema changes deployed inconsistently — 10%. - Multi-region transactions that partially failed — 10%.

Fix:

Once root cause is known, fix is specific. General fix: pick a 'source of truth' region, replicate its value to the other(s), restart any broken replication. Document why divergence happened. Add monitoring to catch the next divergence faster — most divergence detection is via customer reports, which is too slow.

The thing I'd push back on: if the team's instinct is 'just merge them somehow' without diagnosing, push back hard. Merging without understanding the cause means it'll happen again. Take the operational pain of fixing properly the first time."

What makes this senior: structured diagnosis before fix, ranked root causes from experience (40% replication broken silently), addressed the meta-issue of detection latency ("most divergence is found via customer reports"), and explicitly pushed back on premature fixes. Interviewers love the "diagnosis-first, ranked root causes" structure — it's how staff engineers think.

Interviewer: "Your CTO wants to put data in 'the cloud' — but a major customer is asking for SOC 2 + ISO 27001 + GDPR compliance, with data in EU only. What's your response?"

You: "These are three orthogonal compliance vectors and I want to address them separately.

SOC 2 is a process audit. It verifies you have appropriate security controls. SOC 2 Type II takes 6+ months to obtain (you need 6+ months of audit period). It's not architecture — it's process discipline. You can run on any cloud provider; you need security processes documented and audited.

ISO 27001 is a similar process audit (information security management systems). Often paired with SOC 2 because the controls overlap. 6-12 months to obtain.

GDPR with EU data residency is the architectural one. This is what determines our cloud architecture.

My recommendation:

For the customer-blocking deal: use AWS, GCP, or Azure with EU regions (eu-west-1, europe-west, etc.). All three have full EU regions with GDPR-aligned offerings, including support for the EU Data Boundary commitment.

Architecture: Pattern 4 (region-pinned). Customer's data in EU region. Authentication carries an EU claim. Routing logic enforces EU customers' traffic stays in EU services.

Audit each service path: which third parties does the request touch? Stripe (yes, has EU processing), email provider (verify their EU data handling), error tracking (Sentry has EU instance), analytics (Segment can route EU events to EU destinations only). Each one is a yes/no question for residency.

For SOC 2/ISO 27001: kick off the audit process now. Pick an auditor experienced in cloud-native SaaS. Plan for 9-12 months to first SOC 2 Type II report, 6-9 months for ISO 27001.

The thing to negotiate with the customer: in-flight assurances. SOC 2 Type II takes time; for the first 6 months we'd be in audit period. Many enterprise customers accept SOC 2 Type I (point-in-time) plus a written commitment to Type II within a defined period. ISO 27001 is harder to fast-track. The contract can include compliance-roadmap commitments.

What I'd avoid: promising 'we'll be SOC 2 in 30 days.' That's not how the audit works, and credibility matters with enterprise compliance teams."

What makes this senior: distinguished compliance categories cleanly (process audits vs architectural), identified GDPR as the architectural driver, gave specific timelines for SOC 2 / ISO 27001 (9-12 months / 6-9 months), addressed third-party service compliance as a flow concern, and gave realistic negotiation guidance with the customer. The customer-facing nuance separates senior from staff.

Interviewer: "When would you NOT use multi-region?"

You: "More often than people think. Specifically:

  1. Single-continent customer base. If 95% of your users are in North America, multi-region within North America (us-east + us-west) gives you DR but not real latency improvement — it's far cheaper to be in one region with a CDN. Most B2B SaaS startups serving the US can stay single-region for years.

  2. Read-heavy workloads where stale is OK. A content site, a marketing platform, a documentation site — CDN solves their problem. Adding regions just adds cost and complexity.

  3. Workloads with strict consistency that don't have global users. A trading platform serving NYSE traders has zero benefit from a Tokyo region. Latency between regions would actually hurt if any state were replicated globally.

  4. Pre-product-market-fit startups. Multi-region adds engineering load that can't be justified without enterprise revenue. Solve it when a customer is paying for it.

  5. Workloads where compliance pushes the opposite direction. Some healthcare and financial workloads must stay in-country, single-region, with documented infrastructure. Multi-region is prohibited, not optional.

The senior framing: multi-region is an architectural cost. It's only worth paying if you have a specific business need that justifies it — customer SLA, residency requirement, redundancy requirement, latency requirement. 'Best practice' is not a justification. 'Future scale' is not a justification. Specific current requirement is.

The wrong question is 'should we go multi-region?' The right question is 'what specific problem would multi-region solve, and is there a cheaper way to solve it?'"

What makes this senior: has the courage to recommend against multi-region in clear cases, distinguishes redundancy from latency benefit (multi-region within continent is mostly DR), and explicitly reframes the question from 'should we' to 'what problem does it solve.' Interviewers appreciate engineers who can argue against complexity, not just for it.

Cheat sheet

THE FIVE PATTERNS

# Pattern When to use Cost / complexity
1 Single region + CDN Most startups, content-heavy apps $ (lowest)
2 Single-region writes, multi-region reads Read-heavy SaaS (95%+ reads) $$
3 Active-active multi-master Local writes everywhere, eventual consistency OK $$$
4 Region-pinned (per-user/tenant) Data residency, B2B SaaS, social products $$$
5 Globally consistent (Spanner) Finance, inventory, must-be-strongly-consistent $$$$

LATENCY PHYSICS - ~5ms RTT per 1,000 km (theoretical) - Real RTTs: same-region <2ms, cross-continent 75-160ms, half-globe 200-260ms - Cannot beat the speed of light — only put compute closer

ROUTING METHODS - DNS-based (GeoDNS): simple, slow failover (TTL-bound), resolver-IP issues - Anycast: fast failover (BGP), single IP globally, used by CDNs - Application-layer: precise (per-user routing), needs edge compute

EDGE / REGION / AZ - AZ: data center in region (1-2ms cross-AZ) - Region: 2-6 AZs, isolated from other regions - Edge POP: lightweight presence in cities, cache + TLS + lightweight compute

CONFLICT RESOLUTION (Pattern 3) - LWW: simple, lossy, OK for caches - Vector clocks: detect conflicts, app resolves - CRDTs: math-guaranteed merge, limited types - App-level merge: most flexible, most code - OT: collaborative editing only

RESIDENCY KEYS - GDPR: EU data, Schrems II for US transfers - China PIPL: data in China - India DPDP: data in India for "significant" platforms - All require: home-region routing (Pattern 4), residency-aware logging/backups, third-party compliance

GOTCHAS - Replication lag amplifies during incidents - Cross-region data transfer is expensive ($0.02-0.09/GB) - DNS TTLs control failover speed (use anycast for sub-second failover) - Configuration drift between regions - Time zones and date handling get worse multi-region

SENIOR DECISIONS - Don't over-engineer: most apps don't need multi-region - Compose patterns: different data, different pattern - Start with Pattern 1+CDN, add complexity when forced - Test with latency injection in single-region environments - Plan for residency from day one if you might serve EU/China/India
