MODULE 04

Indexes

Secondary, composite, covering — and why your "obvious" index is sometimes useless

Every database engineer "knows" indexes. Almost none can explain why INDEX(country, city, created_at) and INDEX(city, country, created_at) are completely different beasts. Almost none can explain why a UUID v4 primary key on a write-heavy table can quietly destroy your performance.

By the end of this module, you'll be the rare engineer who can.

Sam thinks he knows indexes

Sam OK indexes I actually feel okay about. Add an index, query gets faster. Don't add too many because they slow writes. I've used EXPLAIN a few times. I'm probably solid here, right?

Maya Quick test. You have a query: WHERE country = 'US' AND city = 'Austin' AND created_at > '2026-01-01'. You add INDEX(city, country, created_at). The query is still slow. Why?

Sam Uh... bad cardinality? Stale stats?

Maya Wrong column order. Your index leads with city, but city has thousands of distinct values and isn't even the most selective filter for what you're looking for. The planner might use it, but it's nowhere near optimal. Now: why specifically?

Sam ...because... B-trees are sorted? So the order of columns matters?

Maya Yes — and that's the whole reason composite indexes have what's called the leftmost prefix rule. Most engineers can recite it. Almost none can derive it from first principles. By the end of this module, you'll be in the second group. Then we'll do covering indexes — which is where the real magic lives. The kind that turns 100ms queries into 1ms queries.

Sam That's a thing?

Maya That's the thing. Most production databases have one or two queries that run a thousand times a second. If you can take any one of those from 100ms to 1ms with a covering index, you just freed up 99% of that query's database load. It's the highest-leverage optimization that exists.

Indexes are sorted secondary structures. Every property follows from that — column order matters, sort direction matters, query shape determines what works. Get the sorted-structure intuition right, and the rest is just consequences.

What an index actually is

Before we tackle the fancy stuff, let's be sure on the basics. An index is a separate B-tree (Module 01) that holds (key, pointer) pairs, sorted by key.

   TABLE                                  INDEX on email
   (heap, unsorted)                       (B-tree, sorted by email)

┌──────────────────────────┐ ┌─────────────────────────┐ │ Row 42: id=7 │ │ alice@x.com → ptr_42 │ │ email=alice@x.com │ ◄────────│ bob@y.com → ptr_19 │ │ ... │ │ carol@z.com → ptr_88 │ ├──────────────────────────┤ │ dan@example → ptr_31 │ │ Row 19: id=12 │ │ eve@test.com → ptr_55 │ │ email=bob@y.com │ ◄────────│ ... │ │ ... │ └─────────────────────────┘ ├──────────────────────────┤ │ Row 88: id=3 │ The index is sorted by email. │ email=carol@z.com │ ◄──┐ Each leaf holds (email, pointer). │ ... │ │ ├──────────────────────────┤ │ The pointer goes back to a row │ ... │ │ in the heap, which is unsorted. └──────────────────────────┘ │ │ └─── two-step lookup: 1. Walk index by email 2. Follow pointer to heap

The lookup is two steps:

Looking up alice@x.com:

Walk the email index B-tree. 3-4 page reads (Module 01).

Find the leaf entry: ("alice@x.com", ptr_42).

Follow the pointer to the heap. One more disk read.

Return the row.

That extra hop in step 3 — index says "the row is at position 42" and the database goes fetch position 42 from the heap — is called a heap fetch in Postgres. It's the source of a lot of "but I added an index, why is it still slow?" pain. Covering indexes (later in this module) are the cure.

Different engines store this differently

Engine Index style The implication
Postgres Heap-organized — index has pointer to heap row Every secondary index lookup costs an extra heap fetch
MySQL InnoDB Clustered primary key — leaves are the rows Primary key lookup = no heap fetch. But secondary indexes store the PK, so it's PK-lookup + secondary-PK indirection
SQL Server Either — clustered index optional Hybrid; depends on schema

Concrete consequence: in Postgres, a query that touches an indexed column plus heap data does (index walk) + (heap fetch per matching row). In MySQL InnoDB on a primary-key lookup, it's just (B-tree walk to leaf, leaf has the row data). MySQL is slightly faster on PK lookups; Postgres is slightly faster on table-wide stuff because the heap can be optimized separately.

Mention this distinction in an interview and you signal you've seen both ecosystems in production. Most engineers don't know.

Secondary indexes

A secondary index is any index that isn't the primary key. Every B-tree index you create with CREATE INDEX is one.

CREATE INDEX idx_email ON users(email);
CREATE INDEX idx_status ON orders(status);
CREATE INDEX idx_created ON events(created_at);

These are the workhorses. They speed up WHERE clauses on the indexed column.

The cost no one wants to discuss

Every secondary index costs writes. Every. Single. One.

When you INSERT a row, every index on that table gets updated too. With 5 indexes, one INSERT becomes 6 B-tree mutations. With 20 indexes, one UPDATE can trigger an I/O storm.

This is the silent killer of write-heavy tables. Junior engineers add indexes liberally to fix slow queries. Their writes get slower. They add more indexes to fix the slow writes (somehow). Now the table has 30 indexes and is fundamentally crippled.

A real-world example:

A team's users table had grown to 19 indexes over three years. Each one was added for a specific use case — a feature flag, a filter, a report. None were removed when the use case went away.

Insert latency on the table was 80ms per row. They couldn't onboard new users fast enough during marketing campaigns.

The fix wasn't more capacity. They audited the indexes, found 12 of them were unused (Postgres has pg_stat_user_indexes for this), and dropped them. Insert latency went to 8ms. 10x improvement, no code change, just delete.

The senior reflex: indexes accumulate. Audit them periodically. Unused indexes are pure write tax.

Postgres command for finding unused indexes:

SELECT
  schemaname, relname, indexrelname,
  idx_scan,
  pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;

Run it once a quarter. You'll find indexes nobody remembers adding.

Composite (multi-column) indexes

This is where most candidates trip up. Let's nail it.

A composite index sorts rows by multiple columns in order.

CREATE INDEX idx_geo ON users(country, city, created_at);

This index sorts: 1. First by country. 2. Then within each country, by city. 3. Then within each city, by created_at.

Composite index sorted by (country, city, created_at):

(country=DE, city=Berlin, created_at=2024-01-01) → ptr_881 (country=DE, city=Berlin, created_at=2024-02-15) → ptr_241 (country=DE, city=Berlin, created_at=2024-03-10) → ptr_512 (country=DE, city=Munich, created_at=2024-01-10) → ptr_117 (country=DE, city=Munich, created_at=2024-04-22) → ptr_338 (country=US, city=Austin, created_at=2024-03-01) → ptr_092 (country=US, city=Austin, created_at=2024-03-22) → ptr_733 (country=US, city=Austin, created_at=2024-05-05) → ptr_465 (country=US, city=Boston, created_at=2024-02-28) → ptr_628 (country=US, city=Boston, created_at=2024-06-15) → ptr_910 ...

Notice: All Berlin entries come before all Munich entries (within DE). All US entries come after all DE entries. Within Austin, time-ordered.

The B-tree leaf is one continuous sorted list. The hierarchy is in the order of the keys, not in any tree structure.

The leftmost prefix rule, derived

Why does the leftmost prefix rule exist? Let's derive it instead of memorize it.

The B-tree is sorted by (country, city, created_at) — country first, ties broken by city, ties broken by created_at.

Now ask: where in the index are all rows where city = 'Austin' (regardless of country)?

Look at the leaf list above. They're scattered. Austin in US is far from any Austin in TX. They're not contiguous in the index.

To answer WHERE city = 'Austin', the database would have to walk the entire index, picking out matches as it goes — exactly as expensive as scanning the whole table. The index is useless for this query.

Now ask: where are all rows where country = 'US' (regardless of city or time)?

They're contiguous. All US entries are between the last DE entry and the first FR entry.

The B-tree can find the start of US with one tree walk and read forward sequentially. Excellent.

This is the leftmost prefix rule, falling out of the layout: you can use any prefix of the index columns starting from the left, but you can't skip the leading column.

Query filters on Index (A, B, C) helps? Why
A ✅ Excellent Top-level prefix
A, B ✅ Excellent Two-level prefix
A, B, C ✅ Excellent Full key
A, C (skipping B) ⚠️ Partial A narrows; C requires scanning all matching A's
B alone ❌ Useless B values scattered through index
B, C ❌ Useless Same — B is not the leading column
C alone ❌ Useless C values scattered

A composite index (A, B, C) works left-to-right. Any prefix is usable. You cannot skip the leading column.

Three queries, one index, three different fates

You have INDEX(country, city, created_at). Three queries hit your service:

-- Query 1
WHERE country = 'US' AND city = 'Austin'

✅ Uses idx_geo. Two-column prefix. Index narrows to rows where country=US AND city=Austin — typically thousands of matches, quickly retrieved.

-- Query 2
WHERE country = 'US' AND created_at > '2024-01-01'

✅ Uses idx_geo, partially. Index narrows by country=US. Then within US rows, the database scans for created_at > date — but the rows aren't ordered by date within country (they're ordered by city first, then date within city). So it's a partial scan within the US slice.

-- Query 3
WHERE city = 'Austin'

❌ Does NOT use idx_geo. No country filter, so no leading-column pin. The planner falls back to a sequential scan or a different index — hopefully one that exists.

A frequent gotcha: candidates remember "leftmost prefix" as a slogan but can't apply it. In the interview, the trap is "I have INDEX(A, B, C). What about a query filtering on B and C?" The answer is useless — the index is wasted bytes for that query. You'd need either a separate index leading with B, or to rethink your indexing strategy entirely.

Column order: the selectivity question

If you have a choice of column orders, what's the right one?

Most selective column first — the column that filters out the most rows quickest.

If country has 200 distinct values and email has 10 million distinct values, an index on (country, email) is wasteful — country barely narrows down anything. An index on (email) alone is dramatically more selective.

But this rule has nuance. Selectivity isn't the whole story.

Selectivity vs query patterns: pick the column that matches your most common query shape, not just the most selective.

If 90% of your queries are WHERE country = ? AND email = ?, then (country, email) is fine — the country filter is fast even if low-cardinality, and the index supports the common pattern.

If 90% of queries are just WHERE email = ?, then (email) alone or (email, country) makes sense.

The senior move: profile your actual queries, then design indexes for the patterns. Don't optimize for selectivity in the abstract.

A worked example

You're designing for a SaaS app's events table:

Common queries: WHERE user_id = ? (very common), WHERE user_id = ? AND event_type = ? (common), WHERE event_type = ? (rare reporting).

Cardinalities: user_id ~10M distinct, event_type ~50 distinct.

Choose: INDEX(user_id, event_type) — supports the first two query shapes via leftmost prefix. The rare event_type-alone query falls back to seq scan, which is acceptable for rare queries.

Resist the urge to add INDEX(event_type) "just in case." The rare query doesn't justify the write cost on a hot table. If it becomes common, then add it.

Sort order: the ASC/DESC trap

This one bites senior candidates too. Indexes are sorted in a direction.

CREATE INDEX idx_recent ON events(user_id, created_at);

That index is sorted by created_at ascending (default).

Now consider this query:

SELECT *
FROM events
WHERE user_id = 42
ORDER BY created_at DESC
LIMIT 50;

Will the index help with the ORDER BY ... DESC LIMIT 50 part?

It depends. Most databases can scan a B-tree in either direction — Postgres and MySQL both support backward scans with comparable speed. So the ASC index can satisfy a DESC query.

But not always efficiently. Specifically, when combined with other constraints (multi-column sort, mixed directions), backward scans get expensive or get rejected by the planner.

Senior practice: match the sort direction to the query. If you almost always want most-recent-first, define the index DESC:

CREATE INDEX idx_recent ON events(user_id, created_at DESC);

Now the LIMIT 50 of "most recent" is reading the front of the index, which is the cheapest possible read.

The mixed-direction trap. This:

ORDER BY priority ASC, created_at DESC

Cannot use INDEX(priority, created_at) for the sort, because that index sorts both ascending. You'd need INDEX(priority ASC, created_at DESC). Postgres supports this. Some older databases didn't, and the candidates who knew this distinction stood out.

Covering indexes — the magic

Now we get to the trick that turns 100ms queries into 1ms queries.

Recall: a normal index lookup is two steps: walk the index, then heap fetch. The heap fetch is one extra disk read per matching row.

The 100,000-row heap fetch problem.

A query has good selectivity — WHERE user_id = 42 AND event_type = 'click'. The index narrows it down to 100,000 matching rows. Index walks are fast — under 5ms total.

But each of those 100,000 rows requires a heap fetch — 1ms each, since they're scattered randomly through the heap. 100 seconds of total disk I/O.

The query is slow not because of the index lookup, but because of the follow-up fetches.

A covering index includes all the columns the query needs — so the database never visits the heap.

-- Original query:
SELECT email, name FROM users WHERE country = 'US';

-- Non-covering: index on country only.
-- Database walks index, then fetches each matching row from heap.
CREATE INDEX idx_country ON users(country);

-- Covering: index includes all needed columns.
-- Database walks index, returns email and name directly. No heap fetch.
CREATE INDEX idx_country_covering ON users(country) INCLUDE (email, name);

WITHOUT COVERING INDEX: ┌─────────────────────────────────┐ │ INDEX walk: country = 'US' │ 1 ms │ → 100,000 matching rows │ └─────────────────────────────────┘ │ ▼ ┌─────────────────────────────────┐ │ HEAP FETCH × 100,000 │ 100,000 ms │ (one per row, random I/O) │ └─────────────────────────────────┘ Total: ~100 seconds.

WITH COVERING INDEX: ┌─────────────────────────────────┐ │ INDEX walk: country = 'US' │ 1 ms │ → 100,000 (email, name) pairs │ │ directly from index leaves │ └─────────────────────────────────┘ Total: ~1 ms.

   ↑

The same logical query. 100,000× faster.

A covering index is one that contains every column referenced by a query — so the database can answer the query entirely from the index, never touching the heap. For hot queries, this is often the highest-leverage optimization that exists.

How databases write covering indexes

Slightly different syntax across engines:

Engine Syntax
Postgres CREATE INDEX ... ON table(key_cols) INCLUDE (extra_cols)
SQL Server CREATE INDEX ... ON table(key_cols) INCLUDE (extra_cols) (same)
MySQL No INCLUDE clause; use INDEX(key_cols, extra_cols) — they're all key columns, sorted on all of them

In Postgres, INCLUDE columns aren't part of the sort key — they're just additional payload at the leaf level. This keeps the index tree shallower than packing them into the key.

Postgres INCLUDE is the cleaner pattern: the index sorts only on the columns you'll filter by, but stores additional values at the leaves. The sort tree stays compact, while the leaves carry just enough extra data to satisfy common queries without heap access. MySQL achieves the same goal by adding columns to the key; the result is similar but the tree is fatter.

When asked about covering indexes in an interview, mention INCLUDE if you're talking Postgres or SQL Server. It signals you know the modern syntax.

When NOT to use a covering index

Covering indexes have a cost: they get bigger, and they have to be updated whenever any of their included columns change.

If you INCLUDE (email, name) and somebody updates a user's name, the index has to be updated too. For tables where included columns change often, the write tax can outweigh the read benefit.

Also: a covering index is bigger than a non-covering one — it stores those extra columns. Bigger indexes mean less of the index fits in cache. For large tables, this matters.

Use covering indexes surgically, on specific hot queries — not as a default.

A worked covering index decision

Hot query: dashboards run this 10,000 times per minute:

SELECT user_id, total_spent
FROM users
WHERE country = 'US' AND status = 'active'
ORDER BY total_spent DESC
LIMIT 100;

Without an index: full table scan. ~5 seconds. Catastrophic at this query rate.

Add INDEX(country, status, total_spent DESC): helps with filtering and partial sort. Each query: ~10ms (1ms index, 9ms heap fetch for 100 rows). Manageable.

Add INDEX(country, status, total_spent DESC) INCLUDE (user_id): now the index can answer the query without ever visiting the heap. Each query: ~1ms.

Trade-off accepted: index is ~30% bigger because it now carries user_id. Updates to total_spent trigger index updates. But the dashboard load just dropped 10x. Worth it for a hot query.

Specialized index types

B-trees are the default but not the only game in town. Knowing these by name signals breadth.

Type Best for Common in
B-tree Equality, range, sort. Default. Everything
Hash Equality only, no range queries Postgres (limited use), Redis
GIN (Generalized Inverted) Many-to-many: array elements, JSON keys, full-text Postgres
GiST (Generalized Search) Geospatial, custom data types Postgres, PostGIS
BRIN (Block Range) Very large append-only tables Postgres
Bitmap Low-cardinality columns on read-heavy systems Oracle, columnar engines
Inverted index Full-text search Elasticsearch, Lucene, Solr

BRIN: the underrated gem

BRIN (Block Range INdex) is one of Postgres's hidden gems. Most engineers don't know it exists.

Instead of indexing every row, BRIN stores the min and max value per block (typically 128 contiguous pages). For naturally-ordered data — like a created_at column where new data is appended in order — BRIN can skip huge chunks of blocks that can't possibly contain matching rows.

The result: an index on a 1B-row time-series table that's 100x smaller than a B-tree, with comparable performance for time-range queries on the natural insertion order.

Mention BRIN in an interview about time-series data, and the senior interviewer's eyebrows go up. Most candidates don't know it's there.

GIN: indexing inside JSON and arrays

You have a Postgres table with a tags TEXT[] column. You want to query "find all rows where tags contains 'urgent'."

A B-tree on tags is useless — it'd index the entire array as one value.

CREATE INDEX idx_tags ON items USING GIN (tags);

Now Postgres maintains an inverted index — for each tag value, a list of rows that contain it. The query WHERE tags @> ARRAY['urgent'] becomes fast.

Same trick works on JSONB columns: CREATE INDEX ... USING GIN (data_column jsonb_path_ops) lets you index by JSON keys and values.

The UUID v4 problem

Random UUIDs as primary keys cause real performance pain on write-heavy tables. This is a senior-level interview topic.

Here's why.

A B-tree primary key index lays rows out in key order. Insert a row with a sequential ID: it lands in the rightmost leaf. The page is hot, in cache, easy to update.

Insert a row with a random UUID: it lands somewhere arbitrary in the index. Probably a cold page. The database has to fault that page in, modify it, and write it back. Each insert hits a different page.

Across millions of inserts: - Sequential keys: ~1 hot page constantly written. Cache-friendly. Fast. - Random UUIDs: every insert touches a different page. Cache thrashing. Slow.

The performance gap can be 5-10x on insert-heavy workloads.

Use UUID v7 instead.

UUID v7 is a newer variant where the leading bits are a timestamp. The result: UUIDs are almost-sortable — newly generated ones land near each other in the index, restoring the cache-friendly pattern.

UUID v7 is supported by most modern UUID libraries. If you need globally-unique IDs but want B-tree-friendly insert performance, this is the answer.

A senior candidate who says "we use UUID v7 because UUID v4 fragments the B-tree" sounds like someone who has actually shipped high-write-rate Postgres.

Three ways to think about indexes

Way 1: the back-of-the-book index.

Open any technical book. The index at the back is sorted alphabetically. To find "snapshot isolation," you flip to S, find the term, and the index says "see page 247."

That's a B-tree index in physical form. Sorted. Has pointers to the actual content. Lets you skip reading the entire book to answer one question.

A composite index is like an index that lists "topics by chapter, then within chapter alphabetically." If you only know "alphabetically," it doesn't help — the chapter is the leading axis.

A covering index is like the table of contents that has the summary next to each entry — so you don't even have to flip to the page to know what's there.

Way 2: the warehouse aisles.

A warehouse stores products in unsorted bins (the heap). A picking list of "where is each product" is the index — sorted by SKU, with bin numbers.

To pick one item: read the picking list, find the SKU, walk to the bin. Two steps.

A covering picking list also tells you the price, the description, the quantity in stock right next to the SKU. For most queries you don't even need to walk to the bin. That's a covering index.

Way 3: the photo album.

Your phone has 50,000 photos. You want to find one taken last March in Paris.

Without indexes, you scroll through every photo (sequential scan).

The phone keeps a date index (sorted by date) and a location index (geotagged by city). With those, finding "March + Paris" is two index lookups, intersected.

A composite (date, location) index is one sorted structure on both. A covering index also stores the thumbnail next to the date entry — so you don't even have to load the full photo to preview it.

Sharpen your pencil

Exercise 1. A 500M row events table. Schema: (user_id, event_type, created_at, payload, region).

The slowest production query is:

SELECT *
FROM events
WHERE user_id = ? AND event_type = ?
ORDER BY created_at DESC
LIMIT 50;

Design the optimal index. Justify the column order, the sort direction, and any covering decision.

CREATE INDEX idx_events ON events(user_id, event_type, created_at DESC)

Column order: - user_id first — most selective (millions of distinct users). - event_type second — narrows further within a user. - created_at third — used for the LIMIT clause.

Sort direction: created_at DESC. The query asks for "most recent 50" — with a DESC index, the engine reads the front of the matching range, satisfying the LIMIT immediately. With ASC, the engine has to find all matching rows then sort them.

Covering: depends on payload size. If payload is small (under ~200 bytes typical) and the query is hot enough to justify, add INCLUDE (payload, region) so the entire query is satisfied from the index. If payload is large (megabytes of JSON), don't — index would balloon. Profile first.

The senior reflex: design for the dominant query pattern. Verify with EXPLAIN ANALYZE. Iterate.

Exercise 2. A team's write-heavy orders table has 19 indexes. Insert latency is 80ms per row. Where do you start?

Step 1: identify unused indexes. Postgres's pg_stat_user_indexes.idx_scan will show you which indexes haven't been used since last stats reset. Anything with idx_scan = 0 over a representative time period is a candidate for removal.

Step 2: identify redundant indexes. Look for index pairs where one is a prefix of another. INDEX(a) is redundant if INDEX(a, b) exists — the latter handles all the queries the former does (well, mostly — it's slightly bigger). Drop the prefix.

Step 3: identify index pairs covering the same query patterns. Two indexes that solve the same problem are usually one too many.

Step 4: examine remaining indexes against actual query patterns. pg_stat_statements shows your top queries. Each remaining index should be justified by at least one common query.

Realistic outcome: 19 indexes drops to 7-10. Insert latency improves proportionally. The fix isn't more capacity — it's less write tax.

Exercise 3. Explain to non-technical Sam, in three sentences, why WHERE LOWER(email) = ? doesn't use an index on email.

The index on email is a sorted list of email values exactly as stored — like "Alice@Test.com" with capitals preserved. When the query asks WHERE LOWER(email) = ?, the database has to compute LOWER() on every row's email to compare — and there's no shortcut to "lowercased emails" in the index. The fix is either to store emails already lowercased, or create a functional index on LOWER(email) that's sorted by the lowercased values.

There are no dumb questions

Q: Should I just index every column?

A: No. Each index slows writes, consumes disk, and bloats the buffer pool. The rule of thumb: index columns used in WHERE, JOIN, ORDER BY, or GROUP BY clauses that are actually slow. Profile first; index second. Adding an index is a tax on every future write to that table.

Q: Do indexes help on small tables?

A: Often no. A sequential scan of 1,000 rows is faster than walking an index B-tree plus heap fetches. The query planner usually figures this out and skips the index. If you find your tiny table is using an index when it shouldn't, you may have stale stats.

Q: What's a "clustered" index?

A: An index where the leaves are the data — the table's physical order matches the index. MySQL InnoDB primary keys are clustered (rows live in the PK B-tree leaves). Postgres has no clustered indexes (heap-organized). The implication: in InnoDB, every secondary index lookup does B-tree-walk + secondary-tree-walk-by-PK rather than B-tree-walk + heap-fetch. Different shape, similar cost.

Q: Can indexes get fragmented?

A: Yes — especially under heavy UPDATE/DELETE traffic. B-tree pages get partial deletes, leaves get sparse, the tree balloons relative to its actual data. Postgres has REINDEX CONCURRENTLY (modern), MySQL has OPTIMIZE TABLE. Periodic maintenance on hot tables is part of the operational reality.

Q: Why do OR clauses kill indexes?

A: WHERE A = ? OR B = ? typically forces the planner to either do a full scan or do two index scans + union. Neither is fast. The fix is often to rewrite as UNION ALL of two queries, each using its own index. Modern planners are getting better at this, but it's still a known anti-pattern.

Q: What about indexes on nullable columns?

A: They work, but WHERE col IS NULL and WHERE col IS NOT NULL have nuances. In Postgres, B-tree indexes by default include NULLs at one end of the tree, so IS NULL queries can use the index. Older databases varied. The senior move: test it with EXPLAIN.

Q: Should I worry about index bloat in production?

A: On UPDATE-heavy tables, yes. Postgres has pgstattuple extension that tells you the bloat ratio. If indexes are 2-3x larger than they should be, REINDEX CONCURRENTLY can help. Newer Postgres versions handle bloat better via deduplication and bottom-up index deletion.

Q: How do I know if an index is "doing its job"?

A: EXPLAIN ANALYZE your hot queries — if you see Index Scan or Index Only Scan (the latter = covering index!), the index is being used. If you see Seq Scan, the planner skipped the index, possibly due to low selectivity, missing stats, or the query being too cheap to bother. Combined with pg_stat_user_indexes, you can confirm an index is earning its keep.

Three myths to dynamite

"More indexes = faster database."

False. Indexes speed up reads they cover, and slow down writes that touch them. Past about 5-10 indexes on a hot table, the write tax often exceeds the read benefit. Senior engineers audit indexes regularly and remove unused ones.

"Indexes always help."

False. On small tables, the planner often skips indexes because seq scans are faster. On certain query shapes (LIKE '%foo%', large IN lists, OR clauses), indexes don't help. Indexes also don't help when stats are stale and the planner picks the wrong plan. An index helps when (a) the query is selective enough, (b) the planner knows it, and (c) the data fits the index's strengths.

"You should always use UUIDs as primary keys for security."

False. UUID v4 fragments B-trees and hurts write performance. Sequential IDs are vastly more cache-friendly and faster to insert. If you need globally-unique IDs, use UUID v7 — it's almost-sortable and gets you both unguessability and B-tree friendliness. Or use a Snowflake-style ID. UUID v4 is the worst of both worlds for primary keys.

Interview gotchas

Forgetting ORDER BY DESC in the index. If your query is ORDER BY created_at DESC LIMIT N and your index is sorted ASC, the engine has to read all matching rows then sort. Always match the sort direction.

OR clauses kill indexes. WHERE A = ? OR B = ? typically forces the planner to do a full scan. Rewrite as UNION ALL of two queries when performance matters.

Functions on indexed columns. WHERE LOWER(email) = ? cannot use an index on email. You need a functional index on LOWER(email), or to store the column already-lowercased.

Composite index column order matters AND sort direction matters. Both. Most candidates remember one. The senior detail is both.

Skipping the leftmost column kills the index. INDEX(A, B, C) queried on just (B, C) is wasted bytes. Make sure your common query patterns lead with one of your indexed columns.

Mock interview

A query that used to run in 50ms now takes 8 seconds in production. The query and the data haven't changed in the last week. What do you check first?

Three things, in order of likelihood:

One — stale stats. The query planner uses table statistics to choose between index scan and seq scan. If a write-heavy table hasn't been ANALYZEd in a while, the planner might be choosing seq scan thinking the table is small. Run ANALYZE table_name and re-run the query.

Two — index bloat or fragmentation. Especially on Postgres with frequent UPDATEs, the B-tree can grow much larger than the data warrants. Check pg_stat_user_indexes for size; consider REINDEX CONCURRENTLY if the bloat is significant.

Three — cache eviction. The hot pages of the index/table fit in the buffer pool when traffic is light. Under load — or after a deploy that flushed the cache — the buffer pool gets churned and what used to be a memory access becomes a disk read. The fix may be more RAM, a smaller working set, or partitioning.

If none of those: I'd EXPLAIN ANALYZE and look at the plan. Did the optimizer pick a different plan than before? That points to stats. Did it pick the same plan but spend much more time? That points to I/O — cache or bloat.

Triage list, ordered by probability. "I'd EXPLAIN ANALYZE" is the senior reflex — investigate, don't guess.

EXPLAIN ANALYZE shows the plan changed. Yesterday it was an Index Scan. Today it's a Seq Scan. The table has 50M rows. Why would the planner pick seq scan?

A few possibilities, all related to how the planner estimates cost:

Stats are stale and now wrong. The planner thinks the table is smaller than it is, or thinks the WHERE clause is less selective than it is. With wrong selectivity estimates, the cost calculation flips between index scan and seq scan. Run ANALYZE and check.

The query is genuinely returning a lot of rows. If yesterday the query hit 1% of the table (acceptable index scan target) and today it hits 30%, the planner correctly switches to seq scan — index scan with 15M heap fetches would actually be slower than reading the whole table sequentially. Check the cardinality of the WHERE values today vs yesterday.

A recent random_page_cost config change. Postgres's planner has a setting that estimates the cost ratio of random vs sequential I/O. On NVMe SSDs, the default of 4.0 is conservative — random I/O is much closer to sequential than the default assumes. If someone tuned it (or didn't), it can flip plan choices.

Stats sample didn't catch a hot value. Postgres's stats by default sample 30,000 rows for histograms. If your filter targets a high-cardinality but rare value, the sample might not represent it well. ALTER TABLE ... ALTER COLUMN ... SET STATISTICS 1000 raises the sample size for that column.

Multiple specific hypotheses, each with a concrete check. Mentioning random_page_cost and SET STATISTICS shows operational depth.

ANALYZE didn't help. The plan still picks seq scan. The query is genuinely returning 1% of the table — about 500K rows. What's going on?

At 1% selectivity, on a 50M row table, the planner has a real choice: 500K index lookups + 500K heap fetches, or one full seq scan. The crossover point in Postgres is usually around 5-10% of the table — below that, index scan wins; above, seq scan wins. 1% should be solidly in index-scan territory.

If it's still picking seq scan, the most likely remaining cause is correlated columns. The planner assumes columns are independent. If your WHERE has two predicates and both are individually 30% selective, the planner estimates 9% combined. But if the columns are correlated (say, country = US and state = California — almost all CA users are in US), the actual selectivity is closer to 30%, and the planner is now expecting too few rows.

The fix in Postgres: extended statistics. CREATE STATISTICS ON (col_a, col_b) FROM table_name; ANALYZE table_name;. Now the planner has real correlation data and stops over-narrowing the estimate.

If extended stats don't help: investigate whether the query needs a covering index. If the predicate is selective and the heap fetch is what's blowing the cost budget, adding INCLUDE columns might tip the planner back toward index scan.

If none of that helps, you can force an index scan with SET enable_seqscan = off for that one query as a temporary measure, while you investigate further. But forcing plans is a workaround, not a fix.

Knows the actual crossover threshold (~5-10%). Mentions extended statistics — a Postgres 10+ feature most candidates haven't used. Acknowledges the temporary workaround without defaulting to it.

Last one. Walk me through your decision process for adding a new index in production.

A checklist I'd actually run through:

One — is there a real query problem? Profile first. pg_stat_statements for top slow queries. If the query isn't actually slow or isn't actually run often, no index is needed. Most "should we add an index?" conversations should end here.

Two — is the query selective enough? If the WHERE narrows to under ~5% of the table, an index is potentially worthwhile. If it returns 50%, an index won't help — the planner will skip it.

Three — does an existing index already cover this? Check if a leftmost-prefix of an existing composite index works. Adding redundant indexes is the most common form of index bloat.

Four — does column order match query patterns? If the query is WHERE A = ? AND B = ?, design INDEX(A, B) or INDEX(B, A) based on which is most selective AND most commonly queried alone. Don't pick blindly.

Five — would a covering index make sense? If the query is hot and returns a small set of columns, INCLUDE-ing those columns can transform the latency. Trade-off: bigger index, more write tax.

Six — what's the write impact? Run a quick estimate of how many writes per second hit this table. Each new index multiplies that work. For very hot tables, even a single new index can shift the write latency budget noticeably.

Seven — deploy with CREATE INDEX CONCURRENTLY. Plain CREATE INDEX locks the table. Concurrent version doesn't, but takes longer and has its own failure modes. For production, always concurrent.

Eight — verify after. After deploy, check that the planner is actually using the new index (EXPLAIN ANALYZE). And monitor pg_stat_user_indexes over the next week. If idx_scan stays at zero, the index isn't earning its keep — drop it.

Indexes are like committing a piece of code to a critical path. Same level of care.

Eight-step checklist. Mentions CREATE INDEX CONCURRENTLY — a deployment detail most candidates miss. The closing line — "indexes are like committing a piece of code" — is the kind of senior framing that lands well.

Cheat sheet

Indexes — One Page

Secondary indexes

Any index besides the PK. Costs writes (every index updated on INSERT/UPDATE), helps reads. Audit and drop unused indexes regularly — they're pure write tax.

Composite indexes

Multi-column. Sorted left-to-right. Leftmost prefix rule: any prefix usable, can't skip leading column. Column order = most-selective-and-most-queried first. Sort direction matters too — match ORDER BY ... DESC with a DESC index column.

Covering indexes

Include all columns the query needs, so no heap fetch. Postgres/SQL Server: INCLUDE (...). Often the highest-leverage optimization for hot queries — 100ms → 1ms is realistic.

Specialized index types

  • B-tree — default, equality + range + sort.
  • Hash — equality only.
  • GIN — JSON, arrays, full-text.
  • GiST — geospatial, custom types.
  • BRIN — huge naturally-ordered tables. Hidden gem for time-series.
  • Bitmap — low-cardinality, columnar/OLAP.

Killer rules to memorize

  • ASC/DESC matters in the index definition.
  • Functions on columns disable indexes (use functional indexes instead).
  • OR clauses kill indexes — rewrite as UNION ALL.
  • UUID v4 fragments B-trees on insert — use UUID v7 or sequential IDs.
  • ANALYZE regularly so the planner has fresh stats.
  • Use CREATE INDEX CONCURRENTLY in production (Postgres).

Production checklist before adding an index

  1. Profile to confirm a real query problem.
  2. Verify selectivity (under 5% of rows is the sweet spot).
  3. Check no existing composite index already covers it.
  4. Match column order to query patterns.
  5. Consider covering with INCLUDE.
  6. Estimate write impact.
  7. Deploy with CONCURRENTLY.
  8. Verify use after deploy; drop if unused after a week.

The 30-second verbal answer

"An index is a sorted secondary structure. Composite index column order follows leftmost-prefix and selectivity. Covering indexes include extra columns to skip the heap fetch — often the biggest single optimization for hot queries. Each index is a tax on every write to the table, so audit and drop unused ones."

Always pair with

Query planner, cost-based optimizer, selectivity, cardinality, EXPLAIN ANALYZE, B-tree page layout, write amplification, MVCC.
