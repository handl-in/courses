MODULE 03

Row vs Columnar Storage

The third axis of storage choice — and why BigQuery runs your aggregation 100x faster than Postgres on identical data

You move a 50-column, 10-billion-row table from Postgres to BigQuery. The same SELECT AVG(price) FROM orders WHERE date > '2026-01-01' query goes from 8 minutes to 4 seconds.

Same data. Same total bytes. Same ANSI SQL. Different physical layout on disk.

If you can't explain — in detail — why that 100x speedup happened, this module is for you.

Maya and Sam: round 3

Sam shows up with a notebook this time. Trying to take this seriously.

Sam OK so I was reading job descriptions yesterday and a bunch said "experience with OLAP and OLTP." I sort of know what those mean — analytical vs transactional — but every time someone says "use a column store," I nod like I get it. I don't actually get it.

Maya That's actually really common. Most engineers learn row-based databases — Postgres, MySQL, Mongo — and never see a column store from the inside. Then one day someone says "we should use BigQuery for this" and you're like sure and you nod.

Sam Exactly!

Maya Here's the thing. The choice between row and column storage is the third huge axis of database design. Module 1 was sort-as-you-go vs sort-later. Module 2 was the support cast for both. This module is about something completely different — the physical layout of bytes on disk. Not how you sort them. How you arrange them.

Sam And that one decision causes a 100x speed difference?

Maya Sometimes more. Once you see it, you'll never confuse OLTP and OLAP requirements again. And you'll know exactly when to suggest a columnar store in an interview — and when not to.

Sam When not to is just as important?

Maya More important. Suggesting columnar for OLTP is the kind of mistake that ends an interview early. Don't do that.

Row stores arrange bytes by entity — one row's data is contiguous on disk. Column stores arrange bytes by attribute — one column's data is contiguous on disk. Same data. Wildly different access patterns.

Read that key idea once more. The whole module is about consequences of that arrangement difference.

The hook: two queries, two storage shapes

Let's make this concrete with a single table and two queries.

Imagine an orders table with 50 columns and 10 billion rows. Each row is roughly 400 bytes. Total table size: about 4 TB.

We're going to ask two questions:

Query A: SELECT * FROM orders WHERE id = 12345 → Fetch one specific order, with all 50 columns.

Query B: SELECT SUM(amount) FROM orders WHERE date > '2026-01-01' → Sum a single column across (let's say) 200 million rows.

Same data. Same query language. Opposite access patterns.

There is no single physical layout that wins both. Pick row, you win A. Pick column, you win B. Pick both at the same scale, you pay for two storage systems.

A storage layout optimizes for one access pattern at the expense of others. Always.

Row-based storage

Row stores keep one row's bytes physically contiguous on disk. To read row 5, you read one block of bytes, and everything about that row is right there.

                            ROW STORE LAYOUT

┌────────────────────────────────────────────────────────────────────────┐ │ Row 1: id=1 name="Alice" age=30 country="US" ... 46 more cols │ ├────────────────────────────────────────────────────────────────────────┤ │ Row 2: id=2 name="Bob" age=25 country="UK" ... 46 more cols │ ├────────────────────────────────────────────────────────────────────────┤ │ Row 3: id=3 name="Carol" age=40 country="DE" ... 46 more cols │ ├────────────────────────────────────────────────────────────────────────┤ │ Row 4: id=4 name="Dan" age=35 country="US" ... 46 more cols │ ├────────────────────────────────────────────────────────────────────────┤ │ ... │ └────────────────────────────────────────────────────────────────────────┘

To read row 3 in full: one disk seek, read one row's worth of bytes. ALL 50 columns delivered together.

To sum the "amount" column across all 10B rows: read every row in full, extract amount, throw away the other 49 columns. Massive waste.

This layout is the natural fit for OLTP workloads — Online Transaction Processing.

The folder cabinet.

A row store is like a filing cabinet where each customer has their own folder. The folder contains everything about them — name, address, recent orders, notes — all together.

If a customer calls and asks for their account status: pull their folder, read whatever you need, file it back. Fast.

If you need to sum all customers' balances: pull every folder, read just the balance, file it back. Tedious. Tens of thousands of file pulls just to get one number per customer.

Cabinets are built around access by entity. They're great for "tell me about X." They're terrible for "sum this attribute across everything."

Where row stores shine

Workload Why row wins
Look up a user's profile One disk read, all fields fetched together
Update an order status Locate the row, mutate, write back — minimal I/O
Insert a new customer Append the bytes to a page, done
Fetch shopping cart items for one user Range scan a few rows of cart_items
Show a single product's full details One row, all 30 columns at once

This is the world of OLTP: lots of small reads and writes, each touching one or a few full rows. Postgres, MySQL, SQLite, MongoDB (WiredTiger) — all row stores.

Where row stores hurt

You're an analyst running a quarterly report on a 4 TB row-stored orders table:

SELECT
  region,
  product_category,
  SUM(amount) AS revenue
FROM orders
WHERE date > '2026-01-01'
GROUP BY region, product_category;

The query needs three columns — region, product_category, amount — out of 50. The other 47 are irrelevant.

In a row store, the database can't read just three columns. It reads every full row — all 50 columns of every row that matches the WHERE — because rows are stored together.

Even if your three columns total 30 bytes per row, the database reads 400 bytes per row. You're throwing away 92% of the I/O.

For 200 million rows, that's 80 GB of data read, of which 6 GB is what you actually need. On a disk doing 500 MB/sec, that's 160 seconds vs 12 seconds. 13x slower than physically necessary.

This is the workload row stores hate: scanning lots of rows but only needing a few columns.

Column-based storage

Column stores invert the layout. Instead of storing rows together, they store all values of one column together.

                          COLUMN STORE LAYOUT

Column "id": ┌─────────────────────────────────────────────────────────┐ │ 1, 2, 3, 4, 5, 6, 7, 8, ..., 10,000,000,000 │ └─────────────────────────────────────────────────────────┘

Column "name": ┌─────────────────────────────────────────────────────────┐ │ "Alice", "Bob", "Carol", "Dan", ..., 10B values │ └─────────────────────────────────────────────────────────┘

Column "age": ┌─────────────────────────────────────────────────────────┐ │ 30, 25, 40, 35, ..., 10B values │ └─────────────────────────────────────────────────────────┘

Column "country": ┌─────────────────────────────────────────────────────────┐ │ "US", "UK", "DE", "US", "US", "US", "UK", ... │ └─────────────────────────────────────────────────────────┘

Column "amount": ← read JUST this for SUM(amount) ┌─────────────────────────────────────────────────────────┐ │ 99.50, 12.00, 47.30, 15.99, 8.50, 200.00, ... │ └─────────────────────────────────────────────────────────┘

   ↑

To sum the "amount" column: read just this single contiguous block of values. The other 49 columns are not touched at all.

To reconstruct row 3 in full: seek to position 3 in every column block. 50 separate seeks. Painful.

The library card catalog.

Imagine a library where instead of books, the storage rooms are organized by attribute: one room contains all the titles, another room contains all the authors, another contains all publication years. To find a specific book, you'd have to query each room — annoying. But if you want to count how many books were published before 1900, you only need to walk into the publication-year room. The other rooms don't exist as far as you're concerned.

Card catalogs work this way. They're terrible for "give me everything about this book" and great for "count books matching this property."

Where column stores shine

Workload Why column wins
SUM(amount) FROM orders WHERE date > '...' Reads only amount and date columns. 96% less I/O.
Funnel analysis across user events Touches few columns; entirely sequential.
Dashboards aggregating millions of rows Aggregations vectorize beautifully.
Log analytics ("count errors per service per minute") Group-by + aggregate over narrow column subset.
Anything with ML feature extraction Loads single feature columns at a time.

This is the world of OLAP: Online Analytical Processing. BigQuery, Snowflake, Redshift, ClickHouse, Druid, Pinot — all column stores.

Where column stores hurt

You build a "user profile page" backed by a column-stored users table. The page needs all 50 fields of one user.

The query: SELECT * FROM users WHERE id = 12345.

In a column store, this becomes 50 separate reads — one per column file — to assemble one row. Each read seeks into a column block to position 12345. 50 seeks for one logical row.

A row store would have done this in one seek. A column store, used this way, can be 50x slower.

This is why you don't use BigQuery as your user-profile backend.

Column stores are terrible for high-frequency single-row reads and updates. If you tell an interviewer "use BigQuery for our user authentication service," that interview is going downhill quickly.

The 100x: three multiplicative wins

Now the question that started the chapter: why is the columnar aggregation so much faster?

Three reasons. They multiply.

Win #1: Less I/O

You read only the columns the query needs.

For our SUM(amount) query: out of 400 bytes per row, you read maybe 8 bytes (the amount column). That's 2% of the data volume for the same logical work.

Even if everything else were equal — same disk speed, same CPU — you'd already be 50x faster from I/O alone.

Cloud data warehouses like BigQuery and Snowflake charge by bytes scanned, not query time. A row-stored data warehouse would be financially ruinous. The columnar layout is what makes "pay per query" pricing economically viable. The cloud business model literally depends on this layout choice.

Win #2: Compression

Here's where it gets really good. Adjacent values in a row are different types — id, name, age, country — they don't compress together well. Adjacent values in a column are the same type, often the same value. They compress brilliantly.

Column "country" (uncompressed): "US", "US", "US", "US", "US", "UK", "UK", "US", "DE", "DE", ...

Compressed via run-length encoding: [("US", 5), ("UK", 2), ("US", 1), ("DE", 2), ...]

Or via dictionary encoding: Dictionary: { 0: "US", 1: "UK", 2: "DE", 3: "FR", ... 200 entries } Column data: [0, 0, 0, 0, 0, 1, 1, 0, 2, 2, ...] (single byte per row instead of variable-length string)

For columns with low cardinality (few distinct values), this is 10-50x compression on top of any byte-level compression.

Real-world ratio:

A typical row-stored Postgres table compresses about 2-3x via TOAST and on-disk compression.

The same data in Parquet (a columnar format) typically compresses 5-15x.

Same data. 5-7x more compression simply because of the layout.

Less storage cost. Less I/O. The compression directly amplifies the I/O win from #1.

Common columnar compression schemes you should know by name:

  • Run-length encoding (RLE): store value + count instead of repeating. Great for low-cardinality columns.
  • Dictionary encoding: store distinct values once in a dictionary, replace each row with an index. Great for strings with limited cardinality (country, status, category).
  • Delta encoding: store difference from previous value. Great for sorted timestamps or sequential IDs.
  • Bitpacking: if values fit in 12 bits, don't waste 16 or 32. Pack them tight.
  • Zstandard / LZ4: byte-level final pass on top of all the above. Modern formats apply this last.

Mention "RLE" or "dictionary encoding" in an interview about columnar formats and you signal real understanding.

Win #3: Vectorized execution

This one is subtle but huge. Now that data of one type is laid out contiguously, the CPU can process it in batches using SIMD (Single Instruction Multiple Data) instructions.

ROW-AT-A-TIME (traditional row store execution):

for each row in input: extract amount from row ← memory access if amount > threshold: ← branch total += amount ← arithmetic advance to next row ← memory access

Time per row: ~5-10 nanoseconds. 100M rows: ~500ms - 1s of CPU time.

VECTORIZED (column store execution):

for each batch of 1024 amount values: load batch into SIMD register ← one cache-aligned load apply threshold mask via SIMD ← one instruction, 8-16 lanes parallel add unmasked values to running total via SIMD advance to next batch

Time per row: ~0.5-1 nanosecond. 100M rows: ~100ms.

THIS IS PURELY A CPU EFFICIENCY WIN — not from doing less work, but from doing the same work much faster.

DuckDB, ClickHouse, and Velox (Meta's query engine) push vectorization to its limits — entire query operators are written assuming columnar data and SIMD-able operations. ClickHouse's column processing benchmarks show 1-2 GB/sec per CPU core on simple aggregations. That's bandwidth, not throughput. The CPU is the bottleneck, not the disk.

The math

Multiply them together:

ROW STORE on aggregation: 1.0× I/O (reading everything) 1.0× compression (poor due to mixed types) 1.0× CPU efficiency (one row at a time) ----- 1.0× total

COLUMN STORE on aggregation: 20-50× I/O reduction (read 2-5% of bytes) 3-7× compression bonus (further I/O reduction) 5-10× vectorized CPU ----- 300-3500× total potential speedup

Real-world numbers: typically 30-200× faster. 100× is a reasonable mid-range.

That's the 100x. Three independent multipliers.

A subtle point that interviewers sometimes probe: column stores don't create new performance — they avoid wasting it. The disk's bandwidth and the CPU's SIMD lanes were always there. Row stores just used them inefficiently for analytical workloads. Column stores let you actually achieve the hardware's theoretical performance for column-aggregation work.

Three ways to internalize this

Sometimes the same idea clicks differently. Here are three angles.

Way 1: spreadsheets.

Open a spreadsheet. Column-store thinking says: each column is its own file. Row-store thinking says: the whole spreadsheet is one continuous stream of cells, row by row.

If you ask "average salary in column F?" — column thinking lets you fetch just F. Row thinking has to read all columns to extract column F.

The catch: if you ask "show me row 47 in full," column thinking has to gather from every column file. Row thinking just streams row 47.

Way 2: physical books.

Imagine a 1000-page book where each page is one row of data. Reading page 47 ("show me row 47") is a single page-flip. Easy.

Now imagine you want to count how many pages contain the word "sunset." You have to read every page. Slow.

Now imagine the same content but reorganized: a separate booklet per "column" where each booklet contains just one column's values down the page. To find the word "sunset," you read just that one booklet. Fast.

But to read full page 47, you have to gather position 47 from every booklet — slow.

Way 3: the warehouse.

A row-store warehouse organizes inventory by order: each customer's full order on its own pallet. To pick an order: one pallet. To count how many of one product were sold: walk every pallet.

A column-store warehouse organizes by SKU: all units of product X on one pallet, all of Y on another. To count product X: one pallet. To assemble a customer's order: visit many pallets.

Both warehouses have the same total goods. The layout decides which queries are fast.

Hybrid systems and modern reality

The world isn't strictly OLTP-or-OLAP anymore. Most systems do something hybrid.

In-database hybrids

Some databases offer columnar tables alongside row tables in the same engine.

System Hybrid mechanism
SQL Server Clustered columnstore indexes (entire table stored columnar)
Postgres Extensions: cstore_fdw, citus columnar, hydra
MySQL Limited; usually requires bolt-on tools like ClickHouse Mirror
Oracle In-Memory Column Store (dual representation)
TiDB / SingleStore / Aurora Native HTAP with row + column maintained simultaneously

These systems pay for it: 2x storage, doubled write amplification, complex consistency between layouts.

Lakehouse formats: the modern shift

The big architectural change of 2019-2025 has been separating storage from compute. Data lives in object storage (S3, GCS) as columnar files (Parquet, ORC). Multiple query engines read it.

A modern data platform stack:

   OLTP databases (Postgres, MySQL — row stores)
                │
                ├── CDC stream
                ▼
              Kafka
                │
                ▼
   Object storage (S3) with Iceberg / Delta Lake / Hudi tables
   (Parquet files inside, columnar layout)
                │
       ┌────────┼────────┐
       ▼        ▼        ▼
    Spark    Trino    DuckDB    ← multiple query engines, same data

OLTP stays in row stores. Analytics happens on columnar files. The same underlying files serve dashboards, ad-hoc analysts, and ML pipelines.

The modern answer to "row vs columnar" is increasingly: both, in different layers. Row store for the OLTP service of record. Columnar files in object storage for analytics. CDC bridges them.

Parquet: the file format that ate the world

Parquet is the dominant columnar file format. You will see it in every modern data platform. Some things to know:

  • Files contain "row groups" (typically 128 MB each), each internally columnar.
  • Each row group has metadata: min/max per column, null counts, distinct counts.
  • Query engines use this metadata for predicate pushdown — skip entire row groups whose min/max can't match the WHERE clause.
  • Compression is per-column-chunk and configurable.
  • Schema evolution is built in.

Parquet plus Iceberg (a table format on top of Parquet) gives you ACID-ish transactions on object storage. The combination is what makes BigQuery's external tables, Snowflake's Iceberg tables, and Databricks' Delta Lake all viable.

When someone says "lakehouse," they basically mean Parquet + table format + a query engine. Naming Parquet in an interview signals real-world data platform exposure.

What about wide-column stores?

A common confusion. Cassandra and HBase are sometimes called "wide-column" stores. Are they columnar?

"Cassandra is a columnar database."

False. Cassandra is a wide-column row store. The "wide-column" name comes from the data model: a row can have a flexible, sparse set of columns. But the physical layout is row-oriented — a partition's data is stored together.

Cassandra is fantastic for OLTP-shaped workloads (event ingestion, time-series). It's not what you reach for to run aggregations on billions of rows. For that, you'd CDC out to a real columnar store.

Don't confuse the data model name with the storage layout.

Sharpen your pencil

Exercise 1. A team is debating: "We have a 200-column events table that's about 50 billion rows. Most queries are conversion funnels — counting events of certain types over date ranges, joined to user attributes. Some queries fetch all 200 columns of a single user's events for support tickets."

Which storage layout? Justify in 3 sentences. What does the minority use case cost you?

Columnar. The dominant workload is funnel/conversion queries — aggregations and counts over a few columns across many rows — which is the canonical OLAP shape where columnar wins by 30-100x. The 200-column table size makes columnar's compression even more valuable: each column is its own compressible chunk, and most queries touch only 5-10 of the 200.

The cost of the minority case (full-row fetch for support tickets): in a column store, this becomes 200 separate column reads to assemble one user's events. Mitigations: (a) keep a small recent-window mirror in a row store like Postgres for the support tool, fed by CDC; (b) accept that support tickets pay 2-5 seconds of latency since they're rare; or (c) use a system like ClickHouse that supports both query patterns reasonably with ORDER BY user_id.

The senior reflex: architecture follows the dominant query pattern. The minority case gets a workaround, not a redesign.

Exercise 2. A startup wants to "use BigQuery for everything." Their app needs user authentication (sub-50ms), shopping cart updates (frequent writes), order history (fetch one user's orders), and end-of-day analytics. What do you tell them?

"BigQuery for everything" is a workload mismatch. BigQuery is a columnar analytical engine — designed for scan-heavy aggregations, billed by bytes scanned, with seconds-of-latency queries. Three of the four use cases are OLTP-shaped:

Authentication, cart updates, order history are point lookups and small writes. They need sub-50ms latency, frequent updates, and per-user isolation. Use Postgres or DynamoDB — a row store / key-value store. BigQuery for these would be slow, expensive, and architecturally inappropriate.

End-of-day analytics is OLAP-shaped — aggregations across many rows, batch frequency. BigQuery is excellent here, fed by CDC from the OLTP system.

The right architecture: Postgres for the app, BigQuery for analytics, CDC bridging them. Two storage systems, each doing what it's good at. The senior framing: stop looking for one tool. Look for the right tool per workload.

Exercise 3. Explain to Sam, in 3 sentences, why columnar storage compresses better than row storage. No jargon.

Columnar storage groups all values of the same type together — a million ages are next to each other, a million country codes are next to each other. When data is uniform like that, you can use clever tricks: store "US, US, US, US" as "US × 4," store country names as small numbers via a dictionary, and pack everything tighter. Row storage interleaves different types — an age, a string, a date, a money value, all next to each other — which leaves no patterns for the compressor to exploit.

There are no dumb questions

Q: Are columnar stores append-only?

A: In practice, mostly yes. UPDATEs and DELETEs are usually implemented as "delete vectors" (a bitmap marking row positions as deleted) plus new inserts of the changed data. Periodic rewrites consolidate everything. Iceberg, Delta Lake, and Hudi all use variations of this. True in-place column updates are rare and slow — you'd have to rewrite the affected column block.

Q: Why don't row stores just compress better and use SIMD?

A: They try, but they can't get the same wins. SIMD on heterogeneous data doesn't work — different bytes are different types. Compression on heterogeneous data has poor ratios. The fundamental bottleneck is the layout: row stores are mathematically forced to read more bytes for column-wise queries. You can't optimize past the layout.

Q: Does columnar work for joins?

A: Yes, with care. Hash joins (Module 06) work fine — you build a hash table of the smaller table and probe with the larger. The join key column gets read from both sides. Modern columnar engines like DuckDB and ClickHouse do joins very well. The expensive case is many-to-many joins across huge tables — but that's expensive in row stores too.

Q: What about real-time data? I thought columnar was for batch.

A: Used to be true. Modern columnar stores like ClickHouse, Druid, Pinot, and Rockset support streaming ingestion with sub-second freshness. They use techniques like writing recent data to small "real-time segments" (often row-flavored or hybrid) that get compacted into proper columnar format in the background. The boundary between "OLTP" and "real-time analytics" has blurred a lot.

Q: Can I add a column to a columnar table easily?

A: Yes — actually easier than in row stores. Adding a column is just creating a new column file. Existing data isn't touched. Old rows have an implicit default for the new column. This is one of the advantages of columnar layouts that doesn't get talked about enough — schema evolution is cheap.

Q: What's the deal with "column-family stores" — are they columnar?

A: Different concept. Column-family stores (Cassandra, HBase, BigTable) group columns into "families" stored together. A family might contain 5-10 related columns. Within a family, the layout is still row-ish. They're called column-family because of the data model, not the disk layout. Confusing? Yes. Blame 2000s naming conventions.

Q: How do columnar stores handle text and JSON?

A: Variable-width columns get stored with an offset table — pointers to the start of each value. JSON columns are common but tricky: pure JSON loses much of the columnar benefit, since the structure is inside the value. Modern formats like Parquet have "nested types" that flatten JSON-like structures into multiple inner columns, regaining the benefit. ClickHouse has a JSON type that does this transparently.

Q: Is there a use case where row and column are equally good?

A: Yes — small tables. If your table fits in RAM and the query hits all of it anyway, layout barely matters. Both can serve a 100K-row dimension table in under 10ms. Layout choice matters when data doesn't fit in cache and access patterns differ.

Three myths to dynamite

"Columnar is just better."

False. Columnar is better for analytical workloads. It's worse for high-frequency single-row reads, worse for frequent updates, worse for low-latency point lookups. Always anchor to workload before recommending a layout.

"Cassandra is a columnar database."

False. Cassandra is a wide-column row store. Within a partition, data is stored together — that's row-oriented. The "wide-column" name describes the data model (sparse columns), not the disk layout.

"Use a column store and you don't need indexes."

Half-true. Column stores rely on a different toolset — predicate pushdown via per-row-group min/max metadata, plus optionally bloom filters per column block, plus partition/cluster ordering. You don't have B-tree indexes per column the way Postgres does. But you absolutely care about how data is physically partitioned and clustered, which is the columnar equivalent.

Interview gotchas

Saying "columnar is just better." Senior interviewers will press: better at what? At what cost? Always anchor your statement to a workload type.

Forgetting compression in your explanation. If you describe columnar advantages without mentioning compression, you've described 30% of the story. Always mention all three: I/O reduction, compression, vectorization.

Confusing wide-column with columnar. Cassandra/HBase = wide-column row stores. Different from Parquet/BigQuery = columnar. Different layouts, different use cases.

Suggesting columnar for OLTP. "We should put our user table in BigQuery for fast queries" is a sign you don't understand layouts. OLTP belongs in row stores; columnar is for analytical workloads.

Not knowing Parquet by name. It's the dominant columnar format. Mentioning Parquet, Iceberg, or Delta Lake when asked about modern data platforms signals real-world experience.

Mock interview

We're building a real-time dashboard showing per-user spending in the last 24 hours, refreshed every 30 seconds, for 50 million users. Where do you store the data?

The query shape — aggregation over a time window, fanout across millions of users, sub-second response — is OLAP-shaped, so columnar is the right family. The complication is the real-time part — continuous ingestion at scale plus 30-second freshness.

I'd consider three options.

ClickHouse, columnar with high-throughput streaming ingestion. Excellent for this exact workload — purpose-built for real-time aggregations on event streams. Probably my default. Partitioned by day, ordered by (user_id, timestamp), queries become fast range scans within a user's data.

Druid or Pinot, similar shape, optimized for the multi-tenant dashboarding use case specifically. Mature operationally. Slightly more setup complexity.

BigQuery or Snowflake with streaming inserts and materialized views. Higher operational simplicity since they're managed, but the streaming-to-fresh-query window is typically a few seconds — usually fine for 30-second refresh, but worth verifying.

Names three concrete options ranked by suitability. Mentions specific tuning details (ORDER BY clause for ClickHouse) — signals hands-on experience.

You said "default to ClickHouse." Why not Postgres with materialized views? It's simpler.

Postgres is a row store. For 50 million users with continuous ingestion, the spending aggregation query has to scan a lot of bytes per refresh — Postgres reads full rows even when you only want the amount column. At 30-second refresh frequency across many concurrent dashboards, that I/O adds up fast.

The materialized view fights this — but you have to refresh it. Refreshing a materialized view of "all 50M users' last-24h totals" every 30 seconds is itself a heavy aggregation, and it'll either lag behind or steal capacity from OLTP queries on the same Postgres.

For toy scale — say a few hundred thousand users — this is fine. At 50M users with continuous ingestion, you're fighting the storage layout. The right tool is one that's columnar, supports streaming, and is designed for the dashboard read pattern. That's ClickHouse-shaped.

Doesn't reflexively diss Postgres. Acknowledges where it works (small scale), explains where it breaks (this scale). Reasoned, not dogmatic.

ClickHouse is great. But how does the data actually get in?

Two clean patterns:

Pattern 1: Direct streaming via Kafka. Producers write spending events to Kafka. ClickHouse pulls via the Kafka table engine — built-in consumer that reads from a topic and inserts into a target table. Native, fast, durable.

Pattern 2: CDC from the OLTP system. If spending events first land in Postgres (because that's where the actual transaction lives), use Debezium to stream changes to Kafka, then into ClickHouse. The OLTP system stays the source of truth; ClickHouse is the analytical mirror.

In practice, both patterns coexist. The OLTP system handles "did the payment go through?" — strict consistency, row store. The analytical mirror in ClickHouse handles dashboards. CDC keeps them in sync.

Brings in CDC unprompted — shows the candidate is thinking architecture, not just storage. The "two patterns" framing is a senior speech pattern: enumerate options, don't just commit prematurely.

Last one. Suppose tomorrow you're told the dashboard query latency is too high — sometimes 3 seconds at p99. What do you investigate first?

Three things, in order:

One: data distribution and ordering. ClickHouse query speed is dominated by how much data the engine has to scan. If queries always filter by user_id and timestamp, the table should be ORDER BY (user_id, timestamp). If it isn't, switch — that single change can be a 10x improvement.

Two: partition strategy. If queries usually look at "last 24 hours," partition by day. Old partitions can be pruned automatically; recent partitions stay small and fast.

Three: materialized views for hot patterns. ClickHouse has incremental materialized views — they update as new data arrives. If a specific aggregation is hot ("total spend per user in last 24h"), maintain a continuously-updated rollup. Queries hit the rollup, not the raw events. Often gets you another order of magnitude.

If after all that the query is still 3 seconds, it's probably a CPU or memory bound rather than I/O — the engine is doing the right thing but the operation is genuinely heavy. Then you either accept it or move to a more tailored solution like a real-time precomputed inbox per user.

Investigation order matches reality: cheapest, highest-impact tweaks first. "Probably CPU or memory bound rather than I/O" is the kind of phrase that signals "I've debugged this before."

Cheat sheet

Row vs Columnar Storage — One Page

Row store (OLTP world)

Bytes arranged by entity. One row's data contiguous on disk.

Strong: point lookups, frequent updates, fetching full rows, write-heavy mixed workloads. Weak: aggregations on few columns, scan-heavy analytical queries.

Used by: Postgres, MySQL InnoDB, SQLite, MongoDB WiredTiger, Cassandra (yes, despite the wide-column name).

Column store (OLAP world)

Bytes arranged by attribute. One column's data contiguous on disk.

Strong: aggregations, scans of few columns, dashboards, analytical workloads. Weak: full-row fetches, frequent updates, point lookups.

Used by: BigQuery, Snowflake, Redshift, ClickHouse, Druid, Pinot, DuckDB, Vertica. Files: Parquet, ORC.

Why columnar wins on analytics — three multiplicative wins

  1. Less I/O — read only the columns the query needs (often 2-5% of bytes).
  2. Better compression — adjacent values are same type, often same value (RLE, dictionary, delta encoding work well).
  3. Vectorized execution — SIMD on contiguous typed data (5-10x CPU efficiency).

Multiplied: 30-200× faster, sometimes 1000×.

Modern reality — the lakehouse

Storage and compute separated. Parquet files in object storage (S3, GCS), with a table format (Iceberg / Delta Lake / Hudi) on top. Multiple query engines (Trino, Spark, DuckDB, Snowflake) read the same files.

The pattern that ate the data warehouse market.

Hybrid systems

  • Postgres + cstore_fdw or Citus columnar (columnar tables in row engine).
  • SQL Server clustered columnstore.
  • TiDB / SingleStore / Aurora (HTAP — both layouts maintained).
  • Druid / Rockset / Pinot (real-time + columnar).

You pay 2x storage and writes for both layouts. Use only when warranted.

The 30-second verbal answer

"Row stores keep one row's bytes together — fast point reads and updates, slow on column aggregations. Column stores keep one column's bytes together — fast aggregations through I/O reduction, compression, and SIMD vectorization, slow on full-row fetches. Use row for OLTP, column for OLAP. Modern systems combine both via CDC from row-store OLTP into columnar lakehouse formats."

Always pair with

Compression (RLE, dictionary, delta), vectorization, predicate pushdown, OLTP vs OLAP, HTAP, Parquet, Iceberg, CDC.
