MODULE 10

Replication

Leader-follower, multi-leader, and the failover stories that should make you nervous

Your boss says "let's add a read replica to scale." Innocent enough — until users start seeing stale data, then duplicate writes when failover goes wrong, then split-brain.

Replication is where databases go from "single node" to "system." It's also where most engineers' production confidence runs out. By the end of this module, you'll be able to talk through every replication topology and know exactly what fails when.

Sam learns about distributed pain

Sam OK, distributed time. I get the basic idea — we have a primary and replicas, writes go to the primary, reads can go to replicas. We add replicas as we need more read capacity. Right?

Maya Mostly right. Now: a user submits a comment on your site. Their browser sends the POST. Your server writes to the primary, gets a 200, returns success to the user. The user's page reloads — and the comment isn't there. They refresh. Still not there. They refresh again, 30 seconds later. Now it appears. What just happened?

Sam Oh. The reload hit a replica that hadn't gotten the update yet?

Maya Exactly. Replication lag. The user wrote to the primary, the read went to a follower, the follower hadn't received the write yet. Their own action seems to have failed — even though the system worked perfectly by its own definition.

Sam That sounds like a bug.

Maya It is. It's called the "read your own writes" problem and it's the first thing that breaks when you add replicas. There are five things that break. We're going to walk through all of them.

Sam Five things?

Maya Read-your-writes. Replication lag during failover. Split-brain. Multi-leader conflicts. The fan-out wall. Each of them has cost real engineering teams real downtime. By the end of this module you'll have the vocabulary, the failure modes, and the playbook.

Replication has three main topologies: leader-follower (one writer, many readers), multi-leader (writes accepted in multiple regions), and leaderless (any node accepts writes, quorum reads). Each makes different tradeoffs. None gets you fast writes, fresh reads, and continued operation during partition all at the same time. Pick what you sacrifice.

Most production systems are leader-follower. Multi-leader exists for geo-distributed writes. Leaderless is for high-availability key-value workloads. Senior engineers can articulate when each is appropriate.

Leader-follower: the dominant pattern

One node is the leader (also called primary or master). All writes go there. Followers (also called secondaries, replicas, or slaves) replicate from the leader.

The basic flow:

Client sends a write to the leader.

Leader writes to its WAL (Module 02) and commits locally.

Leader sends the WAL records (or a logical change stream) to each follower.

Each follower applies the records to its own data files.

Reads can hit any follower — with caveats we're about to discuss.

A typical Postgres setup: 1 primary, 2 replicas. The primary takes all writes. Reads are load-balanced across the replicas via a pooler like PgBouncer or PgCat. Writes complete on the primary; replicas catch up "eventually" — usually within milliseconds.

Sounds simple. The complications start with three letters: lag.

Sync vs async — the most important distinction

This is the choice that defines everything else about your replication.

Asynchronous

Leader acks the write to the client before followers acknowledge.

Pro: fast writes — no network round-trip wait.

Con: if leader crashes after ack but before replication, the write is lost.

Used by: default Postgres, default MySQL, most cloud-managed setups.

Synchronous

Leader waits for at least one follower to confirm before acking.

Pro: writes durable on multiple nodes before client sees success.

Con: latency = leader's local time + slowest sync follower's network. One slow follower stalls writes.

Used by: Postgres with synchronous_standby_names, MySQL with semi-sync.

There's also semi-sync — at least N out of M followers must confirm. Common middle ground.

The default in most databases is async. This means: - Writes are fast (good). - Writes can be lost on leader failure (bad).

Most production teams don't realize this until the first failover incident. Senior engineers verify the durability stance before incidents.

The mailroom analogy.

Async replication is like sending a letter via the mailroom and walking out before they confirm it's been delivered. Fast for you. If the mailroom has a fire before delivery, your letter is gone — but you don't find out for days.

Sync replication is like sitting in the mailroom until they hand you a delivery confirmation. Slow. Annoying. But you know the letter arrived.

Semi-sync is like requesting a confirmation from "any 2 of 3 mailrooms." You wait, but if one mailroom is slow, the others can confirm. Faster than full sync, safer than pure async.

Replication lag — the silent enemy

The "ghost data" incident (very common pattern):

A user submits a comment. Server writes to primary, returns 200. User's browser refreshes the page. Page query is load-balanced to a replica. Replica hasn't received the write yet. User sees their own comment is missing.

User refreshes again. Now it appears.

The user thinks the system is broken. The system thinks everything is fine. Replication lag is the gap between these two perceptions.

This is the single most common production complaint in any system that adds read replicas. It has many fixes, ranging from cheap to architectural.

Read-your-writes consistency

The technical name for the property the user expects: "reads should reflect their own prior writes." Three common workarounds:

Strategies for read-your-writes:

Read-from-leader after write. Tag the user's session as "must read from leader for the next 30 seconds." Routes their reads to the primary, where the data is fresh. Other users still hit replicas. Simplest fix; works for most apps.

Wait for replication. Capture the LSN at write time, store it in the user's session. On next read, query the chosen replica's pg_last_wal_replay_lsn() — wait until it's ≥ the captured LSN before serving the read. More precise; more complex.

Sticky sessions. Route a user always to the same replica (via a session-aware load balancer). At least the lag they experience is consistent — they don't toggle between fresh and stale on each request.

The simplest pattern that handles most of the pain: route a user's reads to the leader for a few seconds after they write. Cookies or session state mark the user as "in read-your-writes window." After the window expires, normal load balancing.

This is what Reddit, Stack Overflow, and many high-traffic sites do under the hood.

For "I just posted, why don't I see it?" — the simplest fix is to read the user's own writes from the leader for a short window. Don't try to fix all reads. Most reads tolerate slight staleness; only the user's own actions need freshness.

Failover — the painful part

The leader dies. Now what?

The cluster must:

The failover dance:

Detect the failure. Heartbeat timeouts trigger the suspicion. Too aggressive = false positives = thrashing. Too slow = long downtime. Typical: 3 missed heartbeats over 10-30 seconds.

Elect a new leader from among the followers. Usually the most up-to-date follower wins.

Reconfigure clients to point at the new leader. DNS, service mesh, or connection pool updates.

Handle un-replicated writes that were on the dead leader. This is where data loss happens.

Each of these is a source of bugs.

The split-brain disaster

The failure mode that haunts every replication setup:

  1. A network partition isolates the leader from its followers.
  2. Clients are still connected to the leader (different network path) — they keep writing.
  3. Followers can't reach the leader — they think it's dead.
  4. Followers elect a new leader from among themselves.
  5. Now there are two leaders, both accepting writes from different subsets of clients.
  6. When the partition heals, the two leaders have conflicting writes. Some data must be lost.

This is split-brain. Real systems prevent it via quorum (majority must agree on leader) or fencing tokens (only the new leader can authoritatively act).

Split-brain is the single most dangerous failure in replication. Two leaders both think they're the source of truth. Reconciliation after the fact often loses data — the system has to pick which version of the conflicting writes wins. Whichever side loses, the users on that side experience their writes silently disappearing.

Prevention is the only real defense. Quorum-based promotion (majority of nodes must agree). Fencing tokens (each leadership term has a monotonically-increasing number; old leaders' writes are rejected). STONITH ("Shoot The Other Node In The Head") — explicitly kill the old leader before promoting the new one.

A real-world failover war story

The GitHub 2018 incident — the canonical replication failure case.

In October 2018, GitHub had a 24-hour partial outage caused by a routine network change.

The sequence:

  1. A 43-second cross-coast network partition isolated MySQL clusters in different regions.
  2. Failover kicked in. Clusters in the West Coast region promoted local replicas, started accepting writes.
  3. Network healed. Now there were two clusters with divergent writes — East Coast had been writing, West Coast had been writing, neither knew about the other's changes.
  4. GitHub had to pick which side won for each affected piece of data. They couldn't merge the divergence — there was no automated way to know which writes mattered more.
  5. The repair took ~24 hours of running careful reconciliation jobs and accepting that some data would be lost or marked inconsistent.

The blameless postmortem GitHub published is required reading for anyone running replicated MySQL. The lessons: - A 43-second network blip caused a 24-hour outage. - Async replication + automated failover + multi-region = a recipe for split-brain. - The recovery was harder than the failure.

This is why senior engineers are paranoid about failover policies. "It works in steady state" is not the bar. "It survives a network blip without diverging" is the bar.

Tools and approaches for safer failover by database:

Database Failover tool / approach
Postgres Patroni, Stolon, repmgr, pg_auto_failover
MySQL Orchestrator, ProxySQL, MHA, MySQL InnoDB Cluster
MongoDB Built-in replica sets with majority elections
Redis Redis Sentinel, Redis Cluster
Kafka Built-in (controller-managed)

The common thread: all production-grade tools require quorum-based promotion. Manual failover or majority-of-1 setups are how split-brain happens. Always run with quorum.

Multi-leader replication

Multiple nodes can accept writes. Writes propagate to other leaders.

A globally distributed app: users in NYC and Tokyo. You deploy a leader in each region. NYC users write to NYC's leader; Tokyo writes to Tokyo's. Leaders replicate to each other asynchronously. Local writes feel fast everywhere.

Sounds great. The problem appears the moment two users in different regions update the same record concurrently.

Multi-leader
Wins Geographic write locality. Continued operation during inter-region partition. No single point of failure for writes.
Losses Conflict resolution. Two users in different regions update the same record. Now what?

Conflict resolution strategies

The four common conflict resolution patterns:

Last write wins (LWW): pick the write with the latest timestamp. Easy. Lossy — one of the writes is dropped silently. Has a fatal subtlety: clock skew across regions can mean the "latest" write actually happened earlier in real time.

Application-defined merge: store both versions, let the app decide what to do. Common in CRDT-style designs.

Operational transform / CRDT: design the data so updates are commutative — they merge automatically without conflict. Used by collaborative apps like Google Docs and Figma.

Custom callback: tell the database "when conflict, run this function to merge." Flexible, requires careful business logic. Riak made this approach famous.

Last write wins seems simple but has a fatal flaw: clock skew. If NYC's clock is 100ms ahead of Tokyo's, NYC writes always "win" — even if they happened earlier in real time.

The fix: use logical clocks (vector clocks, hybrid logical clocks) instead of wall clock when you can. They give you a partial ordering that respects causality without depending on synchronized clocks.

Don't say LWW in an interview without mentioning the clock skew problem. Senior engineers know.

Read replicas: the workhorse

A "read replica" is just an asynchronous follower used for offloading read traffic. The most common reason teams add replication.

Use cases: - Reporting / analytics queries that would slow down OLTP if run on the primary. - Geographic read locality — replica near read-heavy region. - Scaling read throughput horizontally.

Limitations: - Stale reads (replication lag). - Not infinitely scalable — at high replica count, the leader saturates sending data. - Doesn't help write throughput at all.

Read replicas don't help writes. Junior engineers sometimes think "we'll scale by adding replicas." Reads scale; writes don't. The leader is still doing all write work, plus the additional work of streaming WAL to N replicas. More replicas can actually slow down the leader by saturating its network bandwidth.

The fan-out wall

The fan-out limit. A Postgres leader can typically support 5-10 streaming replicas before WAL shipping becomes the bottleneck. Past that, you have options:

Cascading replication: replicas replicating from replicas. The leader streams to a few "hub" replicas, which then stream to "leaf" replicas. Adds slight extra lag at the leaves but spreads the WAL-shipping load.

WAL archive + restore: replicas pull WAL from object storage instead of streaming directly from the leader. More tolerant of intermittent connectivity, slightly higher lag.

Move to logical replication for some replicas: filter and transform data, send only what each replica needs. More CPU on the leader, less network bandwidth per replica.

For very large systems: physical replication for hot replicas, logical replication for downstream consumers (analytics, ML). The senior pattern at scale.

A typical scaling progression:

  • Small: 1 primary, 1 sync replica for HA. Done.
  • Growing: 1 primary, 1 sync replica, 2 async read replicas. Reads load-balanced across the asyncs.
  • Larger: 1 primary, 1 sync replica, 5+ async replicas. Connection pooling becomes critical.
  • At scale: cascading replication or logical replication for downstream systems. Plus consider sharding (Module 15).
  • Very large: separate read clusters per workload (analytics, search, OLTP), each fed by its own replication path.

The senior framing: scaling reads via replicas is fine until ~10 replicas. Past that, the architecture must change.

Three more ways to think about replication

Way 1: photocopying.

Async replication is like photocopying a document and mailing the copy. Fast for you (you finish the original work before the copy arrives). If the original is destroyed before the copy arrives, the copy never exists.

Sync replication is like dictating to a court reporter who confirms each sentence as you speak. Slow. But you know there's a verified second copy in real time.

Read replicas are like keeping copies of every memo at five different branch offices. Fast lookup at any branch. Each branch might be a few minutes behind the headquarters. If you absolutely need the latest version, call headquarters.

Way 2: a busy household.

Single-node database is one person managing the family calendar. Authoritative, but everyone has to ask them.

Leader-follower is one person managing the calendar and posting copies on every fridge. Family members can read any copy. If the master copy gets lost, anyone with a recent fridge copy can become the new authority.

Multi-leader is each parent independently managing their own calendar and trying to sync at dinner. Works great until both parents schedule conflicting things for the kid on Saturday.

Split-brain is the parents stop talking for a week, both schedule things, and now the kid has two simultaneous obligations.

Way 3: source code branches.

Single-node = one main branch, everyone commits to main. Strict serialization.

Leader-follower = main branch with read-only mirrors. Faster lookups, but mirrors might be a few commits behind.

Multi-leader = feature branches that get merged later. Conflicts arise when two branches modify the same line. Manual or automated merge resolves them.

Split-brain = two long-lived branches diverge silently for weeks. Eventually you need a merge conflict resolution process. Some commits will be lost.

Sharpen your pencil

Exercise 1. Your team is adding a read replica to a Postgres setup. After deployment, users complain about "ghost data" — submitting a form, then immediately not seeing it. What's happening, and what's the fix?

Diagnosis: replication lag exposing read-your-writes. The user's write went to the primary; their next read got load-balanced to a replica that hadn't received the change yet. Classic.

Three fixes, in order of preference:

Fix 1: Sticky-read-after-write window. In the user's session, route all reads to the primary for N seconds (e.g., 30) after a write. Simple, works, gives users consistent UX. Most production systems use this pattern.

Fix 2: Replication slot or LSN tracking. After write, capture the LSN. On next read, wait until the chosen replica's apply LSN ≥ that captured LSN. More precise, more complex. Useful when read-your-writes must work without trapping the user on the primary for any longer than necessary.

Fix 3: Read from primary for cache-miss-prone queries. If the data being read is "user's own recent action," always read from primary. Save replicas for "lookup user N's profile."

What NOT to do: tell the team "just live with eventual consistency." Users hate that, and rightly so. The system should honor "show me my own work."

Exercise 2. Your Postgres setup is currently 1 primary + 1 async replica. You want to add HA — surviving primary failure without data loss. What do you change?

The key insight: async replication can lose recent writes on primary failure. If you want zero data loss, you need synchronous replication.

The setup:

  1. Configure synchronous_standby_names = 'replica1' on the primary. Now commits wait for replica1 to acknowledge.

  2. Add at least one more async replica (so you have primary + sync_replica + async_replicas). Why: if the sync replica is down, all writes block. Having a second sync-eligible replica via ANY 2 (replica1, replica2) gives you safe quorum.

  3. Add an automated failover tool — Patroni or pg_auto_failover. The tool monitors health and promotes a replica when the primary fails. Critical: it must use quorum-based promotion to avoid split-brain.

  4. Configure clients to discover the current primary. PgBouncer in front of Patroni-managed clusters handles this transparently.

The trade-offs you accept: - Write latency increases by the network round-trip to the sync replica. - If all sync replicas are down, writes block. (Better than data loss, but operationally significant.) - Failover takes seconds to tens of seconds — not instant.

The senior framing: HA is a property of the whole topology and configuration, not a switch you flip. Each piece (sync replication, automated failover, quorum, client discovery) plays a role. Test the failover under realistic conditions before declaring victory.

Exercise 3. Explain to non-technical Sam, in two sentences, why "split-brain" is the worst thing that can happen during failover.

Split-brain is when the system promotes a new primary while the old primary is still alive and accepting writes — so you suddenly have two authoritative sources of truth that disagree. Reconciling the disagreement after the fact almost always means picking which writes to keep and which to throw away, which means some users' actions silently vanish — the worst possible failure mode for a database that's supposed to remember things.

There are no dumb questions

Q: What's the difference between physical and logical replication?

A: Physical replication ships byte-for-byte changes to disk pages — the replica is an exact bit copy of the primary. Logical replication ships row-level operations ("INSERT into table X with values Y") which the replica applies via SQL-like operations. Physical is faster and exact; logical is more flexible (can replicate to different versions, filter rows, transform). Module 11 covers this in depth.

Q: Can the same node be both leader and follower?

A: In some cases yes — multi-leader topologies have nodes that are leaders for some data and followers for others. In standard leader-follower, no — a single node is one or the other for the whole database. Replica chains (cascading replication) have intermediate nodes that are followers of the primary and leaders for downstream replicas, blurring the line.

Q: What happens during automatic failover if the network just briefly blips?

A: This is where things get dangerous. If failover triggers too aggressively (too few missed heartbeats), you can promote a new leader while the old one is still alive — split-brain. The mitigation: tune detection thresholds carefully, require quorum for promotion, and use fencing to ensure the old leader can't continue writing after demotion.

Q: Why don't all systems use synchronous replication?

A: Latency. Every commit pays the network round-trip to the sync replica. Across regions that can be 100+ ms per commit. For latency-sensitive OLTP, this is unacceptable. The trade-off: throughput vs durability vs consistency. Async writes are the default because most apps prefer fast writes to perfect durability.

Q: How do I monitor replication lag?

A: In Postgres: SELECT now() - pg_last_xact_replay_timestamp(); on a replica gives time-based lag. pg_stat_replication on the primary shows per-replica state including LSN gaps. In MySQL: SHOW SLAVE STATUS; gives Seconds_Behind_Master. Set alerts on these — lag over 30 seconds usually indicates a problem.

Q: What's the relationship between replication and backups?

A: Replicas are not backups. A bug that deletes data on the primary deletes it on replicas too — replication faithfully copies the deletion. Backups are point-in-time snapshots that protect against logical errors. You need both. Senior engineers say "replicas for HA, backups for recovery from data corruption."

Q: Can I have a replica in a different cloud provider?

A: Yes — and many enterprises do for disaster recovery. Cross-cloud replication usually goes through a CDC pipeline (Module 11) rather than native streaming, because cloud-managed databases often don't expose the streaming protocol externally. Or you run your own Postgres and stream natively.

Q: What's "leaderless" replication?

A: A topology with no fixed leader. Any replica accepts writes. Reads check multiple replicas (quorum reads) to find the latest version. Popularized by Amazon's Dynamo paper. Cassandra and Riak use this model. Tradeoffs: better write availability during failures (no leader to elect), more complex consistency model, requires application-level conflict handling.

Three myths to dynamite

"Adding replicas scales the database."

Half-true. Replicas scale reads. They do nothing for writes — the leader still does all write work, plus more (streaming to replicas). Past about 10 replicas, the leader's network becomes the bottleneck. Scaling writes requires sharding (Module 15), not more replicas.

"Sync replication means no data loss."

Half-true. Sync replication means no data loss if at least one sync replica survives. If all sync replicas die before async ones catch up, the unreplicated writes are lost. Multi-replica quorum sync gives you safety as long as a majority survives.

"Read replicas are just like the primary, just slightly behind."

Misleading. Replicas can lag arbitrarily under load — minutes or hours during heavy writes. They can serve drastically stale data during catch-up. They can have different query plans (different stats). Treat them as different beasts, not perfect mirrors.

Interview gotchas

Treating "replication" as one thing. Synchronous, asynchronous, semi-sync, logical, physical — all different. Specify which.

Forgetting that read replicas don't help writes. Writes still pile up on the leader. If write throughput is your bottleneck, replicas don't fix it — sharding does.

Saying "multi-leader is just better." Multi-leader trades simplicity for write availability. Conflicts are a real engineering cost. Most production systems are leader-follower for that reason.

Recommending automated failover without quorum. "We have automated failover" is a liability without quorum-based promotion. Split-brain is the result of getting failover wrong.

Not knowing the GitHub 2018 incident. Replication failover stories are interview territory. Knowing the canonical case (network blip → split-brain → 24-hour recovery) signals real-world awareness.

Mock interview

We have a Postgres primary and three read replicas. We want to scale further. Add more replicas, or do something else?

Three considerations:

One — what's the bottleneck? If writes are saturating the primary, more replicas don't help. The primary is doing the same write work plus shipping WAL to each replica. More replicas = more network/CPU on the primary. There's a fan-out wall around 5-10 replicas in Postgres.

Two — what kind of reads are slow? If reports are slow, putting them on a dedicated reporting replica helps. If user-facing latency is high, more replicas help only if the bottleneck is read concurrency, not query plan or data size. Sometimes the fix is "tune the slow query," not "add hardware."

Three — is staleness acceptable? More replicas = more replicas to keep in sync = potentially worse tail latency on lag during heavy write spikes.

Realistic options ranked: - Connection pooling (PgBouncer or PgCat) to reduce connection overhead. Many "scale" problems are actually connection exhaustion, not throughput. - Materialized views for hot reports — Module 05. - Cascading replication: replicas replicating from replicas. Spreads the WAL-shipping load. Slight extra lag. - Partitioning if a single huge table is the issue. - Sharding if writes have outgrown one node — Module 15.

I'd reach for sharding as a last resort because it's expensive operationally. But there's a real ceiling on a single-leader Postgres — somewhere around 100K writes/sec on premium hardware, far less on commodity. If the team is approaching that, plan the sharding work now, not after the wall.

Multiple diagnostic angles. Specific tools by name. The "sharding as last resort but plan early" framing — operationally aware.

We've decided to add synchronous replication for HA. The team is worried about latency spikes. What do you tell them?

The concern is legitimate. Sync replication adds the network round-trip to a sync replica into every commit's latency. On the same data center, that's typically 0.5-2ms — usually acceptable. Cross-AZ within a region: 1-3ms. Cross-region: 50-200ms — usually unacceptable.

Three mitigation strategies:

One — keep sync replicas close. Place at least one sync replica in the same data center or AZ as the primary. Cross-region replicas can be async — they're for disaster recovery, not for the synchronous critical path.

Two — use quorum sync. synchronous_standby_names = 'ANY 2 (replica1, replica2, replica3)'. Commits wait for any 2 of 3 to ack. If one is slow, the others can confirm. This protects against single-replica latency without giving up safety.

Three — measure the impact. Before deploying, run a benchmark with sync replication enabled. The latency hit might be lower than the team fears, especially with a well-located replica. If it's a problem for some workloads, you can use sync for critical writes (SET LOCAL synchronous_commit = on) and async for non-critical writes (SET LOCAL synchronous_commit = off) — per-transaction control.

The framing: sync replication is a conscious latency-vs-durability trade. Quantify both sides before deciding the global default.

Specific numbers (RTT estimates by topology). The "per-transaction control" detail signals depth — most engineers don't know synchronous_commit is a session-level setting.

The on-call engineer wakes up to "primary database unreachable." Walk me through the first 10 minutes.

A triage flow, in order of urgency:

Minute 0-2: confirm scope. Is the primary actually down, or is it a network partition that looks like the primary is down? Check from multiple monitoring vantage points. A network blip and an actual crash require different responses.

Minute 2-5: check failover state. Did automated failover already trigger? If yes, is the new primary healthy and accepting writes? Check application metrics — are writes succeeding? Reads succeeding? If the failover went cleanly, the immediate crisis is resolved; now we investigate the original cause.

Minute 5-7: if no automated failover, manual decision. Is the primary really gone, or is it about to recover? Premature manual failover causes split-brain — the original primary comes back, sees the new primary, and now you have two leaders. If in doubt, wait a few minutes for the original primary or for the failover tool to reach quorum.

Minute 7-10: client traffic. Once the new primary is established, verify clients are connecting to it. Connection pools may need to refresh. Stale connection caches can route writes to a defunct old primary for several minutes.

During all of this: communication. Update the incident channel. Note assumptions made. If data loss is possible (un-replicated writes lost on the dead primary), flag it for the team to investigate after the immediate crisis.

After the crisis (later): - Postmortem the failover behavior. Did it work as designed? - Verify replicas are catching up properly. - Investigate the original primary failure cause. - Check for any data loss from the failover gap.

The senior reflex: don't act fast in distributed system incidents. Acting fast is how you turn a small incident into a big one. Confirm the situation, then act deliberately.

Time-boxed plan. The "don't act fast in distributed incidents" framing is the senior insight. Mentions the post-crisis steps that junior engineers forget.

Last one. Your CEO read about multi-leader databases and wants to know "why aren't we using Cassandra so we never have downtime?"

The CEO is reacting to a real frustration — outages are bad — but the proposed solution misunderstands what each system gives up.

The conversation I'd have:

One: Cassandra is leaderless, not multi-leader, but that's a side issue. What the CEO actually wants is "never go down." Both leaderless and multi-leader systems achieve this at the cost of consistency and developer experience. They keep accepting writes during failures, but the writes can conflict, and the application has to handle resolution.

Two: our app may not tolerate that. Most applications are written assuming they read what they wrote, that constraints hold, that two concurrent writers don't both succeed in mutually contradictory ways. Cassandra-style systems can break all of these. Migrating means rewriting how the application handles data — months of work and ongoing complexity.

Three: there are gradations. We don't have to go all the way to Cassandra to improve uptime: - Sync replication with quorum across multiple AZs: survives single-AZ failures. - Read replicas in multiple regions: survives single-region read failures. - Active-passive cross-region with documented manual failover: survives regional failures with a recovery time objective measured in minutes. - Active-active cross-region (multi-leader): survives without downtime but accepts conflicts.

Each step has trade-offs. The CEO's "never go down" goal probably means "fewer pages, less customer impact" — and we can get a long way without abandoning our current model.

Four: ask what the actual incident rate is. If we have one significant incident per quarter, the cost of architectural change probably outweighs the benefit. If we have weekly incidents, that's different. Quantify the pain before prescribing the cure.

The framing: every "never goes down" architecture has hidden costs. Often the right answer is to harden the current architecture (better monitoring, better failover, better testing) rather than rip and replace. Get the requirements right before redesigning.

Diplomatic with leadership. Distinguishes the goal ("less customer impact") from the proposed solution ("Cassandra"). Provides the gradient of options. The "ask what the actual incident rate is" instinct grounds the decision in data — the senior way to handle exec proposals.

Cheat sheet

Replication — One Page

Topologies

  • Leader-follower: one writer, many readers. Most common. Postgres, MySQL, MongoDB default.
  • Multi-leader: writes accepted in multiple places. Conflict resolution required.
  • Leaderless: any node accepts; quorum reads. Cassandra, DynamoDB.

Sync vs Async

  • Async: leader acks before followers confirm. Fast, can lose writes on crash.
  • Sync: leader waits for follower ack. Durable, slower.
  • Semi-sync (quorum): N of M followers must confirm. Best of both.

Replication lag → broken read-your-writes

Three fixes: 1. Read from leader for N seconds after user's own write. 2. LSN-based wait for replication to catch up. 3. Sticky sessions (consistent lag per user).

Failover

  1. Detect failure (heartbeat timeout).
  2. Elect new leader (quorum required!).
  3. Reconfigure clients.
  4. Handle un-replicated writes (data loss possible).

Tools: Patroni/pg_auto_failover (Postgres), Orchestrator (MySQL), built-in replica sets (Mongo), Sentinel (Redis).

Split-brain

Two leaders accepting writes during partition. Reconciliation loses data.

Prevent via: - Quorum-based promotion (majority must agree). - Fencing tokens (monotonically-increasing leader epoch). - STONITH (kill old leader before promoting new).

Multi-leader conflicts

  • LWW (last write wins) — lossy, clock-skew prone.
  • App-defined merge.
  • CRDTs (commutative updates).
  • Custom callbacks.

Always pair LWW with: clock skew warning. Use HLC or vector clocks.

Read replicas — limitations

  • Don't help write throughput.
  • Fan-out wall ~5-10 replicas in Postgres.
  • Cascade or move to logical replication for higher fan-out.
  • Stale reads possible — handle via sticky reads or LSN waits.

War story to know

GitHub 2018: 43-second network blip → automated failover → split-brain across regions → 24-hour recovery. Required reading for replication interviews.

The 30-second verbal answer

"Replication has three topologies: leader-follower, multi-leader, leaderless. Most production is leader-follower. Sync vs async is the durability-vs-latency trade. Replication lag breaks read-your-writes — fix with sticky reads to leader. Failover risks split-brain — prevent via quorum and fencing. Multi-leader requires conflict resolution; LWW has clock-skew gotchas."
