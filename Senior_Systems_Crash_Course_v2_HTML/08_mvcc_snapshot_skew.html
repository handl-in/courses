MODULE 08

MVCC, Snapshot Isolation & Skew

The mechanism that makes Postgres readers not block writers — and the operational pain that comes free with it

You COMMIT a write at 10:00:00.001. Another transaction reads at 10:00:00.000 — one millisecond before your commit. Does it see your write?

The answer is "no, because of MVCC." The interesting answer is why MVCC works that way, what it costs, and why understanding it is the difference between debugging Postgres and being mystified by it.

Sam meets the dark art

Sam OK so last module you mentioned MVCC like five times. I nodded. Let me confess: I have no idea what it actually is. I've heard "Postgres uses MVCC" approximately one thousand times. Never read what that means.

Maya You're not alone. Most engineers know MVCC as "magic that makes Postgres fast." It is magic. It also has a bill that comes due — and the bill is called VACUUM.

Sam I've heard about VACUUM too. Something about cleaning up?

Maya Yes — and when VACUUM falls behind, your tables bloat, your queries slow down, and you can't figure out why. Senior Postgres engineers spend a non-trivial amount of their lives tuning VACUUM. Knowing why explains both the magic and the bill.

Sam What's the magic?

Maya Readers never block writers. Writers never block readers. Two transactions can do whatever they want with the same row, and neither has to wait for the other. That's the whole point. The cost: every UPDATE creates a new version of the row, and the old version sits there until cleanup decides nobody needs it anymore.

Sam And this is how snapshot isolation works?

Maya Exactly. MVCC is the mechanism. Snapshot isolation is the guarantee it provides. Same idea, two names depending on whether you're talking implementation or behavior. By the end of this module you'll be able to switch between the two vocabularies fluently — and explain why VACUUM is the operational pain you can't escape.

MVCC = Multi-Version Concurrency Control. Every write creates a new row version with metadata about which transactions can see it. Every read sees a consistent point-in-time snapshot. Readers never block writers. Writers never block readers. (But writers still block writers.)

The price: dead row versions accumulate. VACUUM cleans them up. When VACUUM falls behind, you suffer.

Why MVCC exists

To appreciate what MVCC gives us, we need to remember what came before.

The pre-MVCC world: 2-phase locking (2PL).

Old-school databases handled concurrency with locks. To read a row, you took a shared lock. To write, you took an exclusive lock. They conflicted:

  • Long readers blocked writers.
  • Long writers blocked readers.
  • Reports running for an hour froze the OLTP system.

Everyone was unhappy. Reports got moved to nighttime batch windows. "Don't run queries during business hours" was the engineering culture.

MVCC was the breakthrough. The insight: what if reads and writes didn't need to share data? What if every transaction got its own version of the truth?

The Wikipedia analogy.

Wikipedia keeps every revision of every article. When you read an article right now, you see the current version. But you can ask for "the version as of January 15, 2024" — and the system can show you exactly that, because the old version is preserved.

If two editors are simultaneously editing the same article, they don't block each other. Both see their starting version. Both make changes. The system reconciles them — possibly with a merge conflict, possibly automatically.

That's MVCC. Every write creates a new version. Every read sees the version that existed at its start time. No locking required for reads. No locking required for the read paths of writers.

The cost: storing all those versions. Wikipedia's database is much bigger than the "current articles" would be. Same with MVCC databases.

MVCC turned databases from "lock-and-wait" into "snapshot-and-go" — the breakthrough that made high-concurrency OLTP possible.

How MVCC actually works (Postgres-style)

This is the part most engineers never see. Let's open it up.

Every row in a Postgres table has hidden columns:

Hidden column Meaning
xmin The transaction ID (XID) that created this row version
xmax The XID that deleted/superseded this row version (or NULL if still live)
ctid The physical tuple ID — where on disk this version lives 
                               PHYSICAL ROW VERSIONS

Initial state — Alice's account is created by transaction 42:

┌─────────────────────────────────────────────────────────────────────┐ │ id=1, name='Alice', balance=100 xmin=42 xmax=NULL ctid=(0,1) │ └─────────────────────────────────────────────────────────────────────┘

Transaction 70 updates the balance to 200:

┌─────────────────────────────────────────────────────────────────────┐ │ id=1, name='Alice', balance=100 xmin=42 xmax=70 ctid=(0,1) │ ← OLD ├─────────────────────────────────────────────────────────────────────┤ │ id=1, name='Alice', balance=200 xmin=70 xmax=NULL ctid=(0,2) │ ← NEW └─────────────────────────────────────────────────────────────────────┘

Notice: BOTH versions exist on disk. The old one is marked as "deleted by xmax=70" but it's still physically there. Other transactions running with snapshots from before XID 70 can still see the old version.

Some time later, no transaction needs the old version anymore. VACUUM reclaims the space:

┌─────────────────────────────────────────────────────────────────────┐ │ (empty slot — reclaimable) │ ├─────────────────────────────────────────────────────────────────────┤ │ id=1, name='Alice', balance=200 xmin=70 xmax=NULL ctid=(0,2) │ └─────────────────────────────────────────────────────────────────────┘

The visibility check — what makes MVCC work:

When transaction 88 reads Alice's account, for each version of the row, the engine asks:

Is xmin (creator) committed AND xmin ≤ 88 (or = 88)? If no → version is invisible. Move on.

Is xmax (deleter) NULL OR uncommitted OR xmax > 88? If no → the version was deleted before our snapshot. Invisible. Move on.

If both checks pass → this is the version we should see.

By following this rule consistently, every transaction gets a consistent point-in-time snapshot without any locks on rows. The snapshot is determined by which XIDs are visible to it.

Walking through a concurrent example:

T1 starts at XID=100. Reads Alice's balance: $50.

T2 starts at XID=101. Updates Alice's balance to $200. Commits at XID=101.

T1 reads Alice's balance again. Still sees $50. Why?

When T1 looks at the row, it sees two versions: - Version 1: xmin=42, xmax=101, balance=$50 - Version 2: xmin=101, xmax=NULL, balance=$200

For Version 2: xmin=101 is greater than T1's snapshot horizon (100). T1 ignores it. For Version 1: xmax=101 is greater than T1's snapshot horizon. T1 ignores the deletion. Sees $50.

T1's view of the world is frozen at its start time. Other transactions can do whatever; T1 sees its own consistent reality.

A subtle naming convention: when a senior engineer says "Postgres uses snapshot isolation," they mean MVCC plus a snapshot taken at transaction start. MVCC is the mechanism; snapshot isolation is the guarantee. Same idea, different vocabulary depending on the audience. Use the right vocabulary for the conversation.

Snapshot isolation, formally

Now we can define the isolation level rigorously.

Snapshot Isolation (SI) is an isolation level where: - Each transaction reads from a consistent snapshot taken at its start. - Writes are visible only to that transaction until it commits. - Conflicts: if two concurrent transactions write the same row, the second to commit aborts (first-committer-wins).

Postgres calls SI by the name "Repeatable Read" (it's actually stronger than the SQL standard's RR — see Module 07). Oracle's "Serializable" is also actually SI. The naming is a mess across vendors.

What SI prevents

Anomaly Prevented by SI?
Dirty read ✅ Yes — uncommitted versions are invisible
Non-repeatable read ✅ Yes — your snapshot is frozen
Phantom read ✅ Yes — new INSERTs after snapshot are invisible
Lost update ✅ Yes — first-committer-wins on conflicting writes
Write skew ❌ NO

Snapshot isolation is NOT serializable. It prevents dirty reads, non-repeatable reads, phantom reads, and lost updates. But it allows write skew — a class of bugs that violate invariants spanning multiple rows.

This is why Postgres has a separate Serializable level (SSI — covered later in this module). And why Oracle's "Serializable" can have write skew bugs.

Read skew vs write skew — the distinction

These two anomalies sound similar. They're different. Senior engineers know exactly which is which.

Read skew (prevented by SI)

The bank balance read skew.

T1 wants to display Alice and Bob's combined balance.

T1 reads Alice's balance: $500. Concurrent T2 transfers $400 from Alice to Bob. Commits. T1 reads Bob's balance: $1000 (post-transfer).

T1 reports total: $1500.

But Alice was $500 and Bob was $600 at one moment in time, totaling $1100. After the transfer, Alice is $100 and Bob is $1000, also totaling $1100.

T1 saw a combination that never existed. Money apparently appeared from nowhere.

This is read skew — observing values from different points in time within the same transaction. Snapshot isolation prevents it. T1 would consistently see Alice=$500 and Bob=$600 (its snapshot's view) regardless of T2's commit timing.

Write skew (NOT prevented by SI)

We covered the doctor on-call example in Module 07. Here it is again, with the MVCC perspective.

The doctor on-call write skew, MVCC view.

Hospital invariant: at least one doctor must be on call.

State at start: Alice and Bob both on call (2 doctors, satisfies invariant).

T1 (Alice goes off-call) starts at XID=100. Snapshot includes both Alice and Bob with on_call=true. T2 (Bob goes off-call) starts at XID=101. Snapshot also includes both Alice and Bob with on_call=true.

T1: reads "2 doctors on call, OK to go off." UPDATE Alice. COMMIT. T2: reads from its snapshot — still sees "2 doctors on call." UPDATE Bob. COMMIT.

MVCC's first-committer-wins doesn't catch this because the writes target different rows — T1 writes Alice, T2 writes Bob. No row-level conflict. No abort.

The invariant ("at least 1 on call") is logical, spanning rows. MVCC can't see it.

Why doesn't MVCC catch write skew?

MVCC's conflict detection is row-level. Two transactions are in conflict if they both write the same row. The first commits; the second aborts (or has its writes ignored, depending on implementation).

But write skew involves transactions writing different rows whose changes together violate an invariant. MVCC has no concept of "invariant." It only knows about row versions.

To catch write skew, the database needs to detect a more general pattern: read-write dependencies between transactions. T1 read what T2 was about to write. T2 read what T1 was about to write. Those reads fed the decisions that became the writes. If both commit, the result depends on data that would have changed if either had run alone.

Detecting this is the job of Serializable Snapshot Isolation (SSI) — covered later in this module.

  • Read skew: observing inconsistent combinations of values from different times. Prevented by SI.
  • Write skew: making decisions based on a snapshot, then writing in ways that together violate an invariant. Not prevented by SI. Requires Serializable.

The cost: dead tuples and VACUUM

Here's the bill that comes due.

Every UPDATE creates a new version. The old version isn't deleted immediately — other transactions may still need it. So Postgres accumulates dead tuples — old row versions that no transaction needs anymore.

Without cleanup, the table grows forever. Even if your data stays the same logical size, the physical table balloons.

A background process called VACUUM reclaims dead tuples.

What VACUUM does:

Scans the table looking for dead tuples (versions with xmax < oldest_active_xid).

Marks the slots they occupied as reusable.

Updates table-level statistics about the live row count, free space, etc.

For VACUUM FULL specifically: rewrites the table compactly, freeing space back to the OS. (Locks the table — rare in production.)

Regular VACUUM is non-blocking. It runs alongside normal operations. Postgres has autovacuum that runs automatically based on a per-table threshold (default: 20% of rows changed since last vacuum).

When VACUUM falls behind: bloat

A real-shaped scenario.

A team's users table has 10M rows. Each row is ~500 bytes. The table should be ~5 GB on disk.

Their application updates every user row about 100 times per day (last_seen timestamp, login counts, profile tweaks). That's a billion UPDATEs/day.

Each UPDATE creates a new row version. If autovacuum isn't keeping up, dead tuples pile up. After a week, the table is 50 GB on disk — 10x its actual data size.

Reads now scan 10x more pages. Index lookups follow more pointers. Every query slows down. The buffer pool can't hold the working set anymore. Performance crater.

The team's first instinct: "we need more RAM." Wrong — the data is still 5 GB. They need VACUUM tuning, not bigger hardware.

Bloat is the operational pain of MVCC. Specifically of Postgres MVCC, because Postgres keeps dead tuples in the heap. Other MVCC databases (Oracle, SQL Server) handle the cleanup differently — Oracle uses undo segments, for instance — but everyone with MVCC has some equivalent of the bloat problem.

Tuning autovacuum

The autovacuum settings most senior Postgres engineers tune:

  • autovacuum_vacuum_scale_factor (default 0.2) — vacuum when 20% of rows changed. Lower this for large tables (e.g., 0.05 for tables over 100M rows). 20% of a billion rows is 200M dead tuples — way too many to clean up at once.

  • autovacuum_naptime (default 1 minute) — how often the autovacuum launcher checks for work. Lower for high-churn workloads.

  • autovacuum_max_workers (default 3) — how many tables can be vacuumed in parallel. Raise if you have many large tables.

  • autovacuum_vacuum_cost_limit (default 200) — controls how aggressive vacuum is. Higher = vacuums faster but with more I/O contention.

A senior reflex: the default autovacuum settings are fine for small databases and terrible for large ones. Tune them per-table for hot tables. ALTER TABLE big_table SET (autovacuum_vacuum_scale_factor = 0.02);

VACUUM FULL — the nuclear option

VACUUM FULL rewrites the table compactly, releasing space back to the OS. Sounds great. But:

  • It takes an exclusive lock on the table. No reads, no writes during the operation.
  • For large tables, can take hours.
  • In production, it's almost always the wrong answer.

Modern alternatives: - pg_repack extension: rewrites the table without long locks. Online operation. The standard tool for production bloat removal. - Partitioning + drop old partitions: if your data is naturally time-partitioned, this avoids needing to repack.

Mention pg_repack in an interview about Postgres operations and you sound like someone who's actually managed bloat in production.

Long-running transactions: the silent killer

A senior pain point.

A nightly reporting job runs at 2 AM. It does BEGIN ISOLATION LEVEL REPEATABLE READ, scans many tables, and runs for two hours.

During those two hours, its snapshot is locked open. Postgres cannot remove any row versions that might be visible to that transaction — because if it did, the transaction's reads would see inconsistent state.

So for two hours, dead tuples accumulate without being reclaimable. Tables bloat. Other transactions' UPDATEs add new dead versions, and none can be cleaned up.

When the report finishes at 4 AM, autovacuum can finally clean up the backlog. But by then, the bloat damage is done — tables are oversized, indexes need maintenance, queries that were fast at midnight are slow at 5 AM.

Long-running transactions are MVCC's worst enemy. Every Postgres operations team eventually learns this:

  • Avoid BEGIN ... long work ... COMMIT patterns where the long work is reading/computing, not transacting.
  • For analytical queries, consider running them with a small statement_timeout to bound damage.
  • Monitor the oldest open transaction (pg_stat_activity.xact_start) — if it's been open more than a few minutes on a write-heavy database, you have a problem.

The senior detection trick: monitor txid_current() - txid_snapshot_xmin(txid_current_snapshot()). If that gap grows unbounded, you have an old transaction holding back vacuum.

Same idea, three more ways

Way 1: the office whiteboard.

A whiteboard tracks the day's projects. Instead of erasing each project's status when it changes, the office uses sticky notes — when status updates, a new sticky goes on top of the old one.

Anyone walking in mid-day sees the most recent sticky for each project. But anyone who took a photo of the board at 9:00 AM still has a record of that state — they can answer questions as of 9:00 AM, even if the board has changed since.

Once nobody needs the 9:00 photo anymore, the office takes down the old stickies underneath. That's vacuum.

If too many photos are still active, the board fills up with stickies. Same with MVCC bloat.

Way 2: the time-traveler's library.

Imagine a library where books are versioned. When an author releases a new edition, the old edition isn't thrown out — both sit on the shelf, with version numbers.

Researchers can ask for "the 1995 edition" and get exactly that, even though the 2024 edition is also available. The library never destroys editions while researchers might need them.

Periodically, the librarian checks: are any researchers still consulting the 1995 editions? If no, they go to the basement archive. That's vacuum.

If a researcher has been consulting the 1995 edition for a year straight, the library can't archive it. Everyone else's "old editions" pile up too. The shelves get crowded. Bloat.

Way 3: the email thread.

A long email thread accumulates replies. The full history is preserved. When you open the thread, you see the latest message at the top, but you can scroll back to see any prior message.

If five people are reading the thread simultaneously, one might be at the latest message; another might be reading replies from yesterday. They don't conflict — each sees what they're looking at, frozen as of when they opened.

The thread can grow until it's pruned (auto-archive after a year, manual cleanup, etc.). Without pruning, the inbox fills.

Postgres SSI — the Serializable upgrade

We finished Module 07 with: "Serializable prevents write skew." Time to see how Postgres makes that work.

Serializable Snapshot Isolation (SSI) is Postgres's implementation. Built on top of MVCC. The trick: track which transactions read what other transactions are writing.

How SSI catches write skew:

T1 reads rows X and Y at its snapshot. Decides to write Z.

T2 reads rows Y and X at its snapshot. Decides to write W.

SSI tracks: T1 read what T2 might write (Y). T2 read what T1 might write (X). This is an rw-antidependency in both directions — a cycle.

At commit time, SSI checks for cycles. If detected → abort one of the transactions with a serialization failure.

Application catches the error, retries.

SSI is optimistic — it doesn't take locks on reads. It just records which reads happened. Other isolation implementations (strict 2PL) take read locks proactively and slow everyone down.

The trade-off: SSI has lower steady-state cost but requires retry logic in the application. Under low contention, SSI is fast. Under high contention, retries dominate.

Mention "Postgres SSI" or "rw-antidependency tracking" in an interview about Serializable, and you sound like someone who's read the actual Postgres documentation.

SSI's hidden cost: predicate tracking.

To detect rw-antidependencies, SSI has to track every read's predicate (what range of rows it touched), not just specific rows. This means SSI can have higher memory overhead than RR, and very wide range scans can have more conflicts than narrow ones.

In practice, this is rarely the dominant cost — but it's worth knowing about for high-throughput workloads.

How databases stack up on MVCC

System Snapshot mechanism Cleanup Notes
Postgres xmin/xmax in heap tuples Autovacuum / pg_repack Bloat is the operational pain
MySQL InnoDB Undo log Purge thread Less bloat-prone but undo log can fill
Oracle Undo segments + read-consistent blocks Automatic Undo retention controllable
SQL Server Version store in tempdb (RCSI mode) Automatic Tempdb growth is the watch-out
CockroachDB MVCC in RocksDB Compaction-driven Distributed MVCC
Spanner TrueTime-based versioning Automatic Globally consistent timestamps

Postgres puts versions in the heap — old and new tuples coexist in the same table file. This is unique among major databases. Other engines (MySQL InnoDB, Oracle) put old versions in a separate undo log/segment area, keeping the main table compact.

Postgres's choice has trade-offs: - Pro: simpler architecture; no separate undo machinery. - Pro: row updates are local — no separate undo write. - Con: bloat lives in the table; must be vacuumed. - Con: index entries point to old tuple locations until vacuumed.

This is why "Postgres bloat" is a thing while "MySQL bloat" usually means something else (the undo log or temp tables).

Sharpen your pencil

Exercise 1. A team reports their Postgres database is 8x larger on disk than the actual data should be. Tables are heavily updated throughout the day. Diagnose, then propose three fixes ordered by complexity.

Diagnosis: bloat. Frequent updates create dead tuples. If autovacuum isn't keeping up, the heap accumulates obsolete row versions. Verify with pg_stat_user_tables (look at n_dead_tup vs n_live_tup) or the pgstattuple extension.

Three fixes ordered:

Fix 1 (lightest): tune autovacuum per-table. For high-churn tables, lower autovacuum_vacuum_scale_factor from default 0.2 to something like 0.05. The default is too lenient for big, hot tables.

ALTER TABLE hot_table SET (autovacuum_vacuum_scale_factor = 0.05);

Increase autovacuum cost limits if I/O budget allows. Add more autovacuum workers for parallelism if you have many tables.

Fix 2 (medium): pg_repack to reclaim existing bloat. Tuning prevents future bloat. Existing bloat needs reclaim. pg_repack rewrites tables online without long locks. Schedule during a quieter window.

Fix 3 (architectural): identify long-running transactions. Check pg_stat_activity for old xact_start times. If reports or batch jobs hold long snapshots, they're preventing vacuum from cleaning anything during their run. Either bound their runtime, run them on read replicas, or use shorter transactions.

The senior reflex: bloat is a symptom of either too-loose vacuum settings or long transactions blocking it. Fix the cause before reaching for VACUUM FULL.

Exercise 2. You're running at default Postgres isolation (Read Committed). A coworker says: "I switched our entire app to Repeatable Read for safety." What concerns would you raise?

Three concerns:

Concern 1: VACUUM impact. Repeatable Read holds snapshots open for the duration of each transaction. In Postgres specifically, this prevents vacuum from cleaning up dead tuples that those snapshots might still reference. If your app has any longer-running transactions (analytical queries, complex business logic), bloat will accumulate faster. Need to monitor and tune.

Concern 2: Doesn't actually fix all bugs. RR prevents dirty reads, non-repeatable reads, and phantoms (in Postgres). It does NOT prevent write skew. If the app has invariants that span multiple rows (limits, counts, "at least one X"), RR is insufficient. The team might think they're "safer" but still have invariant-violation bugs.

Concern 3: Conflict semantics change. Under RR, conflicting writes can produce serialization errors that the app must handle. If the app wasn't built with retry logic, these errors will surface as user-facing failures. Switching isolation levels without adding retry handling causes incidents.

The right framing: choose isolation per-transaction based on what specific anomalies need preventing. Don't make global isolation changes for vague "safety" reasons.

Exercise 3. Explain to non-technical Sam, in two sentences, why MVCC is fast but eventually requires "vacuum."

MVCC keeps every old version of changed data so that concurrent readers never have to wait for writers — they just read the version that was current when their query started. The catch is those old versions don't disappear automatically; eventually you need a cleanup process (called "vacuum") to free up the space, and if cleanup falls behind, your tables grow much larger than the data warrants and queries slow down.

There are no dumb questions

Q: Does MVCC mean "no locks at all"?

A: No. MVCC eliminates read-write locks. Reads don't block writes; writes don't block reads. Write-write locks still exist — two transactions trying to update the same row will serialize. MVCC is not a magic pony. Senior engineers say "MVCC eliminates reader-writer contention" to be precise.

Q: Can MVCC databases handle deletes?

A: Yes. A delete is implemented by setting xmax on the existing row version (no new version created). Once no transaction can see the deleted row anymore, vacuum reclaims it.

Q: What happens to indexes during MVCC updates?

A: Until Postgres 8.3, every UPDATE created new index entries for every index on the table — even if the indexed column didn't change. HOT (Heap-Only Tuple) updates improved this: if no indexed column changed, the new tuple version chains off the old one within the same page, and index entries still point correctly. Massive performance improvement for update-heavy tables. Senior detail to mention.

Q: Why does Postgres have separate VACUUM and ANALYZE?

A: They do different things. VACUUM reclaims space from dead tuples. ANALYZE updates statistics for the planner (Module 06). Autovacuum runs both, on different schedules. You can run them separately for surgical needs: VACUUM ANALYZE table_name; does both.

Q: What's "transaction wraparound" and why does it sound scary?

A: Postgres transaction IDs are 32-bit. After ~2 billion transactions, they wrap around to zero. Without intervention, this would make old data appear newer than it is, breaking visibility checks. Postgres avoids this with freezing during vacuum — marking very old tuples with a special "always visible" flag. If autovacuum can't keep up with the wraparound rate, Postgres will eventually shut down the database to prevent corruption. Real production incidents have happened from this. Senior operators monitor age(datfrozenxid).

Q: How do I see the actual MVCC versions in Postgres?

A: The pg_visibility extension exposes per-page visibility info. The xmin/xmax columns are accessible as xmin, xmax system columns: SELECT xmin, xmax, * FROM users WHERE id = 1;. For seeing physical versions, use pageinspect extension. Mostly used for debugging weird MVCC issues.

Q: How does MySQL InnoDB do MVCC differently?

A: InnoDB stores the current row in the table and pushes old versions to an undo log (a separate area). To read an older version, the engine walks the undo chain. Pros: the table stays compact (no bloat in the heap). Cons: long-running transactions can fill the undo log; reads on old data are slower because they walk the chain. Different design, similar end result.

Q: Does MVCC work for distributed databases?

A: Yes — but the snapshot mechanism gets harder. Spanner uses TrueTime (atomic clock-backed timestamps) to give every transaction a globally meaningful snapshot point. CockroachDB uses HLC (Hybrid Logical Clocks). FoundationDB uses a centralized commit timestamp service. The principle is the same as single-node MVCC; the implementation handles clock skew across nodes.

Three myths to dynamite

"MVCC means no locks at all."

False. MVCC eliminates reader-writer locks. Writers still block writers — two transactions writing the same row serialize. MVCC removes the most common contention pattern (long readers blocking writers), not all contention.

"VACUUM is just a maintenance chore — set it and forget it."

False. The default autovacuum settings are tuned for small databases. On large hot tables, defaults are too lenient and bloat accumulates. Tune autovacuum per-table for hot tables. Monitor bloat. Watch for long transactions blocking cleanup.

"Snapshot Isolation is the same as Serializable."

False. SI prevents most anomalies but allows write skew. Serializable prevents all anomalies. The naming confusion: Postgres calls SI "Repeatable Read" and has a separate "Serializable" (SSI). Oracle calls SI "Serializable" — confusingly, this is not true serializable. Always verify what the database actually does, not what it's labeled.

Interview gotchas

Saying "MVCC eliminates locks." Eliminates reader-writer locks. Not all locks. Senior engineers are precise about which contention MVCC removes.

Forgetting VACUUM. MVCC's cost is dead tuples. If you describe MVCC without mentioning the cleanup step, you're missing 30% of the operational reality. Always mention VACUUM, autovacuum, or bloat in MVCC discussions.

Conflating "Repeatable Read" with "Snapshot Isolation." They're related but distinct in academic terms. Postgres's RR is SI in implementation. MySQL's RR uses gap locks. Oracle calls SI "Serializable." Naming is a vendor mess; mention this awareness.

Not knowing about transaction wraparound. Postgres-specific, but real. 32-bit XIDs wrap around after ~2 billion transactions. If autovacuum can't keep up, the database shuts down. Operators monitor for this. Mentioning wraparound in an interview signals deep Postgres operational experience.

Recommending VACUUM FULL casually. It locks the table. Almost always the wrong answer in production. The senior answer is pg_repack or proper autovacuum tuning.

Mock interview

A team is migrating from MySQL to Postgres. They report that "transactions behave differently" — specifically a previously-correct stored procedure now hits race conditions. What do you tell them?

Several likely culprits, drawing on MVCC differences:

One — default isolation differs. MySQL InnoDB defaults to Repeatable Read. Postgres defaults to Read Committed. The procedure may have been relying on RR's stable snapshot — under Postgres RC, repeated reads can see different values mid-transaction. The fix: BEGIN ISOLATION LEVEL REPEATABLE READ or set the session default.

Two — undo vs heap-stored versions. MySQL stores old row versions in an undo log; Postgres stores them in the heap. This means MySQL's "consistent read" walks the undo chain to reconstruct old versions; Postgres reads directly. Subtle differences in performance and memory profiles, especially for long-running reads on heavily-updated rows.

Three — gap locks vs predicate locks. MySQL InnoDB at RR uses gap locks to prevent phantoms — locks ranges, not just rows. Postgres at RR uses MVCC snapshots — no locks needed for phantom prevention. If the procedure relied on MySQL's gap-locking semantics ("range locked, others can't insert into it"), Postgres won't behave the same way. The fix: explicit SELECT FOR UPDATE over the relevant range, or upgrade to Serializable for SSI conflict detection.

Four — autocommit and isolation defaults at the connection pool. Some connection pools set non-standard isolation per connection. Verify SHOW transaction_isolation matches what the app expects.

The senior reflex: don't assume "ACID is ACID." The semantics of concurrent transactions are vendor-specific even when the syntax matches. Test the procedure under realistic concurrent load on both systems before declaring the migration done.

Names specific MVCC differences (undo vs heap, gap locks vs predicate locks). Connects each difference to a likely failure mode. The closing principle is the senior framing.

Two weeks after migration, your team says Postgres is "slower over time" — queries that were fast at launch are now sluggish. They blame Postgres. What's likely happening?

This sounds like classic bloat from MVCC. Let me work through the diagnosis:

Step one: confirm bloat. Check pg_stat_user_tables.n_dead_tup vs n_live_tup on the slow tables. If dead tuples are 50-90% of live tuples, you have heavy bloat. Use pgstattuple extension for more accurate measurement.

Step two: identify the cause. Why isn't autovacuum keeping up? A few common reasons:

  • Long-running transactions blocking vacuum. Check pg_stat_activity for old xact_start times. Reports, batch jobs, or even forgotten developer sessions can pin vacuum back. Even a single transaction open for hours prevents cleanup of any tuple that became dead during that transaction's lifetime.

  • Default autovacuum is too lenient. The default autovacuum_vacuum_scale_factor = 0.2 means "wait until 20% of rows are dead." On a 100M-row table that's 20M dead tuples accumulated before vacuum even starts. By the time it runs, the workload has produced more, and vacuum is permanently behind.

  • Insufficient autovacuum workers. Default 3. If you have many large tables churning concurrently, vacuum can't reach them all in time.

Step three: fix.

  • Tune autovacuum per hot table: ALTER TABLE hot_users SET (autovacuum_vacuum_scale_factor = 0.05);
  • Investigate and bound long-running transactions. Set statement_timeout for analytical queries. Move reports to read replicas.
  • Use pg_repack to reclaim existing bloat without locking the table.
  • Monitor going forward: dashboard n_dead_tup, oldest transaction age, autovacuum activity.

Step four: education.

The team blames "Postgres" but the issue is operational tuning. MySQL doesn't have this exact failure mode because of its undo log architecture, but it has its own (undo log can fill, temp tables under pressure). Every MVCC database has an operational tax. Postgres's tax is named VACUUM.

Specific tools and queries. Connects symptom to mechanism (MVCC → dead tuples → vacuum). Closes with the right framing — every MVCC database has a tax, just different ones. Educates the team without being condescending.

Walk me through how Postgres's Serializable isolation level actually works under the hood. I want to know why it can catch write skew when Repeatable Read can't.

Postgres's Serializable is SSI — Serializable Snapshot Isolation. It's an extension of MVCC, not a replacement.

The mechanism, step by step:

One — every transaction still gets a snapshot at start. Same as RR. Reads see a consistent point-in-time view. This part is unchanged.

Two — SSI tracks rw-antidependencies. When a transaction reads a row, SSI records that it read what might be modified by other transactions. When it writes, SSI records what it wrote. The engine builds a graph of reads-that-might-conflict-with-writes across active transactions.

Three — at commit time, SSI checks for dangerous patterns. Specifically: cycles in the dependency graph that would mean the result can't be equivalent to any serial order. The classic dangerous pattern is two transactions that read what each other wrote — write skew is exactly this shape.

Four — if a dangerous pattern is detected, one transaction aborts. Returns a serialization failure (SQLSTATE 40001). The application must retry.

The contrast with Repeatable Read:

RR doesn't track read-write dependencies. It only checks for write-write conflicts on the same row. The doctor on-call write skew has no row-level conflict — T1 writes Alice, T2 writes Bob — so RR sees no problem and lets both commit. SSI's dependency tracking catches it because both transactions read what the other was about to invalidate.

The cost: SSI maintains the dependency graph in memory. Predicate-style reads (range scans) generate predicate-level dependencies. Under high concurrency and complex queries, the bookkeeping can be non-trivial. For most workloads, the overhead is small — but it's not zero.

What it gives you: if your transactions are correct in isolation, SSI guarantees they're correct concurrently. You don't have to think about every concurrent interaction. The trade-off is retry overhead, which the application must handle.

This is why Postgres added SSI in version 9.1 — it's the only way to get true Serializable on a snapshot-isolation foundation without going to strict 2PL.

Names the academic concept (SSI), explains the mechanism crisply, contrasts with RR explicitly, and acknowledges the cost. The "if your transactions are correct in isolation, they're correct concurrently" framing is the value prop of Serializable, stated cleanly.

Last one. We're seeing transient 40001 errors in our application logs since enabling Serializable. The team wants to switch back. How do you handle this?

Slow down. Transient 40001s are expected behavior at Serializable — they're the engine telling you it caught a write skew or other dependency cycle. The fix is to handle them properly, not to retreat.

The conversation I'd have with the team:

Acknowledge the pain. Errors in logs are noisy and stressful. The instinct to "make them go away" is real. But making them go away by lowering isolation means the bug the error was preventing now silently corrupts data. That's worse, just less visible.

Diagnose the rate. What's the actual error rate? 1-in-10,000 transactions hitting 40001 is fine. 1-in-10 is excessive contention that needs investigating. The number tells you whether the error rate is "normal SSI working as designed" or "a real contention problem."

Implement retry logic if it's not already there. The pattern: - Catch SQLSTATE 40001 in the data layer. - Retry the transaction with exponential backoff. - Cap retries (5 attempts, then surface to user). - The transaction body must be safe to retry (idempotent at the business-logic level).

Investigate persistent conflict patterns. If the same query keeps hitting 40001, examine why. Common causes: - Hot row contention (counter, last-modified row). Apply counter sharding. - Long-running transactions with broad reads. Split into shorter transactions. - Queries that read way more than they need (turning narrow queries into broad ones increases conflict surface).

Rollback as last resort. If after investigation the contention truly is unmanageable and the cost of write skew bugs is acceptable, you can selectively use RR for the worst cases. But "we got serialization errors" is not by itself a reason to abandon Serializable — it's a reason to engineer the application properly.

The framing: Serializable shifted the cost from "wrong results" to "retries." Retries are visible, debuggable, fixable. Wrong results are invisible until they cause a customer incident. The visible cost is preferable.

Empathetic but firm. Distinguishes "expected behavior" from "real problem." Provides the diagnostic framework. Closes with the strongest possible framing for why Serializable is worth the operational cost.

Cheat sheet

MVCC, Snapshot Isolation & Skew — One Page

MVCC

Multi-Version Concurrency Control. Every row carries hidden xmin (creator XID) and xmax (deleter XID). Readers see versions visible to their snapshot. Readers don't block writers; writers don't block readers. Writers still block writers on same row.

Snapshot Isolation (SI)

Each transaction reads from a snapshot taken at start. Conflicting writes: first-committer-wins. Postgres "Repeatable Read" = SI. Oracle "Serializable" = SI. MySQL InnoDB RR ≈ SI plus gap locks.

Prevents: dirty read, non-repeatable read, phantom (in PG/MySQL), lost update. Does NOT prevent: write skew.

Read skew vs Write skew

  • Read skew: see inconsistent values across time (Alice old, Bob new). Prevented by SI.
  • Write skew: each txn reads & decides correctly per-snapshot, both write disjoint rows, together violate invariant. NOT prevented by SI. Requires Serializable.

Postgres SSI (Serializable)

Built on MVCC. Tracks rw-antidependencies between transactions. At commit, detects cycles → aborts one txn (SQLSTATE 40001). App must retry. Optimistic — no read locks.

VACUUM (the bill)

Old row versions accumulate as dead tuples. Autovacuum reclaims them when no transaction can see them anymore. Bloat = dead tuples accumulating faster than vacuum cleans up.

Causes of bloat: - Default autovacuum settings too lenient for big hot tables. - Long-running transactions holding snapshots open (block vacuum). - Insufficient autovacuum workers.

Fixes: - Tune autovacuum_vacuum_scale_factor per-table. - Bound long transactions (statement_timeout, run on replicas). - pg_repack to reclaim existing bloat without locking. - Avoid VACUUM FULL in production.

Transaction wraparound (Postgres-specific)

32-bit XIDs wrap after ~2B transactions. Vacuum freezes old tuples to mark them "always visible." Failure to keep up causes database shutdown. Monitor age(datfrozenxid).

MVCC across databases

  • Postgres: versions in heap (bloat in tables).
  • MySQL InnoDB: undo log (compact tables, undo log can fill).
  • Oracle: undo segments.
  • SQL Server: tempdb version store (RCSI mode).
  • CockroachDB: distributed MVCC over RocksDB.

The 30-second verbal answer

"MVCC means every write creates a new version with metadata about which transactions can see it. Readers never block writers. Snapshot isolation is the guarantee MVCC provides — each transaction sees a consistent point-in-time view. SI prevents most anomalies but allows write skew, which Postgres SSI catches via rw-antidependency tracking. The cost: dead row versions accumulate, requiring VACUUM. Bloat from poor vacuum tuning is the most common Postgres operational pain."
