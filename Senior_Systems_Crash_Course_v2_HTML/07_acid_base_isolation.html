MODULE 07

ACID, BASE & Isolation Levels

The most overused phrase in database marketing — finally explained correctly

"Are you ACID compliant?" is the most overused phrase in database marketing. Almost nobody asking it knows what the four letters mean precisely. The answer "yes" is rarely the whole story.

By the end of this module, you'll be the rare engineer who knows what ACID actually guarantees, what it doesn't, and why "Serializable" means three different things in three different databases.

Sam confesses again

Sam OK, transactions. I get the basics — BEGIN, do stuff, COMMIT. Either everything happens or nothing. ACID. Atomic, Consistent, Isolated, Durable. Easy.

Maya Quick test. Two users both run a transaction at the same moment. Both read the inventory. Both decrement it. Both commit. Now you've sold 1001 units of a 1000-unit product. Why?

Sam Uh... a race condition? But ACID was supposed to prevent that?

Maya ACID's "I" — Isolation — is supposed to. But Postgres's default isolation level doesn't actually prevent this scenario. MySQL's default is different. Oracle calls something else "Serializable" that isn't quite the standard's serializable. The "I" in ACID is a slider, not a switch. And every database has the slider in a different place.

Sam Wait, ACID isn't... ACID? It varies?

Maya ACID is a vocabulary. Isolation is a spectrum with four levels in the SQL standard. Each database picks defaults and implements them slightly differently. Most engineers say "we're ACID compliant" without knowing which point on the spectrum their database actually runs at by default.

Sam And BASE?

Maya The philosophical opposite. Trade strong guarantees for availability and scale. Cassandra, DynamoDB, eventually-consistent stores. Also a spectrum. Also varies by configuration.

By the end of this module, you'll be able to answer: "what isolation level does your default Postgres use, and what bug class does it allow?" If you can't answer that crisply right now, you're not yet senior on transactions. We're going to fix that.

ACID is a guarantee about transaction behavior. The four letters are: Atomicity (all-or-nothing), Consistency (constraints hold), Isolation (concurrent transactions don't interfere), Durability (commits survive crashes). Isolation is the dial that controls how strict the I is. BASE is the philosophical opposite — relax guarantees to gain availability.

ACID, decoded

Let's go letter by letter and be precise.

Letter Meaning Concrete guarantee
Atomicity All or nothing Either every write in the txn happens, or none do
Consistency Valid state → valid state Constraints, invariants are preserved
Isolation Concurrent txns don't see each other's mess Levels: Read Uncommitted, Read Committed, Repeatable Read, Serializable
Durability Once committed, it stays committed Survives crashes (via WAL — Module 02)

The "C" is the weakest letter. It's not really a database property — it's an application property. The database lets you define constraints (UNIQUE, FOREIGN KEY, CHECK), but most application invariants are enforced in code. People often skip past C in interviews; you should too. The interesting letters are A, I, and D.

Atomicity in 90 seconds

The classic atomic operation:

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;  -- A pays
UPDATE accounts SET balance = balance + 100 WHERE id = 2;  -- B receives
COMMIT;

Atomicity guarantees: if the second UPDATE fails — or the server crashes between them — the first UPDATE is rolled back. You never see "money left A but didn't arrive at B."

This is implemented via the WAL (Module 02). Every change is logged before applied. On rollback or crash, the database refuses to apply un-committed log records. The data file may even briefly contain partial state during a crash, but recovery undoes anything pre-commit.

Atomicity is the "marriage ceremony" guarantee.

When two people get married, the legal status flips at one specific moment — the "I do" plus signature. Before that moment: not married. After: married. There's no intermediate state of "kind of married" that lasts.

Atomicity in databases is the same. The transaction either happened or it didn't. There's no committed state where the bank robbed Peter without paying Paul. The database might briefly know about un-committed work, but it's never visible in a half-done state.

Q: Does atomicity work across multiple tables?

A: Yes — within a single database. A transaction touching tables A, B, and C atomically commits or atomically rolls back, regardless of how many tables are involved. Across multiple databases or services, atomicity gets much harder — that's the realm of 2PC and sagas (Module 13).

Q: What if I have a constraint violation mid-transaction?

A: Most databases mark the transaction as failed at the violation. Subsequent statements in the same transaction either error out or are silently ignored, depending on the database. The COMMIT becomes effectively a ROLLBACK. Postgres halts the transaction at the first error. Oracle lets you SAVEPOINT to recover. Behavior varies.

Durability in 60 seconds

We covered this in Module 02. Quick recap:

After COMMIT acks, the change survives: - Process crash - OS crash - Power failure - Disk failure (if you have proper replication)

Durability requires fsync to disk before the COMMIT ack returns. Trade durability for throughput by relaxing fsync — many shops do for non-critical writes. Postgres's synchronous_commit = on is the durability switch; off means trade safety for ~5x throughput.

Durability is the most boring of the four, ironically. Once you've covered WAL fsync semantics in Module 02, durability is "the database does what we already designed." The interesting letters are A and I.

Isolation: the rabbit hole

This is where it gets interesting. Isolation is the most interview-relevant part of ACID because it has multiple levels, the levels map to real bugs, and every database does it slightly differently.

The SQL standard defines 4 isolation levels. Each prevents specific concurrency anomalies. Senior engineers know which anomalies survive each level — and which database implements which anomaly differently.

The four anomalies

Before we can talk about isolation levels, we need to know what they protect against. Here are the four canonical anomalies. Memorize them.

Setup for all four examples:

Two transactions running concurrently: T1 and T2. Each touches a row, runs some logic, commits or rolls back. The interleaving of their operations creates the anomaly.

Anomaly 1: Dirty Read

T2 reads a value that T1 has written but not yet committed.

Time: T1 T2 ───── ──────────────────── ───────────────── 1 BEGIN 2 UPDATE balance = 1000 BEGIN 3 SELECT balance → reads 1000 ← UNCOMMITTED VALUE 4 ROLLBACK (T2 is now operating on a value that NEVER officially existed)

Dirty reads are catastrophic. They let one transaction see another's experimental state. The classic example: a transaction tentatively sets a balance, the user sees that balance and acts on it, then the original transaction rolls back. Now the user has acted on data that doesn't exist. All sane isolation levels prevent dirty reads.

Anomaly 2: Non-Repeatable Read

T2 reads the same row twice and gets different values, because T1 committed in between.

Time: T1 T2 ───── ──────────────────── ───────────────── 1 BEGIN 2 SELECT balance → reads 100 3 BEGIN 4 UPDATE balance = 200 5 COMMIT 6 SELECT balance → reads 200 (DIFFERENT VALUE within same txn!)

Why this matters: a transaction that reads the same data twice expects consistent values. If T2 was computing some derived value based on the balance, the first computation and the second use different inputs. Logic that assumes "the value didn't change" produces wrong results.

Anomaly 3: Phantom Read

T2 runs the same range query twice and gets a different set of rows because T1 inserted/deleted in between.

Time: T1 T2 ───── ──────────────────── ───────────────── 1 BEGIN 2 SELECT * FROM accounts WHERE balance > 100 → returns 5 rows 3 BEGIN 4 INSERT new account with balance=500 5 COMMIT 6 SELECT * FROM accounts WHERE balance > 100 → returns 6 rows ← PHANTOM ROW (the new INSERT appeared!)

Phantoms are subtle. They're not about a row's value changing — that's non-repeatable read. They're about which rows match a query changing. A new INSERT or DELETE between two reads produces different result sets for the same query.

The reason this matters: business logic often does "find all rows matching X, do something with each." If the set of matching rows changes mid-transaction, you might miss new ones or process now-deleted ones.

Anomaly 4: Write Skew (Serialization Anomaly)

The hardest one. Two transactions read overlapping data, each makes a decision based on what it read, and each writes — but their combined effect violates an invariant.

The doctor on-call example.

Hospital invariant: at least one doctor must always be on call.

Current state: two doctors — Alice and Bob — both on call.

Two transactions, run concurrently:

T1 (Alice goes off-call):
  SELECT COUNT(*) FROM doctors WHERE on_call = true;
  → reads 2.  "OK, 2 ≥ 1, I can go off."
  UPDATE doctors SET on_call = false WHERE name = 'Alice';
  COMMIT;

T2 (Bob goes off-call) — concurrent with T1:
  SELECT COUNT(*) FROM doctors WHERE on_call = true;
  → reads 2.  "OK, 2 ≥ 1, I can go off."
  UPDATE doctors SET on_call = false WHERE name = 'Bob';
  COMMIT;

Both transactions read the same snapshot (2 on call). Both commit successfully — they didn't even touch the same row, so no row-level conflict. Result: zero doctors on call. Invariant violated.

Write skew is the anomaly that survives even snapshot isolation. The transactions operate on disjoint rows, so there's no row conflict. But the decision each one made was based on a snapshot that the other transaction was about to invalidate. Only Serializable isolation catches this.

The four isolation levels

Now the levels. Each one prevents some anomalies and allows others.

Level Dirty read? Non-repeatable read? Phantom read? Write skew?
Read Uncommitted ❌ allowed ❌ allowed ❌ allowed ❌ allowed
Read Committed ✅ prevented ❌ allowed ❌ allowed ❌ allowed
Repeatable Read ✅ ✅ prevented ❌ allowed (per standard) ❌ allowed
Serializable ✅ ✅ ✅ prevented ✅ prevented

The Postgres trap. Postgres's "Repeatable Read" actually prevents phantoms (it implements snapshot isolation, which is stronger than the standard's RR). MySQL's "Repeatable Read" prevents some phantoms via gap locks but is weaker than Serializable. The SQL standard table is just a starting point — every database has its own version.

Why do databases offer weaker levels at all? Performance. Stronger isolation requires more locking, more conflict detection, more retries. For most read traffic, weak isolation is "good enough" — and dramatically faster. Real systems run mostly at Read Committed or Repeatable Read, escalating to Serializable only for specific critical operations.

Read Uncommitted

Almost never used in practice. Allows dirty reads. The only place you'd see it: data warehousing where you're computing rough estimates from a snapshot and tolerate some uncertainty. Even there, it's rare.

Most major databases don't even implement it as a real level — Postgres treats READ UNCOMMITTED as Read Committed (silently upgrades). Oracle doesn't offer it. MySQL InnoDB does, with caveats.

You will likely never need this level. Knowing it's the weakest is enough.

Read Committed

The default in Postgres, Oracle, and SQL Server. Prevents dirty reads — every SELECT sees only committed data. But within a single transaction, two SELECTs of the same row can see different values if another transaction commits in between.

This is fine for most queries. But it surprises engineers who assume "transactions give me a consistent view of the database." They don't, at this level.

The Read Committed surprise. New Postgres developers often discover this the hard way:

BEGIN;
SELECT balance FROM accounts WHERE id = 1;  -- reads 100
-- ... some time passes; another txn updates balance to 200, commits ...
SELECT balance FROM accounts WHERE id = 1;  -- reads 200!
COMMIT;

In a single transaction, two reads can see different values. This violates many engineers' mental model of "transactions = consistent snapshots." If your code assumes the second read returns the same value as the first, you have a latent bug.

The fix: upgrade to Repeatable Read for those transactions. Or use SELECT ... FOR UPDATE to lock the row.

Repeatable Read (Snapshot Isolation in disguise)

MySQL InnoDB's default. Postgres also offers it.

Within a transaction, every read sees a consistent snapshot taken at transaction start. Repeated reads of the same row return the same value, regardless of other transactions' commits.

In Postgres, RR also prevents phantom reads (via MVCC snapshots — Module 08). In MySQL, RR prevents phantoms via gap locks. Both are stronger than the SQL standard's RR.

This is enough for most application logic. The transaction sees a consistent point-in-time view of the database. It's only insufficient when business invariants span multiple rows in ways the database can't see.

Postgres's "Repeatable Read" is actually Snapshot Isolation. They're often used interchangeably, but they're technically distinct concepts in the academic literature. For practical purposes in Postgres, RR = SI. Mention this distinction in an interview and you signal real depth.

Serializable

The strongest level. Postgres calls it Serializable; Oracle calls something else "Serializable" (it's actually SI; see below).

Serializable isolation guarantees that the result of running concurrent transactions is equivalent to some serial order — as if the transactions had run one after another, in some unspecified sequence. No anomalies of any kind.

This catches write skew. If two transactions would together violate an invariant, one of them gets aborted with a serialization failure. The application must retry.

Real implementation: Postgres uses SSI (Serializable Snapshot Isolation) — it runs transactions at SI but tracks "dangerous patterns" (rw-antidependencies) that could lead to write skew. At commit time, it aborts cycles.

Other engines use strict 2-phase locking (S2PL) — locks acquired throughout the transaction and only released at commit. Slower, simpler.

"Serializable" doesn't mean "transactions run one at a time." It means the result is equivalent to some serial order. Engines implement this in different ways:

  • Postgres SSI — optimistic; runs at SI, detects conflicts, aborts on bad cycles.
  • Strict 2PL — pessimistic; takes locks; serial order emerges from lock acquisition.
  • OCC (Optimistic Concurrency Control) — read freely, validate at commit, abort on conflict.
  • Calvin-style deterministic execution — pre-orders all transactions; runs them in agreed order. Used by FoundationDB.

Mention SSI as Postgres's mechanism in an interview, and you sound like someone who's read the manual.

Serializable is not free. Conflicts cause aborts; the application must retry. Code that runs Serializable must be idempotent and retry-aware. Throughput is also lower than Read Committed — typically 2-10x lower under contention.

Use Serializable surgically — for transactions where correctness genuinely requires it. Don't make it the default for the whole application.

How databases stack up

System Default Strongest Mechanism
Postgres Read Committed Serializable (SSI) MVCC + predicate locks
MySQL InnoDB Repeatable Read Serializable MVCC + gap locks
Oracle Read Committed Serializable (= SI) MVCC; "Serializable" is actually SI
MS SQL Server Read Committed Serializable Locking by default; SI optional
CockroachDB Serializable Serializable MVCC + retries (always SSI)
Spanner Strong Strong TrueTime + Paxos
DynamoDB Eventually consistent (default), Strong (opt-in) Strong Replication-based

The Oracle "Serializable" trap. Oracle's marketing says Serializable; technically it's Snapshot Isolation. Write skew is possible despite the name. If correctness demands true serializability on Oracle, you need explicit locking (SELECT ... FOR UPDATE) or careful application design.

Oracle's confusion has a long history — they've used "Serializable" since before the standard's distinction between SI and Serializable was formalized. The naming is grandfathered in. Senior engineers know to verify, not trust the marketing label.

Three more ways to think about isolation levels

Way 1: photographs of a busy office.

Read Uncommitted: you walk through the office randomly grabbing papers off desks, including drafts that haven't been signed yet. Sometimes the draft gets thrown out and you have a useless document.

Read Committed: you only grab papers that are signed. But each time you walk in, the office has changed — some papers have appeared, others moved. Your view of the office at 9:01 differs from your view at 9:02.

Repeatable Read: you take a photograph at 9:00 and work from the photo. Anything that changed afterward is invisible to you. The photo is consistent — but it's frozen in time.

Serializable: you take the photo at 9:00 AND if anyone else also took a photo and made changes that conflict with what you'd do, the office throws out one of the changes to keep the world consistent.

Way 2: the bank teller analogy.

Read Uncommitted: the teller sees pending check deposits as if they were already cleared. Acts on them. If the check bounces, the teller's actions were based on a fantasy.

Read Committed: the teller only sees cleared transactions. But each lookup in the system shows the current state — Alice's balance might be different at 10:00 vs 10:01 because Bob made a withdrawal in between.

Repeatable Read: the teller takes a snapshot of all relevant accounts at the start of the customer's visit. Throughout the visit, those balances stay consistent — even if other tellers are modifying things. New deposits don't show up to this teller mid-visit.

Serializable: the teller's actions and other tellers' actions are reconciled so the final state is equivalent to having processed customers one at a time. Sometimes the system says "sorry, retry" — but the result is always consistent.

Way 3: drafts of a shared document.

Read Uncommitted: you can read other people's typing as it happens, including typos they haven't fixed yet.

Read Committed: you can only read text others have saved. But each time you scroll, you see the latest saved version — text might appear or disappear as others save.

Repeatable Read: you opened the document at 9:00 and you see exactly that version, regardless of what others save. Your view is frozen until you re-open.

Serializable: you and others can edit. The system reconciles changes so the document's final state is equivalent to one of you having edited at a time. Sometimes you get "sorry, somebody else made conflicting changes — please retry."

BASE: the rebellion

In the late 90s and early 2000s, large web companies hit a wall — ACID didn't scale across geo-replicated systems. The CAP theorem (Module 12) gave the theoretical reason. The pragmatic response was a new acronym: BASE.

Letter Meaning
Basically Available The system stays up
Soft state State may drift between replicas
Eventual consistency Given no new writes, replicas converge

Cassandra at default settings is a BASE system.

You write to one replica. The replica gossips the write to others over time. A read may hit a replica that hasn't received the gossip yet → stale read. Eventually (milliseconds to seconds), all replicas converge to the same value.

For a "like" counter on a social post, this is fine. For a bank balance, it's a felony.

ACID and BASE aren't a binary choice. You pick the right consistency for the right operation.

A modern system might: - Use ACID transactions for billing (Postgres or Spanner). - Use eventual consistency for analytics counts. - Use strong consistency on writes + eventual on reads for social feeds. - Use Serializable only on a few critical paths.

This is what people mean by "polyglot persistence" or "choose your consistency". It's not "ACID or BASE"; it's "ACID where it matters, BASE everywhere else."

Per-operation consistency is the modern way. DynamoDB makes this explicit — by default, reads are eventually consistent. With ConsistentRead=true, they're strongly consistent. The same database, different consistency per operation.

Cassandra exposes consistency levels: ONE, QUORUM, LOCAL_QUORUM, EACH_QUORUM, ALL. You pick per query. Senior engineers match consistency to operation criticality.

CAP isn't a system-wide property — it's a per-operation choice in modern systems.

A worked example: the inventory race

Let's apply everything to a real interview-shape problem.

The setup:

A flash sale system. 100,000 users hit "buy" simultaneously on 1,000 inventory units. The schema:

products(id, name, stock_count INT)
orders(id, product_id, user_id, created_at)

The naive purchase flow:

BEGIN;
SELECT stock_count FROM products WHERE id = 42;
-- application checks: stock_count > 0?
INSERT INTO orders (product_id, user_id, ...) VALUES (42, ...);
UPDATE products SET stock_count = stock_count - 1 WHERE id = 42;
COMMIT;

At Read Committed (Postgres default), what goes wrong?

Race condition walk-through:

T1 reads stock_count = 1. "Great, plenty in stock." Proceeds.

T2 (concurrent) reads stock_count = 1. "Great, plenty in stock." Proceeds.

T1: INSERT order. UPDATE stock to 0. COMMIT.

T2: INSERT order. UPDATE stock to -1. COMMIT.

You sold 2 units of a 1-unit inventory. The decrement to -1 doesn't even raise an error unless you have a CHECK constraint.

This is lost update at Read Committed. Both transactions read the same value, both wrote based on it, both committed.

Five fixes

Five strategies to fix the race, ranked from cheapest to most architecturally invasive:

Atomic decrement with a guard condition.

UPDATE products SET stock_count = stock_count - 1
WHERE id = 42 AND stock_count > 0;

If the row was updated, you got inventory. If 0 rows affected, you didn't. Single statement, atomic at the row level. No isolation level upgrade needed. Cheapest fix.

SELECT ... FOR UPDATE — pessimistic row lock.

BEGIN;
SELECT stock_count FROM products WHERE id = 42 FOR UPDATE;
-- now no other txn can read this row until we commit
INSERT INTO orders ...
UPDATE products SET stock_count = stock_count - 1 WHERE id = 42;
COMMIT;

Locks the row. Other transactions wanting it wait. Correct, but serializes contention on hot rows.

Repeatable Read or Serializable isolation.

BEGIN ISOLATION LEVEL SERIALIZABLE;
-- ... same logic ...
COMMIT;  -- might fail with serialization error → retry

Now the database detects the conflict and aborts one transaction. Application must retry. Cleaner semantics, harder to reason about retries.

Counter sharding.

Instead of one stock_count row, shard inventory across N rows:

inventory(product_id, shard_id, count)

Updates go to a random shard. Total stock is SUM(count). Now contention is N-way smaller. Common pattern for "hot counter" problems at scale.

Move out of the database.

For very high contention, move stock counters to Redis with atomic INCR/DECR. Or use a queue-based reservation pattern. The database becomes the source of truth for committed orders, not for stock-in-flight.

The senior thinking process:

For a low-volume scenario (a few orders/sec), step 1 (atomic decrement) is sufficient and simplest. For a flash sale (10K orders/sec), step 4 (counter sharding) becomes necessary because step 1's lock contention on a single row dominates throughput.

The escalation: start simple, profile, add complexity only when warranted. Don't reach for Serializable as a default for ordinary write problems — it's a tool for specific cases where simple fixes won't work.

Sharpen your pencil

Exercise 1. A team's Postgres app reports occasional balance check failures: "balance went negative" — even though they have application code that checks the balance before deducting. They run at the default isolation level. What's happening, and what are three fixes ordered by complexity?

Diagnosis: lost update at Read Committed.

The application reads the balance, checks it's sufficient, deducts. Between the read and the deduct, another transaction can read and deduct, and both succeed. Classic lost update.

Three fixes, ordered:

Fix 1 (cheapest): atomic guard in the UPDATE.

UPDATE accounts SET balance = balance - $amount
WHERE id = $id AND balance >= $amount;

If the row was updated, you had sufficient balance. If 0 rows affected, you didn't. No isolation upgrade needed.

Fix 2 (medium): SELECT FOR UPDATE. Lock the row before reading. Other transactions wait. Correct but introduces serialization.

Fix 3 (architectural): Serializable isolation with retry logic. Wrap the transaction in BEGIN ISOLATION LEVEL SERIALIZABLE. Catch serialization failures and retry. Cleanest semantics, requires application support for retries.

The senior reflex: start with the cheapest fix that solves the actual problem. Don't reach for Serializable as a default.

Exercise 2. A junior engineer says "we should use Repeatable Read for everything — it's safer than Read Committed." Two arguments why this isn't always the right move.

Argument 1: Performance cost. Repeatable Read holds snapshots longer. In Postgres specifically, longer snapshots prevent VACUUM from cleaning up dead tuples that those snapshots might still reference. Long-running RR transactions cause bloat in tables and indexes. At scale, this becomes operational pain — bloated tables get slower, VACUUM works harder, performance degrades. Default Read Committed avoids this.

Argument 2: Doesn't actually fix all bugs. Repeatable Read prevents non-repeatable reads but not write skew (Module 08). For business invariants that span multiple rows ("at least one doctor on call," "max 5 active sessions per user"), RR doesn't help. If the goal is "make the application safer," RR is a half-measure — Serializable is the actual answer for invariant-based bugs, and Serializable has its own retry costs.

The senior framing: isolation level should match the specific needs of specific transactions, not be a global default chosen for "safety." Pick by operation.

Exercise 3. Explain to non-technical Sam, in two sentences, why "ACID compliance" is more nuanced than the marketing makes it sound.

ACID is a vocabulary — it tells you what guarantees a database can offer, but each guarantee comes in different strengths and each database picks its defaults differently. So "yes, we're ACID" can mean a system that catches most concurrency bugs by default (some configurations of Postgres) or one that catches almost none (some configurations of MySQL with weak isolation), and the difference matters when you're trying to figure out if your app is actually safe under load.

There are no dumb questions

Q: Why doesn't the database always run at Serializable?

A: Performance. Serializable requires conflict detection, predicate locks (or full SSI machinery), and aborts that the application must retry. For most read traffic, weaker levels are dramatically faster and good enough. The senior pattern is to default to Read Committed and opt into stronger levels for specific transactions where correctness demands it.

Q: Can I mix isolation levels within an application?

A: Yes — and you should. Most queries can run at the database default. Specific transactions that need stronger guarantees use SET TRANSACTION ISOLATION LEVEL ... at the start. The mix is normal in production code.

Q: What's the difference between "Serializable" and "Strict Serializability"?

A: Serializable means "result equivalent to some serial order" — but that order doesn't have to match real-time. Strict Serializability adds: the order must respect the actual time order of transactions (T1 finishes before T2 starts → T1 appears before T2 in the serial order). Most databases offer Serializable; only a few (Spanner, FoundationDB) offer Strict Serializability.

Q: Is "linearizability" the same as "serializability"?

A: No. Linearizability is single-key — operations on one register appear in real-time order. Serializability is multi-key — transactions appear in some serial order. Strict Serializability = linearizability + serializability. Different academic concepts often conflated in practice. For interviews, "strong consistency" usually means linearizable; "ACID Serializable" usually means serializable.

Q: When would I use Read Uncommitted?

A: Almost never. Some data warehousing scenarios where you're computing rough estimates and tolerate some staleness. Most databases don't even offer it as a real level — Postgres treats READ UNCOMMITTED as Read Committed silently. Don't go looking for use cases.

Q: What does SELECT FOR SHARE do?

A: Acquires a read lock on the row — others can read it, but not modify it. Useful when you want to ensure a row doesn't change during your transaction without preventing concurrent reads. Less common than FOR UPDATE (write lock), but real.

Q: Why does MySQL default to Repeatable Read while Postgres defaults to Read Committed?

A: Historical decisions. MySQL's RR is needed because of replication semantics (statement-based binlog requires RR to be safe). Postgres's RC is fine because of physical replication (which doesn't have the same requirement). Different design choices, both valid.

Q: Can I see what isolation level my session is at?

A: Yes. In Postgres: SHOW transaction_isolation;. In MySQL: SELECT @@transaction_isolation;. Useful for debugging "why is this transaction behaving weirdly" — sometimes a connection pool sets a non-default level.

Three myths to dynamite

"Postgres is ACID compliant."

True but misleading. Postgres provides ACID transactions, but its default isolation is Read Committed — not Serializable. To get full Serializable behavior, you opt in with SET TRANSACTION ISOLATION LEVEL SERIALIZABLE. Almost no production app does this by default. So "Postgres is ACID" is true; "your app is therefore safe from all concurrency bugs" is false.

"NoSQL means non-ACID."

False. Many modern NoSQL systems offer ACID transactions per-document (MongoDB, DynamoDB) or even multi-document (DynamoDB transactions, MongoDB 4.0+). Cassandra famously doesn't, but offers lightweight transactions via Paxos. Don't say "NoSQL = no ACID" without nuance.

"Repeatable Read prevents all phantoms."

False (per the SQL standard) and true (in Postgres and MySQL specifically). The SQL standard says RR allows phantoms. Postgres's RR uses MVCC snapshots that prevent them. MySQL InnoDB uses gap locks. Both major engines disagree with the standard, in different ways. Always specify the database when discussing isolation behavior.

Interview gotchas

Saying "we use Postgres so we're ACID." Postgres's default is Read Committed. Many concurrency bugs survive Read Committed. Knowing this distinction is the difference between junior and senior framing.

Calling Oracle's "Serializable" actually serializable. It's Snapshot Isolation. Write skew is possible. Verify the actual semantics, don't trust the label.

Confusing "Repeatable Read" with "Serializable." RR prevents non-repeatable reads but allows write skew. Serializable prevents both. Most write-skew bugs survive RR.

Treating ACID as a binary checkbox. ACID is a vocabulary; each letter has nuances and the implementations differ. Senior engineers articulate the specific level and what it does/doesn't prevent.

Forgetting BASE isn't "no consistency." Eventual consistency is still a guarantee — just a weaker one. "BASE = the system might lose your data" is wrong. BASE = "the system stays available; replicas converge over time."

Mock interview

You see two transactions both succeed, but together they violate a business invariant — like two doctors going off-call when at least one must be on. The system uses Repeatable Read. What's happening, and how do you fix it?

This is write skew — the canonical example. Both transactions check "are at least 2 doctors on call?" and read 2. Both decide "I can go off." Both UPDATE — different rows. They commit. Now zero doctors are on call.

Repeatable Read in MVCC implementations like Postgres gives each transaction a consistent snapshot. The reads are accurate as of snapshot time. But the writes don't conflict — they touch different rows — so neither aborts. The invariant ("at least one on call") spans rows in a way the snapshot can't see.

Three ways to fix it:

One: Upgrade to Serializable. Postgres SSI detects this exact pattern at commit time and aborts one transaction. The application must handle the retry. Cleanest semantics; performance cost is contention-dependent.

Two: Materialize the conflict. Make the writes touch a shared row. Add a team_status row that all "go off-call" transactions UPDATE. Now they conflict on that row's lock and serialize naturally — Repeatable Read is enough.

Three: Pessimistic locking. SELECT * FROM doctors WHERE on_call = true FOR UPDATE before deciding. The lock prevents the second transaction from proceeding until the first finishes.

The deeper lesson: isolation level is a ceiling, not a floor. Read Committed and Repeatable Read protect against specific named anomalies but not all consistency violations. Serializable is the only level that promises "if your transactions are correct in isolation, they're correct concurrent."

Names the anomaly (write skew). Explains why RR doesn't catch it (the writes don't conflict). Three concrete fixes with trade-offs. The closing principle is the kind of crisp summary that lands in interviews.

You upgrade to Serializable. Now the application starts seeing transient errors — "could not serialize access due to read/write dependencies among transactions." What's happening?

Postgres SSI detected a serialization conflict and aborted one of the transactions. This is expected behavior at Serializable isolation — the engine is doing its job, telling the application "if I let both of these commit, the result wouldn't be equivalent to any serial order. Pick one."

The application must:

Catch the error. Postgres returns SQLSTATE 40001. Your data access layer should recognize this and trigger retry logic.

Retry the transaction. The retry is not idempotent in general — it re-runs the whole transaction. The data may have changed since the first attempt; the retry might succeed, fail again, or read different inputs and produce different outputs. The retry must be idempotent at the business-logic level, or you risk processing the same event twice.

Bound retries. Don't retry forever. Typical pattern: 3-5 retries with exponential backoff. Beyond that, surface the error to the user.

Monitor retry rates. A small percentage of retries is normal; a high percentage means contention is bad. Investigate which transactions conflict frequently and consider: - Splitting into smaller transactions to reduce contention windows. - Counter sharding for hot rows. - Falling back to pessimistic locking for the worst offenders.

Serializable is correct, but it's not free — it shifts cost from "wrong results" to "retries." Most apps that adopt it discover this curve and tune their retry logic carefully.

Specific error code (40001). Walks through the retry pattern with caveats. Names the retry-rate monitoring as an operational concern. The closing — "shifts cost from wrong results to retries" — is the senior framing.

A team is migrating from MySQL to Postgres. They report that "transactions behave differently" — specifically a previously-correct stored procedure now hits race conditions. What do you tell them?

A few likely culprits:

One — default isolation differs. MySQL InnoDB defaults to Repeatable Read. Postgres defaults to Read Committed. The stored procedure may have been relying on RR's stable snapshot — under Postgres RC, repeated reads can see different values mid-transaction.

The fix: SET DEFAULT_TRANSACTION_ISOLATION = 'repeatable read' per session, or wrap the proc's logic in an explicit BEGIN ISOLATION LEVEL REPEATABLE READ.

Two — locking semantics differ. MySQL gap locks prevent phantoms by locking ranges; Postgres snapshot isolation prevents phantoms via versioning. If the procedure was relying on lock semantics — for example, SELECT FOR UPDATE over a range to block inserts — the behavior differs subtly. Postgres's predicate locking via SSI is different machinery.

Three — SSI conflict aborts. If they upgrade to Postgres Serializable, they may suddenly see retry-required errors that didn't exist in MySQL — Postgres aborts on rw-antidependency cycles. The application must handle these retries.

Four — UPSERT semantics. MySQL has INSERT ... ON DUPLICATE KEY UPDATE. Postgres has INSERT ... ON CONFLICT. The semantics are similar but not identical, especially around what locks are acquired and what the planner does for performance.

Five — autocommit and connection pool defaults. MySQL has had autocommit-on by default since forever. Connection pools sometimes set non-default isolation levels per connection, and the difference between MySQL and Postgres pool configurations bites teams during migrations.

The senior reflex: don't assume "ACID is ACID." The semantics of concurrent transactions are vendor-specific even when the syntax matches. Test the proc under realistic concurrent load on both systems before declaring the migration done.

Five specific differences, each with the actual mechanism. "Don't assume ACID is ACID" is exactly the senior framing — both systems are "ACID compliant," and that says nothing about whether they behave the same way.

Last one. The team has a critical money-transfer flow. They want to know: should we use Serializable or Repeatable Read with explicit locks?

Both can be correct. The choice depends on contention, retry tolerance, and team operational comfort.

Serializable approach:

BEGIN ISOLATION LEVEL SERIALIZABLE;
-- read source balance, check, deduct, insert into destination
COMMIT;  -- might fail; retry

Pros: simpler code (no explicit locking dance). The database detects all conflicts. Correct even for invariants the developer forgot.

Cons: retry burden on the application. Under contention, retries can dominate throughput. Some queries' SSI cost (predicate locks) is non-trivial.

Explicit locking approach:

BEGIN;
SELECT balance FROM accounts WHERE id = $source FOR UPDATE;
SELECT balance FROM accounts WHERE id = $dest FOR UPDATE;
-- check and modify
COMMIT;

Pros: predictable performance. No retry logic needed. Failure mode is "wait for lock" not "abort and retry" — easier for some apps to reason about.

Cons: deadlock risk if locks are acquired in inconsistent order across transactions. The fix: always lock account IDs in sorted order, so any two transactions touching the same set of accounts agree on the order.

My default for money transfers: explicit locking with sorted IDs. The reasoning: money transfers are high-stakes; predictable behavior matters more than elegant abstractions. If a deadlock happens, the database aborts one transaction and the application retries — same outcome as Serializable, but with explicit semantics.

I'd verify with the actual system: measure contention, decide based on data. If lock contention is bad and retries are tolerable, switch to Serializable. If retries are expensive (e.g., they generate audit log noise), stick with explicit locking.

The framing that matters: there's no single right answer for transactions. Senior engineers know both approaches, can articulate trade-offs, and pick based on the specific characteristics of the system.

Doesn't pick one and dismiss the other. Articulates the trade-offs of each, names a specific deadlock-prevention pattern (sorted ID acquisition), and closes with the meta-insight that there's no single right answer. That meta-framing is what makes the candidate sound like someone who's actually shipped these systems.

Cheat sheet

ACID, BASE & Isolation Levels — One Page

ACID

  • Atomicity: all-or-nothing.
  • Consistency: constraints hold (mostly an application property).
  • Isolation: concurrent txns don't see each other's mess. Configurable.
  • Durability: commits persist (via WAL fsync).

Four anomalies

  • Dirty read = read uncommitted data.
  • Non-repeatable read = same query, different value.
  • Phantom read = same range query, different rows.
  • Write skew = both txns read & decide based on stale view; both writes succeed but invariant breaks.

Four isolation levels (weakest → strongest)

Level Dirty NR Read Phantom Write Skew
Read Uncommitted Allowed Allowed Allowed Allowed
Read Committed Prevented Allowed Allowed Allowed
Repeatable Read Prevented Prevented Allowed (standard); Prevented in PG/MySQL Allowed
Serializable Prevented Prevented Prevented Prevented

Database defaults

  • Postgres: Read Committed
  • MySQL InnoDB: Repeatable Read
  • Oracle: Read Committed; "Serializable" is actually SI
  • SQL Server: Read Committed
  • CockroachDB: Always Serializable

Implementing Serializable

  • Postgres: SSI (optimistic, abort on conflict)
  • MySQL InnoDB: gap locks + S2PL
  • Strict 2PL: pessimistic locking
  • Calvin/FoundationDB: deterministic ordering

BASE

Basically Available, Soft state, Eventually consistent. Trade ACID for distributed availability. Modern reality: per-operation consistency, not system-wide.

Fixing concurrency bugs (cheapest first)

  1. Atomic guard in UPDATE: WHERE balance >= amount.
  2. SELECT FOR UPDATE row lock.
  3. Repeatable Read or Serializable + retry logic.
  4. Counter sharding for hot rows.
  5. Move out of the database (Redis, queue).

The 30-second verbal answer

"ACID is a vocabulary. The interesting letter is I — Isolation has four levels: Read Uncommitted, Read Committed, Repeatable Read, Serializable. Each prevents specific anomalies. Default is Read Committed in most engines, which permits write skew and lost updates — bugs that survive into production unless you opt into stronger levels or use explicit locking. BASE is the eventual-consistency philosophy for distributed systems. The senior reflex: pick consistency per operation, not as a global default."
