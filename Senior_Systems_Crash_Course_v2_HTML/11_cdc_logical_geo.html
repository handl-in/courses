MODULE 11

CDC, Logical Replication & Geo-Replication

How data flows from your OLTP system to the rest of the world — and the operational pitfalls of getting it wrong

Your engineering team is talking about Debezium, Iceberg, the lakehouse, and CDC pipelines. The architect is throwing around "logical replication slot" like everyone knows what that is.

You don't. Most engineers don't. By the end of this module, you'll be the one who does.

Sam catches up on architecture

Sam OK so last module covered replication — leaders, followers, lag, failover. But everyone at work keeps saying "CDC pipeline" and "Debezium" and "Kafka into Iceberg." How does that fit in?

Maya That's the modern extension of replication. Module 10 was replicas inside the same database for HA and read scaling. This module is about replicating outside the database — to Kafka, to data lakes, to search indexes, to other databases entirely. Same fundamentals, different destination.

Sam So CDC is just... replication?

Maya CDC stands for Change Data Capture. It is replication, but specifically the kind that captures row-level changes — INSERTs, UPDATEs, DELETEs — as a stream of events. Once you have that stream, you can pipe it anywhere. To search engines for indexing. To analytical warehouses. To other services. To data lakes for ML training.

Sam Why is this such a big deal?

Maya Because it solves the integration problem at scale. Without CDC, every team that wants OLTP data writes their own polling job — "SELECT * FROM users WHERE updated_at > $last_check" — and they all duplicate effort, miss updates, hammer the OLTP database. With CDC, the database itself emits an event stream, and consumers subscribe. The OLTP database stays pristine. Everyone else gets a faithful, real-time mirror.

Sam And the operational pitfalls?

Maya Two main ones. Replication slots that fill the disk — the canonical Postgres incident. And geo-replication conflicts that you find out about three months after deployment. We'll cover both.

Physical replication ships byte-for-byte page changes — exact mirrors. Logical replication ships row-level operations — flexible mirrors. CDC is the productized version of logical replication, exposed as an event stream for downstream consumers. The modern data platform is built on this distinction.

Physical vs logical: the foundational split

Every replication mechanism falls into one of two categories. Senior engineers know exactly which.

Physical replication

Ships byte-for-byte changes to disk pages. The replica is a literal bit copy of the primary.

Pro: fastest. No interpretation overhead.

Pro: exact reproduction — indexes, internal state, everything.

Con: replica must be same major version of database.

Con: can't filter or transform data.

Con: the replica is read-only — it cannot be queried for unrelated work.

Used by: standard Postgres streaming replication, MySQL row-based replication (mostly).

Logical replication

Ships row-level operations: "INSERT row X with values Y", "UPDATE row Z set foo=bar". Replica reconstructs by executing them.

Pro: flexible — replicate to different version, schema, or even different DB type.

Pro: can filter rows or columns.

Pro: replica is fully writable; logical replica only mirrors what's published.

Con: slower — operations must be parsed and re-executed.

Con: subtle gaps (DDL, sequences) require care.

Used by: Postgres logical replication, Debezium (everything), MySQL row-based with filters.

A concrete difference:

You have a Postgres 14 primary with 50 columns in users. You want to replicate to a Postgres 16 reporting cluster, but only a subset of columns — and you want to filter out internal users.

Physical replication: you can't. Physical requires same version, same schema, same data. End of conversation.

Logical replication: easy. Define a publication that includes only the columns and rows you want. The downstream replica can be Postgres 16 (cross-version), can have additional indexes, can even have different unrelated tables.

For internal HA, physical wins. For fan-out to other systems, logical is the only option.

Postgres physical replication ships the WAL (Module 02). The very same byte stream the primary writes for crash recovery is sent to replicas. They apply it to their own data files. This is why it's so fast — there's no parsing, no re-execution, just byte-level page mutations.

Postgres logical replication still uses the WAL — but a separate process (logical decoding) reads the WAL, reconstructs row-level operations from page-level changes, and emits them as a logical stream. The output protocol is configurable.

Change Data Capture (CDC)

CDC is logical replication, productized for downstream consumption. Instead of replicating to another database, the change stream is exposed as an event feed.

                          CDC PIPELINE

┌────────────────────────────┐ │ Postgres / MySQL primary │ ← writes go here as usual │ (source of truth) │ └──────────────┬─────────────┘ │ WAL / binlog │ (logical decoding) ▼ ┌────────────────────────────┐ │ Debezium connector │ ← reads source change stream │ (or pg_logical, etc.) │ ← emits structured events └──────────────┬─────────────┘ │ ▼ ┌────────────────────────────┐ │ Kafka │ ← durable event bus └──────────────┬─────────────┘ │ ┌─────────────┼──────────────┬──────────────┐ ▼ ▼ ▼ ▼ Search Analytics Cache Other (Elastic) (Iceberg/ (Redis) services Snowflake)

The CDC pattern: source database stays the single source of truth. CDC tool reads the change stream, publishes events to a durable bus (Kafka). Downstream consumers maintain their own optimized representations — search indexes, denormalized views, caches.

The OLTP database stops being directly hit by every team that needs its data. That's the win.

Why CDC over polling?

The polling antipattern:

Each downstream team writes their own job: SELECT * FROM users WHERE updated_at > $last_seen every minute.

By the third team adopting this pattern: - The primary OLTP database is hammered every minute by N polling jobs. - Each job has slightly different "last seen" semantics → bugs. - DELETEs are missed (they don't have an updated_at). - Schema changes break every poller silently. - Each team reinvents the wheel for retries, error handling, schema evolution.

The primary becomes a pull-target for the whole company. Capacity planning becomes adversarial: "stop polling so often!"

CDC inverts the model. The primary publishes once. Anyone subscribes. No polling, no missed DELETEs, no per-team schema drift.

Debezium: the dominant CDC tool

Debezium is the most-deployed open-source CDC tool. Source connectors for Postgres, MySQL, MongoDB, Oracle, SQL Server, Cassandra. Output to Kafka.

The basic flow for Postgres: 1. Postgres has logical replication enabled (wal_level = logical). 2. A publication is created on the table(s) of interest. 3. A replication slot is created — Postgres holds WAL until the slot is acked. 4. Debezium connects, reads from the slot, parses logical changes. 5. Debezium emits events to Kafka topics — typically one topic per table.

Each event has the row's before-state, after-state, and metadata (source LSN, transaction ID, operation type). Downstream consumers process the stream.

Mention Debezium by name in any conversation about CDC and you sound like someone who's done this.

CDC consumers: what people actually do

Common CDC downstream patterns:

Search index sync. Every user/product/document update triggers a re-index in Elasticsearch or OpenSearch. The OLTP database stays normalized; the search index stays denormalized for fast text search.

Analytics warehouse loading. Stream changes into Snowflake/BigQuery/Redshift via tools like Materialize, Fivetran, or Airbyte (under the hood, CDC). Real-time analytical mirrors of OLTP data.

Lakehouse population. Events flow into Iceberg, Delta Lake, or Hudi tables on S3. Multiple query engines (Trino, Spark, DuckDB) read the same data.

Cache invalidation / population. Updates to Postgres trigger Redis cache writes. Cache stays in sync with database without app-level dual writes.

Microservice integration. Service A's database updates trigger events Service B reacts to. Each service owns its own data; CDC carries cross-service notifications.

Audit logs. Every change automatically flows to an immutable audit log. Compliance-friendly without adding application code.

Replication slots: the canonical pitfall

This is the operational gotcha that bites every team running Postgres CDC for the first time.

A replication slot pins WAL.

When Debezium creates a replication slot in Postgres, it's telling the primary: "don't recycle WAL until I've consumed it and acknowledged."

If Debezium goes down — and stays down — the slot is still there. Postgres keeps every WAL segment generated since the last ack. Indefinitely.

The disk fills up. Once pg_wal consumes the available space, Postgres stops accepting writes. The whole OLTP system goes down.

The 3 AM page:

A team deploys CDC. Things work fine for weeks.

Then Debezium gets restarted during a Kubernetes node failure, and gets stuck in CrashLoopBackOff due to a config mistake. Nobody notices — the consumers downstream still have their cached data.

72 hours later, the primary database alerts: disk at 95%. The team investigates, sees pg_wal is 4 TB. They check pg_replication_slots — there's a stale slot from Debezium, still active, holding 4 TB of WAL.

They have a choice: kill the slot (and lose all the un-streamed changes), or fix Debezium fast enough that the disk doesn't fill before catch-up finishes.

Either way, downstream consumers will have a gap or a delay. The primary database almost went down because of a CDC consumer's failure.

The mitigations every senior CDC operator deploys:

1. Monitor pg_replication_slots.confirmed_flush_lsn lag. Per-slot lag in bytes. Alert when any slot is more than a few hundred MB behind.

2. Set max_slot_wal_keep_size (Postgres 13+). When a slot's WAL backlog exceeds this size, Postgres invalidates the slot rather than fill the disk. The slot has to be recreated and the consumer has a gap, but the primary stays up.

3. Set up dead-slot alerting. A slot whose active = false for more than a few minutes is a smell. The consumer is gone but the slot lingers, accumulating WAL.

4. Use temporary slots when possible. Some clients can use slots that auto-delete on disconnect. Less safe (can lose data on disconnect), but won't fill the disk.

Mention max_slot_wal_keep_size in an interview about CDC operations and you signal you've actually run this in production.

Geo-replication

Replicating data across geographic regions. Different from local HA — you're now dealing with high-latency links and partitions that last hours, not seconds.

The latency reality:

Path Round-trip latency
Same rack 0.1ms
Same data center 0.5-1ms
Same AZ 1-2ms
Same region (cross-AZ) 1-3ms
Cross-region intracontinental (e.g., US East ↔ US West) 60-90ms
Cross-region intercontinental (e.g., US East ↔ EU) 80-150ms
US ↔ Asia (e.g., US East ↔ Tokyo) 150-200ms

These numbers are physics, not performance optimization. The speed of light in fiber sets the floor.

This means: synchronous replication across continents adds 100-200ms to every commit. For latency-sensitive OLTP, this is unacceptable. Geo-replication is therefore almost always async.

Three patterns for geo-replication

The three common patterns:

Single-region writes, multi-region async reads. All writes go to one region's primary. Other regions have async replicas for local reads. Simplest. Local reads are fast; writes pay the cross-region latency only if the user is far from the primary region. Most production systems use this.

Multi-leader / active-active. Each region has a writable leader. Leaders replicate to each other async. Local writes everywhere. Requires conflict resolution (Module 10). Used when write latency matters more than consistency.

Globally synchronous (Spanner-style). Use atomic clocks (TrueTime) or HLC + Paxos/Raft to provide global consistency despite latency. Spanner, CockroachDB, FoundationDB. Writes pay the WAN round-trip cost; consistency is preserved. Expensive but correct.

The hidden cost of geo-replication: it's not just latency.

Cross-region links can have partition events lasting minutes to hours. Cloud providers' "regions" connect via undersea cables that occasionally fail. AWS, GCP, Azure all publish their cross-region partition history.

A geo-replicated system has to handle: - Async replication catching up after multi-hour partitions. - Conflicts arising from concurrent writes during partition. - Failover policies that don't trigger on transient cross-region blips.

Most teams underestimate this. The infrastructure ships in 2 weeks; the operational maturity takes 2 years.

The data residency wrinkle

A regulatory complication:

GDPR (EU), CCPA (California), data residency laws in China, Russia, India, etc. They require that personal data of citizens stays in specific geographic locations.

If your Postgres replica in Singapore accidentally has European user data → GDPR violation. If your CDC pipeline copies user records from EU to US for analytics → potential issue.

Geo-replication topologies must respect these laws. Some patterns:

  • Region-locked tables: certain tables only ever live in their region's database. Cross-region queries require explicit application-level coordination.
  • Field-level filtering in CDC: redact PII before streaming cross-region.
  • Separate global vs regional systems: a global system has anonymized aggregates; regional systems hold the raw personal data.

The senior detail: data residency is a first-class design constraint for any global system. Choose architecture before writing code.

Three more ways to think about CDC

Way 1: a newsletter.

Without CDC, every interested reader has to call the publisher and ask "what's new?" If 100 readers do this every minute, the publisher's phone is jammed.

CDC is a newsletter. The publisher writes once. Anyone interested subscribes. Everyone gets the same content automatically. The publisher's workload doesn't grow with subscribers; the delivery infrastructure (Kafka) does.

A replication slot that fills the disk is like a subscriber whose mailbox is full but they don't unsubscribe — the publisher keeps stockpiling old issues "in case they come back," and eventually their warehouse fills.

Way 2: court reporting.

Physical replication is photocopying every page of every document and shipping the copies. The destination has every byte exactly. Same court, same documents.

Logical replication is having a court reporter transcribe what's said into a structured record. The record can go anywhere — different court, different language, filtered to just the testimony of one witness.

CDC is making the transcription publicly available as a feed. Many parties can subscribe. Each parses the feed and uses what they need.

Way 3: GitHub commits.

Physical replication is git clone --mirror. Bit-exact copy of the repository.

Logical replication is git format-patch — exporting commits as patches that can be applied to any repository, possibly with modifications.

CDC is GitHub's webhook system. The repo emits events for every commit; subscribers (CI, deploy, notification, etc.) react. The repo doesn't care who's listening.

Sharpen your pencil

Exercise 1. Your team wants to keep an Elasticsearch index in sync with a Postgres products table. The current approach: a nightly job that does SELECT * FROM products and reindexes everything. Performance is fine but the search index is up to 24 hours stale. Three options for fresher data, ranked by complexity?

Option 1 (simplest): Polling for changes. Add updated_at indexed column. Job runs every 5 minutes: SELECT * FROM products WHERE updated_at > $last_seen. Apply to Elasticsearch.

Pros: no new infrastructure, easy to debug. Cons: misses DELETEs. Schema changes silently break it. Hammers the OLTP database with frequent queries. Doesn't scale to multiple downstream consumers.

Option 2 (medium): CDC pipeline. Set up Debezium reading Postgres logical replication, publishing to Kafka. Sink connector consumes Kafka and updates Elasticsearch.

Pros: near-real-time freshness (sub-second). Captures DELETEs. OLTP database isn't polled. Other consumers can subscribe to the same stream. Cons: operational overhead — Debezium, Kafka, monitoring slot lag. Initial setup is non-trivial.

Option 3 (complex): Application-level dual writes. Modify the application: every product write goes to Postgres AND Elasticsearch synchronously.

Pros: simplest mental model. Tightest consistency. Cons: distributed transactions across heterogeneous systems are hard. If Elasticsearch is briefly down, do writes fail? Get queued? Get lost? Every failure mode requires careful handling. In practice, dual writes are usually a worse choice than CDC because of these failure modes.

The senior recommendation: if there's only one consumer (search index) and you're early-stage, polling is fine. If you have or will have multiple consumers, build CDC up front. Don't do dual writes unless you have a very specific reason.

Exercise 2. Your Postgres database is alerting on pg_wal directory size. Investigation shows a stale Debezium replication slot holding 80 GB of WAL. Walk through your decision process.

Step 1: Stop the bleeding. Set max_slot_wal_keep_size = 100GB (or appropriate for your disk capacity) immediately. This caps how much WAL any slot can hold before being invalidated. Stops the disk from filling further.

Step 2: Decide whether to keep or drop the slot.

Two scenarios:

  • Debezium will be back soon. Wait for it. Once it reconnects and acks, the slot frees its WAL backlog. Disk usage drops.

  • Debezium is permanently broken or unwanted. Drop the slot: SELECT pg_drop_replication_slot('debezium_slot');. WAL is freed. Downstream consumers will have a gap from the last ack to now — they'll need to re-bootstrap from a fresh snapshot.

Step 3: Determine the data loss scope. If you drop the slot, the downstream system has a gap. Document the time range. Coordinate with downstream owners. Re-bootstrap may take hours or days for large tables.

Step 4: Postmortem. Why did the slot go stale? Common causes: Debezium pod crashed without alerting, Kafka was down, network partition. Add monitoring on pg_replication_slots.active = false for any duration. Don't repeat the incident.

Step 5: Configure for prevention. - max_slot_wal_keep_size permanently set. - Per-slot lag monitoring with alerts at 1 GB and 10 GB thresholds. - Dead-slot detection (slot inactive for >5 minutes alerts). - Document runbook for "slot too large" incidents.

The senior reflex: safe defaults first, root cause second, prevention third.

Exercise 3. Explain to non-technical Sam, in two sentences, what Change Data Capture does and why it's better than polling.

CDC has the database itself emit a stream of events whenever any data changes — every INSERT, UPDATE, and DELETE flows out as it happens. This is much better than polling ("ask the database every minute what changed") because it doesn't miss deletes, doesn't hammer the database with constant questions, and captures changes within a second instead of within a minute.

There are no dumb questions

Q: What's the difference between Debezium and pg_logical?

A: pg_logical is Postgres's built-in logical replication mechanism — replicates from one Postgres to another Postgres. Debezium is a productized CDC tool that reads from pg_logical (or its underlying logical decoding) and emits to Kafka. They're complementary: pg_logical is the source mechanism; Debezium is the consumer that publishes to other systems.

Q: Can I run CDC on a read replica instead of the primary?

A: Yes — and you should, if possible. Postgres supports replication slots on standbys (since v16). Running Debezium against a replica reduces load on the primary. The catch: cascading replication adds slight extra lag, and slot management is per-replica.

Q: What happens during a primary failover with active CDC?

A: Tricky. The primary's replication slots don't automatically transfer to the new primary. After failover, you need to recreate the slots on the new primary and have Debezium reconnect with appropriate offset (usually a fresh snapshot of unacked tables). Some advanced setups use logical failover slots (pg_failover_slots extension or built-in support in newer versions) to make this transparent.

Q: Can CDC handle schema changes?

A: Partially. ALTER TABLE statements are sometimes captured by logical decoding, sometimes not (depends on configuration and database). Most CDC tools handle ADD COLUMN gracefully — new columns just appear. DROP COLUMN and rename can break downstream consumers. Schema evolution requires a registry (Module 14) to manage.

Q: How does CDC handle very large tables on initial sync?

A: First the tool takes a snapshot of the existing table — reading all rows. While snapshotting, it also captures the changes happening concurrently (via the WAL). After snapshot, it applies the captured changes to bring the destination up to date, then enters streaming mode. For huge tables, this initial snapshot can take hours and consume significant primary CPU.

Q: What's the difference between row-based and statement-based replication?

A: MySQL terminology. Statement-based ships SQL statements ("UPDATE users SET ..."); row-based ships actual row changes ("row 42 had values X, now Y"). Statement-based is smaller but has subtle correctness issues with non-deterministic functions (NOW(), RAND()). Row-based is more verbose but always correct. Most modern setups use row-based.

Q: Can I have CDC from one MySQL to another MySQL?

A: Yes, that's MySQL's native binlog replication. CDC tooling like Debezium reads the same binlog and publishes elsewhere. The two are complementary: native binlog replication for HA; Debezium for fan-out to non-MySQL consumers.

Q: Does CDC work with NoSQL databases?

A: Yes. Debezium has connectors for MongoDB, Cassandra, and others. The mechanism varies — MongoDB has change streams; Cassandra uses commit log readers. The pattern (capture changes, publish to event bus) is universal even if the source mechanics differ.

Three myths to dynamite

"CDC is just replication."

Half-true. CDC is logical replication exposed as a consumable event stream for downstream systems other than database replicas. The mechanism is replication; the use case is broader integration. The distinction matters because operational concerns differ — slot management, schema evolution, downstream consumer reliability are CDC-specific.

"Polling is just as good as CDC for most use cases."

Largely false. Polling misses DELETEs unless you implement explicit deletion tracking. Polling has a freshness vs primary-load tradeoff that CDC sidesteps. Polling doesn't scale across multiple consumers cleanly. For one consumer of one small table, polling is fine. Beyond that, CDC pays for itself fast.

"Geo-replication just means replicas in other regions."

False. Geo-replication is the replication topology part. The full picture includes data residency laws, conflict resolution policies, partition tolerance budget, and operational maturity for handling multi-hour cross-region partitions. Senior engineers treat geo-replication as an architectural concern, not a configuration setting.

Interview gotchas

Confusing physical and logical replication. Physical = byte-for-byte. Logical = row operations. Different uses, different tradeoffs. Senior engineers know both names and can explain when each fits.

Forgetting the replication slot disk-fill issue. Mention pg_replication_slots, max_slot_wal_keep_size, and slot-lag monitoring when discussing CDC operations. This is the canonical Postgres CDC pitfall.

Suggesting dual writes over CDC. "Write to Postgres and Elasticsearch in the same transaction" is naive. The two systems can fail independently; you can't atomically commit across heterogeneous datastores. CDC sidesteps this entire class of problems.

Treating geo-replication as just a latency problem. Latency is the obvious cost. Data residency, partition handling, conflict resolution, and operational maturity are equal-magnitude costs. Senior framing: geo-replication is a 1-2 year operational investment, not a deployment.

Not knowing Debezium by name. It's the dominant open-source CDC tool. Naming it in interviews about CDC is table stakes for senior roles.

Mock interview

We have a Postgres OLTP system. The data team wants to build dashboards on this data. They're proposing a 5-minute polling job that copies tables to BigQuery. What do you think?

Several concerns, ranked by likelihood:

One — does polling capture everything? A 5-minute polling job using SELECT * FROM table WHERE updated_at > $last_seen misses DELETEs. Anything deleted between polls is invisible to BigQuery; the dashboards show stale data. The team probably doesn't realize this until a finance dashboard shows refunded orders that were already removed from the system.

Two — does it scale across consumers? Today it's one team. In six months, the search team wants real-time indexing, the ML team wants feature data, the auditing team wants every change. Each builds their own polling job. The OLTP database becomes a pull-target for the whole company. Capacity planning becomes adversarial.

Three — does 5-minute freshness meet the actual need? "5 minutes stale" is fine for some dashboards, not for others. If a CFO sees revenue from 5 minutes ago vs Slack messages reporting current revenue from a different system, that's confusion at minimum, distrust at worst.

My recommendation: build CDC properly the first time.

  • Debezium reads Postgres WAL via logical replication.
  • Publishes to Kafka.
  • BigQuery loads from Kafka via Dataflow or a streaming connector.
  • Future consumers (search, ML, audit) subscribe to the same Kafka stream.

The upfront cost is higher than polling. But polling has a hidden compounding cost — every new consumer makes the OLTP database's life worse. CDC is the architecture that grows.

If the team strongly prefers to start simple, fine: polling for now, but with a documented migration plan when a second consumer appears. Don't paint yourself into a corner.

You convince them. Six months later, the team alerts: Postgres pg_wal directory is at 200 GB and growing. What do you do?

First reflex: stop the bleeding. Set max_slot_wal_keep_size = 250GB immediately to cap the maximum any one slot can hold. This prevents disk fill while we investigate.

Then diagnose:

Step 1: which slot is the problem?

SELECT slot_name, active, restart_lsn,
       pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn) AS lag_bytes
FROM pg_replication_slots
ORDER BY lag_bytes DESC;

If one slot has hundreds of GB of lag, that's the culprit.

Step 2: is the consumer alive? - Check Debezium pod status. If down, restart it. - Check Kafka — is it accepting writes? Disk space? Broker health? - Check the connector logs for errors.

Step 3: if the consumer is alive but slow, why?

Possibilities: - Recent schema change that the connector is mishandling. Check connector error logs. - A massive transaction (huge bulk update) that's still being processed. Wait for it to drain. - A poison pill record the connector keeps choking on. Inspect logs and skip if necessary. - Network partition between Debezium and Kafka. Investigate connectivity.

Step 4: if the consumer is permanently broken, decide whether to drop the slot. Dropping means downstream loses some data and needs a re-snapshot. But the OLTP system stays up.

Step 5: postmortem and prevention. - Why didn't we have alerts earlier? Set per-slot lag alerts at 1 GB and 10 GB thresholds. - Why didn't max_slot_wal_keep_size save us? It wasn't configured. Now it is. - Add dead-slot alerting (active = false for >5 min). - Runbook update for the next person on call.

The senior reflex: safe defaults first, root cause second, prevention third. Don't let prevention get in the way of stopping the immediate damage.

Different scenario. We're going global. Users in EU and US. Some user data is GDPR-regulated. How would you architect the data layer?

This is a data residency problem first, replication problem second. Let me think through it carefully.

Step 1: classify data.

  • PII / GDPR-regulated: emails, addresses, payment info, identifiers tied to individuals.
  • Operational data: order amounts, product IDs, timestamps — usually fine to flow globally.
  • Aggregates: anonymized rollups, perfectly portable.

Step 2: choose a topology.

Option A: Region-locked databases per user. Each user is assigned a "home region" based on their location. Their PII lives only in that region's database. Cross-region queries require explicit user consent or anonymization.

Option B: Region-replicated with field-level filtering. A single logical database is replicated cross-region, but PII columns are filtered out of the cross-region replication. EU keeps email addresses; US doesn't.

Option C: Two completely separate systems. EU has its own complete stack. US has its own complete stack. They share nothing except possibly anonymized aggregates streaming to a central analytics environment.

For most companies, Option A or B is the right answer. Option C is operationally heavy.

Step 3: Architect specifically.

  • Database: Postgres in each region as the OLTP source of truth.
  • Cross-region replication: async, logical, with filtering. EU replica of US database (and vice versa) only includes operational data, not PII.
  • CDC for analytics: Debezium per region, with a column-filter that omits PII before publishing. Anonymous events flow to a central Kafka.
  • Central analytics: aggregated/anonymized data only. PII never lands here.
  • Local reads: each region serves its own users from its local database.

Step 4: Operational concerns.

  • Cross-region partitions are real and last hours. Architecture must work during partition. Local OLTP keeps going; cross-region analytics lags but recovers.
  • Failover policy: don't auto-promote across regions. The complexity of cross-region failover usually exceeds the benefit. Separate region-local HA from cross-region DR.
  • Consent & data subject requests: GDPR includes "right to deletion." When deleted in the EU, must propagate to all places the data was copied (analytics, backups). Build the deletion pipeline up front.

The framing: data residency is a first-class architectural constraint. Naming it "Module 11 architecture" misses the point — it's the spine of every cross-border system.

Categorizes data first (PII vs operational vs aggregates). Three options ranked by operational cost. Concrete architectural recommendations. The "right to deletion pipeline" detail signals real GDPR experience.

Last one. Your team is choosing between Postgres logical replication, Debezium, and Materialize for getting OLTP data into a real-time analytics engine. What's the difference?

All three solve adjacent problems but differ in scope.

Postgres logical replication (built-in): Postgres → Postgres. The destination is another Postgres database, possibly with filtering or transformation. Native, well-supported, simple. Bad fit if you want to feed non-Postgres downstream systems.

Use when: you want a real-time read replica with column/row filtering, possibly cross-version. You don't need to feed Kafka or other consumers.

Debezium: Postgres → Kafka → anywhere. Source connector reads logical replication; output is structured events on Kafka topics. Many sink connectors (Elasticsearch, BigQuery, ClickHouse, etc.) consume from Kafka.

Use when: you have multiple downstream consumers, or you want to fan out to non-Postgres systems, or you want a durable event bus between source and sinks. The standard architectural pattern for OLTP-to-everything.

Materialize: A different beast — not CDC tooling per se, but a streaming database. It maintains materialized views over CDC streams, with sub-second freshness, supporting standard SQL.

Use when: you want to write SQL queries that produce real-time results. The query is the artifact; the streaming machinery is hidden underneath. Particularly good for real-time dashboards and serving-layer denormalization.

A pragmatic combination: Debezium for the data pipeline, Materialize as one of the consumers building real-time SQL views. Or: Debezium for some downstream systems, Materialize directly on Postgres for fast iterative analytics development.

The senior framing: don't pick "the tool" for CDC. Map your downstream needs and pick the architecture that fits. Sometimes the answer is multiple tools — Debezium feeds Kafka, Materialize consumes from Kafka, BigQuery consumes from Kafka. Each does what it's good at.

Names each tool's actual scope clearly. The "different beast" honesty about Materialize — not pretending it's a Debezium competitor. The "pragmatic combination" closing is the senior architectural framing.

  • Logical: row-level operations. Cross-version, filtered, transformable. Slower.

Source database emits a stream of row changes. Tools (Debezium, Maxwell, etc.) publish to event buses (Kafka). Downstream consumers subscribe.

  • Captures DELETEs (polling misses).
  • Sub-second latency (polling has frequency floor).
  • Doesn't poll-hammer the OLTP source.
  • Scales across multiple consumers.

Common CDC consumers

  1. Search index sync (Elasticsearch).
  2. Analytics warehouse (Snowflake, BigQuery).
  3. Lakehouse formats (Iceberg, Delta).
  4. Cache invalidation (Redis).
  5. Microservice integration.
  6. Audit logs.

The Postgres replication slot pitfall

A slot pins WAL until consumer acks. Stale slot → WAL accumulates → disk fills → primary STOPS ACCEPTING WRITES.

Mitigations: - max_slot_wal_keep_size (caps WAL per slot). - Per-slot lag monitoring (alert at 1 GB, 10 GB). - Dead-slot alerting (active = false > 5 min). - Document runbook for "slot too large" incidents.

Geo-replication patterns

  1. Single-region writes, multi-region async reads (most common).
  2. Multi-leader / active-active (with conflict resolution).
  3. Globally synchronous (Spanner-style, expensive).

Latency floor: physics. Cross-continent = 100-200ms RTT.

Data residency

GDPR, CCPA, region-specific laws require PII stays in specific geos.

Patterns: - Region-locked tables (PII never crosses). - Field-level filtering in CDC (strip PII at boundary). - Separate global vs regional systems.

Architectural concern, not a configuration knob.

The 30-second verbal answer

"CDC is logical replication exposed as an event stream for downstream consumers. The OLTP database stays the source of truth; CDC tools like Debezium publish row changes to Kafka, and consumers (search indexes, analytics warehouses, caches) subscribe. The big Postgres operational gotcha is replication slots that pin WAL when consumers go down — set max_slot_wal_keep_size and monitor slot lag. Geo-replication adds physics-level latency and data residency constraints; treat them as architectural concerns."
