MODULE 19

Bottleneck Identification & Observability

USE, RED, the four golden signals, p99 reasoning, and why "the database is slow" is never the actual answer

The dashboard is red. The CEO is in Slack. Customers are tweeting. Your manager asks: "Where's the bottleneck?"

Junior engineers point at the slowest dashboard. Senior engineers know that the slowest dashboard is almost always downstream of the actual problem. They have a method — actually, three methods — for finding the truth in under fifteen minutes. This chapter is those methods, the math behind percentiles that everyone gets wrong, and the operational discipline that separates "we got lucky" from "we knew exactly what to do."

Sam can't find the bottleneck

Sam The checkout API is slow. p99 latency went from 200ms to 4 seconds in the last hour. I checked the database — CPU is at 40%. I checked the application servers — CPU is at 30%. I checked Redis — looks fine. Memory is fine everywhere. Where's the bottleneck?

Maya Wrong question. Better question: which layer's latency increased? You're looking at saturation when you should be looking at where time is being spent.

Sam What's the difference?

Maya A queue with 30% CPU can still have a four-second wait time if the queue is deep. CPU tells you whether the server is busy. Latency tells you whether the request is waiting. Most production bottlenecks aren't CPU-bound — they're queue-bound, lock-bound, or network-bound. CPU at 40% with a 4-second p99? Classic queueing collapse.

Sam So how do I find which layer is queueing?

Maya Decompose end-to-end latency into per-layer time. Look at distributed traces, not dashboards. Find the span where time is being burned. Then — and only then — go look at that layer's metrics to understand why.

The slowest dashboard is rarely the actual bottleneck. Bottlenecks compound: a slow downstream service backs up the layer above it, which exhausts thread pools, which makes the upstream service look slow, which is what you see first. The senior skill is decomposing the request path and finding where time is actually being spent — not where it's appearing to be spent.

The three frameworks every senior engineer knows

You don't show up to an outage and start guessing. You apply a framework. There are three battle-tested ones, and each one answers a different question. Use all three. Knowing when to switch between them is the senior skill.

USE method (Brendan Gregg) — for resources

For every system resource, check three things:

U — Utilization The percent of time the resource was busy servicing work. CPU at 80%. Disk at 60%. Network at 40%.

S — Saturation The amount of work the resource has queued up that it can't service yet. Run queue length. I/O wait queue depth. TCP accept queue.

E — Errors Error events. Disk read errors. Network packet drops. TCP retransmits. Page faults.

Why all three? A resource at 50% utilization with a queue depth of 100 is broken. A resource at 99% utilization with no queue is fine. You need both signals.

USE is for resources: CPU, memory, disk, network, file descriptors, threads. It answers "is this hardware/OS-level resource the bottleneck?"

Real example. Your database CPU shows 45% utilization. Your team says "CPU isn't the problem." Then you check saturation — the run queue length averages 12 (on a 4-core machine, anything over 4 means processes are waiting). Now you know: there's a CPU bottleneck even though utilization looks fine. The 45% number is misleading because short bursts are saturating the cores while the average looks calm.

Lesson: utilization alone lies. Saturation reveals queueing. Errors reveal failures. You need all three.

RED method (Tom Wilkie) — for services

For every service, check three things:

R — Rate Requests per second the service is handling.

E — Errors Rate of failed requests (500s, 503s, timeouts).

The third metric, "D — Duration," gets its own row because it's the most important and the most misunderstood:

D — Duration: distribution of request latencies, expressed as percentiles (p50, p95, p99, p99.9). Never as an average. Averages lie. We'll spend a whole section on why.

RED is for services: HTTP endpoints, RPC handlers, message consumers. It answers "is this service the bottleneck, and how badly?"

Real example. Checkout service: rate is 2000 RPS (normal), errors are 0.2% (normal), p50 is 80ms (normal), p99 is 4500ms (broken). The first three numbers look fine. The fourth tells you that 1 in 100 customers is having a terrible experience. That's a bottleneck, even though "averages look healthy."

Lesson: percentile distributions reveal what averages hide.

The four golden signals (Google SRE) — for user-facing systems

Latency — how long requests take. Distinguish successful latency from failed latency. A failure that returns in 10ms can hide a real success-path problem.

Traffic — demand on the system. Requests per second, sessions per minute, transactions per second.

Errors — rate of failures, broken down by type (4xx vs 5xx, parse errors vs timeouts vs deps-down).

Saturation — how "full" the system is. Often the leading indicator of impending latency increases. A queue at 80% capacity is fine right up until it isn't.

The four golden signals are for user-facing systems: a website, an API, an end-to-end product. They answer "is the user happy, and if not, why?"

Senior interview move. When asked "what would you monitor?" never just list metrics. Name the framework you're applying. "I'd apply USE for the database resources, RED for each service in the request path, and the four golden signals for the user-facing API. That gives me three orthogonal views of the system: hardware, services, and customer experience." That answer signals you've done this for years.

Pause and think. You're paged for a slow API. Which framework do you reach for first — USE, RED, or four golden signals?

Trick question: you reach for all three, but in this order. (1) Four golden signals to confirm there's a real customer-facing problem (latency? errors? saturation?). (2) RED on each service in the path to identify which service is slow. (3) USE on the resources of that service to find the resource bottleneck. The frameworks aren't competitors — they're zoom levels.

Percentiles: the math everyone gets wrong

If you take one thing away from this chapter, take this. Percentiles are not averages. Percentiles do not compose. Averages of percentiles are meaningless. Almost every junior engineer makes these mistakes. Almost every senior interview tests them.

What a percentile actually means

p99 = "99% of requests completed in this time or faster." It's a threshold. If p99 is 500ms, then 1% of requests took longer than 500ms — possibly much longer. p99 says nothing about how much longer. p99.9 and p99.99 fill that in.

Worked example: why averages lie.

You have 100 requests with these latencies (sorted): - 99 requests at 50ms each - 1 request at 5000ms

Average: (99 × 50 + 5000) / 100 = 99.5ms. Looks fine!

p50 (median): 50ms. Looks fine!

p99: 50ms (the 99th sorted value is at index 98, which is one of the 50ms requests).

p99.9: somewhere between 50ms and 5000ms (this single 5000ms request lives in the top 1%, but you'd need 1000+ requests to see p99.9 stably).

The average is a lie because the outlier barely moves it. The p50 is a lie for the same reason. Only when you go to p99 and beyond does the slow request become visible.

Lesson: if you only look at average and p50, you'll miss customer pain that's affecting 1-5% of requests. And 1% of 10M daily requests is 100,000 angry customers per day.

Why averages of percentiles are nonsense

This is the mistake that gets engineers laughed out of senior interviews.

You cannot average p99s. If service A has p99=500ms and service B has p99=300ms, the combined p99 is not 400ms. It could be anywhere from 300ms to 500ms+. Percentiles don't compose linearly.

Why averaging percentiles is wrong.

Service A: 100 requests, mostly fast, one outlier at 5000ms. p99 = 5000ms. Service B: 100 requests, all at exactly 100ms. p99 = 100ms.

Average of p99s: (5000 + 100) / 2 = 2550ms.

Real combined p99 (if you concatenate the 200 requests and recompute): the 99th-percentile-by-rank of 200 requests is the request at index 198. That's still in the "100ms from B" range or the "fast from A" range. The true p99 is around 100ms, not 2550ms.

The "average of p99s" is wildly wrong because it's not a valid statistical operation. You need the underlying distribution to compute a real percentile. Histograms can be merged; percentiles cannot.

Senior tooling move. Never store p99 as a pre-aggregated value. Store histograms (HDR Histogram, t-digest, Prometheus histograms with buckets). Histograms are mergeable — you can sum buckets across services and recompute any percentile. That's why Prometheus uses histogram_quantile() over rate(xxx_bucket[5m]) rather than a pre-computed p99 metric. The histogram-then-quantile pattern is fundamental.

How long-tail latencies destroy systems

A tail latency that affects 1% of requests sounds small. It isn't — because of fanout.

The fanout amplification. Your homepage makes 50 backend calls in parallel and waits for all of them to render. Each call has a p99 of 100ms — that means 1% of calls are slower than 100ms. So the probability that all 50 calls finish in under 100ms is:

(0.99)^50 = 0.605, or 60.5%.

In other words, 39.5% of homepage loads experience at least one tail-latency call that exceeds the per-call p99. The page is slow nearly 40% of the time despite each individual service being "fast" 99% of the time.

This is why senior engineers obsess over p99 and p99.9 even when "averages look fine." Fanout amplifies tails. The more downstream services you call, the worse it gets.

"In a microservices architecture, your customer-facing latency is dominated by your worst service's tail, not your average service's median. Cut tails, not averages."

Gotcha: "we improved our average latency by 30%" doesn't mean customers are happier. If your improvement removed a bunch of fast requests (e.g., added caching that handled the easy cases), the average drops dramatically — but the slow requests that were causing pain are still slow. Always report p50, p95, p99, p99.9 separately. "Average improved" hides everything.

The "where does the time go?" debugging discipline

When latency spikes, the senior approach is mechanical, not magical. Here's the playbook.

Step 1: Confirm the customer experience

The first 60 seconds.

  1. Look at the four golden signals dashboard for the user-facing service. Confirm: is latency actually up? Are errors up? Is traffic up (could be load-driven) or normal (could be infrastructure-driven)?
  2. Distinguish "regional" from "global." Is it one geographic region or all of them? One AZ? One specific endpoint or all endpoints?
  3. Check the timeline. When did this start? What changed at that time — a deploy, a config push, a traffic event?

If you can answer these three before you start looking at deeper metrics, you've already eliminated 80% of possibilities.

Step 2: Decompose the latency

This is the step Sam was missing in the opener. You can't fix a bottleneck by staring at the symptom. You have to decompose the request path.

End-to-end latency = 4500ms

  Edge / CDN: 20ms
  ↓
  Load balancer: 5ms
  ↓
  API gateway: 30ms
  ↓
  Application service: 40ms
  ↓
  ▶ Database query: 4380ms  ◀  ← here
  ↓
  Response serialization: 25ms

The database span owns 97% of the time.
That's the bottleneck. Now go investigate
the database — not the gateway, not
the app server, not the LB.

This is what distributed tracing is for. Jaeger, Zipkin, Tempo, OpenTelemetry, Datadog APM — all of them give you per-span latency. The span that owns the most time is the bottleneck. Don't guess from dashboards; trace the request.

Senior engineers also know: tracing has sampling overhead. Most production systems sample at 1% or use head-based sampling. So you might need to force-trace a few requests during the incident, or use tail-based sampling to capture only slow requests. If your tracing setup samples at 1% during a 5-second outage with 100 requests, you have one trace. Make sure you're capturing slow requests preferentially.

Step 3: Apply USE on the bottleneck layer

Once you've identified which layer is slow (the database, in our trace), apply USE to its resources:

Database USE checklist:

  1. CPU: utilization (% busy), saturation (run queue length), errors (none usually).
  2. Memory: utilization (% allocated), saturation (swap activity, page faults), errors (OOM kills).
  3. Disk: utilization (% busy), saturation (I/O wait queue depth, await time), errors (read errors, retries).
  4. Network: utilization (Mbps used / Mbps capacity), saturation (TX queue, RX drops), errors (TCP retransmits, packet loss).
  5. Connections: utilization (% of pool used), saturation (queued connection requests), errors (connection refused, timeout).
  6. Locks: lock waits, lock timeouts, deadlocks, longest-held lock.

Identify the resource that's saturated. That's where to look next.

Real database debugging. Database CPU is 30% (low), memory is 50% (fine), disk I/O wait is 600ms (huge!), connections are 95% used. Combination of disk-bound queries plus connection pool exhaustion. The two are related: each query is slow on disk, holding its connection longer, which exhausts the pool, which causes new requests to queue waiting for connections, which makes upstream services see "slow database."

Fix: speed up the queries (add an index, fix the plan), and the connection pool exhaustion resolves itself. If you'd just added more connections, you'd have made it worse — more connections doing slow disk I/O means more disk contention.

Flame graphs and profiling

When you've found the bottleneck layer but still don't know which code is slow, you profile. Flame graphs are the visualization.

What a flame graph shows

Flame graph (read bottom to top):

│ http.handler.checkout() ──────────────────────────── 100% │
│ ├─ validate_input()  ─ 5%                                  │
│ ├─ load_user_cart() ─────────── 35%                        │
│ │   ├─ db.query("SELECT...") ── 30%   ← here              │
│ │   └─ cache.get() ─ 5%                                    │
│ ├─ compute_total() ─ 5%                                    │
│ └─ submit_payment() ─────────────────────── 55%            │
│     ├─ http.post(stripe) ─────────── 45%   ← here          │
│     └─ db.insert("orders") ─ 10%                           │
│
The widest boxes are the time consumers.
db.query and stripe.post own 75% combined.

Flame graphs reveal which functions consume the most time by stacking call frames as horizontal bars proportional to time spent. The widest frame is the bottleneck. Read flame graphs bottom-up — the deeper you go, the more specific the function.

When to reach for a profiler

CPU profiler (perf, py-spy, async-profiler, pprof). Use when: CPU is saturated. Reveals which functions are burning cycles. Captures on-CPU time.

Off-CPU profiler (offcputime, async-profiler in wall-clock mode). Use when: CPU is not saturated but latency is high. Reveals where threads are blocked — locks, I/O, network waits. Captures off-CPU time (waiting time).

Don't use a CPU profiler when CPU isn't the bottleneck. It will tell you which function is using CPU when CPU isn't even the constraint. Off-CPU profiling captures the waiting, which is what's actually slow. Most slow systems are I/O-bound, lock-bound, or network-bound — not CPU-bound — so off-CPU profiling is what you usually want.

Tools by language: - Java: async-profiler (best in class), JFR, YourKit - Python: py-spy (zero-overhead), cProfile, scalene - Go: pprof (built-in, excellent) - Node.js: 0x, clinic.js, --inspect with Chrome DevTools - C/C++: perf, gprof, Intel VTune - Database engines: most have built-in profilers (Postgres pg_stat_statements, MySQL Performance Schema, Mongo db.profiler)

Senior interview tip: name a profiler appropriate to the language they're discussing. "I'd flame-graph it with async-profiler" carries more weight than "I'd profile it."

The metrics that actually matter

You can't watch everything. The senior skill is knowing the small set of metrics that matter most — the ones that catch 90% of incidents before they're customer-visible.

For databases

Database metrics every senior engineer monitors:

  1. Query latency p50, p95, p99 per query type. Per-query, not aggregate. Aggregate hides regressions in specific queries.
  2. Active connections / max connections. Connection pool exhaustion is silent until it's catastrophic.
  3. Replication lag. Seconds behind primary. Bytes behind primary. Both.
  4. Deadlocks per minute, lock waits per minute, longest-held lock duration. Lock contention is invisible until it isn't.
  5. Buffer cache hit ratio. Below 95% means the working set doesn't fit in memory; you're hitting disk.
  6. WAL/redo log generation rate. Sudden increase = unusual write load or runaway transaction.
  7. Slow query log entries per minute. Set the threshold (log_min_duration_statement in Postgres) to your p95 latency, not 1 second.
  8. Vacuum / autovacuum activity (Postgres). Bloat eats performance silently.
  9. Disk I/O wait time and queue depth. The actual bottleneck for most OLTP databases.
  10. Failed connections per minute. Anything but 0 is a problem.

For services

Service metrics every senior engineer monitors:

  1. Rate (RPS) per endpoint.
  2. Error rate per endpoint, broken down by error type. A spike in 503s is different from a spike in 401s.
  3. Latency p50, p95, p99, p99.9 per endpoint.
  4. Saturation: thread pool utilization, request queue depth, in-flight requests.
  5. Dependency latency. How long are calls to downstream services taking? This is where bottlenecks hide.
  6. Cache hit ratio. A drop here predicts a database spike 30 seconds later.
  7. Garbage collection pause times (JVM/Go/Node). GC pauses cause tail latency.
  8. Open file descriptors / available file descriptors. FD exhaustion is a classic silent killer.
  9. TCP connection count, TIME_WAIT count. Network stack saturation.
  10. Custom business metrics: orders/min, signups/min, checkout success rate. The leading indicators.

For infrastructure

Infrastructure metrics every senior engineer monitors:

  1. Per-host CPU utilization, run queue length, load average. Load average over the run queue length plus blocked process count tells you saturation.
  2. Per-host memory: used, free, swap activity, page faults. Swap activity > 0 on a production server is usually a problem.
  3. Per-host disk: utilization, await, IOPS, throughput, queue depth. Most modern OLTP problems are disk-related.
  4. Per-host network: bandwidth utilization, packet errors, retransmits, TCP_LISTEN backlog drops.
  5. Container metrics: CPU throttling time (cgroup throttle), memory pressure, OOM kills.
  6. Kubernetes metrics if applicable: pod restart rate, pending pods, image pull errors.

The 80/20 of monitoring. If you only have 10 dashboards, make them: (1) four golden signals for top services, (2) database query latency by query type, (3) connection pool utilization for every pool, (4) cache hit ratio for every cache, (5) replication lag, (6) GC pause times, (7) error rates by type, (8) saturation across resources, (9) dependency latency from each service, (10) business KPIs (orders, signups, success rates). These ten dashboards catch 90% of incidents.

SLI, SLO, SLA — and error budgets

The Google SRE concept that every senior interviewer expects you to know.

SLI — Service Level Indicator A measurable metric that reflects user experience. "Percentage of requests served in under 300ms." "Percentage of requests that returned 200 OK." It's a number you compute.

SLO — Service Level Objective The target for an SLI. "99.9% of requests complete in under 300ms over a rolling 30-day window." It's an internal goal you commit to.

SLA — Service Level Agreement The contractual commitment to customers, with consequences. "If we miss 99.9% availability over a calendar month, we credit you 10% of your monthly bill." Always more lenient than the SLO — your SLA might be 99.9%, your SLO 99.95%, giving you internal buffer before contractual penalties hit.

The error budget

If your SLO is 99.9% over 30 days, you can have 0.1% downtime — that's about 43 minutes per month. That 43 minutes is your error budget. You spend it on:

  • Planned downtime (rare but happens)
  • Failed deploys
  • Capacity-related incidents
  • Genuine outages

The error budget conversation. Your SLO is 99.9% (43 minutes of downtime/month). Halfway through the month, you've already burned 35 minutes on a failed deploy. Engineering wants to ship a risky change. The error budget says: you have 8 minutes left. The senior call: freeze risky deploys until next month, or accept that one more bad deploy means missing your SLO.

This is what error budgets are for — they convert "should we ship this?" from a political debate into a math question. If you have budget, ship. If you don't, freeze.

Senior interview move. When asked "how do you balance reliability vs feature velocity?" — name error budgets. "We measure SLO attainment monthly. When we have budget remaining, we ship aggressively. When we've burned the budget, we freeze risky changes and focus on reliability work. It removes the politics from the decision." That's the SRE-influenced senior answer.

Choosing good SLIs

Bad SLIs: - "Average latency" (averages lie about tails) - "CPU utilization" (a resource metric, not a user experience metric) - "Number of errors" (without a denominator — 100 errors out of 100M is fine, 100 errors out of 1000 is catastrophic) - "Memory usage" (irrelevant to user experience)

Good SLIs: - "Percentage of requests with latency < 300ms" - "Percentage of successful requests" (success = HTTP 200/201/202/204, business-success when applicable) - "Percentage of writes that propagate to read replicas within 5 seconds" - "Percentage of jobs completing within their SLA"

Good SLIs are ratios: numerator (good events) / denominator (total events), measured over a window.

Three exercises

Exercise 1: The mysterious slowdown.

p99 latency on /checkout jumped from 200ms to 2000ms over 30 minutes. CPU on app servers is 35%. CPU on database is 40%. Memory is fine everywhere. Network is fine. No deploys in the last 4 hours. Traffic is normal. Where do you look next, and in what order?

Apply the framework. Distinguish symptom from cause. CPU and memory are resource metrics — they tell you about the host, not the request.

Senior approach:

  1. Distributed tracing first. Pull 5–10 slow request traces. Find which span owns the time. Don't look at dashboards yet.
  2. If the slow span is the database, check: query plans (did a plan flip?), index health, lock waits, connection pool utilization, slow query log.
  3. If the slow span is a downstream service, recurse: look at its RED metrics, then trace into it.
  4. If the slow span is inside the app (not in a downstream call), look at: GC pauses, thread pool saturation, locks in code, synchronous I/O on the hot path.
  5. Specifically check the non-obvious resources: connection pool utilization (could be 100% even when DB CPU is 40%), thread pool utilization (could be queueing even when host CPU is fine), file descriptor count, GC pause times.
  6. Check deployments to dependencies — your team didn't deploy, but did the auth service team? Did the payment provider change something? Did the cloud provider have an incident in the AZ?

The bottleneck is almost certainly queueing somewhere — connection pool, thread pool, downstream dependency, or GC. CPU at 35% with a 10x latency increase is the classic queue-collapse signature.

Exercise 2: The histogram bucket trap.

Your Prometheus histogram for API latency has buckets at: 10ms, 50ms, 100ms, 500ms, 1s, 5s, 10s, +Inf. Your p99 from histogram_quantile(0.99, ...) reads 5s exactly. Your boss wants you to optimize the system to get p99 under 1s. You make a change you believe is a major improvement. The dashboard still reads p99 = 5s. Why?

Bucket boundaries determine percentile resolution. The percentile function interpolates within a bucket.

Senior answer:

histogram_quantile() interpolates linearly between bucket boundaries. If your p99 of requests falls between the 1s bucket and the 5s bucket, the function reports a value somewhere in [1s, 5s]. The exact value depends on bucket counts, not on actual request distribution within the bucket.

Possible reasons your p99 still reads 5s:

  1. Insufficient bucket resolution between 1s and 5s. You need buckets at 1.5s, 2s, 3s — otherwise any request that's between 1s and 5s gets reported as ~5s by the interpolation.
  2. Your improvement moved requests from 4s → 2s, but both still fall in the [1s, 5s] bucket — so the histogram count for that bucket didn't change, and histogram_quantile() still reports 5s.
  3. Stale data in the dashboard time range. Make sure you're looking at the post-change window.

The fix: add buckets between 1s and 5s. Better yet, use exponential buckets (Prometheus has histogram_quantile() with native histograms in newer versions, or use t-digest / HDR for true percentile fidelity). The lesson: bucket choice is the precision of your p99. If you didn't choose buckets correctly, your dashboard is reporting bucket boundaries, not real percentiles.

Exercise 3: The error budget decision.

Your SLO is 99.95% successful requests over 30 days. With 7 days left in the month, you've already used 95% of your error budget. Your team wants to ship a major feature that touches the checkout flow. The change is well-tested, but checkout is your highest-traffic path. What's your senior recommendation?

Error budgets convert reliability vs velocity from a political question to a math one.

Senior answer:

The error budget framework gives a clear answer. With 5% of budget remaining and 23% of the time period remaining, you're burning faster than your budget allows. Shipping a checkout-flow change carries non-zero risk — even a 0.05% error rate during rollout would consume your remaining budget.

Recommendation: 1. Postpone the deploy to the start of the next month, when the error budget resets. State this is the SRE-recommended action: when budget is exhausted, freeze risky changes. 2. If business pressure demands shipping: gate it behind a feature flag at 1% of traffic. The math: 1% rollout × 0.05% error rate = 0.0005% impact, which is within budget tolerance even with current burn. 3. Use this incident as a forcing function for a reliability review. Why was 95% of the budget burned? Were the incidents preventable? What runbooks need updating?

The signal you give your interviewer: you treat error budgets as real constraints, not theater. You separate "we can ship this" from "we should ship this." You have a graduated rollout plan, not a binary go/no-go.

The non-senior answer is "ship it anyway, it's well-tested." The senior answer respects the math: probabilities compound, and a well-tested change has a non-zero error rate at production scale.

No dumb questions

Q: Should I use OpenTelemetry, or stick with my vendor's APM agent?

OpenTelemetry is the open standard, and most modern APMs (Datadog, New Relic, Honeycomb, Tempo) accept OTel data. Senior recommendation: instrument with OpenTelemetry SDK in your code, and choose a backend separately. This avoids vendor lock-in. Vendor agents are easier to start with but harder to migrate from later.

Q: How long should I retain metrics? Logs? Traces?

Metrics: raw at 15s resolution for 14 days, downsampled to 5min for 1 year. Logs: 7-30 days hot, 90 days warm, longer in cheap archival. Traces: 1-7 days at full sampling, longer if you sample only slow ones. Storage costs dominate observability budgets at scale — be intentional about retention.

Q: We have alerts that fire constantly. Should we just disable the noisy ones?

No — that's how you miss real incidents. The senior approach: every alert should be actionable. If an alert can't be acted on by a human, delete it. If an alert fires and resolves on its own, raise the threshold or add hysteresis (e.g., "fire only if condition holds for 5 minutes"). Alert fatigue kills on-call.

Q: What's a "symptom-based" vs "cause-based" alert?

Symptom-based alerts on user impact ("checkout p99 > 1s"). Cause-based alerts on potential causes ("CPU > 90%"). Senior teams alert on symptoms and use causes as diagnostic dashboards. Cause-based alerts often fire when nothing's wrong (CPU spike with no impact) and miss real incidents (no resource saturation but customer pain).

Q: Should I trace every request, or sample?

Sample, unless you're in early development. Full tracing has 5-15% performance overhead and storage costs scale linearly. Common patterns: 1% head sampling (decide at trace start), tail sampling (decide at trace end — sample slow or errored traces preferentially), or "always trace by user" for VIP customers. Honeycomb-style dynamic sampling is the senior pattern.

Q: What's the difference between "structured logging" and regular logging?

Structured logs are JSON or key-value pairs. Regular logs are unstructured strings. The senior pattern: log structured ({"event":"checkout_completed","user_id":123,"amount":42.50,"latency_ms":85}) so you can query, filter, and aggregate. Logging "Checkout completed for user 123 in 85ms" forces grep regex pain forever after.

Q: How do I monitor third-party APIs I depend on?

Two layers: (1) instrument your client calls (latency, error rate, retries). This shows your view of the dependency. (2) subscribe to the vendor's status page or use synthetic checks (probes that exercise their API on a schedule). Real outages often show up in your metrics before their status page updates.

Q: I'm seeing latency spikes that don't correlate with anything. What's happening?

Likely candidates: (a) GC pauses (check GC log times against latency spikes), (b) noisy-neighbor on shared infrastructure (cloud VMs with bursty co-tenants), (c) network microbursts (check TCP retransmits), (d) cron jobs / scheduled work (check the calendar of all your services), (e) DNS lookups (most clients cache poorly). The "uncorrelated spike" usually has a hidden correlation you haven't measured yet.

Three myths

MYTH: "If the dashboard is green, everything is fine."

Dashboards show what you measured. They don't show what you forgot to measure. Real incidents often happen in dimensions you don't have a metric for: a specific customer, a specific endpoint, a specific time-of-day pattern, a specific data shape. Senior engineers add new dashboards in response to incidents — every incident teaches you something you weren't measuring.

MYTH: "More monitoring is better."

More monitoring is worse if it produces alert fatigue, blows up storage costs, and slows down the system. Every metric has cost: collection, transmission, storage, query. The senior approach is fewer, more meaningful metrics, not exhaustive coverage of every counter.

MYTH: "Distributed tracing replaces logs and metrics."

Distributed tracing complements them. Traces excel at "where did the time go for this request." Metrics excel at "how is the system behaving in aggregate." Logs excel at "what was happening at this exact moment." The three are orthogonal — you need all three. Tracing without metrics means you can't tell normal from abnormal. Metrics without tracing means you can't drill into a specific slow request.

Five gotchas

GOTCHA 1: Your timeseries database is a single point of failure.

If Prometheus / Datadog / your metrics backend goes down during an outage, you're flying blind. Run redundant metrics paths: a local agent that writes to disk if the network is down, dual-writes to two regions, or a backup metrics store. The worst time to lose observability is during an incident.

GOTCHA 2: Cardinality explosions kill metrics systems.

Tagging metrics with user_id, request_id, or any high-cardinality dimension can produce millions of unique time series, OOM-ing your metrics server. Rule: tag with low-cardinality labels (service, endpoint, region, status_code). High-cardinality data goes in logs or traces, not metrics. Datadog and Prometheus both bill on cardinality — this can become a five-figure-monthly mistake.

GOTCHA 3: Clock skew breaks tracing.

Distributed traces depend on accurate timestamps across hosts. If your hosts have 50ms clock skew, span timings are off by 50ms — sometimes appearing as negative durations. Run NTP on every host. Modern cloud providers handle this, on-prem deployments often don't. When you see "span ended before it started" in your trace viewer, that's clock skew.

GOTCHA 4: Sampling-based percentiles can lie at low traffic.

If your endpoint gets 100 requests/hour and you sample 1% of traces, you have one trace per hour. Your p99 from that sample is meaningless — you have no statistical signal. For low-traffic endpoints, sample at 100% or use specialized low-traffic instrumentation. The math: you need at least ~1000 samples to estimate p99 stably.

GOTCHA 5: Pre-aggregated percentiles can't be re-aggregated.

If your CDN reports per-minute p99 to your metrics store, you cannot compute hourly p99 by averaging the minute values. You'd need raw histograms. Many vendors hide this behind "percentile" widgets that do average percentiles silently, producing nonsense values. Always verify: am I aggregating histograms (correct) or aggregating percentiles (wrong)?

Mock interview

Interviewer: "Your service's p99 latency just spiked from 200ms to 3 seconds. Walk me through how you'd debug it in production, in real time."

You: "I'd run three frameworks in parallel — they answer different questions.

First, four golden signals on the affected service: confirm latency is up, check whether errors are also up (which would suggest a different failure mode), and confirm whether traffic spiked (load-driven) or stayed flat (infrastructure-driven). I'd also check the timeline — did this start at a specific moment? A deploy, config push, traffic event?

Second, distributed tracing. Pull 5-10 slow request traces. The bottleneck layer is whichever span owns the most time. I'm not guessing from dashboards — I'm reading the actual request paths. If 90% of the time is in the database span, that's where to focus. If 90% is in a downstream service, recurse into that service.

Third, USE on the bottleneck layer. Once I know it's the database, I check CPU utilization and saturation (run queue depth), memory and swap, disk I/O wait time and queue depth, network errors, connection pool utilization, and lock waits. The bottleneck is the resource that's saturated or that has high error rates.

While I'm doing this, I'm checking my hypothesis against the timeline. If a deploy went out 5 minutes before the spike started, the deploy is the prime suspect — roll it back first, debug after."

What makes this senior: named three specific frameworks, distinguished resource metrics from request metrics, mentioned "I'm not guessing from dashboards," called out the deploy timeline as a primary correlation. Connected debugging to mitigation (roll back, then debug).

Interviewer: "You're seeing CPU at 40% utilization but p99 latency is 4 seconds. The team says 'CPU isn't the bottleneck because it's only at 40%.' What do you tell them?"

You: "CPU utilization at 40% can absolutely coexist with a CPU bottleneck — it's a classic queueing collapse signature.

Utilization is the average over a time window. If the window is 1 minute and you have bursty workloads, you can have 100% utilization for 24 seconds and 0% for 36 seconds, which averages to 40% but means requests are queueing for half the window.

I'd ask the team to look at saturation, not utilization. Specifically: run queue length (processes waiting for CPU). On a 4-core machine, anything above 4 means processes are queueing. If they're seeing run queue length of 10-15 with 40% utilization, that's the smoking gun — CPU is bursting to saturation in microsecond windows.

Other classic culprits with 'low' CPU: disk I/O wait queue depth, connection pool exhaustion (apps blocked waiting for a free connection), thread pool saturation in the application server, GC pauses on the JVM. All of these produce 'CPU looks fine but latency is awful.'

The senior framing: utilization tells you whether the server is busy. Latency tells you whether requests are waiting. They are different things. Always look at both."

What makes this senior: explained the math behind why averaged utilization lies, named specific saturation metrics, listed the 4-5 common causes of "low CPU + high latency", and gave a memorable framing ("server busy" vs "requests waiting"). The interviewer is hearing pattern recognition from real incidents.

Interviewer: "Walk me through how you'd design SLOs for a new payment processing service."

You: "Three SLIs, then I'd derive the SLOs from business requirements.

SLI 1 — Availability: percentage of payment requests that return a final answer (success or business-rejection) rather than a system error or timeout. Numerator: requests with a 200 or business-decision 4xx response. Denominator: total requests minus client-side bad-request errors (400s for malformed input, since those aren't our fault).

SLI 2 — Latency: percentage of payment authorization requests completing within 3 seconds. The 3-second number isn't arbitrary — it's the typical card-network timeout, and customers abandon at higher latencies. Histogram-based, computed over rolling 30-day windows.

SLI 3 — Settlement timeliness: percentage of authorized payments that settle within 24 hours. This is a business SLI, not a technical one — it captures the end-to-end value chain.

For SLOs, I'd start tight and loosen if business allows: 99.95% availability, 99.9% latency under 3s, 99.99% settlement within 24h. The settlement is highest because regulatory and customer-trust impact is high.

For SLA, I'd set the contractual number lower than the SLO — 99.9% availability with credit-back terms — so we have buffer between internal goals and contractual commitments.

Then I'd implement error budget tracking, monthly. When budget is depleted, we freeze non-critical changes. When budget is healthy, we ship aggressively. That's the real value of the framework — it converts political velocity-vs-reliability debates into math."

What makes this senior: distinguished SLI from SLO from SLA cleanly, included a business SLI alongside technical ones, gave specific reasoning for the latency threshold (card network timeout), and tied error budgets to deploy decisions. Interviewer is hearing someone who's run on-call rotations.

Interviewer: "A junior engineer reports that they 'reduced the average latency by 40%' on the checkout endpoint. How do you respond?"

You: "First, I'd celebrate the work — improvements deserve recognition. Then I'd ask three questions, in order.

One: 'How did p50, p95, p99, and p99.9 change?' Average improvements often come from removing fast requests (e.g., adding a cache that handles the easy cases) without touching the slow ones. The customers in pain are in the tail. If the tail didn't move, the customers didn't get happier — even if the average looks great.

Two: 'How did you measure?' If they computed average from pre-aggregated minute-level p99s, the math is wrong (you can't average percentiles). I'd want to see the histogram-based methodology and the actual buckets used.

Three: 'How did downstream metrics change?' If checkout calls a payment service and we sped up checkout by reducing payment timeouts, we may have transferred the latency to higher error rates downstream. Improvements can be illusions if they shift cost rather than eliminate it.

The senior framing: 'average latency' is rarely the right SLI. Tail percentiles capture customer pain, especially in fanout architectures where p99 of individual services aggregates badly into homepage p50s. I'd thank the engineer for the work, and ask them to redo the analysis with full percentile distribution and the downstream impact."

What makes this senior: validated the engineer's effort first (good leadership), then gave three pointed questions that would surface common mistakes (fast-case bias, percentile arithmetic errors, latency-shifting). Mentioned fanout amplification of tails. The reply is technically rigorous and respectful — that combination is what separates senior from staff.

Cheat sheet

THE FRAMEWORKS - USE (resources): Utilization, Saturation, Errors. For CPU, memory, disk, network. - RED (services): Rate, Errors, Duration (as percentiles, not averages). - Four golden signals (user-facing): Latency, Traffic, Errors, Saturation.

DEBUGGING ORDER 1. Confirm customer impact via golden signals. 2. Decompose latency via distributed traces — find which span owns the time. 3. Apply USE on the bottleneck layer's resources. 4. Profile if needed: CPU profiler when CPU saturated, off-CPU profiler otherwise.

PERCENTILES - Average lies; medians lie about tails; p99 catches 1% pain. - Percentiles do NOT compose: average of p99s is meaningless. - Use histograms (mergeable) not pre-aggregated percentiles. - Fanout amplifies tails: 50 calls each at p99=100ms means 40% of homepages exceed 100ms.

SLO/SLI/SLA - SLI: a measurable user-experience metric (number). - SLO: an internal target for SLIs. - SLA: contractual commitment to customers (looser than SLO). - Error budget: 100% − SLO. Spend on planned and unplanned changes.

TOP 10 METRICS 1. Per-endpoint latency p50/p95/p99/p99.9 2. Per-endpoint error rate by type 3. Database query latency by query type 4. Connection pool utilization (every pool) 5. Cache hit ratio (every cache) 6. Replication lag 7. GC pause times 8. Saturation across resources 9. Dependency latency from each service 10. Business KPIs (orders/min, signups/min)

ALERT DISCIPLINE - Symptom-based, not cause-based. - Every alert must be actionable. - Alert fatigue → missed incidents. Tune ruthlessly.

GOTCHAS - Cardinality explosions kill metrics systems. - Pre-aggregated percentiles can't be re-aggregated. - Sampling-based percentiles need ~1000 samples to be stable. - Clock skew breaks distributed traces. - Vendor "average percentile" widgets often produce nonsense.

TOOLS - Tracing: OpenTelemetry, Jaeger, Tempo, Honeycomb, Datadog APM - Metrics: Prometheus + Grafana, Datadog, New Relic - Logging: Elastic/OpenSearch, Loki, Datadog Logs - Profiling: async-profiler (Java), py-spy (Python), pprof (Go), 0x (Node)
