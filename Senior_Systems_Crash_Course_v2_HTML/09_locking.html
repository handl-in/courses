MODULE 09

Locking

Pessimistic vs optimistic, deadlocks, and the queue patterns that scale

Two transactions both want to update the same row. Who waits? Who fails? How do you decide which strategy to use before you've shipped to production and started seeing deadlocks at 4 AM?

Most engineers learn locking by getting paged. This module gets you there before the page.

Sam asks the wrong question

Sam OK so I read about optimistic locking and I'm convinced. No locks, no deadlocks, just a version column and retry on conflict. We should switch our whole codebase to optimistic locking, right?

Maya What's your conflict rate?

Sam What do you mean conflict rate?

Maya How often do two concurrent transactions try to modify the same row? If it's 1%, optimistic locking is brilliant — almost everyone succeeds first try, and the rare retry is cheap. If it's 50%, optimistic locking is catastrophic — half your work gets thrown away and redone, every retry races into more retries, and your throughput collapses.

Sam Oh.

Maya Both pessimistic and optimistic locking are correct. The question isn't "which is better." The question is "what's my contention pattern?" The same problem with low contention wants optimistic; with high contention wants pessimistic. You don't get to pick by aesthetic. The workload picks for you.

Sam And deadlocks?

Maya Pessimistic only. Optimistic doesn't deadlock — it just retries. But pessimistic deadlocks are usually fixable in one of three specific ways, and once you know them, you stop fearing the deadlock detector. By the end of this module you'll know exactly when each strategy fits and how to make pessimistic locking safe.

Pessimistic locking assumes conflicts are likely; lock first, then act. Optimistic locking assumes conflicts are rare; act first, then verify. Pick by contention rate, not by preference. Low contention → optimistic. High contention → pessimistic.

Pessimistic locking

You acquire a lock before doing the work. Anyone else who wants the same lock waits.

BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;   -- exclusive row lock
-- ... compute new balance ...
UPDATE accounts SET balance = ... WHERE id = 1;
COMMIT;                                            -- lock released

The bank teller scene:

Two clerks both want to debit account A. Clerk 1 starts the transaction first.

  • Clerk 1: SELECT FOR UPDATE → gets the lock, reads $500, computes new $400, UPDATEs, commits.
  • Clerk 2: SELECT FOR UPDATE → blocked, waits at the lock.
  • Clerk 1 commits. Lock released.
  • Clerk 2: now reads $400 (post-clerk-1's commit), computes correctly from there.

Correctness is automatic. The lock serializes access to that row. There's no race because there's no concurrency on the contended resource.

The cost: throughput on that row caps at "1 transaction at a time, sequentially." Under high contention, the system becomes a queue.

The bathroom door analogy.

Pessimistic locking is a bathroom with a lock. Walk up, lock the door, do your business, unlock. Anyone who arrives meanwhile waits in line.

Two great properties: - Nobody walks in on you. Privacy guaranteed. - The system is simple. No "did somebody else use it" worry.

Two costs: - Lines form. Wait time scales with usage. - If two people both need two bathrooms (master bedroom and guest), and they grab them in opposite orders, you get deadlock.

SELECT FOR UPDATE — the row-level workhorse

SELECT ... FOR UPDATE is the most common pessimistic-locking syntax. It takes a row-level write lock on each row matched.

SELECT * FROM accounts WHERE id IN (1, 2, 3) FOR UPDATE;

Other transactions trying to update those rows wait. Reads (without FOR UPDATE) still proceed via MVCC — they see the pre-lock snapshot.

Postgres also has SELECT ... FOR SHARE — a row-level read lock. Others can read it but not modify it. Useful when you need to prevent change during your transaction without modifying anything yourself.

Example: validating that a user account is active before placing an order. You want to ensure the account doesn't get deactivated mid-transaction. FOR SHARE lets other readers proceed but blocks deactivations.

Optimistic locking

You don't lock. You read the data, do your work, and at write time check "did anyone change this since I read it?" If yes, retry.

This is usually implemented via a version column or a last-modified timestamp:

-- Read
SELECT id, balance, version FROM accounts WHERE id = 1;
-- application reads balance=500, version=7
-- ... compute new balance ...

-- Write with version check
UPDATE accounts
SET balance = 400, version = 8
WHERE id = 1 AND version = 7;
-- if 0 rows updated → someone else modified, retry

The optimistic version of the bank teller scene:

  • Clerk 1: reads (balance=500, version=7).
  • Clerk 2 (concurrently): reads (balance=500, version=7).
  • Clerk 1: computes 400, UPDATE WHERE version=7 → success, version becomes 8.
  • Clerk 2: computes 400, UPDATE WHERE version=7 → 0 rows affected. Conflict. Retries.
  • Clerk 2 retry: reads (balance=400, version=8). Computes 300. UPDATE WHERE version=8 → success.

No locking. No waiting. Just an after-the-fact check.

If contention is rare, this is brilliant — the wasted retry is a small percentage of total work. If contention is heavy, retries dominate and the system thrashes.

The shared Google Doc analogy.

Optimistic locking is editing a shared Google Doc. You type freely. If two people edit the same paragraph at the same moment, the system catches it and one of you sees a "merge conflict" — your version was based on a stale view, please reconcile.

For low-collision usage (people working on different sections), it's perfect. Nobody waits. Productivity is maximum.

For high-collision usage (everybody mashing on the same line), it's a nightmare. Constant merge conflicts. Half your typing gets thrown out.

When to use which: the decision

Pessimistic — use when

  • Conflict rate is high (>5-10%)
  • The work being protected is short (lock held briefly)
  • Wasted retries are expensive (audit logs, external API calls)
  • Correctness must be obvious (financial transactions)

Failure mode: deadlocks. Manageable with discipline.

Optimistic — use when

  • Conflict rate is low (<5%)
  • The work being done is read-heavy then write
  • Wasted retries are cheap (idempotent operations)
  • You want to maximize throughput at low contention

Failure mode: retry storms. Catastrophic at high contention.

The crossover point depends on workload, but a rough heuristic: above ~20% conflict rate, pessimistic wins. Above that, optimistic's retry overhead exceeds pessimistic's queueing cost. Below ~5%, optimistic wins easily — locks are wasted overhead.

The 5-20% range is workload-specific. Profile, don't guess.

Mention "conflict rate determines the choice" in an interview, and you signal you've thought about this beyond the textbook.

Deadlocks: the pessimistic price

A deadlock is when two or more transactions each hold a lock the other needs, and they wait forever.

The classic deadlock:

T1: locks row 5, then wants row 9. T2: locks row 9, then wants row 5.

T1 waits for T2 to release row 9. T2 waits for T1 to release row 5.

Stalemate. Without intervention, both transactions hang forever.

                      THE WAIT-FOR GRAPH

T1 ──holds──→ Row 5 T1 ──wants──→ Row 9

T2 ──holds──→ Row 9 T2 ──wants──→ Row 5

Drawing the wait-for graph (who waits for whom):

     T1 ──waits-for──→ T2
          ▲                │
          │                ▼
          ←──waits-for── (cycle!)

A CYCLE in the wait-for graph means deadlock. No transaction can proceed until another releases its lock.

How databases detect deadlocks

Databases run a deadlock detector in the background. Periodically — typically every 1 second — it builds the wait-for graph and looks for cycles. When detected, the database picks a victim transaction and aborts it. The other(s) proceed.

ERROR: deadlock detected
DETAIL: Process 12345 waits for ShareLock on transaction 4729;
        blocked by process 12346.
        Process 12346 waits for ShareLock on transaction 4728;
        blocked by process 12345.
HINT:   See server log for query details.

Your application must catch deadlock errors and retry. This is non-negotiable for any production app using pessimistic locks.

Different databases pick victims differently.

  • MySQL InnoDB: picks the txn with the least work done (smallest undo log).
  • Postgres: picks the txn currently waiting (the "newer" one to detect).
  • SQL Server: picks based on a deadlock priority setting and rollback cost.
  • Oracle: similar heuristic to Postgres.

Don't assume the victim is the "newer" or "older" transaction — it varies by engine. Application retry logic should be agnostic to which side gets killed.

Avoiding deadlocks: the discipline

The classic prevention rule: always acquire locks in the same order across all transactions.

The deadlock prevention recipe:

Identify which rows your transactions might lock together. If transaction X locks rows A and B, and transaction Y also locks A and B, they're at risk.

Pick a canonical lock order for those rows. The simplest: sort by primary key.

Always acquire locks in that order, in every code path, across every service.

No deadlock is possible because no cycle can form — every transaction is reaching for locks in the same direction.

-- BAD (deadlock prone)
T1: lock(row 5); lock(row 9);
T2: lock(row 9); lock(row 5);

-- GOOD (deterministic order)
T1: lock(row 5); lock(row 9);
T2: lock(row 5); lock(row 9);   -- both lock 5 first

A common pattern: when you must update multiple rows, sort by primary key and lock them in that order. Now any two transactions touching the same set of rows agree on order. No deadlock possible.

For the money transfer pattern (debit account A, credit account B), the senior code looks like:

BEGIN;
SELECT * FROM accounts WHERE id IN ($source, $dest)
  ORDER BY id  -- canonical order
  FOR UPDATE;
-- ... transfer logic ...
COMMIT;

The ORDER BY id makes the lock acquisition order deterministic. Two simultaneous transfers between the same accounts can't deadlock.

The other deadlock prevention strategies

Beyond consistent lock order, four more strategies:

1. Reduce transaction size. Shorter transactions hold locks for less time. Less time held = smaller window for deadlock. The single best generic fix.

2. Use lower isolation when possible. Read Committed locks fewer rows. RR/SSI lock more (or track more dependencies). Use the weakest isolation that's correct for the use case.

3. Use single-row coordinator patterns. If many transactions need to coordinate, have them all lock a single sentinel row first. Serializes them via that one row. Loses concurrency, eliminates deadlock.

4. Move to optimistic locking. If the access pattern doesn't fit consistent ordering well, optimistic might be a better strategy. Lock-free, deadlock-free, but pays in retries.

Lock granularity

Locks can apply at different scopes. The trade-offs cascade through performance.

Scope Example Pro Con
Row Postgres FOR UPDATE High concurrency Many locks → memory cost
Page SQL Server (one disk page) Fewer locks Blocks unrelated rows on same page
Table LOCK TABLE One lock Kills concurrency
Predicate / range SI predicate locks (Postgres SSI) Prevents phantoms Complex implementation
Advisory pg_advisory_lock App-defined semantics App must respect them

Why granularity matters:

A bulk update over 100K rows. Row locks: 100K lock entries in memory, but other transactions can still touch unrelated rows. Page locks: ~1K locks, but all rows on those pages are blocked even if the update only touches some. Table lock: one lock entry, but the entire table is unavailable to others.

Granularity is a memory-vs-concurrency tradeoff. Finer = more concurrency, more memory. Coarser = less memory, less concurrency.

Lock escalation: SQL Server's drama

Lock escalation is a feature SQL Server has and Postgres doesn't.

Under load, if a transaction takes too many row-level locks (~5,000 by default), SQL Server converts them to a single table lock to save memory. Sounds reasonable. In practice, it causes outages.

Once escalated, the entire table is locked. Other transactions wanting any row on that table now wait. The bulk operation finishes; the table unlocks. But for the duration, every other query sees a hang.

The classic lock escalation incident:

A nightly cleanup job runs DELETE FROM events WHERE created_at < .... Touches ~50K rows.

At 5,000 row locks, SQL Server escalates to a table lock. Suddenly, every query touching events waits. The OLTP application grinds to a halt for the next 90 seconds while the delete completes.

The first time this happens, you panic. The second time, you batch the delete: WHERE created_at < ... LIMIT 4000 in a loop, committing each batch. The escalation threshold is never reached.

The mitigation pattern: batch large operations to stay below the escalation threshold.

Other databases don't escalate. - Postgres: never escalates. Holds millions of row locks happily (with predictable memory cost). - MySQL InnoDB: never escalates. - Oracle: never escalates.

Lock escalation is a SQL Server thing. If you're not on SQL Server, you don't have this problem. If you are, batch your big writes.

Advisory locks: the hidden gem

Postgres has a feature most engineers never discover: advisory locks.

Advisory locks aren't tied to any row or table. They're application-defined keys (just a 64-bit integer or two 32-bit integers) that follow normal locking semantics. Take them, hold them, release them. Other transactions trying to take the same key wait.

SELECT pg_advisory_lock(42);   -- take lock with key 42
-- ... do exclusive work ...
SELECT pg_advisory_unlock(42); -- release

Use cases: - "Only one job processes this queue at a time" — without modeling it as a row. - "Singleton initialization across many app instances" — first one wins, others wait or skip. - "Distributed mutex for application-level resources" — much cheaper than implementing your own.

There are also session-level and transaction-level variants, and shared vs exclusive versions. Mention pg_advisory_lock in an interview about Postgres operations and you signal real depth.

SELECT FOR UPDATE SKIP LOCKED — the queue pattern

This deserves its own section. It's the canonical pattern for "claim a job from a queue" in Postgres and MySQL.

The job queue problem:

50 workers race to claim jobs from a jobs table. The naive approach:

BEGIN;
SELECT * FROM jobs WHERE status='pending' LIMIT 1 FOR UPDATE;
UPDATE jobs SET status='claimed', worker_id=$me WHERE id=$found_id;
COMMIT;

Without SKIP LOCKED, every worker that arrives at the same moment locks the same row — the first pending job. 49 of them wait at the lock, do nothing, eventually the first commits, then 49 race to claim the next row. The throughput is bottlenecked by the lock contention, even though there are plenty of jobs to go around.

FOR UPDATE SKIP LOCKED tells the SELECT to silently skip rows already locked by other transactions. Now 50 workers can claim 50 different jobs concurrently — no waiting. The lock contention vanishes.

-- The senior pattern for queue claim:
BEGIN;
SELECT * FROM jobs
  WHERE status='pending'
  ORDER BY created_at
  LIMIT 1
  FOR UPDATE SKIP LOCKED;
-- ... process ...
UPDATE jobs SET status='completed' WHERE id=$found_id;
COMMIT;

Walk through with two workers:

Worker A and B both arrive simultaneously. Both run the SELECT.

Worker A's SELECT locks row 1 (the oldest pending job).

Worker B's SELECT would lock row 1, but SKIP LOCKED makes it skip. It grabs row 2 instead and locks that.

Both workers proceed in parallel — different jobs, no waiting.

A 10x speedup over the naive pattern. Both engines (Postgres ≥ 9.5, MySQL ≥ 8.0) support this.

This pattern is so important for queue workloads that it's the first thing to mention when interviewers ask "how would you build a queue on top of a database." It signals you understand both the contention problem and the modern solution.

You might still want to consider whether a real queue (SQS, RabbitMQ, Redis Streams) is a better choice than a database. But if you're stuck with the database, SKIP LOCKED is the answer.

Three more ways to think about locking

Way 1: traffic intersections.

Pessimistic locking is a 4-way stop sign. Everyone waits their turn. Strict ordering. Slow at peak hour but never collisions.

Optimistic locking is a roundabout. Everyone keeps moving. Most of the time, no problem. Occasionally two cars meet at the same point — minor fender bender, both reverse and try again. Fast at low traffic, ugly at peak.

Lock escalation is when the city decides 50 stop-sign intersections in a row should be replaced with one giant traffic light. Now one signal cycle blocks everything. Fewer signs, but worse user experience.

Way 2: kitchen pots.

Pessimistic: cook puts hand on pot handle, says "mine," uses it, puts down. Anyone wanting that pot waits.

Optimistic: cook grabs whatever pot, uses it, but at serving time checks "anyone else use this and switch ingredients?" If yes, redo. Cheap when nobody else cooks; chaos when many cooks share ingredients.

Deadlock: cook A grabs the saucepan and reaches for the spatula. Cook B has the spatula and reaches for the saucepan. Both stuck. Eventually the head chef (deadlock detector) yells at one to put their pot down.

Lock acquisition order discipline: house rule that pots are always picked up in alphabetical order. Now no two cooks can deadlock — they're both reaching toward the same place.

Way 3: shared documents.

Pessimistic = Microsoft Word document open from a network share, marked "in use" by Alice. Bob waits.

Optimistic = Google Docs. Both edit. System merges or surfaces conflicts.

Advisory lock = a Slack message saying "I'm working on the deploy script for the next 30 minutes, hands off." Not enforced by the system, but everyone respects it because they agreed to.

SELECT FOR UPDATE SKIP LOCKED = a job queue where, when you grab a task, others can see it's claimed and pick a different one — no waiting in line for the same task.

Sharpen your pencil

Exercise 1. Your service has a "claim a job from queue" operation. 50 workers race to claim jobs from a single jobs table. Currently you use SELECT * FROM jobs WHERE status='pending' LIMIT 1 FOR UPDATE; UPDATE jobs SET status='claimed' WHERE id=?. You're seeing severe contention. Workers spend more time waiting on locks than processing.

Three independent improvements you'd propose, in order?

Improvement 1: Add SKIP LOCKED.

SELECT * FROM jobs WHERE status='pending'
ORDER BY created_at LIMIT 1
FOR UPDATE SKIP LOCKED;

This is the idiomatic fix. 50 workers claim 50 different jobs concurrently with no lock waiting. Often a 10x improvement, no architecture change. Always the first thing to try.

Improvement 2: Sharded queue.

Replace the single queue with N partitioned queues (e.g., by hash(job_id) mod N). Each worker rotates through partitions. Reduces contention by N×. Useful when even SKIP LOCKED has too many concurrent attempts on the index scan side.

Improvement 3: Move to a real queue.

If you're using a database as a queue, you're paying for ACID guarantees that may not be needed. SQS, RabbitMQ, Redis Streams, Kafka — purpose-built queues handle this with millisecond latency, no locking, built-in retry and dead-letter semantics.

The general lesson: a database queue is fine until it isn't. When contention dominates, either use the database's queue features (SKIP LOCKED) or move to a queue.

Exercise 2. A team is seeing deadlocks in production logs once per day. Their instinct is to rewrite to optimistic locking. Is that the right call?

Slow down. Three diagnostic questions first:

1. What's the actual deadlock rate? Once per day across millions of transactions is barely measurable — it might be perfectly acceptable as long as the application retries. The cost of switching to optimistic might exceed the cost of one retry per day.

2. What's the conflict pattern? Read the deadlock logs. Are they always the same two queries? If yes, the fix is lock ordering in those specific queries — not a strategy change. Most production deadlocks come from inconsistent lock acquisition order in 2-3 hot code paths. Rewrite those paths.

3. What's the contention rate? If most transactions conflict, optimistic locking will retry-storm and burn CPU. If conflicts are rare, optimistic might be a clean win. Measure first.

The path I'd actually take: - Add deadlock retry logic if it's not already there. (Idempotent operations only.) - Identify the top 2-3 deadlock-producing queries. - Enforce consistent lock order in those — usually sort by primary key and lock in order. - Only consider strategy change if those changes don't bring deadlocks below the noise floor.

Switching to optimistic locking across the codebase is a multi-quarter project that introduces new failure modes. Almost never the right move when you can fix 3 queries instead.

Exercise 3. Explain to non-technical Sam, in two sentences, why SELECT FOR UPDATE SKIP LOCKED is the right pattern for a job queue.

A regular SELECT FOR UPDATE for "give me the next pending job" causes every worker to fight for the same row — 49 of them wait while 1 processes, totally serializing the queue. Adding SKIP LOCKED tells each worker to silently skip rows already claimed by others and grab the next available one, so 50 workers can pull 50 different jobs in parallel without ever blocking each other.

There are no dumb questions

Q: Does a plain SELECT take any locks?

A: In Postgres at the default Read Committed isolation, plain SELECT takes no row locks — MVCC handles read consistency without them. In MySQL InnoDB at Repeatable Read, plain SELECT also doesn't take locks (MVCC). At Serializable in InnoDB, plain SELECT can take shared locks. The general principle: modern MVCC databases avoid read locks for plain SELECT.

Q: What's the difference between SELECT FOR UPDATE and SELECT FOR SHARE?

A: FOR UPDATE is an exclusive lock — others can't read or write the row until you commit. FOR SHARE is a shared lock — others can read but not modify. Use SHARE when you need to ensure a row doesn't change during your transaction without modifying it yourself.

Q: Can two transactions both hold SHARE locks on the same row?

A: Yes. Multiple shared locks are compatible. Only exclusive (FOR UPDATE) conflicts with anything. The lock matrix: shared+shared OK; shared+exclusive blocks; exclusive+anything blocks.

Q: How long can locks be held?

A: Until commit or rollback. There's no automatic timeout in most engines unless you set one. Postgres has lock_timeout and statement_timeout to bound this. Long-held locks are an anti-pattern — short transactions are always better than long ones.

Q: What if my application crashes while holding locks?

A: When the database connection drops, locks are released automatically as part of the implicit rollback. As long as your connection actually disconnects (TCP FIN, RST, or keepalive failure), the locks go away. The risk: a process hanging in a way that doesn't drop the connection — locks linger. Connection-level timeouts (TCP keepalive, server-side idle_in_transaction_session_timeout) bound this.

Q: Can I see what locks are currently held?

A: Yes. Postgres: SELECT * FROM pg_locks JOIN pg_stat_activity USING (pid);. MySQL: SHOW ENGINE INNODB STATUS; and information_schema.INNODB_TRX/INNODB_LOCKS. Essential for debugging "why is everything blocked?" mysteries.

Q: What's "lock-free" programming, and is that the same as optimistic locking?

A: Related but different. Lock-free programming uses CPU-level atomic instructions (CAS — compare-and-swap) to coordinate without OS-level locks. Optimistic locking is the database-level analog: check-and-update with version. Both share the philosophy of "act first, validate at commit." Lock-free is a CPU concept; optimistic locking is a database concept.

Q: How does this all interact with MVCC from Module 08?

A: MVCC handles reader-writer coordination via snapshots. Locks handle writer-writer coordination. They're complementary. A transaction that needs to ensure a row doesn't change during its work uses an explicit lock (FOR UPDATE) on top of MVCC's snapshot semantics. The senior framing: MVCC eliminates one class of contention; explicit locks handle the rest.

Three myths to dynamite

"Always use optimistic locking — no deadlocks!"

False. Optimistic doesn't deadlock, but it has retry storms under high contention. Both strategies fail under contention; they fail differently. The right choice depends on workload, not on aesthetic preference.

"SELECT takes a lock."

False (in modern MVCC databases, mostly). Plain SELECT in Postgres at default isolation takes no row locks — MVCC handles read consistency. SELECT FOR UPDATE/SHARE explicitly take locks. Don't conflate read consistency with locking.

"Deadlocks are bugs that must be eliminated."

False. Deadlocks are expected in any system with pessimistic locking and complex enough access patterns. The goal isn't zero deadlocks — it's deadlocks at a low rate the application can absorb via retry. A few per day is normal. A few per second means you have a real problem to fix.

Interview gotchas

Saying "always use optimistic locking, no deadlocks!" Optimistic doesn't deadlock but has retry storms. Both strategies fail under contention.

Forgetting that SELECT can take locks. Plain SELECT in Postgres at default doesn't, but SELECT ... FOR UPDATE/SHARE does, and DML (INSERT, UPDATE, DELETE) takes locks too. Some isolation levels in some engines also take implicit shared locks.

Not handling deadlock errors in code. Pessimistic locking + no retry logic = guaranteed production incidents. The senior reflex: any code path with FOR UPDATE must have deadlock retry handling.

Recommending VACUUM FULL or LOCK TABLE casually. Both are heavy hammers. Production answer: pg_repack, SKIP LOCKED, batched operations. Don't reach for the heavy options unless you really need them.

Not knowing about SKIP LOCKED. It's the canonical queue pattern. Mentioning it in any "build a queue" or "concurrent claim" conversation signals you've actually built systems.

Multiple diagnostic questions before action. Names the most common root cause (inconsistent lock acquisition order). Ranks fixes by cost. The senior reflex: investigate before rebuilding.

Suppose investigation shows the deadlocks are between two specific transactions that update the same set of rows in different orders. Walk me through the fix.

This is the textbook case for consistent lock acquisition order.

The problem: T1 and T2 both update accounts A and B in transfers. T1 happens to lock A first; T2 happens to lock B first. Eventually they meet — T1 holds A wanting B, T2 holds B wanting A. Cycle. Deadlock.

The fix: in every code path that locks both A and B, lock them in a deterministic order. The simplest:

BEGIN;
SELECT * FROM accounts WHERE id IN ($a_id, $b_id)
  ORDER BY id  -- canonical order
  FOR UPDATE;
-- ... do the transfer ...
COMMIT;

Now T1 and T2 both lock the lower-id account first, then the higher-id. They can't form a wait cycle. T1 might still wait for T2's first lock, but it's a queue, not a deadlock.

Verify by re-running the deadlock-producing scenario. If you can no longer trigger the deadlock, the fix is in.

The deeper habit: any time you find yourself acquiring locks on multiple rows in a transaction, think about whether other code paths might lock the same rows in different orders. If yes, impose a canonical order. This is one of those disciplines that becomes automatic once you've debugged a few deadlocks.

Other options if sorting isn't feasible (e.g., business logic determines order): - Use a single coordinator row that all conflicting transactions must lock first. Serializes them via that one row. - Move to optimistic locking for that specific code path. - Use advisory locks with a deterministic key.

Names the canonical fix (sort by ID), shows the SQL, and explains the verification step. The "deeper habit" framing is the senior pattern.

Switching topics — how would you build a job queue on top of a Postgres database?

First the obvious caveat: Postgres can serve as a queue, but for high-throughput workloads, purpose-built queues (SQS, RabbitMQ, Redis Streams, Kafka) are usually better. They have built-in retry, dead-letter, prioritization, and don't compete with OLTP for capacity.

But if the requirements fit Postgres — modest throughput, want transactional consistency with the rest of the system, want SQL access for monitoring — here's the pattern:

Schema:

CREATE TABLE jobs (
  id BIGSERIAL PRIMARY KEY,
  status TEXT NOT NULL DEFAULT 'pending',
  payload JSONB NOT NULL,
  attempts INT NOT NULL DEFAULT 0,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  started_at TIMESTAMPTZ,
  completed_at TIMESTAMPTZ,
  error TEXT
);

CREATE INDEX idx_jobs_status_created
  ON jobs(status, created_at)
  WHERE status IN ('pending', 'in_progress');

The partial index keeps it small — most rows are 'completed' and don't need to be indexed.

Claim pattern (the critical part):

BEGIN;
SELECT id, payload FROM jobs
  WHERE status = 'pending'
  ORDER BY created_at
  LIMIT 1
  FOR UPDATE SKIP LOCKED;
-- ... process the job in application code ...
UPDATE jobs SET status = 'completed', completed_at = NOW() WHERE id = $found_id;
COMMIT;

FOR UPDATE SKIP LOCKED is the magic. Without it, all workers contend for the same row. With it, each worker grabs a different available job. Both Postgres (≥9.5) and MySQL (≥8.0) support it.

Failure handling: - Wrap the processing in the application's error handler. On failure, increment attempts, schedule a retry (via separate row update), or move to dead letter (separate status). - Use a watchdog process to find rows stuck in 'in_progress' for too long (worker crashed mid-job) and reset them to 'pending' for retry.

Operational concerns: - Periodic cleanup of completed rows (delete or move to archive table). Otherwise the table grows unboundedly. - Monitor for hot-row contention if SKIP LOCKED isn't enough at very high worker counts (>100 concurrent workers). - If throughput exceeds ~1K-10K jobs/sec sustained, consider moving to a real queue.

The senior framing: this works well up to a point, then doesn't scale. Know the threshold and have a migration path before you hit it.

Pragmatic — acknowledges when Postgres isn't the right tool. Provides complete schema with rationale (partial index). The watchdog pattern, cleanup concerns, and scaling threshold show real production thinking.

Last one. A teammate proposes using LOCK TABLE for a particular operation that needs strong guarantees. What do you tell them?

First instinct: push back, but understand the goal first.

Step one — what's the actual requirement? "Strong guarantees" can mean many things: - "No other writes during this operation" → table lock could work, but maybe row-level locks on the affected rows are enough. - "Consistent snapshot for reading" → MVCC and snapshot isolation already give this without any locks. - "Atomic batch update" → standard transaction with row locks usually suffices. - "Bulk migration without interleaving writes" → maybe the only legitimate use of table lock.

Step two — explain the cost. LOCK TABLE in EXCLUSIVE mode blocks all other queries on that table — including reads if it's ACCESS EXCLUSIVE. For a hot table, this can cause an immediate user-visible outage. Even a few seconds of LOCK TABLE during business hours can spike error rates and timeout retries.

Step three — propose alternatives.

For "atomic update across many rows": just use a regular transaction. Row locks are taken automatically by UPDATE statements. Other transactions wait briefly for individual rows but the table stays available.

For "no concurrent writes during a complex operation": Serializable isolation level with retry logic. Lets the database catch conflicts without you taking a table lock.

For "bulk migration": batch into smaller transactions. Yes, individual rows might briefly be in mixed states between batches, but the application can usually tolerate this if writes are designed for it.

For "schema change": Postgres now has many ... CONCURRENTLY variants (CREATE INDEX, REINDEX, REFRESH MATERIALIZED VIEW) that avoid table locks. Use those.

Step four — when to actually use LOCK TABLE. Genuine use cases: - One-time data corrections during a maintenance window. - Very specific schema changes that don't have CONCURRENTLY equivalents. - Initial bulk loads into empty tables (no concurrent traffic anyway).

The framing: LOCK TABLE is the nuclear option. Reach for it when you've genuinely exhausted alternatives, with awareness of the operational cost.

Empathetic — understands the goal first. Provides multiple specific alternatives. Names the legitimate use cases without dismissing them. The "nuclear option" framing is the right mental model.

Cheat sheet

Locking — One Page

Pessimistic

Lock before work. SELECT FOR UPDATE. Wait + possible deadlock.

Use when: high contention, short critical sections, retries are expensive.

Optimistic

Read, work, check at commit. Version column. Retry on conflict, no deadlock.

Use when: low contention (<5% conflict), retries are cheap, want max throughput.

Pick by contention rate

  • Low (<5%): optimistic.
  • Medium (5-20%): measure both.
  • High (>20%): pessimistic.

Deadlock

Cycle in wait-for graph. DB picks a victim and aborts it. Application MUST handle and retry.

Prevent via: 1. Consistent lock acquisition order (sort by PK). 2. Shorter transactions. 3. Lower isolation when correct. 4. Single-row coordinator pattern. 5. Switch to optimistic locking.

Lock granularity

Row → page → table → predicate → advisory.

Postgres: row-level only, no escalation. Holds millions of locks happily. SQL Server: escalates row → table at ~5000 locks. Common cause of incidents. Mitigate by batching.

Postgres-specific patterns

  • SELECT FOR UPDATE SKIP LOCKED — the canonical queue pattern.
  • pg_advisory_lock(key) — application-defined locks, no row required.
  • SELECT FOR SHARE — shared read lock; others can read but not modify.
  • SET lock_timeout = '5s'; — bound how long you wait for a lock.

Senior anti-patterns to avoid

  • Long-held locks (long transactions).
  • Inconsistent lock order (creates deadlocks).
  • LOCK TABLE in production (use alternatives).
  • Forgetting deadlock retry logic with pessimistic locks.

The 30-second verbal answer

"Pessimistic locking takes locks before the work; optimistic locking validates at commit. Pick by contention rate — low contention means optimistic; high contention means pessimistic. Deadlocks are inherent to pessimistic locking; prevent them via consistent lock acquisition order. For queue patterns, SELECT FOR UPDATE SKIP LOCKED is the canonical Postgres/MySQL idiom — workers claim different rows concurrently without blocking."
