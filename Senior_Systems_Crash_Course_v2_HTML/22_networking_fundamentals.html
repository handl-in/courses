MODULE 22

Networking Fundamentals

TCP, connection pooling, TLS, HTTP/2 vs HTTP/3, gRPC, L4 vs L7 load balancers — the network layer that constrains everything above it

Your service is slow. App CPU is fine. Database is fine. Memory is fine. Latency is up. Where is the time going?

Half the time, the answer is the network — but most engineers have never opened the hood. TCP handshakes, TLS negotiations, connection pool exhaustion, head-of-line blocking, DNS lookups that took longer than the actual request. Senior engineers know what's happening underneath because that's where the non-obvious bottlenecks live. This is the chapter that turns "the network looks fine" into specific knowledge of every layer your bytes traverse.

Sam thinks "the network is fine"

Sam The new microservice we deployed is slow. p99 latency is 400ms. The actual handler runs in 5ms. CPU is fine. The database is fine. The downstream service we call has p99 of 30ms. Where's the rest of the 400ms going? The network is fine — I checked, packet loss is zero.

Maya "Network is fine" doesn't mean what you think it means. Zero packet loss is one network property. There are at least eight others that affect latency. Let me ask three questions.

One: does each request open a new TCP connection, or do you reuse connections?

Sam Uh... new connection each request, I think. We're using the default HTTP client.

Maya There's about 100ms gone. TCP handshake plus TLS handshake on every call across regions is 3-7 round trips. That's your bottleneck.

Two: are you doing DNS lookups before each connection, or caching?

Sam I... don't know. The default behavior, whatever that is.

Maya Most clients have a 30-second DNS TTL or worse — many ignore TTL entirely and re-resolve constantly. That's another 5-50ms per request, depending on resolver health.

Three: what HTTP protocol version are you using? And does your load balancer terminate at L4 or L7?

Sam HTTP/1.1. L7 ALB. I think.

Maya HTTP/1.1 means head-of-line blocking — one slow request blocks everything queued behind it on the same connection. L7 ALB means TLS terminates at the LB, then re-encrypts to the backend, doubling TLS handshake costs unless connection reuse is set up correctly.

The network is not fine. The network is your bottleneck. You just didn't measure the right network properties.

"The network is fine" is almost always wrong. Network bottlenecks hide in TCP handshakes, TLS handshakes, DNS lookups, head-of-line blocking, connection pool exhaustion, keep-alive misconfiguration, and load balancer behavior. Senior engineers know what each layer costs and when to look there.

The seven-layer mental model (without the OSI cargo cult)

The OSI model has seven layers. Most engineers can't recite them and shouldn't have to. What matters is a practical mental model of where time and bytes go in a network request.

The practical layers (request path top-to-bottom):

  1. Application — your code. HTTP request, gRPC call, etc.
  2. Encryption (TLS) — encrypts the application data. Adds handshake on first connection, ~negligible cost on subsequent.
  3. Application protocol (HTTP/1.1, HTTP/2, HTTP/3, gRPC) — frames the data into messages.
  4. Transport (TCP, QUIC, UDP) — reliable delivery (TCP/QUIC) or fire-and-forget (UDP). Handshakes, congestion control, retransmissions.
  5. Network (IP) — routes packets from source to destination across hops.
  6. Data link / physical — Ethernet, fiber, wireless. Mostly invisible to applications.

You'll spend 99% of debugging time at layers 1-4. Layers 5-6 mostly affect your infrastructure team, not your service.

Why this matters. When latency is high, ask: which layer is the time happening at? The DNS lookup before the request is layer 5-ish (resolver behavior). The TCP handshake is layer 4. The TLS handshake is layer 2 (in this practical model). The HTTP request itself is layer 1. Different fixes apply at different layers. Without distinguishing them, "the network" is a black box.

TCP: the protocol you depend on but rarely understand

Almost all internet traffic runs over TCP (HTTP/3 over QUIC is the exception). Understanding TCP's hidden costs is foundational to senior network reasoning.

The three-way handshake

Client                          Server
  │                               │
  │── SYN ──────────────────────►│   "I want to talk"
  │                               │
  │◄─── SYN-ACK ─────────────────│   "OK, I'm listening"
  │                               │
  │── ACK ──────────────────────►│   "Great, here we go"
  │                               │
  │═══ data flow begins ═════════│

  Total: 1 round trip (1 RTT) before data can flow

The TCP handshake costs 1 RTT. Same-region: 1-2ms. Cross-continent: 75-160ms. Every new connection pays this cost before sending a single byte of application data.

Worked example: connection cost amplification.

Your client is in Tokyo. Your server is in Virginia. RTT is 150ms.

A single request that opens a new TCP connection: 150ms (handshake) + ~150ms (request/response) = 300ms minimum.

Now add TLS (next section): 150ms (TCP handshake) + 300ms (TLS 1.2 handshake, 2 RTTs) + 150ms (request/response) = 600ms minimum.

If you reuse the connection for the next request: just 150ms (request/response). 75% reduction.

Lesson: connection reuse is not an optimization. It's the difference between a fast service and a slow one for cross-region traffic.

TCP slow start and congestion control

TCP doesn't send at full speed immediately. It starts small (typically 10 packets, ~14 KB) and doubles the send window each RTT until either packet loss occurs or the receiver's window is filled. This is "slow start." It exists to prevent congesting the network.

The slow start math.

Initial congestion window: 10 packets = ~14 KB. Each RTT, the window doubles: 14 KB → 28 KB → 56 KB → 112 KB → 224 KB...

For a 1 MB response with 50ms RTT: - RTT 1: 14 KB sent (986 KB to go) - RTT 2: 28 KB sent (958 KB to go) - RTT 3: 56 KB sent (902 KB to go) - RTT 4: 112 KB sent (790 KB to go) - RTT 5: 224 KB sent (566 KB to go) - RTT 6: 448 KB sent (118 KB to go) - RTT 7: 118 KB sent (done)

Total time: 7 × 50ms = 350ms to deliver 1 MB.

If the connection were already "warmed up" (large window from prior use), the same 1 MB might transfer in 1-2 RTTs (50-100ms). 3-7x faster.

This is the reason short-lived connections are inefficient — they never escape slow start.

Senior knowledge: BBR congestion control. Modern Linux kernels support BBR (Bottleneck Bandwidth and RTT), Google's congestion control algorithm, in addition to the legacy CUBIC algorithm. BBR is much better over high-latency, lossy paths (cross-region, mobile). Many teams enable BBR (net.ipv4.tcp_congestion_control=bbr) and see 10-30% throughput improvements on long-haul connections.

If asked about cross-region tuning in interviews, mention BBR. It's a senior signal that you've optimized real networks, not just configured them.

Keep-alive and connection reuse

The keep-alive concept. Instead of closing a TCP connection after each request, keep it open. Subsequent requests reuse the open connection, paying zero handshake cost.

Implementation: - HTTP/1.1: keep-alive is default. The Connection: keep-alive header explicitly enables it. Server may close after N requests or N seconds. - HTTP/2: connection multiplexing — one connection serves many concurrent requests. - HTTP/3 (QUIC): similar to HTTP/2, plus connection migration (survives IP changes).

Keep-alive misconfiguration is a top-5 production pitfall. Common mistakes:

  1. Server-side timeout shorter than client-side. Server closes the connection after 30s; client tries to reuse it after 31s; gets a "connection reset" error. Result: half of requests fail mysteriously.

  2. Client doesn't enable keep-alive. Many language defaults open new connections per request unless you explicitly configure a connection pool / persistent client.

  3. Pool too small. If your client pool has 10 connections and you make 100 concurrent requests, 90 wait for a free connection. Latency goes up; you never knew the pool was the bottleneck.

  4. Pool too big. Each connection consumes file descriptors and memory at both ends. A pool of 10,000 against a service with 32 file descriptors per process is broken.

The senior fix: set keep-alive aggressively (idle timeout 60-120s on both ends), size the pool to match your concurrency × worst-case-latency requirement (Little's Law again), and measure connection reuse rates as a metric.

Real keep-alive incident. A team had p99 latency of 200ms for an internal API, where the actual handler ran in 8ms. Investigation showed each request was opening a new TCP+TLS connection — costing ~150ms per call. The "fix" was a 5-line change to enable connection pooling in the HTTP client. Result: p99 dropped from 200ms to 12ms. That single configuration line saved more latency than weeks of code optimization would have.

Lesson: connection reuse settings are the first thing to check when an internal service has surprising latency. The cost of not reusing connections is enormous.

TLS: the encryption layer that costs more than you think

TLS (formerly SSL) is non-negotiable for production traffic. It's also a major performance cost if you don't understand its nuances.

The TLS 1.2 handshake (2 RTTs)

Client                          Server
  │                               │
  │── ClientHello ───────────────►│   protocol versions, cipher suites
  │                               │
  │◄─── ServerHello ─────────────│   chose cipher
  │◄─── Certificate ─────────────│   server's public cert
  │◄─── ServerHelloDone ─────────│
  │                               │
  │── ClientKeyExchange ─────────►│   premaster secret
  │── ChangeCipherSpec ──────────►│
  │── Finished ──────────────────►│
  │                               │
  │◄─── ChangeCipherSpec ────────│
  │◄─── Finished ────────────────│
  │                               │
  │═══ encrypted data flows ═════│

  Total: 2 RTTs before data flows (TLS 1.2)

TLS 1.2 handshake = 2 RTTs. Combined with TCP's 1 RTT handshake, opening a fresh HTTPS connection costs 3 RTTs before any application data flows. Cross-region (150ms RTT), that's 450ms — entirely overhead, no application progress yet.

TLS 1.3 (1 RTT, 0-RTT for repeat clients)

TLS 1.3, finalized in 2018, drastically simplifies the handshake.

TLS 1.3 improvements:

  1. 1 RTT handshake instead of 2 — the client speculatively sends key share data in the first message. Saves a full round trip.

  2. 0-RTT resumption. A client that's connected before can send application data in the first message using a pre-shared key from the previous session. Zero handshake delay for repeat connections.

  3. Mandatory forward secrecy. Even if the server's private key leaks later, past sessions can't be decrypted.

  4. Removed weak ciphers (RC4, 3DES, etc.). Smaller cipher suite reduces handshake size.

For TLS 1.3: - New connection: 1 RTT (TCP) + 1 RTT (TLS) = 2 RTTs, vs 3 with TLS 1.2. - Resumed connection: 1 RTT (TCP) + 0 RTT (TLS) = 1 RTT total. Application data in the first packet. - TCP Fast Open + TLS 1.3 0-RTT = sub-50ms internet roundtrips theoretically possible.

TLS 1.3 0-RTT comes with a caveat. Replay attacks: an attacker who captures the 0-RTT data can replay it later, since the server has no way to know it's a replay. Mitigation: only use 0-RTT for idempotent operations (GETs, not POSTs). The HTTP client/server need to handshake about which operations are 0-RTT-eligible.

Many production deployments disable 0-RTT specifically because of this trap. CloudFlare and Cloudflare Workers do extensive engineering to make 0-RTT safe. Most application teams should leave 0-RTT off unless they understand the implications.

TLS session resumption

Even before TLS 1.3, session resumption was the trick. Two main mechanisms:

  1. Session IDs (legacy). Server stores session state, client sends session ID, server resumes if it has the matching state. Requires server-side state, doesn't scale across load-balanced fleets.

  2. Session tickets. Server encrypts the session state and sends it to the client as a "ticket." Client sends the ticket back on reconnection, server decrypts and resumes. Stateless on the server — works across LB fleets if all servers share the ticket key.

Either mechanism reduces TLS 1.2 handshake from 2 RTTs to 1 RTT for repeat clients.

Session ticket key rotation. If all your servers in a load-balanced fleet need to decrypt the same tickets, they need to share a ticket key. That key needs to be rotated periodically (every 24-72 hours typically), and rotated consistently across all servers. Many teams do this badly:

  • Single server holding the keys, others can't decrypt.
  • Rotation that's not synchronized — half the fleet uses old key, half uses new.
  • Keys in source code or unrotated for years (security vulnerability).

The senior approach: a small managed service or shared secrets store distributing ticket keys, with clean rotation logic. Or: use a TLS-terminating LB (NGINX, Envoy, AWS NLB+ACM, AWS ALB) that handles all of this for you.

DNS: the lookup that's slower than you think

Every connection starts with "what IP do I connect to?" That's DNS. And DNS is one of the most under-monitored sources of latency.

The DNS lookup path

Application: "connect to api.example.com"
     │
     ▼
OS DNS cache (sub-ms if hit)
     │ (miss)
     ▼
OS resolver (/etc/resolv.conf)
     │
     ▼
Recursive resolver (e.g., 8.8.8.8, 1.1.1.1)
     │ (miss → recursive lookup)
     ▼
Root nameservers ──► .com nameservers ──► example.com NS
     │
     ▼
api.example.com → 203.0.113.1 (returned with TTL)
     │
     ▼
Cached at: recursive resolver, OS, application

A cold DNS lookup can take 20-200ms. Hot (cached): <1ms. The variance matters because DNS sits in the critical path before every connection — even if your app, network, and database are perfect, a slow DNS lookup adds latency invisibly.

Common DNS pitfalls

Pitfall 1: Java's DNS caching ignores TTLs.

The default JVM behavior caches DNS lookups forever (or until JVM restart) regardless of the record's TTL. This causes problems when: - A service IP changes (failover, scaling) — your JVM still calls the old IP. - A DNS-based load balancer rotates IPs — your JVM is stuck on one.

Fix: set networkaddress.cache.ttl to a sane value (60 seconds typically) in java.security. Or use -Dsun.net.inetaddr.ttl=60. This is a common production foot-gun — Java apps in cloud environments need this set explicitly.

Pitfall 2: HTTP clients that re-resolve DNS per request.

Some HTTP clients re-do DNS resolution for every request, even within a connection pool. Result: cached DNS at OS level helps, but you still pay 1-5ms per request for the cache lookup. With a high-RPS service, that adds up.

Fix: ensure your HTTP client caches resolved IPs at the connection-pool level, refreshing only on failure or TTL expiry. Most modern clients (Go's net/http, Python's httpx with proper config) do this; older or default clients often don't.

Pitfall 3: DNS is a single point of failure.

If your DNS provider has an outage, every new connection fails — even though "the network" is fine. The 2016 Dyn DDoS attack famously took down Twitter, Netflix, and others not because those services failed, but because DNS did.

Mitigation: multi-provider DNS. Run primary DNS at one provider (Route 53), secondary at another (Cloudflare or NS1). Most managed DNS services support this. Also: long-cached A records mitigate brief outages.

Senior monitoring move. Most teams don't graph DNS lookup time. Add it. Specifically: - DNS resolution time per call (p50, p99). - DNS error rate. - DNS TTL distribution (short TTLs = more lookups = more variance). - Resolver latency by resolver (1.1.1.1 vs 8.8.8.8 vs your private resolver).

When latency mysteriously increases, DNS is one of the first three things to check.

HTTP/1.1 vs HTTP/2 vs HTTP/3: pick the right protocol

The HTTP version you choose has major performance implications, especially for high-RPS services and high-RTT clients.

HTTP/1.1: head-of-line blocking

HTTP/1.1 sends one request at a time per TCP connection. Even with keep-alive (connection reuse), a slow request blocks all subsequent requests on the same connection — "head-of-line blocking" at the application layer.

Why HTTP/1.1 needs many connections.

Browsers typically open 6-8 parallel HTTP/1.1 connections per host to overcome head-of-line blocking. That means: - 6-8 TCP+TLS handshakes (high cost on first page load). - 6-8 separate slow-start curves. - 6-8 file descriptors per host.

Workarounds in HTTP/1.1: domain sharding (split assets across cdn1.example.com, cdn2.example.com, etc. to allow more parallel connections), pipelining (rarely supported in practice).

These workarounds were practical for years but became unnecessary with HTTP/2.

HTTP/2: multiplexing on a single connection

HTTP/2 multiplexes many concurrent requests on a single TCP connection. Requests are framed and interleaved at the protocol level. No per-connection slow-start cost; no domain sharding needed.

HTTP/2 features that matter:

  1. Multiplexing. N parallel "streams" on one TCP connection.
  2. Header compression (HPACK). Repeated headers are referenced by table position, not re-sent. Major savings for chatty APIs.
  3. Server push. Server proactively sends resources the client will need. (In practice, mostly deprecated — browsers stopped supporting it well.)
  4. Binary framing. More efficient than HTTP/1.1's text format.
  5. Stream prioritization. Client can hint which streams matter more.

For internal services and most public APIs, HTTP/2 is a clear win over HTTP/1.1.

HTTP/2 still has TCP-level head-of-line blocking. A single TCP packet loss blocks all multiplexed streams on that connection until the packet is recovered. So you've moved head-of-line blocking from the application layer to the transport layer — better than HTTP/1.1, but not solved.

This is what HTTP/3 fixes.

HTTP/3 (QUIC): no TCP, real multiplexing

HTTP/3 runs over QUIC, which runs over UDP. QUIC implements its own reliability, flow control, and congestion control — but does so per-stream rather than per-connection. A packet loss on one stream doesn't block other streams.

HTTP/3 (QUIC) advantages:

  1. No TCP head-of-line blocking — independent streams.
  2. Faster handshake — TLS and transport handshake combined into 1 RTT (or 0 RTT for repeat clients).
  3. Connection migration — TCP is tied to the source IP+port; QUIC connections survive client IP changes (mobile network roaming, Wi-Fi → cellular handoff). Critical for mobile applications.
  4. Modern crypto by default — QUIC requires TLS 1.3.

Cost: UDP is sometimes blocked or rate-limited by enterprise firewalls and middleboxes. QUIC packet inspection is harder. Server-side implementations are newer and have less battle testing than TCP.

Adoption status (as of 2025): - Public web: ~30% of sites support HTTP/3, including Cloudflare, Google, Facebook, Akamai. Browsers all support it. - Internal services: rare. Most teams use HTTP/2 internally. - Mobile: HTTP/3's connection migration is genuinely valuable; mobile-heavy apps benefit.

Senior recommendation: HTTP/3 at the edge (CDN, public API gateway) where mobile clients connect. HTTP/2 inside your data center. HTTP/1.1 only for legacy compatibility.

gRPC: HTTP/2 with structured framing

gRPC is widely used for internal service-to-service communication. Knowing what it is — and isn't — is senior table stakes.

What gRPC actually is:

  1. Transport: HTTP/2 (mandatory). Inherits multiplexing, header compression.
  2. Serialization: Protocol Buffers (protobuf) by default. Compact binary format. Schema-defined contracts.
  3. RPC patterns: unary (request-response), server streaming, client streaming, bidirectional streaming.
  4. Interface definition: .proto files generate client and server stubs in 10+ languages.

What gRPC is not: - A new transport protocol (it's HTTP/2). - A magic performance trick (HTTP/2 + protobuf is the magic, available without gRPC). - Browser-friendly (browsers can't make raw HTTP/2 calls — needs gRPC-Web or similar).

gRPC strengths - Strong typing (protobuf schemas). - Code generation across languages. - Bidirectional streaming. - HTTP/2 multiplexing inherits all benefits. - Smaller payloads than JSON (~30-60% smaller). - Built-in deadline propagation, cancellation, and metadata.

gRPC weaknesses - Binary format — hard to debug in browser dev tools. - Schema migration complexity (additive-only changes safe; removing fields is breaking). - Operational tooling (proxy, observability) is more limited than HTTP/JSON. - Browser support requires gRPC-Web shim. - Less mature in some languages than REST.

Senior framing: gRPC is the right default for internal service-to-service communication where both sides own the schema. JSON over HTTP/REST is the right default for external APIs and browser-facing endpoints. The two coexist comfortably — most modern microservice architectures have a "gRPC inside, REST outside" topology.

Load balancers: L4 vs L7

Senior interviewers love asking "what's the difference between an NLB and an ALB?" or "L4 vs L7 — which would you choose?" The distinction matters.

L4 (transport layer) load balancers

L4 load balancers route based on IP/port, treating traffic as opaque TCP/UDP streams. They don't understand HTTP, can't read URLs, and don't terminate TLS by default.

L4 strengths - High throughput (millions of connections/sec). - Low latency (sub-millisecond added). - Protocol-agnostic — works for HTTP, gRPC, MySQL, Redis, anything TCP/UDP. - Long-lived connections handled gracefully. - Cheaper than L7 typically.

L4 weaknesses - No content-based routing (can't route /api/users to one fleet, /api/orders to another). - Limited HTTP-aware features (no path-based routing, no header rewriting). - TLS termination requires a proxy in front. - Can't do HTTP-level health checks (only TCP-level).

L4 implementations: - AWS Network Load Balancer (NLB). - HAProxy in TCP mode. - IPVS / kube-proxy. - F5 BIG-IP (hardware appliance, classic data center). - Hardware load balancers in general.

L7 (application layer) load balancers

L7 load balancers understand the application protocol (typically HTTP). They can route based on URL, headers, cookies, body content. They typically terminate TLS, rewrite headers, and do content-aware decisions.

L7 strengths - Path-based routing (/api/users → user service, /api/orders → order service). - Header-based routing (canary deploys, A/B testing). - TLS termination at the LB (offloads from backends). - HTTP-aware health checks. - Request rewriting, retries, circuit breaking. - Authentication / rate limiting at the LB layer.

L7 weaknesses - Higher latency (~1-5ms added, often more with TLS termination). - Lower throughput per instance than L4. - Protocol-specific (an HTTP LB doesn't help a Redis backend). - More expensive to operate.

L7 implementations: - AWS Application Load Balancer (ALB). - NGINX (the dominant open-source L7). - Envoy (modern, programmable, used by Istio service mesh). - HAProxy in HTTP mode. - Traefik. - Cloudflare and similar CDNs (L7 by nature).

The classic mistake. A team deployed a high-performance gRPC service behind an AWS ALB (L7). Latency was 30ms p99 — fine. They scaled traffic 10x. Latency went to 200ms. The ALB became the bottleneck — at 100K RPS of long-lived gRPC streams, the ALB couldn't keep up.

Solution: switch to NLB (L4) for the gRPC service. ALB-style features weren't needed (gRPC handles routing internally). Latency dropped to 12ms; throughput became unbounded.

Lesson: L7 is the right default for HTTP/REST APIs. L4 is better for high-throughput, simple-routing, long-lived-connection workloads (gRPC, databases, raw TCP).

Senior framing. Use L7 when you need application-aware routing, TLS termination at the LB, or HTTP-specific features (path routing, retries, header manipulation). Use L4 when you need raw throughput, low latency, protocol-agnostic load balancing, or you're routing protocols that aren't HTTP.

Service meshes (Istio, Linkerd) typically deploy L7 sidecars (Envoy) per pod. The mesh provides L7 features at the edge of every service — not at a centralized LB. This is the modern pattern for microservices, replacing the centralized L7 LB with distributed L7 sidecars.

Connection pooling: the most-fixed network bug

If there's one network configuration that causes more incidents than any other, it's connection pooling. Every senior engineer has war stories.

What a connection pool actually does

A connection pool maintains a set of pre-established TCP+TLS connections to a remote service. Requests check out a connection, use it, and return it. New connections are created when the pool is empty and recycled when idle too long.

Pool parameters: - Pool size (max connections) — upper limit on concurrent connections. - Min idle / pre-warmed — connections kept open even when not in use. - Idle timeout — close connections idle longer than X seconds. - Max age — close connections older than Y, regardless of activity. - Connection timeout — give up waiting for a free connection after Z seconds.

Sizing the pool: Little's Law again

Pool size = arrival rate × average request duration. This is Little's Law applied to connection slots.

Worked example.

Your service makes 5,000 RPS to a downstream. Average request duration: 50ms (0.05s).

L = λ × W = 5000 × 0.05 = 250 concurrent connections needed on average.

For p99 of 500ms (10x average), peak concurrent might hit 250 × 10 = 2500. With safety margin: size pool to 500-1000 connections.

Now check the receiving side. If the downstream is one server with max_connections = 100, your pool of 500 is broken. Coordinate pool size with the receiving service's capacity.

The pool exhaustion cascade. Your pool size is 100. A downstream slows down — request duration goes from 50ms to 500ms. Concurrent demand becomes 5000 × 0.5 = 2500 — but you only have 100 slots. The other 2400 wait on the pool.

What happens to waiting requests? They sit in the pool's queue, eating thread time, blocking upstream of you. Now your service slows down because callers wait for connections. Upstream services time out. The slow downstream cascades up the entire request chain.

Mitigation: set pool wait timeout aggressively (e.g., 100-500ms). Better to fail fast than queue up. When the pool is exhausted, return an error to the caller — let them decide to retry, fall back, or fail. Senior engineers configure pool wait timeouts at every layer.

Real cascade. Service A → Service B → Service C. Service C slows down (10x latency). Service B's connection pool to C exhausts. Service B's threads block on the pool. Service B's pool to A exhausts (because B's threads are stuck). Now A is timing out on B. The slow C took down A and B.

Without pool wait timeouts, the cascade was inevitable. With aggressive wait timeouts (200ms), B fails fast on C, B returns errors to A, A's circuit breaker opens, A serves degraded responses. Same root cause, contained blast radius.

Three exercises

Exercise 1: The mysterious 200ms.

Your internal service-to-service call has p99 latency of 220ms. The downstream service reports its handler runs in 8ms. Network packet loss between the services is 0%. RTT between hosts (measured by ping) is 0.4ms. Where is the 220ms going? Walk through your investigation.

The numbers don't lie. 220ms ≠ 8ms (handler) + 0.4ms (RTT). The remaining 211ms is somewhere in the network stack. Where?

Senior debugging order:

  1. Connection lifecycle. Is the call opening a new TCP+TLS connection per request? Check the client config. If yes: TCP handshake (1 RTT = 0.4ms) + TLS handshake (2 RTTs for TLS 1.2 = 0.8ms). That's 1.2ms total, not 211ms. Probably not the cause.

  2. DNS resolution. Is DNS being resolved per request? Some clients re-resolve constantly. Add metrics. If DNS is taking 100-200ms (slow resolver, no caching), that's a possible cause — especially if the resolver is misconfigured or cross-AZ.

  3. HTTP version and head-of-line blocking. If HTTP/1.1, are concurrent requests queuing on a connection? With low RTT, the queueing time itself becomes the latency. Worth checking.

  4. Connection pool exhaustion. Most likely culprit. Pool size of 10, concurrent demand of 100, average duration 8ms — wait time accumulates. With 100 RPS and pool size 10, average pool wait might be 50-100ms; p99 wait might be 200ms+.

  5. TLS session resumption / handshake. If sessions aren't resuming and full TLS handshakes are happening, even on a 0.4ms RTT, kernel-side processing of the handshake could add ~30-100ms.

  6. L7 LB or service mesh sidecar. If traffic goes through a sidecar (Envoy/Istio), the sidecar adds 1-5ms. If misconfigured (e.g., synchronous TLS at sidecar with re-handshake), much more.

  7. Application-layer retries. Hidden retry logic that retries silently on first failure or timeout could add hundreds of ms.

Most likely root cause given the symptoms: connection pool exhaustion or DNS re-resolution. Both are "the network" but invisible to ping/packet-loss metrics.

Fix verification: add pool size and wait time metrics. Add DNS lookup latency metrics. The metric that's surprisingly high is your answer.

What this signals: systematic walk through every network-layer cost, prioritized by likelihood given the symptom shape (high latency, low RTT, low handler time).

Exercise 2: HTTP/1.1, HTTP/2, or HTTP/3 — which would you pick?

You're designing a new public-facing mobile API. Mobile clients in 100+ countries. Average payload 5-50 KB. Most users on cellular networks (variable RTT, occasional packet loss). Latency is critical (every 100ms costs measurable revenue). What protocol do you choose, and why?

The mobile and cellular signals point strongly in one direction.

Senior answer:

HTTP/3 (QUIC) for mobile clients to edge.

Why: 1. Connection migration. Mobile users frequently switch networks (cellular → Wi-Fi → cellular). HTTP/3 connections survive IP changes; HTTP/2 (over TCP) breaks on IP change, requiring full reconnect (+TCP+TLS handshake = 200-600ms penalty). For mobile, this is decisive.

  1. Better packet loss recovery. Cellular networks have non-trivial packet loss. QUIC's per-stream multiplexing means a single lost packet doesn't block other in-flight requests, which TCP would (TCP head-of-line blocking).

  2. Faster handshake. TLS 1.3 + QUIC = 1 RTT for new connections, 0 RTT for repeat. On a 200ms RTT mobile link, this is significant.

  3. Wide CDN support. Cloudflare, Fastly, Akamai, AWS CloudFront all support HTTP/3. Practical to deploy.

Practical architecture: - Mobile client → CDN edge over HTTP/3. - CDN edge → origin region over HTTP/2 (HTTP/3 to origins is less common; HTTP/2 is fine here because mobile-specific concerns don't apply). - Inside origin region → service-to-service over HTTP/2 + gRPC for internal calls; HTTP/2 + JSON for any public-facing fragments.

The fallback: clients that can't do HTTP/3 (some corporate networks block UDP) fall back to HTTP/2 over TCP. Modern HTTP libraries handle this transparently.

What I'd avoid: HTTP/1.1 anywhere in the modern stack. The 6-8 parallel connections × handshake-cost-per-connection is a worse experience for the latency-sensitive use case described.

What this signals: matched protocol to the use case (mobile + cellular + global = HTTP/3), gave a layered architecture (different protocols at different layers), addressed fallback compatibility.

Exercise 3: L4 or L7 for a Redis-backed service?

You're load-balancing traffic to a fleet of Redis instances. Each Redis instance handles a subset of keys (sharded by consistent hashing). The clients open long-lived connections (persistent TCP). Some clients send 100K commands/sec on a single connection. What kind of load balancer do you choose, and why? Are there alternatives to a load balancer entirely?

The question hints at the right answer. Long-lived connections, high throughput, non-HTTP protocol — all point one way. But "do you need an LB at all?" is a real consideration.

Senior answer:

Option 1: L4 load balancer (NLB or HAProxy in TCP mode).

Why L4 specifically: - Redis is not HTTP. L7 features (path routing, header rewriting) don't apply. - L4 handles long-lived connections gracefully — no per-request overhead. - L4 throughput is high enough (NLB handles millions of connections; HAProxy in TCP mode similarly). - TLS termination not needed for internal traffic (or done at the application layer).

Why L7 would be wrong: - L7 LBs are HTTP-aware; they don't usefully understand Redis protocol. - L7 LBs add 1-5ms+ latency per packet, which on 100K commands/sec connection is a measurable throughput hit. - L7 LBs typically don't handle 100K-RPS persistent connections as well as L4.

Option 2: No load balancer — client-side routing.

For sharded Redis, the better answer might be: clients know the shard map and connect directly to the right Redis instance. This is how Redis Cluster works natively — clients learn the cluster topology and route to the correct shard.

Strengths of client-side routing: - Zero LB overhead. - Client cache of cluster topology. - Direct path: client → Redis (no intermediate hop).

Weaknesses: - Clients need cluster awareness. - Topology changes (resharding) require client config update or learn-on-MOVED-redirect.

My recommendation: if using Redis Cluster, prefer client-side routing. If using a manually-sharded Redis, an L4 LB (NLB) is the right pick.

What this signals: chose L4 over L7 with specific reasoning (protocol-agnostic, long-lived connections, latency budget), then questioned the premise by suggesting client-side routing might eliminate the LB entirely. The "do you need this thing at all?" question is the staff-engineer signal.

No dumb questions

Q: Should I always use HTTP/2 between internal services?

For most cases, yes. HTTP/2's multiplexing eliminates the need for many connections, header compression saves bandwidth, and most modern HTTP libraries support it transparently. Exceptions: extremely simple internal services where HTTP/1.1 with keep-alive is sufficient, or specialized protocols (Redis, Kafka, gRPC's HTTP/2 via gRPC libraries).

Q: How do I check if my client is actually reusing connections?

Most HTTP clients expose pool metrics. Look for "connections opened per second" — if it equals your RPS, you're not reusing. Should be a tiny fraction (just enough to refresh expired connections). Also: netstat -an | grep ESTABLISHED | wc -l on the client tells you how many connections are open. With proper pooling, this should be small and stable.

Q: What's TCP_NODELAY (Nagle's algorithm)?

Nagle's algorithm batches small TCP writes to reduce packet overhead — but adds up to ~40ms of latency to small writes. For latency-sensitive applications (interactive APIs, gaming, real-time), set TCP_NODELAY=1 to disable it. For bulk-data applications, leave it on. Most modern HTTP libraries set TCP_NODELAY by default. Check your library if latency seems mysteriously bumpy.

Q: What's the difference between TCP keep-alive and HTTP keep-alive?

TCP keep-alive (kernel feature) probes idle connections to verify they're still alive — defaults to 2 hours, basically useless. HTTP keep-alive (application feature) reuses TCP connections for multiple HTTP requests. Different things. When people say "keep-alive" in HTTP context, they almost always mean HTTP keep-alive. TCP keep-alive is rarely tuned in modern systems; idle timeouts in load balancers handle it instead.

Q: When should I terminate TLS at the load balancer vs at the backend?

Terminate at LB (default): simpler certificate management (one place), offloads CPU from backends, allows L7 LB features. Terminate at backend (TLS passthrough): when end-to-end encryption is regulatory required, when backends need client cert info, or when the LB doesn't support your TLS feature (e.g., mTLS in some configurations). Most apps terminate at LB; regulated industries often passthrough.

Q: How does mutual TLS (mTLS) differ from regular TLS?

Regular TLS: server proves its identity to client (via certificate). mTLS: both sides authenticate via certificates. Used when both ends need to prove identity — common in internal microservices (zero-trust architecture), B2B integrations, IoT. Service meshes (Istio, Linkerd) make mTLS easy to apply across all internal traffic.

Q: What's the difference between a CDN and a reverse proxy?

A reverse proxy sits in front of your backend and forwards requests (NGINX, HAProxy, Envoy). A CDN is a globally distributed network of reverse proxies that cache static content close to users (Cloudflare, Fastly, Akamai). All CDNs are reverse proxies; not all reverse proxies are CDNs. Modern CDNs do both — caching plus L7 reverse proxy features (WAF, rate limiting, edge compute).

Q: How important is HTTP compression?

Significant. gzip or brotli compression typically reduces JSON/HTML/CSS/JS by 60-80%. For a 100 KB response, that's a 70-80 KB savings — multiple RTTs of slow-start avoided on a fresh connection. Always enable compression at LB or origin. Brotli is generally better than gzip for text. Don't compress already-compressed content (images, video, archives) — wastes CPU.

Three myths

MYTH: "TLS is too expensive — we'll skip it on internal traffic."

Modern CPUs have AES-NI hardware acceleration. TLS 1.3 with hardware support adds <5% CPU overhead and microseconds of latency. The "TLS is expensive" wisdom is from 2010. Skipping TLS internally is a security risk (lateral movement, eavesdropping in shared networks, no defense-in-depth) that buys you negligible performance. Senior teams use TLS everywhere.

MYTH: "More connections = more throughput."

Up to a point. Past the application's actual concurrency capacity, more connections add overhead without throughput gain. Each connection costs file descriptors, kernel memory, and TCP slow-start time. Pool sizes should match Little's Law expectations, not be arbitrarily large. A pool of 10,000 connections to a service that handles 1,000 concurrent is wasteful and may even be slower than a smaller pool due to context-switching overhead.

MYTH: "HTTP/2 fixes everything."

HTTP/2 fixes head-of-line blocking at the application layer. It doesn't fix TCP-level head-of-line blocking, doesn't help with connection migration on mobile (HTTP/3 does), doesn't help with bursty cellular networks (HTTP/3 helps more), and doesn't reduce TLS overhead. It's a major improvement over HTTP/1.1 but not a silver bullet. The right protocol depends on the use case.

Five gotchas

GOTCHA 1: TIME_WAIT exhaustion.

When a TCP connection closes, the OS holds it in TIME_WAIT state for ~60 seconds (default). On a busy server making many short-lived connections, you can run out of TIME_WAIT slots and start failing to open new connections. Symptoms: "Cannot assign requested address" errors. Fix: use connection pooling (so connections don't churn), enable net.ipv4.tcp_tw_reuse=1 (reuse TIME_WAIT slots for new connections), or scale horizontally. The deeper fix: stop opening so many short-lived connections.

GOTCHA 2: SYN flood / half-open connection limits.

Linux's TCP accept queue is bounded (net.core.somaxconn, default 128 in older kernels). Under heavy load or SYN flood attack, new connections get dropped silently. Tune somaxconn to 1024+ on busy servers, set net.ipv4.tcp_syncookies=1 for SYN flood protection. Critical for high-RPS services.

GOTCHA 3: MTU mismatch and packet fragmentation.

Standard Ethernet MTU is 1500 bytes. Cloud networks often use jumbo frames (9000 bytes) internally but standard MTU at boundaries. A misconfigured MTU somewhere in the path causes packet fragmentation (slow), or worse, packet drops if "DF" bit is set. Symptoms: works for small payloads, fails or slows dramatically for larger ones. Fix: ensure MTU consistency end-to-end, or set Path MTU Discovery to find the right size dynamically. Common in VPN and overlay-network environments.

GOTCHA 4: Asymmetric routing.

Outbound packets take one path; reply packets take a different path. Causes: multiple network interfaces, multi-homed hosts, BGP weirdness. Symptom: connections hang or fail intermittently. Stateful firewalls along the asymmetric path drop packets they didn't see the start of. Diagnostic: traceroute in both directions and compare. Fix: align routing, or configure firewalls to accept asymmetric traffic.

GOTCHA 5: Slow DNS lookups during high-load failures.

When many things start failing, every retry triggers a fresh DNS lookup (because the cache may have invalidated). Your already-stressed DNS resolver is now also under attack from your own service. Cascading failure: DNS resolver becomes slow → connections take seconds to even start → service appears completely down. Mitigation: aggressive DNS caching with longer TTLs at the OS level, redundant resolvers, and (importantly) a DNS lookup metric so you see this trend before it cascades.

Mock interview

Interviewer: "An engineer on your team says their service is slow because of 'network issues.' What questions do you ask them?"

You: "Six questions, in this order:

One: 'How do you know it's the network and not your application?' I want to confirm they've decomposed the latency. Did they look at distributed traces, or are they assuming based on dashboards?

Two: 'New connections per request, or are you reusing?' This catches the 80% case — connection pool misconfig is the #1 cause of 'mysteriously slow service-to-service calls.' If they don't know, that's the answer right there.

Three: 'What HTTP version, and is keep-alive enabled?' HTTP/1.1 with default settings is a different latency profile than HTTP/2 with proper pooling.

Four: 'How long does DNS resolution take?' Most teams don't measure this. I want to see the metric. If they don't have it, that's the next thing to add.

Five: 'Is TLS handshaking on every call?' Session resumption and connection reuse should mean handshakes are rare. If they're not, that's a config bug.

Six: 'Is there a sidecar, LB, or proxy in the path? What's its overhead?' Each hop adds latency; service mesh sidecars in particular can add several ms each direction. If they don't know what's in the path, we draw the diagram together.

The pattern I'm probing for: do they have visibility into the network layers, or are they treating 'network' as a black box? Senior engineers have visibility. Less-experienced engineers say 'network is slow' as a synonym for 'I don't know what's slow.'

After these six questions, I almost always know the root cause — or the missing metric needed to find it."

What makes this senior: structured probing rather than guessing, the "do they have visibility" framing as a meta-skill diagnostic, and the explicit acknowledgment that 'network is slow' is often shorthand for 'I haven't measured.' Interviewers love this kind of structured, mentorship-flavored answer.

Interviewer: "When would you NOT use HTTP/2?"

You: "Three real cases.

One: when your clients can't support it. Some legacy SDKs, embedded systems, or very old client libraries are HTTP/1.1-only. You don't deprecate working customers to chase a protocol upgrade.

Two: when middleboxes break it. Some corporate proxies, ancient WAFs, and intercepting firewalls don't handle HTTP/2 framing correctly. You see weird intermittent failures only from certain enterprises. The pragmatic choice: HTTP/1.1 fallback for those routes.

Three: when the workload doesn't benefit. A simple, low-RPS internal service making one request at a time per client doesn't gain much from HTTP/2's multiplexing. The single-connection optimization is real, but small. Operational simplicity might win.

I'd also flag a non-decision case: HTTP/2 with poor server implementation can be worse than HTTP/1.1 (head-of-line blocking at TCP, server-side stream concurrency limits hit, larger memory footprint). The library quality matters. nginx HTTP/2 is solid; some older application server implementations of HTTP/2 had real issues.

What I would not say: 'we don't need HTTP/2 because our service is fast already.' That's the wrong analysis — HTTP/2 is about scalability and concurrency improvements, not just speed of individual calls. A fast HTTP/1.1 service can become a slow one under concurrent load that HTTP/2 would handle gracefully."

What makes this senior: had clear, specific reasons against HTTP/2 (real engineering tradeoffs, not just preferences), distinguished good from bad reasons to skip it, and pushed back on a common bad reason. The "what I would not say" move is staff-engineer level — it's mentorship embedded in the answer.

Interviewer: "Walk me through what happens when a user types https://example.com in their browser, with all the network layers."

You: "Standard senior interview question. I'll trace the layers.

DNS resolution. Browser checks its cache first (~1ms hit, skip if hit). On miss: OS DNS cache. On miss: send query to configured DNS resolver. Resolver may have it cached. If not: recursive lookup — root nameservers, then .com nameservers, then example.com's authoritative nameserver. Returns IP with TTL. Total: 5-200ms uncached, sub-ms cached.

TCP handshake. Browser opens TCP socket to the IP, port 443. Three-way handshake: SYN, SYN-ACK, ACK. 1 RTT. Sub-ms locally, 75-150ms cross-region.

TLS handshake. ClientHello with TLS 1.3 support advertised. Server picks cipher, sends certificate. Client validates the cert chain (may itself require fetching intermediate certs — another lookup). Key exchange. 1 RTT for TLS 1.3 (or 0 RTT for repeat connections if 0-RTT enabled).

HTTP request. Browser sends GET / with HTTP/2 (or HTTP/3 if available). Server processes, returns the HTML. 1 RTT.

Resource fetching. Browser parses HTML, discovers CSS/JS/images. Opens additional streams on the existing HTTP/2 connection (no extra handshakes). Each resource: request → response, often in parallel.

Render. Once enough HTML and critical CSS arrive, browser starts rendering. JS may run, fetch more resources, manipulate DOM.

Connection lifecycle. Browser keeps the TCP+TLS connection alive for subsequent navigation to the same origin (typically 10s-60s idle).

Round-trip count for a fresh connection from a non-cached client: - DNS: 1 RTT (worst case) - TCP: 1 RTT - TLS 1.3: 1 RTT - HTTP request/response: 1 RTT - Total: 4 RTTs before content arrives.

For a cross-region 150ms RTT: 600ms base before any pixel renders. That's why CDN edge caching is critical — getting that handshake to a nearby edge POP cuts this to <100ms.

The senior optimization moves: DNS prefetching (<link rel='dns-prefetch'>), preconnect (<link rel='preconnect'>), TLS session resumption, HTTP/3 with 0-RTT. Each one knocks an RTT off the critical path."

What makes this senior: layered the answer with specific RTT counts, computed total user-facing latency, identified CDN edge caching as the architectural lever, and named specific browser optimizations. The "the optimization moves" wrap-up shows pattern-recognition about what's actually deployed in production.

Interviewer: "Your team is using HTTP/1.1 with keep-alive, pool size 50, between two services that talk constantly. The receiving service starts seeing connection-pool-exhausted errors. The sending team's response is 'increase the pool size.' What do you tell them?"

You: "Probably not increase the pool size. That's the symptom-treatment answer, not the root-cause answer.

First, I want to know: is the receiving service actually slower than expected? Pool exhaustion happens when connections are held longer than expected. Either the request rate spiked, or per-request duration increased. Increasing the pool only buys time if it's a temporary spike; if request duration is permanently up, you'll exhaust again at the new size.

Diagnostic questions: 1. What's the per-request duration trend? (RED method on the receiving service.) 2. What's the actual concurrent connection count vs the pool max? Are we hitting the limit briefly or sustained? 3. What does the receiving service's connection handling look like? Are its downstream calls slow, causing connections to be held longer? 4. Is this a noisy customer / hot key issue?

If the request duration is genuinely higher (e.g., due to a feature that legitimately takes longer), then yes, increase the pool — but also increase the receiving service's connection limit to match (don't just create demand it can't serve).

But there's a different question to ask: should you be using HTTP/1.1 here at all? With HTTP/2, one connection multiplexes many concurrent requests. Pool of 50 HTTP/1.1 connections becomes pool of 5-10 HTTP/2 connections, each handling much more concurrency. Less FD usage, less handshake overhead, less pool-exhaustion risk. For two services that 'talk constantly,' the upgrade to HTTP/2 (or HTTP/3 internally) is often the better fix.

The senior framing: 'increase the pool' is rarely the right primary answer to pool exhaustion. Look at why the pool is exhausting — duration change, rate change, downstream issue, protocol choice — and fix the root cause."

What makes this senior: rejected the proposed quick fix, asked the diagnostic questions to find root cause, identified that protocol upgrade (HTTP/1.1 → HTTP/2) might be the real fix, and explicitly named "symptom treatment vs root cause" framing. The willingness to push back on a teammate's suggestion is also a leadership signal.
