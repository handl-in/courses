MODULE 15

Partitioning & Consistent Hashing

How to split data across nodes when one machine isn't enough — and why naive hashing is a trap

Your single Postgres node has hit its limit. Writes are queueing. Disk is filling. Vertical scaling has run out of CPUs.

The answer is "shard the database" — split the data across multiple nodes. Sounds simple. By the end of this module you'll know exactly why every team that says "we'll just hash the user ID and split it into 4 shards" finds themselves in operational pain six months later.

Sam confronts horizontal scale

Sam OK so we've talked about read replicas — they help with reads but not writes. We've talked about denormalization and caches and materialized views. Now I'm looking at a write-heavy workload — 50K writes per second sustained — and our single Postgres is dying. What do I do?

Maya You've reached the boundary where horizontal scaling becomes the only option. Welcome to partitioning. It's also called sharding. Most engineers handwave through this in interviews — they say "shard the database" without explaining what that actually means. Today we make sure you can explain it.

Sam Just split the data into pieces, right? Each piece on a different machine?

Maya Right. The question is how you split. Pick wrong and you get hot partitions, expensive cross-shard queries, or operational hell when you try to add a node. There are three main approaches — range, hash, and consistent hash — and the choice has consequences for years.

Sam Why three? Just pick the best one.

Maya Each is best at something different. Range partitioning is great for time-series. Hash partitioning is great for write-balanced workloads with predictable shard counts. Consistent hashing is great when you'll need to add and remove nodes often. Pick the wrong one for your workload and you're either rebuilding it later or living with operational pain forever.

Sam And consistent hashing — that's the one with the famous "ring," right?

Maya That's the one. By the end of this module you'll be able to draw the ring, explain why it solves the rehashing problem, and know about virtual nodes — the trick that prevents the next failure mode after consistent hashing.

Partitioning splits data across nodes by some key. Range partitioning orders by key — great for time-series, vulnerable to hot ranges. Hash partitioning distributes by a hash — balanced, but rehashing on shard count change is catastrophic. Consistent hashing solves the rehashing problem with a ring topology and minimal data movement. Pick by workload, not by what's familiar.

Why partition at all

Replicas (Module 10) scale reads. Partitioning scales writes.

The wall every fast-growing system hits:

A single Postgres primary has hard limits — typically around 50K-100K writes/sec on premium hardware, 10K-30K on commodity. Beyond that: - Connection contention saturates the planner. - WAL fsync becomes the bottleneck. - Backup and maintenance windows get long. - Even "just add hardware" runs out — you can't buy a 1024-core single Postgres machine.

The only way to scale writes past one node is partition the data so different writes go to different nodes. That's sharding.

Replicas scale reads. Partitioning scales writes. There's no third axis.

The three partitioning strategies

Each makes a different trade-off.

Range partitioning

Data sorted by a key (often time). Each partition holds a contiguous range.

Used by: time-series databases, Postgres native partitioning by date, BigQuery date-partitioned tables.

Pro: range queries are efficient. "Last 7 days" hits one or two partitions.

Con: hot partition risk. New writes typically all go to the latest partition. Need a strategy to spread load.

Hash partitioning

Data distributed by hash(key) mod N. Each shard gets a roughly equal slice.

Used by: most relational sharded systems (Vitess, Citus), DynamoDB, Cassandra (under the hood).

Pro: writes spread evenly. No hot partition.

Con: range queries are expensive — must hit every shard. Rehashing on shard count change is catastrophic.

The third strategy — consistent hashing — is a refinement of hash partitioning that solves the rehashing problem. We'll cover it after we see why it's needed.

Real systems often combine. DynamoDB has a partition key (hashed) and a sort key (range within the partition). Cassandra has the same: partition key for distribution, clustering keys for ordering within a partition. You get hash-style distribution with range-style queries inside each partition. This is the dominant pattern in modern wide-column stores.

Range partitioning in depth

An events table partitioned by date:

CREATE TABLE events (
  id BIGSERIAL,
  user_id INT,
  event_type TEXT,
  created_at TIMESTAMPTZ
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2024_01 PARTITION OF events
  FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');
CREATE TABLE events_2024_02 PARTITION OF events
  FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');
-- ...etc

Reads narrow naturally:

SELECT * FROM events WHERE created_at > '2024-12-01';
-- Postgres only scans the relevant partition(s).

This is partition pruning — the planner reads only partitions that could contain matching rows. For time-bounded queries on time-partitioned tables, it's free performance.

The catch: all new writes go to the latest partition. If your write rate is 50K/sec, that one partition is doing all the work. The other partitions sit idle, holding old data.

Range partitioning has a built-in hot partition problem when keyed by time. Today's partition is hot; yesterday's is cold. The system isn't really distributing writes — it's distributing storage.

This is fine if your workload is read-heavy with bounded write rate. It's catastrophic if you need to scale write throughput. For write scaling, range partitioning by time is rarely the answer.

The exception: if writes are genuinely distributed across the range (uncommon for time, common for, say, range-partitioned-by-user-id with user IDs as random UUIDs).

Where range partitioning shines:

  • Time-series workloads (logs, events, metrics) where queries are typically "last N days" and old data ages out.
  • Easy archival: drop old partitions instantly via DROP TABLE events_2023_01; — no DELETE needed, no vacuum churn.
  • Big tables that benefit from per-partition statistics (the planner has more accurate info).
  • ETL pipelines that load historical data in bulk into specific partitions.

For these workloads, range partitioning is a win even at moderate scales. Used widely in Postgres, BigQuery, Snowflake, ClickHouse, TimescaleDB.

Hash partitioning in depth

A users table sharded by hash:

You have N=4 shards. Decide each user's shard via:

shard = hash(user_id) mod N
shard = hash(user_id) mod 4

User 42: hash → 5,193,847,201 → mod 4 = 1. User 42 lives on shard 1. User 99: hash → 9,712,556,033 → mod 4 = 1. Also shard 1. User 100: hash → 4,029,113,887 → mod 4 = 3. Shard 3.

Writes for any user always land on the same shard. Reads for a user always come from the same shard. No coordination needed.

The hash function (e.g., SHA-256 truncated, MurmurHash) is uniform — over millions of users, each shard gets roughly N/4 of the load.

Hash partitioning gives you write-balanced distribution. Same key → same shard, deterministically. No central coordinator needed. Each shard operates independently.

The rehashing catastrophe

Now suppose you need to add a 5th shard. Traffic has grown.

The naive rehash:

Before: shard = hash(user_id) mod 4
After:  shard = hash(user_id) mod 5

User 42's hash is 5,193,847,201. - Mod 4: shard 1. - Mod 5: shard 1.

User 99's hash is 9,712,556,033. - Mod 4: shard 1. - Mod 5: shard 3.

User 100's hash is 4,029,113,887. - Mod 4: shard 3. - Mod 5: shard 2.

Most users now belong on a different shard than before. Roughly N-1/N of the data has to move (about 80% for N=5). For a system with TBs of data, that's a multi-week rebalancing operation, during which:

  • Some users are on the old shard, some on the new.
  • Reads must check both possibilities.
  • Writes must coordinate which shard "wins."
  • The cluster is in a degraded state for the whole window.

Naive hash partitioning gets you trapped at your initial shard count. Every rehash event is a major operation. Most teams that pick hash mod N end up living with whatever N they started with — which is often wrong as the system grows.

The most common workaround in production: never rehash. Add capacity by replacing nodes with more powerful ones (vertical scale per shard) or accepting that you can't easily change shard count. Ugly.

Consistent hashing: the elegant fix

Consistent hashing solves the rehashing problem. Instead of hash mod N, it places nodes and keys on a ring of hash values.

Consistent hashing: imagine the hash space as a ring (0 to 2^64). Place each node at a position on the ring (typically by hashing the node's identifier). Place each key on the ring (by hashing the key). Each key belongs to the first node clockwise from its position.

When a node is added or removed, only the keys that were assigned to that node's neighborhood need to move. On average, 1/N of the data moves, not N-1/N.

                      THE CONSISTENT HASHING RING

                               0
                          ●Node A
                              │
                      ╱──────────────╲
                   ╱                    ╲
                ╱                          ╲
              ╱             ●k1               ╲
            ╱                                    ╲
          ╱            ●k2                         ╲
         │                                            │
         │                                            │

●Node D ──┤ ├── ●Node B │ │ │ ●k3 │ ╲ ╱ ╲ ╱ ╲ ●k4 ╱ ╲ ╱ ╲ ╱ ╲──────────────╱ │ ●Node C 2^64

Each key (●k) is placed on the ring by hashing its value. Each key belongs to the FIRST NODE CLOCKWISE from its position.

k1 → Node B k2 → Node B k3 → Node C k4 → Node D

Adding a node:

A new node E is added. Its position is determined by hash("Node E").

Suppose E lands between Node A and Node B on the ring.

Only the keys that were assigned to Node B and now fall between A and E move to E. Other keys are unaffected.

Average data moved: 1/N (where N is now the new node count). For a 4-node cluster becoming 5, ~20% moves — but only the chunk between A and E, not all keys.

The reverse: removing a node.

If Node B fails or is decommissioned, the keys assigned to Node B all shift to the next node clockwise — Node C. Only Node B's keys move; the rest of the cluster is unaffected.

This means in a healthy cluster, adding or removing a node disrupts only ~1/N of the data, not most of it.

Consistent hashing turns "rehashing is catastrophic" into "rehashing is bounded." The first fundamental win of distributed system design.

The hidden problem with naive consistent hashing

Pure consistent hashing as described has a subtle flaw: node placement on the ring is uneven.

The skew problem.

Hash("Node A") might land at position 100. Hash("Node B") might land at position 1,000,000. Hash("Node C") might land at position 1,500,000. Hash("Node D") might land at position 50,000.

Now look at the gaps. Node A→B has a gap of ~1,000,000 (lots of keys land here). Node B→C has 500,000. Node C→D wraps around with a giant gap.

Some nodes get far more load than others. A few nodes might handle 50% of all keys; others handle 5%. The cluster is unbalanced.

This isn't a bug in the algorithm — it's a property of placing N points uniformly randomly. With small N (say 10 nodes), the variance is significant.

Naive consistent hashing has high variance in load distribution when N is small. The fix: virtual nodes (vnodes).

Virtual nodes: the production fix

Each physical node is represented by many points on the ring.

With vnodes:

For each physical node, create N virtual representations (typically 100-1000).

Each vnode is placed on the ring at a different hash position.

Each key still goes to the first vnode clockwise. The vnode tells you which physical node owns it.

Now load is averaged across many points per node. Variance is much lower.

              RING WITH VIRTUAL NODES (simplified)

Each physical node has many vnodes scattered around the ring.

       ●A ●C ●A ●B ●A
    ●D                ●B
   ●A                  ●C
  ●B    Many small     ●A
  ●A     "slices"      ●D
   ●C                  ●B
    ●A                ●C
       ●D ●A ●B ●C ●A

Each physical node has, say, 256 vnodes spread around the ring. Load is averaged across many positions per node. Adding or removing a physical node = adding/removing all its vnodes.

The data movement is more evenly spread across remaining nodes, not concentrated on one neighbor.

Vnodes are the production reality of consistent hashing.

Cassandra: 256 vnodes per physical node by default (num_tokens = 256). DynamoDB: thousands of partitions; physical nodes own many. Riak: similar model.

Pure consistent hashing is theoretical. Real systems always use vnodes. Mention vnodes when discussing consistent hashing in interviews — it signals you've moved past the textbook description.

The vnode advantage on node addition:

In naive consistent hashing, adding a node means it takes over the keys from one neighbor. That one neighbor loses 1/N of its data; the new node takes that exact chunk.

With vnodes, the new node has 256 positions scattered around the ring. Each position takes a small chunk from a different existing node. The result: data moves from many nodes to the new one, in parallel. The migration time is proportionally shorter, and no single node bears the bulk of the rebalancing load.

This makes scaling out much smoother — adding capacity is a gradual change, not a sudden burden on one neighbor.

Choosing a partition key

The choice of partition key is one of the most consequential decisions in a sharded system. Senior engineers know what to look for.

The criteria:

High cardinality. The key should have many distinct values. country (200 values) is a bad partition key for global data. user_id (millions) is good.

Even distribution. The values should be roughly uniformly distributed. If 10% of users are "power users" who generate 90% of the events, sharding by user_id will create hot shards.

Query alignment. Most queries should be answerable from a single partition. If you shard by user_id but most queries are WHERE post_id = ?, every query becomes a fan-out across shards. Bad.

Stability. The key shouldn't change over time. A row's partition key should be set at creation and never updated. Changing it means the row physically moves between shards.

A bad partition key example:

A multi-tenant SaaS app shards by tenant_id. There are 10,000 tenants, but the top 5 tenants generate 80% of traffic. 5 shards are saturated; the others are idle.

Possible fixes: - Composite key: shard by (tenant_id, hash(record_id)). Within a hot tenant, records spread across multiple shards. - Heavy tenant isolation: large tenants get their own dedicated shards (manual override of the hashing). - Tenant splitting at high scale: above a threshold, a tenant is internally further subdivided.

The senior detail: partition strategy must match traffic distribution, not just data distribution. Look at your top-10 keys before sharding.

The "partition by primary key" trap. Sharding by id works only if writes are uniformly distributed across IDs. If you use sequential IDs (BIGSERIAL), the latest IDs go to the latest shard — same hot partition problem as range partitioning. Use UUIDs (or hashed sequential IDs) when possible to spread writes naturally.

Range vs hash: the deeper trade-off

Range partitioning

Wins on: range queries (last N days), batch processing, easy archival.

Loses on: write hot spots (latest range gets all writes), uneven load if data is skewed.

Best for: time-series, log data, append-mostly workloads.

Hash partitioning

Wins on: even write distribution, predictable load.

Loses on: range queries (must scan all shards), rehashing on shard count change.

Best for: user-keyed OLTP, key-value lookups, write-heavy workloads.

The combination pattern: hash to choose a partition (write distribution), range within a partition (query efficiency).

DynamoDB's partition key + sort key: (user_id, timestamp). Hash by user_id distributes writes; sort by timestamp lets you query "user X's last 100 events" efficiently within their partition.

Cassandra: same model. PARTITION KEY (user_id), CLUSTERING KEY (event_time).

This combination is the modern default for write-heavy systems with range queries within an entity. Mention it when designing a sharded schema.

Three more ways to think about partitioning

Way 1: postal sorting.

Range partitioning is sorting mail by ZIP code into adjacent bins. ZIPs starting with 9 go in one bin; 0 goes in another. Easy to find Chicago mail (60xxx → second-to-last bin), but if everyone's writing to California (9xxxx), one bin overflows.

Hash partitioning is sorting mail by the hash of the recipient's name. Each person's mail consistently goes to the same bin, and bins are roughly equal sizes. Finding "the Smiths' mail" is fast (one bin), but "all California mail" requires checking every bin.

Consistent hashing is hash partitioning where the bins are arranged around a circular conveyor belt. When you add a new bin, only the mail in that bin's local section needs to move — everything else stays where it was.

Way 2: a library with multiple branches.

Range partitioning: each branch has books in alphabetical range. Branch 1 has A-F; Branch 2 has G-M; etc. Browsing books by topic is annoying (must visit multiple branches), but finding "Books by King" is one branch.

Hash partitioning: each branch has a roughly random subset based on a hash of the book's ISBN. Browsing all the King books is annoying (visit every branch), but the load on each branch is balanced. Adding a branch means redistributing huge chunks of books — operationally painful.

Consistent hashing: each branch claims a position on a circular reading-list. New branches take over local sections without disrupting the rest.

Way 3: parking lots in a city.

Range parking: lot A is for cars from blocks 1-5, lot B for 6-10. Most cars park near home; you know where to find each car. But if everyone's working downtown today, one lot fills up.

Hash parking: each driver always uses lot N (based on their license plate hash). Lots are evenly used. Finding your car is reliable. But if a new lot opens, every driver's "their lot" suddenly changes — chaos for a week.

Consistent hash parking: lots are arranged in a circle. Each driver parks in the first lot clockwise from their license plate's position. New lots only steal drivers from their immediate neighbors. Drivers far from the new lot don't change behavior.

Sharpen your pencil

Exercise 1. A team has a 4-shard Postgres cluster sharded by hash(user_id) mod 4. They're at write capacity. They want to grow to 6 shards. What's the operational reality, and what should they do?

The operational reality is grim.

Going from hash(user_id) mod 4 to hash(user_id) mod 6 changes the shard for most users — roughly 5/6 of the data has to move. For a busy production database, that's a multi-day or multi-week migration during which: - Reads must check both old and new shard locations. - Writes must coordinate to avoid splits. - Replication is in flux. - Rollback is hard.

The plan would have to look like:

Option A: Accept the operational pain. Set up dual-writes. Backfill in batches. Cut over reads gradually. Plan for 2-4 weeks of degraded operations. Engage the on-call team for the duration.

Option B: Move to consistent hashing now. Replace the modulus-based scheme with a vnode-based ring. The new scheme is N-agnostic — adding the 5th and 6th shards moves only ~1/5 and ~1/6 of the data respectively, and only from existing nodes. Future shard additions become routine instead of catastrophic.

The migration to consistent hashing is itself a one-time pain — but it's a one-time pain that pays off forever.

Option C: Don't rehash; vertical scale per shard. Buy beefier hardware for each of the 4 shards. Trade money for avoiding the migration. Sometimes the right call if growth is bounded.

Option D: Use a sharding-aware database. Replace the manual sharding with Vitess or Citus, which handle resharding (or its avoidance) natively. Bigger lift but solves the problem fundamentally.

The senior framing: the cost of the wrong sharding scheme compounds. If you're going to grow indefinitely, build for consistent hashing from the start. If you're locked in, weigh "one painful migration to consistent hashing" against "permanent struggle with mod-N."

Exercise 2. A multi-tenant SaaS application is considering sharding by tenant_id. They have 10,000 tenants, but the top 100 generate 80% of traffic. What concerns would you raise and how would you fix them?

The concern: hot shards.

If you shard by tenant_id with N=10 shards, hash will distribute the 10,000 tenants roughly 1,000 per shard. But the top 100 tenants — generating 80% of traffic — could land predominantly on a few shards. Some shards melt; others idle.

Multiple fixes, depending on how aggressive the skew:

Fix 1 (mild skew): composite partition key. Shard by hash(tenant_id, record_id). Within a hot tenant, records spread across multiple shards. The tenant is no longer "all on one shard" — they're amortized across the cluster.

The trade-off: queries scoped to a single tenant ("get all records for tenant X") now fan out across multiple shards. Acceptable if tenant-scoped queries can use efficient parallel fan-out.

Fix 2 (heavy skew): tier the tenants. - Standard tenants: hashed to a shared cluster. - Power tenants (above some traffic threshold): get dedicated shards.

This requires routing logic in the application: "is this a power tenant?" → route to dedicated. Otherwise → hash. Operational complexity, but matches reality.

Fix 3 (extreme skew): isolate per tenant. The biggest tenants get their own database entirely. Sometimes called cell-based architecture. Each tenant is on its own infrastructure. Maximum isolation; maximum operational cost. Used by Salesforce, AWS internal services, big SaaS providers.

Senior heuristic for picking: - Skew under 5x → composite key, problem solved. - Skew 5-50x → consider tiering. - Skew above 50x → isolation. The largest tenants behave like their own product.

The framing: partition strategy must match traffic distribution, not just data distribution. Always look at the top 1% of keys before deciding on a partitioning scheme.

Exercise 3. Explain to non-technical Sam, in two sentences, why "consistent hashing" is so much better than hash mod N.

With hash mod N, the shard a piece of data lives on depends on N — so changing N (adding or removing a server) changes where most data lives, requiring you to move most of the data across the cluster. Consistent hashing places servers on a circular ring such that adding a server only steals data from its immediate neighbors on the ring, so only about 1/N of the data has to move when you add or remove a node — making cluster scaling routine instead of catastrophic.

There are no dumb questions

Q: What's the difference between partitioning, sharding, and replication?

A: Partitioning/sharding = splitting data across nodes (different rows on different machines). Replication = copying the same data across nodes (same rows on multiple machines). They're complementary — production systems usually do both. Each shard has multiple replicas; the shards together hold the full dataset.

Q: How do I do JOINs across shards?

A: With great pain. Cross-shard joins typically require: (1) fetching data from one side and looking up matching rows on each shard, or (2) co-locating related data on the same shard via a partition key strategy (e.g., shard orders by user_id same as the user table — joins between them are local). The senior pattern: design schemas to keep related data on the same shard so most queries are single-shard.

Q: What's the difference between Vitess and Citus?

A: Both are sharding solutions for relational databases. Vitess is for MySQL — open-sourced from YouTube, handles sharding, replication, and connection pooling at scale. Citus is for Postgres — adds distributed tables, parallel queries, and reference tables. Both let you write mostly normal SQL while the underlying engine handles sharding logic. Cloud-managed equivalents: Aurora, AlloyDB, Cosmos DB.

Q: Can I shard a database without dedicated tooling?

A: Yes — at the application layer. Application code computes which shard a query goes to, opens connections to multiple databases, routes accordingly. Many large companies build this themselves rather than adopt Vitess/Citus. Operational reality: it works but every query path needs sharding awareness. When most queries follow simple patterns (single-key lookup), it's manageable. When queries are diverse, the application code becomes complex fast.

Q: What's "rendezvous hashing" and is it different from consistent hashing?

A: A different algorithm that solves the same problem. For each key, you compute a hash for every node and pick the highest. Adding a node means re-computing for each key but each key still belongs to one consistent node. Simpler implementation, comparable performance. Used in some load balancers and CDNs. Mention it as awareness; consistent hashing with vnodes is more common.

Q: How does Cassandra handle "skinny rows" vs "wide rows"?

A: Cassandra's data model is wide-row by design. A row's partition key determines which node it lives on; clustering keys define the order of "wide row" entries. A user with 10,000 events all live on the same node, sorted by event time. You design schemas to make common queries fit one row. Wide-row design is essential for Cassandra performance.

Q: What about "directory-based" partitioning?

A: A central service (the "directory") maps keys to shards. The application asks the directory for a key's location, then queries that shard. Used historically for cases where neither hashing nor range fits well, but modern systems prefer algorithmic placement. Directory becomes a single point of failure unless replicated. Some systems still use it for "where is this user's data" lookups (e.g., legacy migrations from monolith to sharded).

Q: How does Postgres handle partitioning?

A: Postgres has declarative partitioning (range, list, or hash) within a single database — not across nodes. Each partition is a separate table; the planner routes queries appropriately. For sharding across machines, you need an external tool: Citus, pgbouncer with sharding logic, or application-level routing. Postgres's native partitioning is great for organization within one node, not for horizontal scale.

Three myths to dynamite

"Sharding is just splitting data."

Misleading. Sharding is splitting data plus deciding how the application routes queries, plus designing schemas to minimize cross-shard operations, plus operating multiple synchronized clusters. The "splitting" is 10% of the work.

"Consistent hashing is always better than mod-N."

Half-true. Consistent hashing is better when you'll add or remove nodes. If your shard count is genuinely fixed (small system, no growth plans), hash mod N is simpler and operationally fine. Consistent hashing has a complexity cost — vnodes, ring management, lookup logic. Use it where the rebalancing benefit applies.

"More shards means more performance."

False past a point. Each shard adds operational complexity, cross-shard query coordination, and per-shard backup/maintenance. At some point, more shards means worse performance because of coordination overhead. The right shard count is enough to handle peak load with headroom — not maximum possible.

Interview gotchas

Saying "we'll just shard by user_id" without considering the skew (power users vs typical users), query patterns (most queries fit one shard?), and the partition key's stability (does it change?).

Forgetting that range queries are expensive on hash-partitioned data. Hash partitioning + a query like "all events from last hour" = scan every shard. If range queries are common, hash isn't the right strategy.

Treating consistent hashing as just "a hash function with a ring." The production reality is vnodes — many positions per physical node — for load balancing. Pure consistent hashing has high variance with small N.

Recommending mod-N hashing for a system that will grow. Every team that picks this regrets it within 18 months. Plan for consistent hashing or external sharding tools.

Not knowing that Postgres native partitioning isn't sharding. Postgres's PARTITION BY divides one table on one node. For multi-node sharding, you need Citus, Vitess (MySQL), or application-level logic.

Mock interview

We're designing a system that needs to handle 100K writes/sec sustained. A single Postgres node can't keep up. Walk me through the design.

At 100K writes/sec sustained, single-node Postgres is not the answer. Sharding is required. Let me work through the design choices.

Step 1: clarify the workload.

What's the access pattern? "100K writes/sec" tells me write rate but not shape: - All writes for distinct entities (users posting events)? Hash sharding by entity is the answer. - Mostly time-series append (logs, metrics)? Range partitioning by time, possibly with hashing within. - Heavy reads alongside writes? Need to factor in read replicas per shard. - Cross-entity queries common? Cross-shard query overhead matters.

I'll assume the common case: each write belongs to a user/entity, and most reads scope to that entity.

Step 2: pick the partition key.

If user_id is the natural entity: - High cardinality (millions of users)? ✓ - Even distribution? Need to verify — check the top 1% of users for skew. - Query alignment? Most queries should be WHERE user_id = ?. - Stable? Yes (assigned at user creation).

Good candidate. But if there's skew (top tenants generating 80% of writes), I'd consider composite keys.

Step 3: choose the partitioning strategy.

For 100K/sec write-heavy, I'd lean toward consistent hashing with vnodes. Reasons: - Even write distribution (no hot range). - Future-proof — adding shards as growth continues is routine, not catastrophic. - Vnodes prevent variance-based imbalance.

Trade-off: range queries across the entire dataset hit every shard. If the workload includes "show me all events from yesterday," that's a fan-out. We'd need to decide if that's worth optimizing — possibly via a separate analytical store fed by CDC.

Step 4: pick the technology.

Three real options: - Citus on Postgres: distributed Postgres, sharding-aware. Familiar SQL, great for OLTP. Open source. - Vitess on MySQL: similar but for MySQL. Battle-tested at YouTube/Square scale. - Cassandra/ScyllaDB: built for this from day one. Better at write throughput, less SQL-friendly. - CockroachDB / TiDB: distributed SQL with consensus per range. Higher write latency than the above but stronger consistency.

For 100K writes/sec with structured queries, I'd lean Citus or CockroachDB depending on consistency requirements. If we can tolerate eventual consistency on cross-shard transactions, Citus. If we need strong consistency across shards, CockroachDB.

Step 5: plan for replication and HA per shard.

Each shard needs at least 2 replicas for HA. With 10 shards and 3 replicas each, that's 30 nodes. Operational reality: you're running a fleet now, not a database.

Step 6: design for observability.

  • Per-shard metrics: write rate, latency, replication lag.
  • Hotspot detection: alert on any shard taking 2x the average load.
  • Resharding tooling: how do we add a shard if usage exceeds capacity?

The senior framing: sharding is a 6-month commitment, not a deploy. The design conversation today determines what the team operates for years. Choose architecture that supports growth from the start — composite keys for skew, consistent hashing for elastic scale, and a sharding-aware database to manage the complexity.

Six-step structured walkthrough. Names specific technologies with trade-offs. The "operational reality" framing for 30-node fleet acknowledges the human cost. The "6-month commitment not a deploy" closing is the senior reflex.

The team chose Citus and is sharded by user_id. After 6 months, one shard is consistently at 90% CPU while others sit at 30%. What's happening, and what do you do?

Classic hotspot. Diagnosis first.

Step 1: identify which shard.

Postgres metrics per shard reveal the offender. Look at: - Top queries on the hot shard via pg_stat_statements. - Top users by query count or write rate on the hot shard. - I/O patterns (is one user dominating writes?).

Step 2: identify the cause.

Two possibilities:

Cause A: skewed user activity. A few users generate the bulk of traffic. They happen to land on this shard via the hash. The shard has 1/N of users but more than 1/N of activity. Common with multi-tenant SaaS — top tenants dominate.

Cause B: data growth on specific users. A few users have grown to enormous data sizes. Even moderate activity on a 100GB user's data is heavy. Per-row work is the same; per-user volume is the issue.

Step 3: pick a fix based on the cause.

For Cause A (skewed activity):

  • Composite key sharding: switch from hash(user_id) to hash(user_id, record_id) so a single user's records spread across multiple shards. Solves the dominance problem at the cost of cross-shard queries for that user. Citus supports this with manual partitioning logic.
  • Tenant tier system: identify the top users; route them to dedicated shards manually. Keeps hashing for typical users; isolates the heavy ones.
  • Cell architecture: at extreme scale, top users get their own database entirely. Salesforce/AWS internal pattern.

For Cause B (data growth):

  • Vertical scaling on the hot shard: bump its CPU/memory specifically. Quick fix; buys time.
  • Cold-data archival: move historical data for the heavy users to a separate analytical store. Reduces working-set size for the OLTP shard.
  • Time-based partitioning within the shard: partition each user's data by time so old data can be physically separated.

Step 4: long-term planning.

Once the immediate hotspot is solved, ask: will this happen again? Build observability and sharding flexibility: - Hot-shard alerts based on CPU and I/O ratios across shards. - Tooling to move users between shards (manual or automated). - Document the heavy users; track them as a special class.

The senior framing: hot shards are a sign of mismatched partition strategy, not a sign of bad luck. Either the partition key is too coarse (one user dominates) or the data distribution shifted (a tenant grew). Both have known solutions. The fix is to match strategy to traffic — and to build for ongoing rebalancing as the system evolves.

Distinguishes two causes (skewed activity vs data growth) with different fixes. Specific solutions ranked by complexity. The "hot shards are sign of mismatched strategy" framing is the right diagnostic mental model.

A junior says: "we're using Cassandra, so consistent hashing handles everything for us — we don't need to think about partition keys." Where do they go wrong?

The junior is technically correct that Cassandra handles consistent hashing. But "Cassandra handles partitioning" doesn't mean "you don't think about it." Let me work through the specifics.

Cassandra does: - Place data on the ring via consistent hashing of the partition key. - Use vnodes to balance load (256 per physical node by default). - Replicate based on the configured replication factor. - Handle node addition/removal with proportional data movement.

Cassandra does NOT: - Choose a good partition key for you. That's your job. - Detect or fix hot partitions caused by skewed access. Same hot-shard problem we just discussed. - Optimize for your query patterns. You design the schema to fit queries. - Prevent oversized partitions. A single partition exceeding 100MB starts hurting.

The specific traps the junior will hit:

Trap 1: choosing low-cardinality partition keys. Picking country or tenant_id as the partition key. Few distinct values, so few partitions, so a few nodes get all the data. Same issue as hash with skew.

Trap 2: oversized partitions. Cassandra recommends partitions stay under 100MB and 100K rows. If your partition key is user_id and a power user accumulates millions of events, that one partition gets enormous. Reads become slow; compactions are painful; the node holding it suffers.

The fix: design partition keys that bound size. (user_id, year_month) keeps each partition to one month of data. Trades wider rows for a multi-key query.

Trap 3: query/key mismatch. The whole point of Cassandra's design is that queries dictate the schema. If your query is WHERE user_id = ? AND timestamp > ?, the partition key should make that single-partition. If you query WHERE event_type = ?, you need a different table partitioned by event_type.

This is "denormalize for queries" taken to the limit. Cassandra encourages duplicating data into multiple tables, each partitioned for a specific query pattern.

Trap 4: cross-partition aggregations. Cassandra is bad at "count all events" or "sum across all users." Those aggregations span the whole ring. For analytics, you stream data to a separate analytical store (Snowflake, ClickHouse) via CDC or batch.

The framing for the junior: consistent hashing solves the data-distribution problem; it doesn't solve the schema-design problem. The partition key is your contract with the database — it determines what's fast and what's slow. Pick wrong and Cassandra is worse than Postgres, not better.

The lesson: the database hides one set of complexity (manual sharding) but exposes another (data modeling discipline). No tool eliminates the need to think about the workload.

Specific Cassandra traps with concrete examples (the 100MB partition limit, query-driven schema). The "tool hides one complexity, exposes another" framing is the senior insight that distinguishes someone who's actually used Cassandra in production.

Last one. We're early-stage. Should we shard from day one or start single-node and shard later?

The honest answer: almost always start single-node and shard later — but design with the future split in mind.

Why not shard from day one: - Premature sharding adds operational complexity. You're running multiple nodes when one would suffice. - The right partition key depends on actual usage patterns, which you don't know yet. - Sharding tools (Citus, Vitess) require operational maturity to run safely. Early teams should focus on shipping product, not on managing fleets. - Vertical scaling Postgres goes a long way. Modern hardware can handle 50K-100K writes/sec on a single beefy node. For most startups, that's "forever" in their first 5 years.

Why design for sharding eventually: - Choose schemas where the eventual partition key is obvious. A natural entity ID (user_id, account_id) appears as a column in most tables. This is the future partition key. - Avoid cross-entity queries that won't survive sharding. Joins across user/account boundaries are easy on a single node, painful when sharded. Write code that's okay being single-tenant within a shard. - Use UUID v7 (or hashed IDs) for primary keys, not auto-incrementing integers. Avoids the hot-tail problem when you do shard.

The actual progression I'd recommend:

Stage 1 (early-stage): single-node Postgres. Maybe a read replica if reads matter. Focus on shipping product, not infrastructure.

Stage 2 (growth): read replicas for read scaling. Start measuring write throughput. Identify the would-be partition key in your schema.

Stage 3 (write-bound): vertical scaling, materialized views, caching. Buy time. Track when these stop working.

Stage 4 (sharding required): introduce Citus or move to a sharding-aware database. Prepare for 3-6 months of migration work. Have a clear partition key by now.

Stage 5 (multi-shard fleet): dedicated team owning the data tier. Per-shard observability, automated resharding, all the operational discipline.

The senior framing: premature sharding is a common engineering vice. Teams pre-engineer for scale they may never reach, paying operational cost daily. Build for the next 6-12 months of scale, not the next 5 years. Re-architect when you actually hit limits — that's when you have the data to do it right.

The exception: if you're entering a market with a known scale ceiling (say, building a new payment processor competing with existing 100K-TPS systems), you may need to start sharded. Most teams aren't in that position.

Pragmatic and senior. The 5-stage progression maps to real engineering reality. "Premature sharding is a common engineering vice" — the kind of meta-observation that signals experience. Acknowledges the rare cases where sharding from day one is right.

Cheat sheet

Partitioning & Consistent Hashing — One Page

Why partition

Replicas scale reads. Partitioning scales writes. Single-node OLTP caps around 50K-100K writes/sec on premium hardware. Past that, must shard.

Three strategies

Range partitioning - Sorted by key, contiguous ranges per partition. - Wins: range queries, easy archival (drop old partitions). - Loses: hot partition risk (newest range gets all writes when keyed by time). - Best for: time-series, logs, append-mostly.

Hash partitioning (hash mod N) - Distributed by hash of key. - Wins: even write distribution, predictable load. - Loses: range queries fan out across all shards. Rehashing is catastrophic — N→N+1 moves N-1/N of data. - Best for: user-keyed OLTP, key-value lookups.

Consistent hashing - Ring topology. Each key goes to first node clockwise. - Wins: adding/removing nodes moves only ~1/N of data. No catastrophic rehashing. - Use vnodes (virtual nodes) to spread load across many ring positions per physical node. Cassandra default: 256 vnodes/node. - Best for: elastic clusters that grow and shrink.

Combination pattern

Hash for distribution, range within partition. DynamoDB partition key + sort key. Cassandra partition key + clustering keys. Modern default for write-heavy systems with within-entity range queries.

Choosing a partition key

  1. High cardinality — many distinct values.
  2. Even distribution — no power users dominating.
  3. Query alignment — most queries should be single-shard.
  4. Stability — key shouldn't change after row creation.

Hot partition fixes

  • Composite key: hash(tenant, record_id) — spreads tenant across shards.
  • Tenant tiering: power users → dedicated shards.
  • Cell isolation: top users → own database.

Tools

  • Citus — distributed Postgres.
  • Vitess — distributed MySQL (YouTube origin).
  • CockroachDB / TiDB — distributed SQL with consensus.
  • Cassandra / ScyllaDB / DynamoDB — built-in sharding via consistent hashing.
  • Postgres native partitioning: organizes one table on one node — not sharding.

Anti-patterns

  • hash mod N for systems that will grow (catastrophic rehash later).
  • Sharding by primary key when keys are sequential (BIGSERIAL → hot tail).
  • Sharding by low-cardinality keys (country, tenant) without considering skew.
  • Premature sharding when single node would still suffice.

The progression

  1. Single-node Postgres.
  2. Read replicas for read scaling.
  3. Vertical scale + caching + matviews.
  4. Sharding required → introduce Citus/equivalent.
  5. Multi-shard fleet with observability.

The 30-second verbal answer

"Replicas scale reads; partitioning scales writes. Three strategies: range (great for time, vulnerable to hot ranges), hash (balanced but rehashing is catastrophic), and consistent hashing (ring topology, only 1/N of data moves on rebalance, vnodes solve the variance problem). The modern pattern combines hash for distribution and range within partition. Pick the partition key for high cardinality, even distribution, query alignment, and stability."
