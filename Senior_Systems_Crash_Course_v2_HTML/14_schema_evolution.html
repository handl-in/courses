MODULE 14

Schema Evolution & Schema Registry

How to change the structure of your data without breaking every consumer downstream

You add a column. The deploy goes out. Five minutes later, three downstream services start throwing errors and the on-call channel lights up.

Schema evolution is the unglamorous discipline of changing data shapes safely. It's also where most CDC pipelines, microservice integrations, and data lakehouses quietly fall apart. By the end of this module, you'll know exactly which changes are safe, which require ceremony, and how schema registries make the whole thing tractable.

Sam learns about contracts

Sam OK so we've got CDC streaming changes from Postgres into Kafka and downstream into a bunch of consumers. Yesterday I added a column to the users table — loyalty_tier. Just a VARCHAR. Innocent enough. Twenty minutes later I'm in a war room because three consumer services started crashing.

Maya Welcome to schema evolution. The thing nobody mentions in tutorials about microservices.

Sam The column was additive. Why would adding something break anything?

Maya Depends entirely on how the consumers are written. If they use a strict deserializer that fails on unknown fields — which is the default in many systems — your "additive" change is a breaking change. The producer's events suddenly have a field consumers don't expect. Crash.

Sam That's not adding, that's mismatching.

Maya Exactly. Schema evolution is fundamentally about contracts between producers and consumers. The producer doesn't have one consumer — it might have ten, scattered across teams, each consuming the same events with different code, different versions, different tolerance for change. Every schema change is a coordination problem with people who aren't in the room.

Sam And a schema registry helps with that?

Maya A schema registry centralizes the contract. Every event is tagged with a schema version. Every consumer knows which version they expect. Compatibility rules are enforced at publish time, before anyone gets paged. By the end of this module you'll know which changes are forward-compatible, which are backward-compatible, why the difference matters, and what the operational discipline looks like.

Schema evolution is the discipline of changing data structure safely across producers and consumers that may upgrade independently. Backward compatibility = new schemas work with old data. Forward compatibility = old code works with new data. Full compatibility = both. Schema registries enforce these guarantees at publish time, preventing breaking changes from reaching consumers.

Why schema evolution is hard

It's hard because of one fact: you don't deploy producers and consumers atomically.

The fundamental coordination problem:

You have a UserCreated event. Producer service emits it; 6 consumer services process it (search index, analytics warehouse, billing, notification, recommendation, fraud detection).

You want to add a new field, loyalty_tier. The producer is ready. You deploy.

But: - Consumer A deployed yesterday with the old schema. Hasn't restarted. - Consumer B is in the middle of a slow blue/green deploy. Half its instances are old, half are new. - Consumer C is owned by another team, who hasn't deployed in 3 weeks. They didn't even know you were changing the schema. - Consumer D processes events from Kafka where there are 6 hours of old events still queued, plus new events being written.

Every consumer must handle both old and new versions of events for some window of time. The "window" might be milliseconds (instant deploy) or weeks (slow rollouts, third-party consumers, retention of historical data).

The producer cannot assume anything about consumer state. It must change the schema in a way that all consumers can handle, regardless of which version they're running.

You don't deploy producers and consumers atomically. Therefore every schema change must be safe under partial deployment.

The two compatibility directions

This is the central mental model. Memorize it.

Backward compatibility: a new consumer can read old data. (New code, old events.) Forward compatibility: an old consumer can read new data. (Old code, new events.) Full compatibility: both at once.

                THE COMPATIBILITY DIRECTIONS

Producer (v1) ────────────────► Consumer (v1) │ │ deploys ▼ Producer (v1) ────────────────► Consumer (v2) ← BACKWARD COMPAT Consumer reads v1 data correctly.

─────────────────────────────────────────────────────────────────

Producer (v1) ────────────────► Consumer (v1) │ │ deploys ▼ Producer (v2) ────────────────► Consumer (v1) ← FORWARD COMPAT Old consumer reads v2 data correctly.

─────────────────────────────────────────────────────────────────

Both directions safe → FULL COMPATIBILITY Producer and consumer can each upgrade independently in either order, including mixing versions during rollout.

A practical example.

You have an event:

{ "user_id": 42, "name": "Alice" }

You want to add email.

Backward compatible? A v2 consumer expecting {user_id, name, email} reads a v1 event missing email. The consumer has to handle missing-field gracefully — typically by treating email as nullable. Yes, backward compatible if the new field is optional or has a default.

Forward compatible? A v1 consumer (only knows user_id, name) reads a v2 event with the extra email field. The consumer has to ignore unknown fields. Yes, forward compatible if consumers are permissive about extra fields.

If the new field is required and consumers reject events missing it: not backward compatible. If consumers reject events with unknown fields: not forward compatible.

The discipline: your producers and consumers must be designed for both directions, every time.

Safe vs unsafe schema changes

Here's the cheat sheet you'll consult forever.

Change Backward Forward Notes
Add optional field ✅ ✅ Safe. Consumers default to null/missing.
Add required field ❌ ✅ Old data has no value for it. Avoid.
Remove optional field ✅ ❌ New data missing it; old consumers expecting it might break.
Remove required field ❌ ❌ Always breaking. Avoid at all costs.
Rename field ❌ ❌ Effectively remove + add. Always breaking.
Change field type (compatible widening) ✅ ⚠️ int→long is safe-ish; consumers may need adjusting.
Change field type (incompatible) ❌ ❌ int→string. Always breaking.
Reorder fields ✅ ✅ In named-field formats (JSON, Avro). Breaking in positional (Protobuf without field numbers).
Add enum value ⚠️ ❌ Old consumers don't know the new value. May crash on switch statement.
Make optional field required ❌ ✅ Old data may have null. Backward-incompatible.
Change default value ⚠️ ⚠️ Old data uses old default; new data uses new. Subtle bugs.

The most common mistake: assuming "additive" changes are safe. Adding a field can break consumers if: - They use strict deserialization (default in many libraries). - They use the new field in routing logic and don't handle missing. - They don't expect the field at all and have schema-validation failures.

Treat every schema change as risky until proven otherwise. The same rule applies whether you're using JSON, Avro, Protobuf, or SQL.

Three serialization formats, three philosophies

Schema evolution behaves differently depending on the wire format. Senior engineers know which format to choose for which problem.

JSON

Schema: implicit (in the consumer code).

Strength: human-readable, debuggable, ubiquitous.

Weakness: no enforced contract. Consumers each interpret. Easy to drift.

Compatibility: depends entirely on consumer behavior. Strict parsers reject unknown fields; permissive parsers ignore.

Use when: REST APIs, simple events, when human inspection matters.

Avro

Schema: explicit, attached to data (or via registry).

Strength: rich evolution rules; producer + consumer schemas can differ explicitly.

Weakness: not human-readable; requires schema for any interpretation.

Compatibility: enforced via reader/writer schema rules. Default-based field resolution.

Use when: data lakehouses (Iceberg, Hudi), Confluent Kafka, structured pipelines.

Protobuf

Schema: explicit, compiled .proto files.

Strength: compact, fast, strong evolution rules via field numbers.

Weakness: not human-readable; requires .proto for interpretation.

Compatibility: field numbers are the contract. Adding fields is safe; never reuse a number.

Use when: gRPC, internal microservice communication, performance-critical wire formats.

JSON Schema / OpenAPI

Schema: separate documents describing JSON structure.

Strength: language-agnostic, integrates with existing JSON APIs.

Weakness: validation is optional and easy to skip.

Compatibility: depends on how strictly enforced.

Use when: REST APIs that want documented and validated contracts.

The modern data platform stack typically uses Avro or Protobuf for events, not JSON. Reasons: - Compact wire format (Avro/Protobuf are ~10x smaller than JSON for the same data). - Schema is enforceable, not just documented. - Evolution rules are baked into the format.

Confluent's Schema Registry is the dominant tool for managing schemas alongside Kafka. Stores Avro schemas (or Protobuf, or JSON Schema), enforces compatibility rules at publish time. Mention Confluent Schema Registry by name in interviews about Kafka and CDC, and you sound like someone who's worked in this space.

Schema registry: the central enforcer

A schema registry is a service that stores schema definitions, assigns version numbers, and enforces compatibility rules at write time. Producers register schemas before publishing events. Consumers retrieve schemas to deserialize correctly. The registry rejects schema changes that violate the configured compatibility rules.

                      SCHEMA REGISTRY ARCHITECTURE

┌─────────────────┐ │ Producer │ │ (publishes │ 1. Register schema for "user_events" │ events) │ ───────────► └─────────────────┘ ┌────────────────────┐ │ Schema Registry │ │ │ │ Stores: │ │ - schema versions │ │ - compatibility │ │ rules │ │ - schema IDs │ └────────────────────┘ ▲ │ │ 4. Fetch schema by ID │ ┌─────────────────┐ │ │ Consumer │ ──────────────────────────┘ │ (reads events │ │ from Kafka) │ └─────────────────┘

Wire format: ┌──────────┬──────────────────────────────────────┐ │ schema │ serialized payload │ │ ID (4 B) │ (Avro/Protobuf bytes) │ └──────────┴──────────────────────────────────────┘

Each event carries a 4-byte schema ID (not the full schema). Consumers fetch the schema definition from the registry once, cache it, and use it to deserialize.

What the registry enforces

The publish-time check:

Producer attempts to register a new schema version for a topic.

Registry compares new schema against existing schemas using configured compatibility level.

If the change is incompatible (per the rules), registry rejects the publish. Producer must fix the schema before continuing.

If compatible, registry assigns a new version number and stores the schema.

Producer's events now reference this schema by ID.

This is the moment a breaking change is prevented from reaching consumers. Without a registry, breaking changes propagate; consumers discover them at runtime. With a registry, the offending deploy fails at the publish step, before any event is sent.

Compatibility levels

Confluent Schema Registry supports several compatibility modes. Choose based on consumer flexibility:

Mode Allows Use when
NONE Any change Never use in production — defeats the purpose
BACKWARD New consumers can read old data Consumers upgrade after producers
FORWARD Old consumers can read new data Consumers upgrade before producers
FULL Both directions Independent producer/consumer upgrades
BACKWARD_TRANSITIVE Backward against ALL prior versions Stricter — most paranoid
FORWARD_TRANSITIVE Forward against ALL prior versions Stricter
FULL_TRANSITIVE Both, against all versions Maximum strictness

The default to choose: FULL_TRANSITIVE. It's the strictest, but it gives you the most flexibility in production:

  • Producers can be deployed in any order.
  • Consumers can be deployed in any order.
  • Old events in Kafka still consumable by new consumers.
  • New events publishable while old consumers are still running.

The discipline cost: every schema change must be designed to be compatible in both directions, against every prior version. This forces good practices — never remove fields, never change types incompatibly, always use optional new fields.

Mention "FULL_TRANSITIVE compatibility" in an interview about schema design, and you signal you've done this in production.

The expand-then-contract pattern

When you genuinely need a breaking change — rename a field, change a type — the canonical pattern is expand then contract.

The two-phase migration:

Expand: producer writes both the old and new field. Consumers continue to read the old field.

Migrate consumers: each consumer is updated to read the new field instead of the old. Deploy at their own pace.

Verify: confirm all consumers have migrated. Check metrics, logs, no consumers still reading the old field.

Contract: producer stops writing the old field. The old field is gone.

Renaming email to email_address:

Phase 1: producer writes {user_id, email, email_address} — both fields, identical values.

Phase 2: consumers update to read email_address. They can deploy at their own pace; old code still reads email.

Phase 3: monitor. Use schema registry to see which consumers are still on old schema versions. Reach out to teams who haven't migrated.

Phase 4: producer drops email, writes only {user_id, email_address}.

The whole migration might take weeks depending on consumer count. The senior reflex: plan migrations as multi-phase deployments, not single deploys.

Don't skip Phase 3. It's tempting to "just deploy and see what breaks." That's how outages happen. Verify migration completion before contracting. The migration window is when you're paying the dual-write cost; the contract step is when it's safe to stop.

Database schema evolution: the OLTP variant

So far we've been talking about events and message buses. Database schemas have similar issues, with extra wrinkles.

The classic Postgres pitfalls

Adding a column with a default value used to lock the table for a full rewrite. Pre-Postgres 11, ALTER TABLE ADD COLUMN ... DEFAULT 'foo' would rewrite every row. For a 100M-row table, that's hours of exclusive lock — production outage.

Postgres 11+ fixed this for non-volatile defaults: the default is stored as metadata, not written to existing rows. Adding a column with a default is now fast.

But this is one of many gotchas. Senior Postgres engineers know which ALTER TABLE operations are safe and which are dangerous.

The Postgres ALTER TABLE safety reference:

Operation Lock type Notes
ADD COLUMN (no default, nullable) ACCESS EXCLUSIVE briefly Fast — just metadata
ADD COLUMN ... DEFAULT 'x' (PG 11+) ACCESS EXCLUSIVE briefly Fast since PG 11
ADD COLUMN ... DEFAULT 'x' (PG 10-) ACCESS EXCLUSIVE for full rewrite Avoid on large tables
DROP COLUMN ACCESS EXCLUSIVE briefly Fast — but data isn't reclaimed until VACUUM FULL
ALTER COLUMN TYPE Often requires full rewrite Slow — same lock duration as a table scan
ADD CONSTRAINT (non-validated, NOT NULL with default) ACCESS EXCLUSIVE briefly Fast
VALIDATE CONSTRAINT ROW SHARE Slow but online
RENAME COLUMN ACCESS EXCLUSIVE briefly Fast — metadata only
CREATE INDEX SHARE Slow but online
CREATE INDEX CONCURRENTLY ROW EXCLUSIVE Slow, online, always use in prod

The senior reflex: before any DDL on a production table, look up its lock requirements. Don't run blind.

The dance: backward-compatible DDL

For a deploy where the application code and the schema both change:

The expand-then-contract pattern, applied to a column rename in a database:

Add the new column. ALTER TABLE users ADD COLUMN email_address TEXT; (Fast in PG 11+.)

Backfill. Copy existing email values to email_address. Often via a batch job: UPDATE users SET email_address = email WHERE email_address IS NULL; Watch for vacuum churn.

Dual-write in the application. Application writes both email and email_address going forward. Reads still come from email.

Migrate readers. Application code switches to read email_address instead of email. Deploy.

Stop writing the old. Application stops writing to email. The column is now stale but still present.

Drop. ALTER TABLE users DROP COLUMN email; (Fast — metadata, but the data is still there until VACUUM FULL.)

Do not deploy schema changes and code changes in the same deploy unless you can roll back atomically — and you usually can't, because the schema can't be rolled back as easily as code.

The pattern: schema change first, code change second. Or schema change as additive only; code change handles both old and new schemas. Then later schema change to remove the old.

This discipline is what separates teams that ship safely from teams that have weekly schema-related outages.

Three more ways to think about schema evolution

Way 1: editing a contract.

A contract has been signed by both parties. You want to change a clause. You can't just edit it — both parties have copies. You must:

  1. Add an addendum with the new clause (additive, both parties can ignore or use it).
  2. Both parties sign and acknowledge.
  3. Eventually amend the original to remove the obsolete clause.

That's expand-then-contract. The "addendum first" phase is the safe one. Skipping it and just editing creates legal disputes.

Way 2: phone keypads.

When phone numbers added a digit (e.g., 7→10 digits in many regions), the transition wasn't instant. For years, both formats worked — you could dial 7 digits and the system understood, or 10 and same. Eventually the 7-digit format was deprecated and removed.

Schema evolution is similar. The producer publishes both the old and new format. Consumers can use either. After enough time, the old format is removed.

The transition window is when you bear the cost of dual support. It's never zero, but it's bounded.

Way 3: linguistic loanwords.

A language adds a new word from a loan source. Initially, both the new loanword and the old native equivalent coexist. Speakers gradually shift to one or the other. Eventually, one dies out — but only after enough speakers have adopted the change.

Schema evolution mirrors this. New fields and old fields coexist for a transition period. The "language" (your event format) gradually shifts. The cost of incompatible change is high — speakers can't communicate. So the change is staged.

Sharpen your pencil

Exercise 1. A team is publishing OrderCreated events to Kafka with this schema:

{
  "order_id": "uuid",
  "user_id": "uuid",
  "total_cents": "integer",
  "items": [{...}]
}

They want to add a currency field, default "USD" — for orders to support multi-currency in the future. Walk through the deploy plan.

The straightforward path: add as optional with a default.

Step 1: Update the schema in the registry. - Add "currency": { "type": "string", "default": "USD" }. - Verify FULL_TRANSITIVE compatibility passes. - Producer can now write events with or without the field.

Step 2: Producer code update. - Producer writes currency on every event going forward — for new orders, this is "USD" by default; for orders in non-default currencies, the actual code. - For events still in Kafka without the field: consumers must handle missing-field as "USD".

Step 3: Consumer code updates. - Each consumer that needs currency adds handling: read the field if present, default to "USD" otherwise. - Consumers can deploy at their own pace.

Step 4: Long-term consideration — should currency ever be required?

Once all old events have aged out of Kafka (typically days to weeks based on retention), you could make currency required. But that's a backward-incompatible change. The senior reflex: leave it optional permanently if there's no compelling reason to require it. The cost of optional-with-default is near zero; the cost of required is "old events break."

Step 5: Verify. - Monitor schema usage in the registry — what schema versions are being read by consumers? - Confirm no consumers are stuck on old schemas indefinitely.

The whole change might be a 1-day deploy if all consumers are well-behaved, or 1-week if consumers are owned by other teams. Plan for the slow consumers, not the fast ones.

Exercise 2. Your team has been doing schema changes by editing JSON event structures and deploying. They've had three incidents in two months from breaking schema changes. Architect a fix.

The diagnosis: no enforced schema contract. JSON without a registry means each consumer interprets events at runtime; mismatches surface as crashes. The team is paying for absence of structure.

The fix: introduce a schema registry.

Step 1: Choose a format.

Three options: - Avro + Confluent Schema Registry: most popular for Kafka. Compact, evolution rules baked in. Requires schema for any interpretation. - Protobuf + Confluent Schema Registry: similar benefits. More common when also using gRPC for service-to-service calls. - JSON Schema + Confluent Schema Registry: keeps JSON wire format but adds enforced schemas.

For most teams, Avro is the default for new event-driven systems. Mature tooling, clear evolution semantics.

Step 2: Roll out gradually.

  • Start with one new event type, written and consumed in the new format. Prove the workflow.
  • Set compatibility level to FULL_TRANSITIVE in the registry.
  • Producers register schemas before deploying; the registry rejects breaking changes.
  • Consumers fetch schemas from the registry, cache them, deserialize.

Step 3: Migrate existing event types.

For each existing JSON event type: - Define an Avro/Protobuf schema mirroring the current shape. - Producer dual-writes: emit both JSON and Avro. - Consumers gradually switch to Avro. - Once all consumers migrate, producer drops JSON.

This is the expand-then-contract pattern applied to format migration.

Step 4: Discipline.

  • Schema changes go through PR review.
  • The schema registry's compatibility check runs in CI — schema PRs that would break compatibility fail the build.
  • Document conventions: optional new fields, never remove, never rename without expand-then-contract.

The expected outcome:

  • Breaking changes are caught at PR time, not at runtime.
  • Consumer teams know what events look like without reading producer code.
  • New consumers can be onboarded by reading the schema, not by guesswork.
  • The 3-incidents-in-2-months pattern goes to zero.

The senior framing: schema registry is infrastructure for safe distributed systems, not a nice-to-have. Treating it as optional is the root of recurring schema-related outages.

Exercise 3. Explain to non-technical Sam, in two sentences, the difference between forward and backward compatibility.

Backward compatibility means new code can read old data — like a new version of your phone's photo app being able to open photos from 5 years ago. Forward compatibility is the reverse: old code can read new data — like an older photo app being able to open a newly-saved photo even if it doesn't understand all the new metadata. Both directions matter because in distributed systems, the producer of data and the consumer of it might upgrade at different times, and you don't want either side to break the other.

There are no dumb questions

Q: Why not just use JSON everywhere?

A: JSON is fine for human-facing APIs and small-volume event streams. For high-volume event pipelines (millions of events per second), JSON's verbosity costs real money in Kafka storage and bandwidth. Avro/Protobuf are 5-10x smaller. Plus JSON has no enforced schema — every consumer must validate independently, and inconsistencies are common. For internal event pipelines, Avro/Protobuf is the modern default.

Q: Can I use a schema registry without Kafka?

A: Yes. Schemas can describe any event format. Confluent Schema Registry is most known with Kafka but works with other systems. Apache Iceberg has its own schema layer. Some teams use Buf for Protobuf-based gRPC schemas. The pattern (centralized schema authority, compatibility enforcement) is broader than any specific tool.

Q: What about gRPC's "proto file" approach — is that a schema registry?

A: Sort of. The .proto file is the schema. Tools like Buf Schema Registry centralize them, enforce compatibility rules, and provide breaking-change detection in CI. Buf is essentially "schema registry but for Protobuf and gRPC." Different tooling, same concept.

Q: How do I know which schema version a consumer is on?

A: The wire format includes a schema ID. Consumers fetch the schema from the registry. Most registries log which schema IDs each consumer client uses. You can audit the registry to see "consumer X is reading schema version 5" and confirm migration progress. This visibility is one of the registry's main operational benefits.

Q: What's "schema-on-read" vs "schema-on-write"?

A: Two philosophical approaches. Schema-on-write: structure is enforced when data is written (relational databases, Avro with registry). Schema-on-read: data is written without strict structure; structure is inferred when reading (JSON in document stores, raw S3 files). Schema-on-read is more flexible but harder to maintain — every consumer interprets independently. Lakehouse formats (Iceberg) are schema-on-write, which is part of why they're more rigorous than raw S3 + JSON.

Q: How does CDC handle schema changes?

A: Mostly captures DDL (ALTER TABLE) and propagates as schema-change events in the stream. Debezium, for instance, emits special "schema change" messages. Consumers must handle these — usually by re-reading the schema. The discipline: announce schema changes in advance to give consumers time to prepare.

Q: What if I genuinely need to remove a field?

A: Use expand-then-contract. Phase 1: producer continues writing it but documents as deprecated. Phase 2: consumers stop reading it. Phase 3: producer stops writing it. The "stop reading" phase requires verification — every consumer team must confirm. This can take weeks; plan accordingly.

Q: Should schema files live in the producer's repo or a shared location?

A: Both options have valid reasons. Producer-owned: schemas live with producer code; clear ownership. Centrally-shared: schemas in a separate repo or registry; multiple producers/consumers can reference. The modern preference is centralized — Buf Schema Registry, Confluent Schema Registry, Schema Repository — because schemas are contracts, not implementation details. Treat them as first-class artifacts.

Three myths to dynamite

"Adding a field is always safe."

False. Depends on consumer behavior. Strict deserializers (default in many libraries) reject events with unknown fields. Adding a field that consumers don't expect can break them. Treat every schema change as risky until proven otherwise.

"We don't need a schema registry — we use JSON."

Misleading. JSON without enforced schemas means each consumer interprets independently — which is exactly the recipe for drift, mismatches, and runtime failures. JSON with a schema registry (JSON Schema + Confluent Schema Registry) is fine; raw JSON without one is the source of recurring incidents.

"Schema registry is enterprise overkill."

False for any system with multiple consumers. The cost of not having one — runtime crashes, hours of triage per incident, fear of touching schemas — is much higher than the cost of operating a registry. For a team of 3 services and 2 events, maybe overkill. For 20 services and 200 event types, mandatory.

Interview gotchas

Treating schema changes as "just deploy it." Schema evolution is a multi-phase deployment by nature. Senior engineers think in expand-then-contract and explicitly plan migration phases.

Not knowing the difference between backward and forward compatibility. Mixing them up signals you don't have a clear mental model. Drill until you can answer "is renaming a field forward-compatible?" instantly.

Recommending JSON without a schema for production event pipelines. Modern data platforms use Avro or Protobuf with a schema registry. JSON is fine for human-facing APIs; for internal events at scale, it's wasteful and dangerous.

Forgetting Postgres ALTER TABLE lock semantics. Some operations are fast (metadata-only); others require full table rewrites with exclusive locks. Senior engineers know which is which before running DDL on a hot table.

Recommending atomic deploys of schema + code. Schemas can't be rolled back like code. The discipline: schema change first (additive only), code change second, schema cleanup later. Never both at once unless you have time-machine deploys.

Mock interview

We have CDC streaming Postgres changes through Kafka into 10 downstream consumers. The team is afraid to make any schema changes because they always break someone. How would you fix this?

This is a textbook case for introducing a schema registry. The fear of schema changes is rational — without enforcement, every change is a coin flip. Let me work through it.

Diagnosis. The team has 10 consumers each interpreting events independently. Schema changes propagate through CDC, hit consumers without prior notice, and break some of them. Classic distributed-system coordination problem.

The fix has three parts.

Part 1 — Introduce a schema registry. - Stand up Confluent Schema Registry (or Buf, depending on whether they're using Avro/Protobuf or want JSON Schema). - Set compatibility level to FULL_TRANSITIVE — strictest setting, gives independent producer/consumer evolution. - Migrate one event type as proof of concept — define schema, switch producer to write Avro/Protobuf, migrate consumers gradually.

Three-part plan with timeline. Acknowledges the cultural change is the hard part — senior engineering reality. The "infrastructure not optional" framing is the right level for this scale.

Walk me through how you'd rename a column in a 100-million-row Postgres table without downtime.

Standard expand-then-contract pattern, with extra care for the table size. Let me walk through it with concrete commands.

Phase 1 — Add the new column.

ALTER TABLE users ADD COLUMN email_address TEXT;

Fast in PG 11+ since no default. Just metadata. The column is nullable.

Phase 2 — Backfill historical data. This is the tricky part on a 100M-row table. You can't do UPDATE users SET email_address = email in one shot — it would take an exclusive-style lock for too long, generate massive WAL, and bloat the table.

The senior pattern: batched, paced backfill.

-- pseudocode for a batched script
WHILE rows_updated > 0:
    UPDATE users SET email_address = email
    WHERE email_address IS NULL
    AND id IN (SELECT id FROM users WHERE email_address IS NULL LIMIT 5000);
    SLEEP 1 second;
END WHILE

5000 rows at a time, with a sleep between batches, lets autovacuum keep up and other queries proceed. Total backfill might take hours; that's fine — it's safe in the background.

Verify completion: SELECT COUNT(*) FROM users WHERE email_address IS NULL AND email IS NOT NULL; should be zero.

Phase 3 — Application code: dual-write. Application writes both email and email_address going forward. Reads still come from email.

This requires backward-compatible code: the application must check both columns when reading, prefer the new one if both exist (handles edge cases during the migration window).

Phase 4 — Application code: read from new column. Switch reads to email_address. Deploy. Now email is purely for backward compatibility — written but not read.

Phase 5 — Stop dual-writes. Application stops writing email. Only email_address is touched going forward.

Phase 6 — Drop the old column.

ALTER TABLE users DROP COLUMN email;

Fast — metadata only. The space isn't reclaimed until VACUUM (autovacuum will eventually). For large tables, you might run pg_repack to compact more aggressively.

Total timeline: 2-3 weeks for a busy production system. Possibly longer if the application code changes need careful review.

Things I'd verify along the way: - Application logs for any "missing email_address" or "missing email" errors during transition. - Replication lag stays bounded throughout the backfill. - Disk usage during dual-write phase doesn't spike (you're writing more data temporarily).

The senior framing: rename = expand + contract. Never just "rename it." Even in databases that support ALTER TABLE RENAME COLUMN instantly (Postgres does), the application code has to handle the old column name during deploy. The dance is unavoidable.

Concrete SQL with reasoning. The batched backfill is the senior detail most engineers miss. Acknowledges PG 11+ specifics, vacuum implications, and pg_repack as the modern compaction tool.

A junior engineer proposes: "let's just store everything as JSON. We'll add new fields anytime, no schema headaches." Why not?

The proposal sounds appealing — "no schema, no schema problems." But the headaches don't disappear; they shift to a different layer. Let me work through the actual costs.

Cost 1: drift across consumers. Without a defined schema, every consumer interprets the JSON independently. Consumer A reads created_at. Consumer B reads createdAt. Consumer C reads created_time. Now the producer has three contracts, all implicit, none enforced. Adding any field requires checking what every consumer does — often by reading their code, which may not even be in the same repo.

Cost 2: silent breakage. Without schema enforcement at publish time, breaking changes propagate. Producer changes a field's type from string to integer. Consumers crash at runtime, not at deploy time. The team finds out via paged alerts.

Cost 3: lost discoverability. A new consumer team wants to subscribe. How do they know what fields the events have? They read the producer code. If the producer is in a different language, they translate. If the producer's behavior differs across versions, they trial-and-error. Schema registry replaces all this with a definition file.

Cost 4: storage and bandwidth. JSON is verbose. For high-volume event streams, you're paying real money for {field_name} repetition vs Avro/Protobuf's binary format. At 1B events/day, the difference is meaningful.

Cost 5: data quality. Without enforced types, "true" and true, "1" and 1, "2024-01-15" and 1705320000 all coexist. Consumers must guess. Bugs from type ambiguity are common.

The counterproposal:

If they value the flexibility JSON provides, they can keep JSON wire format with a JSON Schema in a registry. Confluent Schema Registry supports JSON Schema. They get schema enforcement at publish time and JSON's debuggability.

If they want maximum efficiency: Avro or Protobuf, registered, evolution-tested at PR time.

The framing for the junior: "no schema" doesn't mean "no problem." It means "the problem isn't visible until production." We pay for schema definition either upfront (cheap, deliberate) or in production incidents (expensive, embarrassing). Pick which kind of pain you want.

This is one of those engineering lessons that requires either real-world experience or someone explicit explaining the trade-offs. Worth the conversation.

Five costs ranked. Concrete examples (created_at vs createdAt). The counterproposal acknowledges the junior's underlying motive (flexibility) and offers the modern compromise. Closes with the "pick which kind of pain" framing — senior reflex.

Last one. Your team has been using a schema registry for a year. Now there's a proposal to add a new event type that requires breaking changes to an existing one. How would you handle it?

This is a great test of the discipline. The honest answer: depends on why the breaking change is needed.

Step 1 — Question whether it's really needed.

Often "we need to break it" is a misframing of "we want a different shape." Ask: - Can we add a new optional field that captures the new requirement? - Can we model the new event type as a separate event, parallel to the old one? - Can we deprecate the old field gradually rather than break it?

Step 2 — If breaking is genuinely required, plan the expand-then-contract.

Two paths depending on the change:

Path A: New event type that supersedes the old. - Define the new event type with the desired shape. - Producer writes both events for a transition period. - Consumers switch to new event one at a time. - Eventually the old event is deprecated.

Path B: Backward-incompatible field change in existing event. - This is the harder case. - Add the new field as optional (additive, safe). - Application logic uses the new field if present, the old field if not. - Migrate consumers to use new field. - Eventually deprecate the old field — but this may require a multi-quarter window.

Step 3 — Communicate.

Schedule a meeting with all consumer teams. Walk them through: - Why the change is needed. - The proposed migration timeline. - What action they need to take and by when.

The schema registry's audit log shows which teams are still reading the old schema. Track migration progress concretely.

Step 4 — Set a deprecation date.

Don't leave the old schema indefinitely. Set a date — typically 1-3 months — by which all consumers must migrate. Send periodic reminders to teams not yet migrated. Have an escalation path for the last holdouts.

Step 5 — Verify and contract.

Once all consumers have migrated (verified via registry usage logs), drop the old field/schema. The registry can mark old schema versions as deprecated; eventually they can be deleted entirely.

The senior framing: breaking changes are project-level events. They require communication, timeline, and milestone tracking. Treat them like a deprecation project. The registry shows you the truth — who's on what version — and that visibility is what makes the project trackable.

What I'd push back on: "we can break it in a future deploy." That's how outages happen. Either it's planned with a migration window, or it's deferred. Don't ship breaking changes hoping consumers handle it gracefully.

Step 1 questions whether it's really needed — senior reflex of pushing back gracefully. Two paths for two breaking change types. Communication and tracking framed as project management. The "registry shows you the truth" framing is the operational benefit of having one.

Cheat sheet

Schema Evolution & Schema Registry — One Page

The fundamental problem

You don't deploy producers and consumers atomically. Schema changes must be safe under partial deployment.

Two compatibility directions

  • Backward compatible: new code reads old data.
  • Forward compatible: old code reads new data.
  • Full: both. The production target.

Safe schema changes (FULL compatible)

  • Add optional field with default.
  • Add new event type alongside existing.
  • Reorder fields (in named-field formats).

Unsafe schema changes (require expand-then-contract)

  • Remove field.
  • Rename field.
  • Change field type incompatibly.
  • Make optional → required.
  • Remove enum value.

Serialization formats

  • JSON — debuggable, verbose, schema implicit. Use with JSON Schema for enforcement.
  • Avro — Kafka standard, evolution-aware, requires schema for interpretation.
  • Protobuf — gRPC standard, field-number-based, very efficient.
  • JSON Schema / OpenAPI — describes JSON, validation optional.

Modern data platforms: Avro or Protobuf with a registry.

Schema registry

  • Centralized schema storage.
  • Compatibility enforcement at publish time.
  • Schema IDs in wire format; consumers fetch and cache.
  • Tools: Confluent Schema Registry, Buf Schema Registry, AWS Glue Schema Registry.

Compatibility levels (Confluent)

  • NONE — never use.
  • BACKWARD / FORWARD / FULL — single-version.
  • BACKWARD_TRANSITIVE / FORWARD_TRANSITIVE / FULL_TRANSITIVE — against all prior.

Default: FULL_TRANSITIVE for production event pipelines.

Expand-then-contract

The pattern for breaking changes: 1. Expand: write both old and new. 2. Migrate readers: switch consumers one at a time. 3. Verify: confirm all consumers migrated (via registry usage). 4. Contract: drop old.

Required for any rename, type change, or field removal.

Postgres DDL safety

  • Fast (metadata-only): ADD COLUMN nullable, DROP COLUMN, RENAME COLUMN, ADD CONSTRAINT NOT VALID.
  • Fast (PG 11+): ADD COLUMN with non-volatile default.
  • Slow (full rewrite): ALTER COLUMN TYPE, ADD COLUMN with volatile default (PG 10-).
  • Slow but online: CREATE INDEX CONCURRENTLY, VALIDATE CONSTRAINT.

Always use CONCURRENTLY in production for indexes.

Database deploy discipline

  1. Schema change first (additive only).
  2. Application code change second (handles both old and new).
  3. Schema cleanup later (after migration verified).

Never both at once.

The 30-second verbal answer

"Schema evolution is the discipline of changing data structure safely across producers and consumers that may upgrade independently. Backward compatibility means new code reads old data; forward compatibility is the reverse. Full compatibility — both directions — is the production target. Schema registries enforce these rules at publish time, preventing breaking changes from reaching consumers. For breaking changes, use expand-then-contract: write both versions, migrate readers, verify, then drop the old."

Always pair with

CDC (Module 11), Kafka, Avro/Protobuf, Confluent Schema Registry, Buf, expand-then-contract, dual writes, deprecation.
