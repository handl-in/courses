MODULE 18

Rate Limiting

Token bucket, leaky bucket, sliding windows — and why "we'll add rate limiting" is the start, not the end, of the conversation

A bot abuses your API with 50,000 requests per second. A misconfigured retry storm hammers a downstream service. An overzealous customer's batch job saturates your servers at 3 AM.

Rate limiting is the discipline of saying "no" politely — protecting your system from being overwhelmed by individual callers. Sounds simple. The implementations have nine algorithms, dozens of edge cases, and exactly one configuration that survives contact with production.

Sam meets the noisy neighbor

Sam OK so we're getting hammered. One customer's integration started looping infinitely yesterday — it sent 200,000 requests per minute to our API. Took down our auth service. We need rate limiting. I'll add a per-IP limit, like, 100 requests per second. Done?

Maya Done? You haven't even started. What happens when the customer's traffic comes from 50 different IPs because they're behind a NAT?

Sam Oh.

Maya What about a legitimate customer making 100 requests in one second as a normal burst — search-as-you-type, autocomplete, parallel page loads? Are you blocking them?

Sam Hmm.

Maya What about distributed rate limiting? You have 10 application servers — does each one count requests independently, allowing 1000 RPS in aggregate when you said 100? Or do they coordinate?

Sam I... didn't think about that.

Maya And when you do block someone, what do you tell them? "429 Too Many Requests" with no Retry-After header? They retry immediately. You've created a tight loop instead of stopping one.

Rate limiting is one of those topics where the textbook description is 5% of the actual engineering. The other 95% is choosing the right algorithm, the right scope, the right response, and making it work across distributed systems. By the end of this module, you'll be able to design and defend rate limiting like someone who's actually shipped it.

Rate limiting protects your system from overload by limiting how many requests a caller can make in a time window. The choices: which algorithm (token bucket, leaky bucket, sliding window, fixed window), which scope (per-IP, per-user, per-key, per-endpoint, global), where to enforce (edge, API gateway, application, database), and how to respond (429 with Retry-After, queue, degrade). Each choice has consequences for fairness, accuracy, and operational complexity.

Why rate limiting exists

Three distinct problems, often conflated.

The three motivations:

Protection from abuse. Bots, scrapers, attackers, runaway scripts. The traffic is illegitimate or malicious. You want to block it hard.

Fair resource sharing. Your service has finite capacity. One enthusiastic customer shouldn't consume so much that others starve. You want to ensure everyone gets a slice.

Cost control. Each request costs you money — CPU, database queries, downstream API calls. You charge customers a tier; their tier limits their consumption. Without limits, your unit economics break.

Why these motivations matter:

A "protection from abuse" rate limit can be aggressive — block instantly, no warning. The user is bad-faith.

A "fair resource sharing" rate limit must be careful — legitimate users have legitimate bursts. Blocking them looks like a bug.

A "cost control" rate limit is a business decision, not a technical one. The limit is per the customer's plan, surfaced in invoices and billing.

Mixing them up causes pain. "Block aggressive bots" rules accidentally block legitimate customers' bursts. "Cost control" limits get misconfigured to block when they should just charge overage. Senior engineers separate these.

The four canonical algorithms

Each makes a different trade-off between simplicity, accuracy, and burst handling.

Algorithm 1: Fixed window

Count requests in fixed time windows (e.g., per calendar minute). When the count exceeds the limit, reject.

                      FIXED WINDOW
                      Limit: 10 requests/minute

10:00:00 ─────────── 10:00:59 │ 10:01:00 ─────────── 10:01:59 ╭───────────────────────────╮ ╭───────────────────────────╮ │ Window 1 (count: 0→10) │ │ Window 2 (count: 0→10) │ │ │ │ │ │ Request comes in: │ │ │ │ count++ │ │ │ │ if count > 10: reject │ │ │ ╰───────────────────────────╯ ╰───────────────────────────╯

Reset at minute boundary. New window starts fresh.

The implementation:

Maintain a counter per (user, current_window).

On each request: increment counter.

If counter exceeds limit, reject.

At window boundary, reset counter (or use a new key).

The fixed window's fatal flaw: edge bursts.

Suppose limit is 10 requests/minute. A user sends 10 requests at 10:00:59 (end of window 1). All accepted. Then 10 requests at 10:01:00 (start of window 2). All accepted.

They just sent 20 requests in one second, but neither window saw more than 10. Your "10 requests per minute" limit allowed an effective burst of 20 per second.

This is why fixed window is rarely used alone in production — but it's the simplest implementation, so it's where most engineers start.

Algorithm 2: Sliding window log

Store a timestamp for every request. To check the limit, count timestamps within the last N seconds.

The implementation:

Maintain a list of timestamps per user.

On each request: add current timestamp to list.

Remove timestamps older than the window.

If remaining list size exceeds limit, reject.

The accuracy is perfect:

Limit: 10 requests/minute. The window slides continuously — at any moment, you're counting requests from "now" back 60 seconds.

The 10:00:59 + 10:01:00 burst would be caught: 20 requests fall within the same 60-second sliding window.

Trade-off: you store every request timestamp. For a million users at 100 requests/minute, that's 100M timestamps in memory. Doesn't scale.

Sliding window log is accurate but memory-heavy. It's ideal for low-volume, high-precision limits — say, login attempts per user. For high-volume traffic, the storage cost is prohibitive.

Algorithm 3: Sliding window counter (the modern default)

Approximation of sliding window log with bounded memory. Combines counts from current and previous fixed window.

The math:

Two counters: current window, previous window.

Approximate sliding window count = (previous_window_count × overlap_fraction) + current_window_count.

Where overlap_fraction = (window_size - elapsed_in_current_window) / window_size.

The intuition:

It's 10:00:30 (30 seconds into a 60-second window). Window started at 10:00:00, ends at 10:01:00.

You "look back" 60 seconds, which means: 30 seconds of the previous window (10:00:30 to 10:01:00 — wait, that's the future) and 30 seconds of the current window.

Wait, let me restate: at 10:00:30, the sliding window covers 10:00:30 backward to 09:59:30. That's 30 seconds of the previous (09:59) window and 30 seconds of the current (10:00) window so far.

The approximation: assume the previous window's requests were uniformly distributed. Take 50% of its count + 100% of the current window's count.

If previous window had 8 requests and current has 5: estimate = 0.5 × 8 + 5 = 9. Compare to limit.

Memory: 2 counters per user, regardless of request rate.

Sliding window counter is the production sweet spot. Memory-efficient, reasonably accurate (typically within 1-3% of true sliding window), simple to reason about. Used by Stripe, Cloudflare, AWS API Gateway, and most modern API rate limiters.

Mention sliding window counter in interviews about rate limiting and you sound like someone who's read the implementations, not just the textbook.

Algorithm 4: Token bucket

The most flexible algorithm. Allows bursts up to a configurable size, then refills at a sustained rate.

                      TOKEN BUCKET

  ┌──────────────────────┐
  │   Bucket               │  Capacity: 10 tokens (max burst)
  │                        │  Refill: 1 token per second (sustained)
  │   ●●●●●●●●●●          │
  └──────────────────────┘
        │
        │ Each request consumes 1 token
        ▼
  Request: takes 1 token if available
            if no tokens: reject (or wait)

  Tokens refill steadily over time.
  Burst of 10 immediately allowed (full bucket).
  After burst, refill rate is 1/sec sustained.

Example timeline: t=0: Bucket = 10 (full) t=0: Send 10 requests → bucket = 0 (all allowed) t=1: 1 token refilled → bucket = 1, send 1 → bucket = 0 t=2: 1 token refilled → bucket = 1, send 1 → bucket = 0 ... sustained at 1 RPS thereafter

The implementation:

Each user has a bucket: current token count, last refill timestamp.

On each request: calculate how many tokens to add since last refill (elapsed × rate, capped at bucket size).

If bucket has ≥ 1 token: subtract 1, allow request.

If bucket has < 1 token: reject (or queue, see leaky bucket variant).

Token bucket allows controlled bursts. Users can spend "saved up" tokens for a quick burst, but their sustained rate is bounded by the refill rate. This is exactly the behavior real users want: occasional bursts (page load, parallel calls) without the system breaking, but no sustained abuse.

Algorithm 5: Leaky bucket

Closely related to token bucket but inverted: requests fill the bucket, processed at a constant rate.

The leaky bucket model:

Requests arrive and queue up in the bucket. The bucket has a fixed processing rate — say, 10 requests/second. The bucket also has a maximum size — say, 100.

If the bucket is full (100 queued), new requests are rejected.

The queue smooths bursts. If 100 requests arrive in one second, the system processes 10 per second for 10 seconds.

Trade-off vs token bucket: leaky bucket delays requests; token bucket rejects them when full. Different UX.

When to use which:

  • Token bucket: when bursts are allowed but sustained rate is bounded. Good for HTTP APIs.
  • Leaky bucket: when sustained rate must be smooth. Good for traffic shaping, processing pipelines.
  • Sliding window counter: when accurate per-window enforcement is needed and memory matters.
  • Fixed window: only as a starting point or when edge bursts don't matter.
  • Sliding window log: only for low-volume, high-precision needs.

Most production systems use token bucket for user-facing APIs and sliding window counter for billing/quota enforcement.

The scope question

Algorithms are half the choice. Scope is the other half. Who is the limit per?

Scope Use case Trade-off
Per-IP Stop bots; protect against simple DDoS Easy to evade (NAT, proxy rotation); blocks legitimate users behind NAT
Per-API-key Protect API; align with billing Requires authentication; doesn't help unauthenticated endpoints
Per-user Fair sharing among logged-in users Requires session/auth; doesn't help anonymous traffic
Per-endpoint Protect expensive endpoints Doesn't catch cumulative abuse across endpoints
Per-tenant Multi-tenant SaaS Hard to scope when one user spans tenants
Global Protect total system capacity Doesn't differentiate good vs bad traffic
Composite (e.g., per-API-key + per-endpoint) Layered defense Implementation complexity; multiple checks per request

The senior pattern: layered scopes.

A real production rate limit has multiple layers:

  • Global: total RPS across all customers can't exceed system capacity (say, 100K RPS).
  • Per-tenant: each tenant has a plan-based limit (say, 1000 RPS for premium, 100 for free).
  • Per-API-key: each key within a tenant has a limit (say, 500 RPS, ensuring one runaway integration doesn't consume the tenant's whole budget).
  • Per-endpoint within key: expensive endpoints (search, exports, ML inference) get tighter limits than cheap ones.
  • Per-IP: catch authenticated users sending from too many IPs (potential abuse).

Each request checks several limits in sequence. Any one failing rejects the request. The layers compound to give protection at every level of the architecture.

Per-IP alone is broken in 2026. NAT, IPv6 privacy extensions, mobile carriers' shared IPs, corporate proxies, VPNs — all create scenarios where many users share IPs or one user has many IPs. Modern rate limiting uses authenticated identity (API key, user ID, tenant ID) as the primary scope, with per-IP as a secondary defense.

Distributed rate limiting

The hard part. You have 10 application servers behind a load balancer. A user sends 100 RPS. Each server sees 10 RPS. Each server's local counter says "well under limit." User is over the limit globally but no individual server knows.

This is distributed rate limiting. Three approaches.

Approach 1: Centralized Redis counter

The simple production pattern:

Every server uses Redis as the central counter:

INCR rate_limit:user_42:60s_window
EXPIRE rate_limit:user_42:60s_window 60

Each request becomes one Redis round-trip — typically 1-2ms. The counter is global. All servers see the same number.

For high traffic, you can use Redis Lua scripts to atomically check-and-increment:

local count = redis.call("INCR", KEYS[1])
if count == 1 then
  redis.call("EXPIRE", KEYS[1], ARGV[1])
end
return count

One round-trip, atomic, returns the count. Compare to limit in application code.

Centralized Redis is the dominant production pattern for distributed rate limiting. Simple, accurate, and Redis can handle 100K-1M ops/sec on modest hardware. For most systems, this is sufficient.

Failure modes:

  • Redis down: do you fail open (allow all) or closed (reject all)? Failing closed = worst possible time for an outage. Failing open = bypassed rate limit. Most production systems fail open with alerts, accepting the brief abuse risk.
  • Latency: every request adds 1-2ms. For ultra-low-latency APIs, this matters.
  • Cost: high request rates = high Redis ops. Can become expensive at very high scale.

Approach 2: Local counters with periodic sync

The high-throughput optimization:

Each server keeps a local counter. Periodically (every second, say), it syncs to a central store. Other servers see the synced counts.

Trade-off: brief inaccuracy. A user might exceed the global limit by up to (per-server-burst × server-count) before the sync catches it.

Use when: throughput is too high for centralized Redis on every request, and brief over-allowance is acceptable.

This is how big systems do it. AWS API Gateway, Cloudflare, and similar services don't check a central counter on every request. They use sophisticated approximations — local counters with bounded over-allowance, then global enforcement on aggregate. The exact algorithm is often proprietary.

For the 99% of systems: centralized Redis is fine. Mention this trade-off only when discussing very high-scale (>100K RPS per limit key).

Approach 3: Sticky routing

The "send the same user to the same server" approach:

The load balancer hashes (user_id) and always routes to the same server. That server's local counter is authoritative.

Pros: no central coordination needed. Each server's counter is accurate for its assigned users.

Cons: load isn't perfectly balanced (some users are heavier). Server failures redistribute users to others — counters reset.

This pattern is rare in pure form because of the rebalancing issues, but it appears as part of session affinity in some architectures.

Responding to rate limits

You've decided to reject a request. What do you tell the caller?

The HTTP 429 contract:

Status code: 429 Too Many Requests (introduced in RFC 6585).

Header: Retry-After — number of seconds the client should wait before retrying. Or an HTTP date.

Header: X-RateLimit-Limit — the rate limit ceiling.

Header: X-RateLimit-Remaining — requests remaining in the current window.

Header: X-RateLimit-Reset — when the limit resets (Unix timestamp).

Body: clear error message explaining the limit and how to address it.

A good 429 response:

HTTP/1.1 429 Too Many Requests
Content-Type: application/json
Retry-After: 30
X-RateLimit-Limit: 1000
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1729968600

{
  "error": "rate_limit_exceeded",
  "message": "You have exceeded your rate limit of 1000 requests per minute.",
  "retry_after_seconds": 30,
  "limit": 1000,
  "limit_period": "1 minute",
  "documentation_url": "https://api.example.com/docs/rate-limits"
}

The client knows: what happened, how long to wait, what the limit is, where to learn more.

Bad 429 responses are a frequent cause of cascading failures.

  • No Retry-After: clients retry immediately. Tight loop. They make the problem worse.
  • 429 without a clear message: clients have no signal what's wrong. They retry hopefully.
  • 503 instead of 429: looks like a transient outage; clients retry aggressively.
  • Silent rejection (just close the connection): clients have no signal at all.

Always respond with explicit 429, Retry-After, and a clear message. This is the difference between rate limiting that protects your system and rate limiting that makes things worse.

Stripe's approach to rate limit responses is the canonical model:

HTTP/1.1 429 Too Many Requests
Stripe-Should-Retry: true
Retry-After: 12

The Stripe-Should-Retry header tells clients explicitly whether retry is appropriate. Stripe's SDKs read this and back off accordingly. The protocol embeds the retry semantics, not just the limit.

For high-quality APIs, design the rate-limit response with the SDK in mind. The SDK should know how to handle 429s gracefully.

Soft vs hard limits

Two different policies for what happens at the limit.

Hard limit

Reject all requests over the limit. Return 429.

Use when: protecting from abuse, enforcing strict quotas, or where over-consumption is dangerous.

Trade-off: legitimate burst traffic gets blocked. Customer experience can suffer if limits are too tight.

Soft limit (degraded service)

Continue to serve, but with degraded quality — slower responses, simpler features, less accurate data.

Use when: customer experience matters more than strict quota enforcement.

Trade-off: harder to implement; harder to communicate "you're over your limit but I'll still serve you."

Soft limits in practice:

A SaaS dashboard at 1000 calls/min limit. Customer hits 1500 calls/min.

Hard limit: 500 of those calls return 429. Customer's dashboard shows "rate limited" errors. They call support.

Soft limit: all 1500 calls succeed, but the responses come from cached data with a "may be stale" indicator instead of fresh queries. Customer's dashboard works; metrics are minutes old. They don't notice.

Soft limits are kinder to customers but harder to engineer. Each endpoint must have a degraded mode.

Per-tenant fairness

In multi-tenant systems, rate limiting becomes a fairness problem.

The noisy neighbor problem:

A SaaS platform has 1000 tenants sharing a backend cluster. Total system capacity: 100K RPS.

Without per-tenant limits: tenant A spikes to 50K RPS (50% of system). Tenant B and C, doing normal traffic, see latency spike because the system is saturated. A noisy neighbor degrades others.

With per-tenant limits: each tenant capped at, say, 5K RPS. Spike traffic from any one tenant doesn't affect others.

But: now you have 1000 × 5K = 5M RPS theoretical capacity, 50x the actual capacity. The aggregate of per-tenant limits doesn't equal system capacity.

The senior pattern: layered limits.

  • Per-tenant limit: stops one tenant from saturating.
  • Global limit: stops aggregate from exceeding system capacity.
  • Both enforced; both visible in monitoring.

When the global limit hits, all tenants are slowed proportionally. When a per-tenant limit hits, only that tenant is affected. The two work together.

Per-tenant limits don't help against unauthenticated traffic. If your service has anonymous endpoints, you need IP-based or fingerprint-based limits in front of the per-tenant ones. Layered defense again.

Three more ways to think about rate limiting

Way 1: a nightclub.

Fixed window: the bouncer counts entries in 5-minute slots. Resets at the top of each 5 minutes. People at 4:59 entries plus 5:00 entries can both happen — bouncer doesn't catch the cluster.

Sliding window: the bouncer maintains a list of recent entries with timestamps. At any moment, knows exactly how many entered in the last 5 minutes.

Token bucket: the club has a "VIP card" system. Each card has 10 entries pre-loaded; refills at 1 per minute. Members can burst (use all 10 quickly) or sustain (use 1 per minute), but not exceed the refill rate over time.

Leaky bucket: a single line outside the club, processed at one entry per minute. Burst doesn't matter; the line just gets longer.

Way 2: water rationing.

Hard limit: each household gets 100 gallons/day. Above that, water is shut off.

Soft limit: each household gets 100 gallons. Above that, water still flows but at reduced pressure (slower fills, can't run multiple appliances). Customer notices but isn't cut off.

Token bucket: each household has a tank. Refills at 100 gallons/day. Can use 200 gallons in one day if the tank was full, but sustained usage averages 100/day.

Per-tenant: each district gets 1M gallons/day shared among households. Aggregate per-district enforcement protects against one greedy district. Per-household limits within a district protect against one greedy household.

Way 3: traffic lights.

Hard rate limiting: a strict red light. No traffic passes during red.

Token bucket: a metered onramp. Cars admitted at one per N seconds. Burst accumulates briefly but sustains the rate.

Leaky bucket: a roundabout. Cars enter at any rate but circulate at a fixed throughput. Excess waits.

Sliding window: speed cameras that average over a moving window. Hard to game with momentary speeds.

Layered limits: city-wide gridlock controls (global) plus per-intersection metering (local). Multiple levels of traffic management.

Sharpen your pencil

Exercise 1. Your team is implementing rate limiting for a new API. Initial proposal: per-IP, fixed window, 1000 requests per minute, return 429 when exceeded. Identify three problems and propose a better design.

Three problems with the initial proposal:

Problem 1: per-IP is broken in modern internet. NAT, mobile carriers, corporate proxies, and shared cloud infrastructure mean many legitimate users come from the same IP. Conversely, IPv6 privacy extensions and proxy rotation mean one user can have many IPs. Per-IP alone catches some bots but blocks many legitimate users.

Problem 2: fixed window allows edge bursts. A user can send 1000 requests at the end of one minute and 1000 at the start of the next — 2000 in 2 seconds, all "within limit." Defeats the purpose.

Problem 3: 429 without Retry-After and clear messaging causes retry storms. Clients hammer the API immediately on rejection.

A better design:

Layered scopes: - Per-API-key: 1000 requests/minute (the primary scope, aligned with billing). - Per-tenant: 10,000 requests/minute (catches multiple keys within a tenant). - Per-IP: 5,000 requests/minute (secondary defense against unauthenticated abuse). - Global: total system capacity ceiling.

Sliding window counter (or token bucket for burst-friendly endpoints): provides accurate enforcement without the edge-burst problem of fixed window.

Distributed implementation: centralized Redis counter for accuracy. Lua script for atomic increment-and-check. Fail open with alerts if Redis is unavailable.

429 responses: include Retry-After, X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset headers. Clear JSON error body explaining the limit and pointing to documentation.

Per-endpoint variation: cheap endpoints (GET) get standard limit; expensive endpoints (search, exports) get tighter limits.

The senior framing: rate limiting is layered defense, not a single number. Combine multiple scopes with appropriate algorithms and clear client communication.

Exercise 2. A team is using Redis for distributed rate limiting. Redis goes down for 10 minutes. Walk through what happens.

The crisis: rate limiting depends on Redis. Redis is gone.

Decision point: fail open or fail closed?

Fail closed: every request gets rejected. The system goes from "degraded" to "totally unavailable" because of a Redis outage. This is usually wrong — Redis being down doesn't mean traffic is malicious; it just means we can't enforce limits.

Fail open: every request is allowed without rate limit checks. The risk: if there's an active abuse, it succeeds for the duration of the outage. The benefit: legitimate users are unaffected.

Most production systems fail open because (a) the period is usually brief, (b) rate limiting is not the primary security control (auth is), and (c) the alternative — full outage from a Redis blip — is far worse.

During the 10-minute outage:

  1. Application logs every "rate limit check skipped due to Redis unavailability" event. Surfaces in monitoring.
  2. Alerts fire. On-call investigates.
  3. The team observes: did anyone abuse? If not, no action needed beyond restoring Redis.
  4. If abuse occurred (rare), the abusive traffic is logged and can be addressed retroactively (block the API key, contact the customer, ban the IP).

After Redis recovery:

  • Resume normal rate limiting.
  • Counters reset (since Redis was down). The next minute starts fresh. This is fine — slight under-enforcement for a brief period.

Hardening for the future:

  • Redis replication: primary + replica. Auto-failover means brief Redis outages don't take down rate limiting.
  • Local fallback: each application server has a local in-memory counter as a backup. When Redis is unavailable, fall back to local counters. Less accurate (one user might exceed global limit by up to N×local_limit) but better than no limits.
  • Multiple Redis clusters: rate limit checks shard across multiple Redis instances. One down = partial enforcement, not zero.

The senior framing: rate limiting infrastructure should be highly available. If your rate limiting layer goes down, your business goes down (in fail-closed mode) or becomes vulnerable (in fail-open mode). Treat the rate limiting infrastructure with the same seriousness as the application servers it protects.

Exercise 3. Explain to non-technical Sam, in two sentences, the difference between token bucket and fixed window rate limiting.

Fixed window counts requests in clean time slots — like "no more than 100 between 12:00 and 12:01" — which sounds reasonable but lets someone send 100 right before noon and another 100 right after, sending 200 in two seconds. Token bucket gives each user a small bucket of tokens that refill steadily over time — they can spend tokens quickly for a brief burst (say, opening multiple tabs) but their long-term sustained rate is bounded by the refill speed, which makes it both more accurate and friendlier to normal usage patterns.

There are no dumb questions

Q: Should rate limits be per-second or per-minute?

A: Both, layered. Per-second limits catch sudden spikes (DDoS-style); per-minute limits catch sustained abuse. Per-day limits catch slow, distributed scraping. Real APIs have multiple time horizons enforced together. Stripe famously has limits at multiple windows simultaneously.

Q: How do I rate limit unauthenticated endpoints?

A: Per-IP is the fallback. Combine with browser fingerprinting, request headers (User-Agent), and behavioral analysis (request patterns) for stronger signals. Cloudflare and AWS WAF specialize in this — they're built for unauthenticated traffic.

Q: What about webhooks I receive — should those be rate limited?

A: Yes, but differently. Webhooks come from your customers' systems; you can't refuse them or you'll lose data. Pattern: accept the webhook quickly, queue it, process asynchronously with bounded concurrency. The "rate limit" is on processing, not acceptance.

Q: How does API Gateway rate limiting differ from application-level rate limiting?

A: API Gateway (AWS, Apigee, Kong) handles rate limiting at the edge — before the request reaches your application. Pros: protects backend even from massive bot traffic; doesn't consume your app servers. Cons: less context (can't easily limit based on application state). Common pattern: edge-level coarse limits (per-IP, per-API-key globally) + application-level finer limits (per-feature, per-user-tier).

Q: What's the difference between rate limiting and throttling?

A: Often used interchangeably. Strictly: rate limiting = enforce a maximum (reject excess); throttling = slow down (queue, delay). Token bucket can do either. In practice, "throttling" often means "soft limit with degradation" while "rate limiting" means "hard limit with rejection." Don't fight over the words; clarify the behavior.

Q: Should I rate limit by request count or by request cost?

A: For nuanced systems, cost-based is better. Each request consumes a "weight" — a simple GET might be 1, a complex aggregation might be 100. The user has a weight budget per window. GitHub's API does this — different endpoints consume different amounts of the rate limit. More fair, more accurate to system load. Implementation complexity is higher.

Q: How do I handle clients that legitimately need higher rates?

A: Tier-based limits per API plan. Free tier gets 100 RPS; pro gets 1000; enterprise gets 10000 with the option to negotiate higher. Communicate clearly via documentation and the rate-limit headers. For known integrations, allow custom override on the API key — no need for a tier upgrade for trusted partners.

Q: What about retries that cause rate limit hits?

A: Use exponential backoff with jitter (Module 17). On 429, wait the Retry-After time before retrying. Add jitter to avoid synchronized retry storms. SDK support for this is essential — clients should handle 429 automatically. Stripe's SDK does this transparently.

Three myths to dynamite

"Rate limiting is just a number per second."

False. Rate limiting is a layered system: algorithm choice, scope, time horizons, distributed coordination, response semantics, fairness across tenants. The "number" is the easy part; the rest is the engineering.

"Per-IP rate limiting is sufficient."

False in 2026. NAT, IPv6 privacy, mobile carriers, VPNs, and corporate proxies make IP an unreliable identifier. Per-IP is a useful secondary defense, never the primary scope. Use authenticated identity (API key, user, tenant) as primary; IP as supplement.

"Rate limiting at the API gateway is enough."

False for sophisticated systems. API Gateway handles coarse limits at the edge. But application-level limits (per-feature, per-user-state, cost-based) require knowledge the gateway doesn't have. Layered enforcement is the production reality.

Interview gotchas

Recommending fixed window without acknowledging the edge-burst problem. Fixed window is the simplest algorithm but has a real flaw. Senior engineers know it and choose it deliberately, not by default.

Suggesting per-IP rate limiting alone. In modern internet, IP is unreliable. Always pair with authenticated identity scopes.

Forgetting Retry-After in 429 responses. Without it, clients retry immediately, creating tight loops. Always include Retry-After and clear messaging.

Not addressing distributed enforcement. "We'll add rate limiting" without explaining how it works across multiple servers signals incomplete thinking. Centralized Redis is the standard answer.

Treating soft limits as a panacea. Soft limits sound friendlier but require degraded modes for every endpoint. Implementation complexity is real. Soft limits work where you've engineered them, not by default.

Mock interview

We need rate limiting for our public API. Walk me through your design.

Several questions before I commit to a design:

One — what are we protecting against? Abuse, fair sharing, or cost control? Each motivates different limits. If abuse, aggressive limits are fine. If cost, the limit aligns with the customer's plan. Often all three, layered.

Two — what's the traffic shape? Are bursts legitimate (users browse, then idle, then browse) or symptoms of abuse? Token bucket is ideal for legitimate bursts; sliding window is better for strict enforcement.

Three — what's the scale? A few hundred RPS or hundreds of thousands? The choice between centralized Redis and approximate distributed counters depends on this.

Four — what's the SLA on rate limit availability? If Redis goes down, do we fail open or closed?

Assuming a typical mid-scale public API with mixed traffic, here's my design:

Layered scopes:

  • Global: 100K RPS — total system capacity ceiling.
  • Per-tenant: 5K RPS for paid tier, 500 RPS for free.
  • Per-API-key: 2K RPS within a tenant (so one runaway integration doesn't consume the whole tenant budget).
  • Per-endpoint within key: expensive endpoints (search, ML, exports) get 100-500 RPS; cheap endpoints get 1K+.
  • Per-IP: 5K RPS as a secondary defense.

Algorithm: token bucket for user-facing API. Allows legitimate bursts (page loads, parallel requests) while bounding sustained rate. Bucket size = 2 × refill rate per second, providing a 2-second burst capacity.

Distributed implementation: centralized Redis with Lua script. Per-key keys: ratelimit:{tenant}:{key}:{endpoint_class}. TTL on keys ensures cleanup.

Failure mode: fail open with alerts if Redis is unavailable. Local fallback to in-memory counters as a hedge.

A customer reports they're being rate limited but they think the limit is too low. They're a paying customer. How do you handle this?

This is partly engineering, partly customer success. The right response depends on what's actually happening.

Step 1: gather data.

What endpoint are they hitting? At what rate? What's their plan limit? Pull their usage from logs.

Common findings:

  • They're using the API legitimately but at a higher rate than expected. Their use case has grown. Plan upgrade is the answer.
  • They have a bug in their code. Infinite loop, retry storm, accidental N+1 pattern. Tell them what's happening; they fix it.
  • The limit is genuinely too tight for the use case. Other customers also hit it. Engineering issue.
  • Specific endpoint is too aggressively limited. The endpoint's individual limit doesn't match its actual cost.

Step 2: choose the right path.

If it's a plan-tier issue: customer success conversation. Upgrade or custom contract.

If it's a customer bug: support ticket showing them their request pattern, often with retry storm visible. They fix it.

If it's a limit that's wrong: engineering review. Adjust the limit. Possibly retroactively credit the affected customer.

If it's an endpoint-specific issue: revisit cost model. Should this endpoint cost less than I estimated? Or is the customer using it in a way that makes it expensive?

Step 3: reduce future friction.

Surface clearer signals to customers: - Dashboard in the customer portal showing their current usage vs limit. - Email alerts when they're consistently hitting 80% of their limit. - Documentation of which endpoints are expensive and why.

Step 4: document the decision.

If the customer's case warrants a custom override (large enterprise, special integration, beta customer), document the override on their API key. Note the reason and revisit at renewal.

The senior framing: rate limit incidents are usually signals, not just bugs. They tell you something about how customers are using your API and where your design is misaligned. Listen to the signal.

Walk me through how you'd implement the actual rate limiter. The Redis Lua script and the application logic.

Sure, the canonical implementation. Token bucket with Redis.

The data model:

Per-rate-limit-key, store two values in Redis: - tokens: current token count. - last_refill: Unix timestamp of last refill.

These can be in a single Redis hash: ratelimit:tenant_42:search.

The Lua script (atomic check-and-decrement):

-- KEYS[1]: rate limit key
-- ARGV[1]: bucket capacity (max tokens)
-- ARGV[2]: refill rate (tokens per second)
-- ARGV[3]: current Unix timestamp
-- ARGV[4]: cost of this request (default 1)

local capacity = tonumber(ARGV[1])
local refill_rate = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local cost = tonumber(ARGV[4]) or 1

local data = redis.call("HMGET", KEYS[1], "tokens", "last_refill")
local tokens = tonumber(data[1]) or capacity
local last_refill = tonumber(data[2]) or now

-- Calculate tokens to add since last refill
local elapsed = math.max(0, now - last_refill)
local refill_amount = elapsed * refill_rate
tokens = math.min(capacity, tokens + refill_amount)

local allowed = tokens >= cost

if allowed then
  tokens = tokens - cost
end

-- Update Redis
redis.call("HMSET", KEYS[1], "tokens", tokens, "last_refill", now)
redis.call("EXPIRE", KEYS[1], 3600)  -- cleanup after 1 hour idle

-- Return: allowed (1 or 0), remaining tokens, retry_after seconds
local retry_after = 0
if not allowed then
  retry_after = math.ceil((cost - tokens) / refill_rate)
end
return {allowed and 1 or 0, math.floor(tokens), retry_after}

The application code (Python pseudocode):

def check_rate_limit(tenant_id, endpoint_class, request_cost=1):
    key = f"ratelimit:{tenant_id}:{endpoint_class}"
    capacity = get_bucket_capacity(tenant_id, endpoint_class)
    refill_rate = get_refill_rate(tenant_id, endpoint_class)
    now = time.time()

    try:
        result = redis.evalsha(
            RATE_LIMIT_SCRIPT_SHA,
            keys=[key],
            args=[capacity, refill_rate, now, request_cost]
        )
        allowed, remaining, retry_after = result

        if allowed:
            return RateLimitResult(allowed=True, remaining=remaining)
        else:
            return RateLimitResult(
                allowed=False,
                remaining=0,
                retry_after=retry_after,
                limit=capacity,
                reset_at=now + retry_after
            )
    except RedisError:
        # Fail open with logging
        log_warning("rate_limit_redis_unavailable", key=key)
        return RateLimitResult(allowed=True, remaining=None)

The HTTP handler:

def handle_request(request):
    rate_limit = check_rate_limit(
        tenant_id=request.tenant_id,
        endpoint_class=request.endpoint_category,
        request_cost=request.estimated_cost
    )

    if not rate_limit.allowed:
        return Response(
            status=429,
            headers={
                "Retry-After": str(rate_limit.retry_after),
                "X-RateLimit-Limit": str(rate_limit.limit),
                "X-RateLimit-Remaining": "0",
                "X-RateLimit-Reset": str(int(rate_limit.reset_at)),
            },
            body={
                "error": "rate_limit_exceeded",
                "retry_after_seconds": rate_limit.retry_after,
                # ... clear message
            }
        )

    # Add headers to successful response
    response = process_request(request)
    response.headers["X-RateLimit-Remaining"] = str(rate_limit.remaining)
    return response

Deployment notes:

  • Load the Lua script once per Redis connection; cache the SHA. EVALSHA is faster than EVAL.
  • Per-tenant settings (capacity, refill rate) cached in application memory with periodic refresh.
  • Metrics on rate limit hits: which endpoints, which tenants, what fraction of total traffic.
  • Alerts on Redis errors (fail-open path being taken).

The senior framing: implementation is simple once the design is right. The complexity is in the configuration (per-tenant rates, per-endpoint costs), monitoring (knowing when limits are hitting), and operational handling (Redis failover, fail-open semantics). Code is 20%; operations is 80%.

Last one. Your team is debating: should we build rate limiting in-house, or use a service like Cloudflare or Kong?

Both are valid. The choice depends on what you actually need.

Use a service (Cloudflare, Kong, AWS WAF, Apigee) when:

  • You need edge-level protection. Traffic should be limited before hitting your servers. Reduces backend load even from abusive traffic. Crucial for unauthenticated endpoints under DDoS risk.
  • You don't have rate limiting as a core competency. Don't reinvent the wheel for a non-differentiating feature.
  • You want managed infrastructure. Operations, scaling, and reliability of the rate limiter are someone else's problem.
  • Coarse limits are enough. "X requests/sec per IP" or "X per API key" is what these services do well.

Build in-house when:

  • You need application-aware limits. "User has used 3 of 5 free trials this month" requires application state that edge services don't have.
  • You need cost-based limits. "Each search query costs 5 units; user has 100 units/min." Custom logic.
  • You have integrated billing logic. Rate limits aligned with subscription state. Real-time decisions based on payment status, plan tier, custom contracts.
  • You're at a scale where vendor costs are prohibitive. At very high RPS, rate-limiter-as-a-service can cost more than building it. The break-even depends on the vendor and your traffic.

The hybrid pattern (most production):

  • Edge service (Cloudflare, AWS WAF) for coarse limits, DDoS protection, bot detection.
  • In-house for application-aware limits, business logic, billing alignment.

Both layers complement each other. The edge handles volume; the application handles nuance.

My recommendation for most teams:

Start with the edge service — it's quick to deploy, protects against the most common threats, and doesn't require your team to operate a critical-path service.

Add in-house limits as the product matures and you need application-aware enforcement. Don't build in-house from day one unless you have specific needs the edge can't meet.

The senior framing: rate limiting is infrastructure with multiple layers. The choice isn't "build vs buy" — it's "which layer goes where?" Most production systems have both, each doing what it does best.

Doesn't pick one — articulates trade-offs of each. The hybrid pattern is the production reality. "Which layer goes where?" reframes the question. Pragmatic recommendation for most teams to start with edge service.

Cheat sheet

Rate Limiting — One Page

Three motivations

  • Protection from abuse — block bots, attackers, runaway scripts.
  • Fair resource sharing — prevent noisy neighbors.
  • Cost control — align consumption with business model.

Senior engineers separate these explicitly.

The five algorithms

  • Fixed window — simplest; vulnerable to edge bursts.
  • Sliding window log — accurate; memory-heavy.
  • Sliding window counter — production sweet spot.
  • Token bucket — allows controlled bursts; modern API default.
  • Leaky bucket — smooths bursts via queueing.

Scope choices (layer multiple)

  • Per-IP (secondary defense; broken alone in modern internet).
  • Per-API-key (primary scope for authenticated traffic).
  • Per-user (fairness within auth).
  • Per-endpoint (protect expensive operations).
  • Per-tenant (multi-tenant fairness).
  • Global (system capacity ceiling).

The senior pattern: layered scopes, multiple time horizons.

Distributed implementation

  • Centralized Redis with Lua script — production default.
  • Local counters with periodic sync — high-throughput optimization.
  • Sticky routing — niche; rare in pure form.

Fail open with alerts if Redis is unavailable.

429 response contract

  • Status: 429 Too Many Requests.
  • Headers: Retry-After, X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset.
  • Body: clear message, error code, documentation link.

Stripe's SDK pattern: include Should-Retry semantics. SDKs handle 429 gracefully.

Soft vs hard limits

  • Hard: reject. Use for abuse, strict quotas.
  • Soft: degrade. Use where customer experience trumps strict enforcement.

Most APIs use hard limits. Soft requires per-endpoint engineering.

Modern reality

  • Edge service (Cloudflare, AWS WAF, Kong) for coarse limits + DDoS.
  • In-house for application-aware logic, billing, custom rules.
  • Layered combination in most production systems.

Anti-patterns

  • Per-IP alone (broken by NAT, IPv6, proxies).
  • Fixed window without sliding (edge bursts).
  • 429 without Retry-After (causes retry storms).
  • No global limit on top of per-tenant (aggregate exceeds capacity).
  • Building in-house when edge service would suffice.
  • Not tiering by plan/business value.
