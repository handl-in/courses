MODULE 13

Distributed Transactions, Sagas & Idempotency

2PC, 3PC, sagas, and the patterns that make "do this thing across services" actually work

A user clicks "buy." The order service writes a row. The payment service charges the card. The inventory service decrements stock. The shipping service creates a label.

If any one of those services crashes mid-flow, you're left with: charged-card-no-order, decremented-stock-no-charge, or eight other partial states. None of them are good.

Distributed transactions are how you avoid being the engineer who explains those states to angry customers.

Sam meets the multi-service problem

Sam OK so transactions in one database, I get. ACID. BEGIN, do stuff, COMMIT. But at work we have like 12 microservices that each have their own database. When a user clicks "checkout," we have to update 4 of them. How does that work?

Maya Ha. Welcome to one of the genuinely hard problems in distributed systems. The textbook answer is "two-phase commit." The production answer is "almost nobody does that, because the operational pain is worse than the alternative."

Sam What do they actually do?

Maya Sagas plus idempotency. Sometimes outbox patterns. Sometimes hold their nose and accept eventual consistency. Big point: there is no good way to do distributed transactions. Every approach has costs. The senior skill is knowing the trade-offs of each — when 2PC is right, when sagas are right, and what idempotency actually demands.

Sam Wait, idempotency is involved?

Maya Centrally. The biggest mistake junior engineers make is treating idempotency as an afterthought. In distributed systems, every operation might happen twice. Every retry might be a duplicate. Every network blip might cause a redelivery. If your operations aren't idempotent, distributed retries can't be safe. And without safe retries, none of the patterns we'll discuss actually work.

Sam That sounds harder than I expected.

Maya It is. By the end of this module you'll have the vocabulary and the patterns. But also a healthy respect for "let's just do it in one database if we can." Distributed transactions are real engineering, not a thing you sprinkle on.

Distributed transactions span multiple services or databases. No approach is free. 2PC gives strong consistency at the cost of operational fragility (locks held across services). Sagas give availability at the cost of complexity (compensating actions). Both require idempotent operations to be safely retryable. The senior skill is matching pattern to problem.

The two-phase commit (2PC)

The textbook approach. Coordinator-managed atomic commit across multiple participants.

The 2PC protocol:

Phase 1: Prepare. Coordinator sends "prepare to commit" to all participants. Each participant either: - Locally locks its resources, persists tentative changes, replies "ready." - Or finds it can't commit, replies "abort."

Phase 2a: Commit. If all participants replied "ready," coordinator sends "commit." Each participant finalizes its tentative changes, releases locks, replies "committed."

Phase 2b: Abort. If any participant replied "abort," coordinator sends "abort." Each participant rolls back tentative changes, releases locks.

                      TWO-PHASE COMMIT (2PC)

                   Coordinator
                        │
            ┌───────────┼───────────┐
            ▼           ▼           ▼
        Service A   Service B   Service C
            │           │           │

PHASE 1 (PREPARE): │ ──prepare?── │ ──prepare?── │ │ │ │ │ ──ready────► │ ──ready────► │ ◄──────────────┴──────────────┤ (coordinator collects all "ready"s)

PHASE 2 (COMMIT): │ ──commit──── │ ──commit──── │ │ │ │ │ ──committed─►│ ──committed─►│ ◄──────────────┴──────────────┤

Result: atomic commit across all services. ✓

But what if the coordinator crashes between phase 1 and 2? Or service B crashes after replying "ready" but before "commit"? Resources stay locked — possibly forever.

Why 2PC is correct (in theory)

2PC guarantees atomic commit across multiple participants. Either all participants commit, or all abort. No participant unilaterally decides — they all wait for the coordinator's verdict.

The protocol's safety property: if a participant replied "ready" in Phase 1, it must be able to commit in Phase 2 even after a crash. So Phase 1 acts as a durable promise: "I have written this change tentatively, locked the rows, and I will commit when you say so."

Why 2PC is broken (in practice)

2PC has a fundamental flaw: it's a blocking protocol. If the coordinator crashes between Phase 1 and Phase 2, participants that voted "ready" are stuck — they've locked their resources and don't know whether to commit or abort. They wait. Forever, if the coordinator never recovers.

This means: a single crash of the coordinator can hang every participant's locks indefinitely. In a high-throughput system, this cascades into total unavailability within seconds.

The classic 2PC outage pattern:

A coordinator crashes mid-transaction. Three participants are all in "ready" state, holding locks on rows they're about to modify.

The coordinator restarts. It needs to figure out the state of every in-flight transaction by reading its log. The log says: "transaction 1234 was in Phase 2 commit, status unknown."

The coordinator queries participants: "what's the status of 1234?" Two participants reply "I voted ready, waiting." Third participant times out (network blip).

The coordinator can't unilaterally decide — the third participant might have already committed locally and be waiting to ack, or might have rolled back.

This is the heuristic outcome problem. There's no clean answer. Most production implementations have a manual escalation path: a human operator inspects logs, decides, manually commits or aborts.

In production, this happens. It's the second 3 AM page after the first one.

Why almost no modern system uses 2PC:

  • Locks held during the protocol block all other transactions touching the same rows. Throughput craters under contention.
  • Coordinator crashes leave participants in indeterminate state. Recovery is operationally painful.
  • Cross-service participation requires every service to implement the 2PC protocol. Real-world: services rarely do.
  • Latency = sum of network round-trips × 2 (prepare + commit). Cross-region 2PC is unusable.

XA transactions are a specific implementation of 2PC defined by the X/Open consortium. JDBC has an XAResource interface. Some databases support XA. In practice, almost no production system uses XA at scale. The pain is too high.

If asked about 2PC in an interview, articulate the protocol and the reasons it's almost never used. Senior engineers know both halves.

Three-phase commit (3PC)

3PC adds an extra phase to fix 2PC's blocking issue. In theory.

3PC's extra phase:

Phase 1 (Prepare) — same as 2PC.

Phase 2 (Pre-Commit): coordinator tells participants "all are ready, prepare to commit." Each acks.

Phase 3 (Commit) — coordinator tells participants to actually commit.

3PC's promise: if coordinator crashes after Phase 2, participants can communicate among themselves and decide to commit (since they all know everyone was ready). No more indefinite blocking.

3PC's reality: assumes a synchronous network — bounded message delivery time. Real networks aren't synchronous. Under network partitions, 3PC has the same fundamental issue with a different shape.

In practice, 3PC is academic. Distributed databases either use Paxos/Raft (Module 12) for consensus over a single value, or sagas (next section) for multi-service flows. 3PC is rarely deployed.

Sagas: the practical alternative

If 2PC is too rigid for production, sagas are what most modern distributed systems actually use.

A saga is a sequence of local transactions, each with a corresponding compensating action that undoes its effect. Instead of one big atomic transaction, you have many small ones, with rollback logic for each. If the saga fails partway, you run compensating actions in reverse order to undo the work that already succeeded.

The order checkout saga:

Step 1: Order Service       → CreateOrder         | Compensate: CancelOrder
Step 2: Payment Service     → ChargeCard          | Compensate: RefundCard
Step 3: Inventory Service   → DecrementStock      | Compensate: IncrementStock
Step 4: Shipping Service    → CreateShippingLabel | Compensate: CancelLabel

Happy path: all 4 steps succeed.

Sad path: step 3 fails (out of stock). Saga runs compensations in reverse: - Compensate step 2 (refund the charge). - Compensate step 1 (cancel the order).

User sees an "order failed" message. No charge on their card. No partial states.

                          SAGA EXECUTION

HAPPY PATH:

CreateOrder ──► ChargeCard ──► DecrementStock ──► CreateShippingLabel ✓ ✓ ✓ ✓ SAGA COMPLETE

─────────────────────────────────────────────────────────────────────

SAD PATH (decrement fails):

CreateOrder ──► ChargeCard ──► DecrementStock (FAILS — out of stock) ✓ ✓ ✗ │ ▼ RefundCard ◄── CancelOrder ✓ ✓ SAGA COMPENSATED

Each step is a regular local transaction. Each step has a compensating "undo" step. No global locks. No coordinator-can-die-and-hang issue.

Two saga implementations

Choreography

Each service publishes events. Other services react. No central coordinator.

Pro: simple, decoupled, no coordinator failure mode.

Con: hard to reason about — flow is implicit. Hard to debug "where is this saga right now?"

Common implementation: services publish to Kafka; other services subscribe.

Orchestration

A central orchestrator tells each service what to do step-by-step.

Pro: centralized state — easy to inspect "saga at step 3 of 4."

Con: orchestrator is now a critical service that needs HA.

Common implementation: workflow engines like Temporal, AWS Step Functions, Camunda.

Choreography vs orchestration in practice:

For 2-3 service flows, choreography is simple and good enough. Each service emits an event; the next reacts. Easy to add new services.

For 5+ service flows or complex error handling, orchestration wins. You can see the whole saga state in one place. Debugging is much easier — "where is this transaction stuck?" has an answer.

Temporal is currently the dominant orchestration framework for sagas. It handles retries, timeouts, compensations, and durable state. Mention Temporal in an interview about saga implementation and you sound like someone who's actually built one.

Sagas aren't free

Sagas trade atomicity for flexibility. They're not transactions — they're workflows. Specific costs:

No isolation. During a saga, intermediate states are visible to other readers. The user might see "order created but not yet paid" in their order history briefly. The system has no concept of "this saga's work is invisible until complete."

Compensations aren't always possible. "Send notification email" is hard to compensate — you can send a "disregard previous email" follow-up, but the original was already sent. Some real-world actions are irreversible. The saga has to be designed knowing this.

Compensations can fail too. If your saga is compensating, what if the refund itself fails? Now you have a failed compensation in addition to the original failure. Need to retry, escalate, or accept manual intervention.

Eventual consistency. Until the saga completes, the system is in an intermediate state. Other parts of the application have to handle this gracefully or wait.

The "irreversible action" problem:

A saga step sends an email confirming the order. Step 3 then fails (inventory out). The saga compensates back: refund, cancel order. But the email already went out. The customer received "Your order is confirmed." Now they get a second email "Your order is canceled." They are confused. They call support.

The fix isn't compensation — it's not sending the email until the saga can't possibly fail. Move the email step to after all other steps succeed. Order steps so irreversible ones come last.

This is a key saga design principle: put the most reversible steps first, the most irreversible last. The saga can fail and compensate the early steps with no user-visible damage. Only commit to irreversible side effects when you know the rest succeeded.

Idempotency: the foundation

Now we get to the real foundation underneath all of this.

An operation is idempotent if applying it multiple times has the same effect as applying it once. f(f(x)) = f(x).

In distributed systems, every operation might be retried. Every message might be redelivered. Every network blip might cause a duplicate. If your operations aren't idempotent, retries can corrupt state.

Why retries demand idempotency:

Service A calls Service B's decrementStock endpoint. Network blip. Service A doesn't get the response. Service A retries.

But the first call did succeed — Service B decremented the stock. Service A's retry causes a second decrement. Stock is now -1 when it should be 0.

The fix: Service B's endpoint must be idempotent. It must recognize "this is the same call as before" and not double-decrement.

Three patterns for idempotency

The patterns:

Idempotency keys. Caller generates a unique ID per logical operation. Server stores "I've processed key X" in a deduplication table. On retry with same key, server returns the cached result without re-executing.

Conditional updates. Use the data state itself as the conditional. UPDATE accounts SET balance = balance - 100 WHERE id = 1 AND last_txn_id != 'abc123' — second time around, the WHERE fails, no change.

Operation log. Record every applied operation. On retry, check if it's in the log. Replay only operations not already applied.

Idempotency keys are the dominant pattern in modern APIs.

Stripe pioneered this for payments — every charge request includes an Idempotency-Key header. The same key returns the same response, even if you call the API a thousand times.

The implementation: - Server has a deduplication table: (idempotency_key, response_body, expires_at). - Incoming request: check if key exists. If yes, return stored response without re-executing. If no, execute normally and store the result. - Keys expire (typically 24h) — old retries are unlikely.

Use idempotency keys for any external API call, especially payments and other irreversible actions. Mention "idempotency keys" in any distributed-systems interview and you signal real-world API design experience.

A subtle gotcha: idempotency must be at the operation level, not the request level. If the request is the same byte-for-byte but the logical operation it represents is different (different user, different time), it's not the same operation.

The fix: include semantically meaningful parts in the key. Stripe's idempotency key is a per-charge UUID generated by the client — guaranteed unique per logical charge attempt.

Naturally idempotent operations

Some operations are inherently idempotent:

  • SET balance = 500 — no matter how many times applied, balance is 500. Idempotent.
  • DELETE row WHERE id = 5 — first call deletes, second call says "0 rows affected" but state is the same. Idempotent.
  • UPSERT row WITH id = 5, balance = 500 — same effect each time. Idempotent.

Some operations are inherently NOT idempotent:

  • UPDATE balance = balance + 100 — applies the addition each time. Not idempotent.
  • INSERT new_row(...) — each call creates a new row. Not idempotent (unless using ON CONFLICT).
  • SEND_EMAIL(...) — each call sends another email. Not idempotent.

Design favors the first kind when you can. Express operations as "set X to Y" rather than "increment X by Y." Use UPSERTs instead of INSERTs. The state-based formulation is naturally retry-safe.

The transactional outbox pattern

A specific saga problem: how do you reliably send an event to Kafka and commit a database row, in a way that doesn't lose either?

The dual-write problem:

Naive approach:

BEGIN;
UPDATE orders SET status = 'paid' WHERE id = 42;
COMMIT;
publishToKafka("order_paid", {id: 42});  -- network call

What if Kafka is down between the COMMIT and the publish? The DB updated; the event never sent. Inconsistent.

Reverse:

publishToKafka("order_paid", {id: 42});
BEGIN;
UPDATE orders SET status = 'paid' WHERE id = 42;
COMMIT;

What if the DB update fails after the Kafka send? Event sent for an order that never updated. Inconsistent.

There's no way to atomically commit to both without 2PC, which we've ruled out.

The transactional outbox pattern: write the event to a database table (in the same transaction as the order update). A separate process polls the table and publishes events to Kafka, then deletes them from the outbox.

The same database transaction commits both the order and the event. They're atomic. The publish-to-Kafka step is now decoupled, retryable, and observable.

              TRANSACTIONAL OUTBOX PATTERN

┌─── Application ────┐ │ │ │ BEGIN; │ │ UPDATE orders... │ ───┐ │ INSERT INTO │ │ Atomic: both succeed or both fail │ outbox(event) │ ───┘ │ COMMIT; │ └────────────────────┘ │ ▼ ┌────────────────────┐ │ outbox table │ rows queued for publishing │ (event_id, │ │ payload, │ │ sent_at: NULL) │ └─────────┬──────────┘ │ poller / Debezium reads new rows ▼ ┌────────────────────┐ │ Kafka │ └────────────────────┘ │ consumers ▼ downstream services

Two implementations of the outbox pattern:

1. Application-level poller. A worker process polls the outbox table for unpublished rows. Publishes each to Kafka. Marks as sent (or deletes). Simple, can be implemented in any language.

2. CDC-based outbox. Use Debezium (Module 11) to capture inserts to the outbox table and publish to Kafka automatically. No separate poller. The DB's WAL is the source of truth.

CDC-based is the modern preferred pattern when you have CDC infrastructure already. Lower latency, no polling overhead, handles ordering naturally.

Mention "transactional outbox with CDC" in an interview about distributed messaging and you sound like someone who's done this. It's the canonical solution.

Three more ways to think about it

Way 1: a wedding ceremony.

2PC is the wedding ceremony itself. The officiant (coordinator) asks each party "do you take..." and waits for "I do" from both. If either says no, the ceremony halts. If both say yes, they're married.

But what if the officiant has a heart attack mid-ceremony, after both said "I do"? Are they married? No paperwork is signed. Legally ambiguous. That's the 2PC blocking problem.

A saga is the engagement period instead. Each step (proposal accepted, ring bought, venue booked, invitations sent) is its own commitment. If the engagement breaks, each step has its own undo (return ring, cancel venue, send "wedding canceled" notes). It's not atomic — there's a period where some steps are done and others aren't — but each individual step is durable on its own.

Way 2: shipping a package.

2PC is delivering all packages in a single truck — every recipient must confirm receipt before the trip is "done." If any recipient is unavailable, the truck waits in the driveway, holding all the packages. A breakdown means everyone gets their delivery delayed.

A saga is independent shipments. Each package goes its own way. If one fails, you compensate (issue a refund, send a replacement) without affecting the others. More flexible. No central truck waiting on anyone.

The transactional outbox is the shipping label printed before the package leaves. Once the label exists in the system, the carrier picks it up later — reliably, even if the printer crashes immediately after.

Way 3: signing a contract with multiple parties.

2PC is everyone signing simultaneously in the same room. Everyone says "ready," everyone signs at once. Powerful guarantee. But if one person doesn't show up, nothing happens.

A saga is sequential signing — one party signs and sends the contract to the next. If one party refuses, you go back and explain to the previously-signed parties that the deal's off. Everyone has their own undo (rip up their copy). Less elegant; more practical when scheduling all parties simultaneously is impossible.

Idempotency is making sure that if the contract is somehow signed twice by the same person (mistake, retry), it's still treated as one signature. Each signature has a unique key; duplicates are silently ignored.

Sharpen your pencil

Exercise 1. A team is building a checkout flow involving order, payment, inventory, and shipping services. They're debating: 2PC, choreography saga, or orchestration saga. What do you tell them?

Skip 2PC. Across 4 microservices, the coordinator-blocking failure mode would dominate. One coordinator crash leaves all services with locked resources. Even if it works in steady state, the operational pain is too high.

Choose between choreography and orchestration based on flow complexity.

For 4 steps with clear ordering and reversibility, orchestration is probably better. Reasons: - Centralized saga state means you can inspect "where is this transaction now?" easily. - Compensations are explicit and easier to audit. - Tools like Temporal handle retries, timeouts, and durable state — you don't reinvent.

Choreography would mean each service emits events on completion, and the next listens. Simpler infrastructure, but: - The flow is implicit in the events. Harder to debug. - Adding a new step means changing event subscriptions across services. - Compensation flow is harder to coordinate without a central authority.

The recommendation: orchestration with Temporal (or AWS Step Functions, or Camunda). Define the saga workflow explicitly. Implement each service's "do" and "compensate" steps. Make every operation idempotent (idempotency keys for external calls). Order steps so the most irreversible (sending email, charging card) come last.

Document the compensation logic carefully — that's where junior engineers cut corners and senior ones spot trouble. The "what if compensation itself fails?" question must have an answer (retry, alert, manual escalation).

Exercise 2. A coworker proposes implementing an idempotent payment endpoint by storing the entire request body as a hash and rejecting duplicates. What concerns would you raise?

Three concerns:

1. Request body equality is not the same as logical operation equality.

Two charges for $50 from the same user could be intentional (they bought two things separately). Hashing the request body would silently reject the second one. The user's second purchase is silently dropped. Worse than no idempotency.

Fix: idempotency keys must be unique per logical operation — generated client-side per checkout attempt. Stripe's pattern: client generates a UUID per intent to charge.

2. Hash collisions and edge cases.

If hashing produces collisions (extremely unlikely with SHA-256 but possible), or if the hash is computed on different fields than expected, you get hard-to-debug "duplicate" failures. Idempotency keys should be opaque tokens chosen by the client, not derived from the request.

3. The dedup table needs lifecycle management.

If every payment hash is stored forever, the table grows unboundedly. Stripe's approach: keys expire after 24h. Old retries are unlikely. The table stays bounded.

The corrected design: - Caller generates an idempotency key (UUID) per logical operation. - Server's dedup table: (idempotency_key, response_body, created_at). - On request with key X: check if X exists. If yes, return the stored response. If no, process and store. - Keys expire after a reasonable retention period (24h).

The senior framing: idempotency is a contract between the caller and the API, with the caller responsible for unique keys. Don't try to derive idempotency from the request alone — give the caller the responsibility, since only they know what's a "logical operation."

Exercise 3. Explain to non-technical Sam, in two sentences, why the transactional outbox pattern exists.

When your application needs to do two things at once — like updating a database row and sending a notification to another service — there's a fundamental problem: you can't make both succeed or both fail atomically across systems that aren't in the same database. The outbox pattern sidesteps this by writing the "send a notification" instruction into the same database as a row in a special outbox table; a separate worker reads that table and actually delivers the notification, so the database commit guarantees both pieces happen exactly once.

There are no dumb questions

Q: Are sagas just "eventual consistency"?

A: They're a specific way to implement eventual consistency for multi-step flows. Eventual consistency is the broader concept — "the system will become consistent eventually." Sagas are a structured pattern for getting there with explicit forward and compensating actions. Not all eventually consistent systems use sagas; not all sagas explicitly call themselves "eventually consistent."

Q: When SHOULD I use 2PC?

A: Inside a single database (multiple tables), regular transactions handle this — that's not 2PC. Across databases or services, 2PC is rare in modern systems. Where you'll see real XA: legacy enterprise systems, especially with established middleware (IBM MQ, Tibco), and some financial systems with hard atomic-commit requirements. Almost no modern greenfield system adopts 2PC.

Q: What's the difference between a saga and a workflow?

A: A saga is specifically a multi-step flow with compensating actions. A workflow is a more general term — any orchestrated multi-step process, with or without compensations. All sagas are workflows; not all workflows are sagas. Tools like Temporal handle both shapes.

Q: How does the outbox pattern handle ordering?

A: With CDC-based outbox, ordering is preserved — the WAL captures changes in commit order, so events are published in the order they were committed. With application-poller outbox, you must explicitly order by insertion timestamp or sequence number. Multi-partition Kafka topics can break ordering across partitions; use a partition key (typically the entity ID) to keep related events on the same partition.

Q: Is idempotency the same as exactly-once delivery?

A: Related but distinct. Exactly-once delivery is a guarantee that a message is delivered exactly once between systems — usually impossible in pure form due to network unreliability. Idempotency is an effectively-once-processing model on top of at-least-once delivery. The message might arrive twice; the operation processes it once. Most "exactly once" systems are really "at least once delivery + idempotent processing."

Q: What's a "compensating action" if a delete?

A: A delete's compensation is insert the row back. But: was the row referenced elsewhere? Did anyone read the deleted state? You can't fully unwind some deletes — they're effectively irreversible. Senior pattern: avoid deletes in saga steps; use soft deletes (status flag) instead, with the compensation being "set status back." Real deletion happens later, outside any saga.

Q: What if my saga is taking forever and the user has navigated away?

A: Sagas are async by design. The user shouldn't wait synchronously for the whole saga to complete. Pattern: return immediately with "your order is being processed," show progress on a status page or via push notifications, complete the work asynchronously. Sync UX requires sub-second saga completion; long sagas always need async UX.

Q: How do I test sagas?

A: Hard. You need to test happy paths plus every step's failure-and-compensation flow. Unit tests cover individual services. Integration tests cover the saga flow with deliberately-injected failures at each step. Tools like Temporal have built-in test frameworks. Plan testing time when designing sagas — they have N+1 paths that all need verification.

Three myths to dynamite

"2PC is the standard way to do distributed transactions."

Misleading. 2PC is the textbook way. The production reality is that sagas plus idempotency dominate, with 2PC reserved for legacy enterprise systems and a few specific use cases. If you say "we'll use 2PC" in an interview without acknowledging its operational issues, you sound like you've read a textbook but not run a system.

"Eventual consistency is bad."

False. Eventual consistency is a trade-off — you give up immediate consistency for availability and partition tolerance. Many things in the real world are eventually consistent (mail delivery, bank deposits clearing, social media notifications) and the systems work fine. The bad version is unmanaged eventual consistency where users see contradictory data with no UX accommodation.

"If my operation is naturally idempotent, I don't need idempotency keys."

Half-true. An operation can be idempotent at the data level but still have observable side effects. SET balance = 500 is idempotent but if you accidentally set it three times for three different intended transitions, you've lost two updates. Idempotency keys at the API layer protect against retry-induced lost intents; intrinsic idempotency at the data layer protects against retry-induced state corruption. Both are useful for different reasons.

Interview gotchas

Recommending 2PC for distributed transactions. Even mentioning 2PC without immediately acknowledging its operational issues sounds textbook-only. Senior engineers know 2PC works in theory and saga patterns dominate in practice.

Forgetting compensation actions in saga descriptions. A saga without explicit compensations isn't a saga — it's just a sequential flow that can leave inconsistent state on failure. Always describe both the forward step and the compensation step.

Not addressing irreversible actions. Some saga steps can't be perfectly undone (sent emails, charges to external systems). The senior pattern: order steps so reversible ones are first, irreversible ones last. Mention this when describing saga design.

Treating idempotency as an implementation detail. Idempotency is a contract with callers. The API design includes idempotency keys; the documentation specifies their semantics; the dedup logic is part of the system architecture. Not an afterthought.

Recommending dual writes (DB + Kafka) without the outbox pattern. "Just write to both" introduces silent inconsistency on partial failure. The outbox pattern is the canonical fix. Mention it whenever the dual-write problem comes up.

Mock interview

You're building a checkout system that involves an order service, a payment service, and an inventory service. Walk me through the design.

Sounds like a saga problem. Let me walk through the design.

The core flow: when a user clicks "buy," we need to: (1) create an order, (2) charge the card, (3) decrement inventory. If any step fails, the earlier steps need to be undone.

Architecture choice — saga, not 2PC. Across these three services, 2PC's blocking failure mode would dominate. A saga gives us flexibility and isolates each service's transaction.

Saga choreography vs orchestration? For three steps, choreography would work — order publishes "OrderCreated," payment subscribes and publishes "PaymentCharged," inventory subscribes and publishes "InventoryDecremented." But I'd lean toward orchestration here because: - Adding a fourth service (shipping, notifications) is easier with explicit orchestration. - Compensating flow is more visible. - Debugging "where is this saga now?" is easier with centralized state.

My recommendation: Temporal as orchestrator. Define the saga as a workflow; each service exposes "do" and "compensate" endpoints; Temporal handles retries, timeouts, and durable state.

The flow:

Step 1: CreateOrder         | Compensate: CancelOrder (mark cancelled, no delete)
Step 2: ChargeCard          | Compensate: RefundCard (idempotent refund API)
Step 3: DecrementStock      | Compensate: IncrementStock
Step 4: SendConfirmation    | (no compensation needed if step 4 only fires on success)

Step ordering matters. Notice step 4 is intentionally last and not compensated — it's the irreversible action. We send the email only after everything else succeeds. If step 3 fails, we compensate steps 2 and 1 cleanly, never sending an email about a failed order.

Idempotency everywhere. Every endpoint must accept an idempotency key. The saga retries on transient failures; without idempotency, retries cause duplicate charges or double-decremented stock.

The transactional outbox for the saga's own state. The orchestrator's "saga step completed" events are written to its DB and to Kafka via the outbox pattern, so we never lose state on orchestrator failure.

UX consideration. This saga might take 1-3 seconds. Don't block the UI synchronously. Return immediately: "your order is being processed." Show progress via WebSocket or polling. Push notification on completion.

Failure handling beyond compensations. If the saga is stuck (e.g., one service permanently down, compensation failing), Temporal can alert and escalate to a human operator. Plan for "compensations also fail" — sometimes manual intervention is the right answer.

The senior framing: distributed transactions are hard. The right answer is to make them recoverable, observable, and idempotent — not to chase atomic guarantees that don't exist across services.

Names tools (Temporal). Walks through the failure modes and compensation order. The "step 4 is irreversible and intentionally last" detail is senior-level. The "compensations also fail" plan acknowledges reality.

The team is worried about double-charging customers if the payment service is retried after a network blip. How do you ensure that doesn't happen?

This is the canonical idempotency case. The pattern:

Client generates an idempotency key. A UUID, generated when the user clicks "pay." The same key is sent on every retry of that one logical charge attempt.

Payment service has a deduplication table.

CREATE TABLE payment_dedup (
  idempotency_key UUID PRIMARY KEY,
  response_body JSONB,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

On every charge request: 1. Begin transaction. 2. Try to INSERT into the dedup table. If conflict (key exists), return the stored response. 3. Process the charge (call to the card processor). 4. Store the response in the dedup table. 5. Commit.

Key details:

  • The dedup INSERT and the charge happen in the same transaction. If the charge fails, the dedup row isn't committed. Next retry can attempt afresh.
  • The card processor itself should also support idempotency keys — pass through the same key. Stripe natively supports Idempotency-Key headers for exactly this reason.
  • Keys expire after 24h. Beyond that, retries are unlikely. Old keys get cleaned up; the table stays bounded.

Common mistakes to avoid:

  • Hashing the request body instead of using a key. Two intentionally-distinct charges with the same body get rejected. Bug.
  • Not propagating the key downstream. If the payment service does its dedup but calls the card processor without an idempotency key, the card processor can charge twice on retry. Pass keys through the entire chain.
  • Forgetting key expiration cleanup. The table grows unboundedly without it.

The senior framing: idempotency is a contract — the caller commits to unique keys per intent, the server commits to dedup-and-replay-result. Document this in the API spec. Test it with deliberate duplicates.

Concrete schema. Specific details (Stripe's Idempotency-Key header). Names the common mistakes. The "contract" framing — senior engineers think of idempotency at the API design layer, not the implementation layer.

What if the saga's orchestrator itself crashes mid-saga? How do we recover?

This is exactly why orchestrator durability matters. A few layers of mitigation:

Layer 1: durable state. The orchestrator must persist saga state at every step boundary. Tools like Temporal use an event-sourced model — every step transition is logged. On orchestrator restart, the saga state is reconstructed from the log, and execution resumes from the last consistent point.

Layer 2: idempotency on every step. When the orchestrator restarts, it might re-issue commands the dead orchestrator already issued. Each service must handle this — usually via the same idempotency key pattern. The service recognizes "I already processed this" and returns the same result.

Layer 3: timeouts on stuck steps. If a step has been "in progress" for longer than expected, the orchestrator probes the service: "is this step done yet?" If yes, advance. If no, retry or escalate. Without this, a saga can wait indefinitely on an unresponsive service.

Layer 4: human-readable saga state. Operations should be able to query "where is saga X right now?" and see something like "Step 3 of 4: ChargeCard, in progress, started at 10:23:14, retried 2 times." This is essential for debugging stuck sagas.

Layer 5: explicit failure-handling actions.

What if compensations themselves fail? Pattern: - Retry compensations a few times. - After N retries, mark the saga as "failed, needs manual attention." - Alert the on-call engineer. - Provide tooling to manually complete or roll back individual steps.

A real failure mode I'd plan for: orchestrator crashes mid-compensation. Now you've completed compensations for steps 4 and 3, but step 2's compensation is unknown. On restart, idempotency lets you safely re-issue compensation for step 2. If it succeeded the first time, it's a no-op. If it didn't, it now does.

Tools: Temporal handles most of this out of the box. AWS Step Functions handles it via a different mechanism (state machine with explicit retry config). Camunda has long-standing BPMN workflow support.

The senior framing: orchestrator failure is a plan-for-it concern, not an avoid-it concern. Distributed systems crash. The orchestrator needs durable state, idempotent steps, timeouts, observability, and manual escalation paths. With those in place, an orchestrator crash is a 10-minute incident, not a 24-hour one.

Five-layer answer covering durability, idempotency, timeouts, observability, and manual escalation. Acknowledges that compensations themselves can fail. Names specific tools. The "plan-for-it not avoid-it" framing is the senior reflex.

Last one. Your team uses dual writes — write to Postgres, then send to Kafka. They've started seeing inconsistencies. How would you fix it?

This is the classic dual-write problem, and the canonical fix is the transactional outbox pattern.

The bug they're hitting:

BEGIN;
UPDATE orders SET status = 'paid';
COMMIT;
publishToKafka("order_paid");  // can fail after commit

If publishToKafka fails, the DB has the update but Kafka doesn't. Other services don't see the event. Inconsistent.

Reverse order has the symmetric problem — Kafka has the event but the DB might not have committed.

The outbox fix:

Add a table to the same database:

CREATE TABLE outbox (
  event_id UUID PRIMARY KEY,
  payload JSONB,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  sent_at TIMESTAMPTZ
);

Now the application does:

BEGIN;
UPDATE orders SET status = 'paid';
INSERT INTO outbox (event_id, payload) VALUES (...);
COMMIT;

The order update and the event insert happen in the same transaction. They're atomic.

Then a publisher process delivers events.

Two implementations:

Option A: Application-level poller. A worker queries SELECT * FROM outbox WHERE sent_at IS NULL ORDER BY created_at LIMIT 100, publishes each to Kafka, and updates sent_at = NOW(). Simple but requires a poller per service.

Option B: CDC-based. Use Debezium to capture inserts to the outbox table and publish to Kafka automatically. No separate poller needed; the WAL is the source of truth. This is the modern preferred approach if you have CDC infrastructure.

Why this works:

  • The outbox INSERT and the business state change are atomic (same transaction).
  • The publisher reads from the outbox; it can retry indefinitely until Kafka accepts.
  • If the publisher crashes, on restart it resumes from the unprocessed outbox rows.
  • Consumers see events in the same order they were committed (with proper partitioning).

Operational details:

  • Outbox rows need cleanup (after some retention, delete sent rows).
  • Idempotency keys propagated as the event ID — downstream consumers can deduplicate.
  • Monitoring: alerting on outbox backlog age (rows older than X with sent_at IS NULL mean publisher is stuck).

The migration: to introduce this without a big rewrite, change the application code to write to the outbox alongside business updates (or via CDC capturing existing tables). Migrate the publishing layer to read from the outbox. The dual-writes can be removed once the outbox is verified.

The senior framing: the outbox pattern is the canonical solution to the dual-write problem. Mention it whenever someone says "we need to write to the database and also publish an event." The naive "just write to both" almost always silently corrupts data.

Concrete schema. Two implementation options ranked. Operational details (cleanup, monitoring). The "migration" plan acknowledges the team isn't starting from scratch. The "canonical solution" closing is the right framing — outbox is the answer to dual-writes.

Cheat sheet

Distributed Transactions, Sagas & Idempotency — One Page

2PC (textbook, rarely production)

Coordinator-managed atomic commit. Phase 1: prepare. Phase 2: commit/abort. Blocking failure mode: coordinator crash leaves participants with held locks indefinitely. Used in legacy enterprise (XA transactions). Almost no modern system adopts.

3PC (academic)

Adds pre-commit phase to fix 2PC's blocking. Assumes synchronous network — which real networks aren't. Rarely deployed.

Sagas (the production pattern)

Sequence of local transactions, each with a compensating action. Forward path on success; reverse compensations on failure.

Two implementations: - Choreography: services emit events, others react. Decoupled, hard to debug. - Orchestration: central orchestrator coordinates steps. Easier to inspect; orchestrator is critical service.

Tools: Temporal (modern dominant), AWS Step Functions, Camunda.

Saga design rules

  1. Order steps: most reversible first, most irreversible last.
  2. Every step has a compensation (or document why it's irreversible).
  3. Idempotency on every step — retries are expected.
  4. Plan for compensations failing — manual escalation path required.
  5. Async UX — long sagas don't fit synchronous request/response.

Idempotency

Definition: f(f(x)) = f(x). Applying twice = applying once.

Patterns: - Idempotency keys (Stripe-style): caller-generated UUID per logical operation. Server dedupes via key. - Conditional updates: UPDATE ... WHERE state = expected. - Operation log: record applied operations, skip duplicates on retry.

Naturally idempotent: SET, UPSERT, DELETE. Naturally NOT idempotent: INCREMENT, INSERT, send_email.

Transactional outbox pattern

Solves the dual-write problem (DB + Kafka).

BEGIN;
UPDATE business_table;
INSERT INTO outbox (event);
COMMIT;

Then publisher (poller or CDC) sends from outbox to Kafka.

Atomic — both write together. Reliable — publisher can retry. Modern preferred: use Debezium for CDC-based outbox.

When to use what

Need Use
Atomic across single DB Regular transaction
Atomic across services, can't tolerate eventual 2PC (rarely; legacy systems)
Atomic-ish across services, can tolerate eventual Saga
Reliable DB → Kafka publish Transactional outbox
API retry safety Idempotency keys

Anti-patterns

  • 2PC for greenfield distributed transactions.
  • Sagas without explicit compensations.
  • Dual writes without the outbox pattern.
  • Hashing request body for idempotency (use unique keys).
  • Forgetting that compensations themselves can fail.

The 30-second verbal answer

"2PC is the textbook answer for distributed transactions but rarely used in production due to blocking failure modes. Sagas — sequences of local transactions with compensating actions — are the modern pattern. Idempotency is the foundation: every step must be safely retryable, typically via idempotency keys. The transactional outbox pattern solves the dual-write problem (DB + Kafka). Tools like Temporal handle saga orchestration; the senior skill is matching pattern to problem."
