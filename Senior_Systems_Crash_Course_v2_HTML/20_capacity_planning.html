MODULE 20

Capacity Planning & When to Scale

Growth modeling, headroom thresholds, load testing, and the engineering-leadership conversations that decide when to spend money on scale

Two days before Black Friday, the VP of Engineering asks: "Are we going to be OK?" Junior engineers say "should be fine." Mid-level engineers say "we tested last week, we're good." Senior engineers pull out the capacity model — a spreadsheet, a load test report, and a written argument for which resource will saturate first and at what traffic level.

Capacity planning isn't paranoia. It's the discipline of turning "we'll add servers if we need them" into a defensible engineering plan, with numbers, dates, and triggers. This chapter is how to build that plan, how to load-test honestly, and how to have the conversation with your VP without hand-waving.

Sam guesses at capacity

Sam We've grown 3x this year. The CTO asked "can we handle next year's traffic?" I said "yeah, we should be fine — we have lots of headroom." She asked me to back that up with numbers. I'm not sure where to start. CPU is at 40%, memory's at 50%, our database has 30% headroom. We're fine, right?

Maya You just told me the dashboards' instantaneous values. That's not capacity planning. Capacity planning is: "at our projected growth rate, which resource will saturate first, when, and what's our plan when it does?"

Sam But CPU is only at 40%. We have 60% headroom.

Maya Wrong. You don't have 60% headroom. You have the headroom of your most-saturated resource at peak traffic. If CPU is 40% on average but spikes to 95% during the noon rush, your real headroom is 5%. And growth doesn't move resources uniformly — write traffic might double while CPU stays flat, exhausting your IOPS budget. Or read traffic might 10x while CPU barely moves but your replication lag explodes.

Sam So what do I actually do?

Maya Three things. Model what each resource looks like at 2x, 5x, 10x current traffic. Identify the first resource that hits a saturation wall. Plan the mitigation for that wall — not with hand-waving, with a specific architectural change, a cost estimate, and a date you'd need to make the change.

Capacity planning is not about "do we have headroom?" — it's about "which resource saturates first, when, and what do we do about it?" Headroom is per-resource, not global. Growth amplifies different resources at different rates. Senior engineers build models that predict which wall you hit first and have a plan ready before you hit it.

The four resources every system runs out of

There are exactly four flavors of bottleneck a senior engineer plans for. Every capacity model decomposes into these four:

1. CPU The processor is busy. Symptoms: high utilization, high run queue, throttled containers. Scales with: request rate × CPU per request.

2. Memory RAM is full or being thrashed. Symptoms: swap activity, OOM kills, GC pressure, page cache evictions. Scales with: working set size, connection count, in-flight requests.

3. I/O (disk + network) Disk IOPS, disk throughput, network bandwidth, or packet rate. Symptoms: high I/O wait, queue depth, packet drops. Scales with: write rate, read miss rate, fanout.

4. Concurrency limits Connections, file descriptors, thread pools, lock contention, queue depth. Symptoms: timeouts, queue saturation, "connection refused." Scales with: concurrent users × duration per request.

The hidden fifth: external dependencies. Your system can have infinite headroom internally and still hit a wall because Stripe rate-limits you or S3's per-bucket throughput peaks or DNS queries to your DB hostname time out. Senior capacity planning includes an inventory of every external service in the request path with their published limits — and your current consumption against them.

Real example of "the wrong wall." A team I worked with planned for CPU growth, doubled their server count, and still went down at Black Friday. The actual bottleneck: their MySQL connection pool. Adding application servers made it worse — more apps competing for the same connection pool. Each app could handle 2x traffic but they collectively exhausted DB connections at 1.4x. The mitigation should have been a connection proxy (PgBouncer/ProxySQL) plus connection pooling tuning, not more application servers.

Lesson: doubling the dimension you measured doesn't help if the bottleneck is somewhere you didn't measure.

Little's Law: the math senior engineers cite

If you remember one formula from this chapter, remember this one. Senior interviewers reach for it constantly, and it's surprisingly powerful for back-of-the-envelope reasoning.

Little's Law: L = λ × W

Where L is the average number of items in the system (concurrency), λ is the arrival rate (requests per second), and W is the average time each item spends in the system (latency in seconds).

That's it. Three variables, one equation. Here's why it matters.

Worked example: how many threads do I need?

You're sizing a service. You expect 5,000 RPS. Average request latency is 200ms (0.2s). How many concurrent requests are in flight?

L = 5000 × 0.2 = 1,000 concurrent requests

If each request takes a thread, you need a thread pool of at least 1,000. With safety margin (say 1.5x for variability), size the pool to 1,500 threads.

If the pool is too small (say 500), incoming requests queue up. Queueing increases latency, which increases L (Little's Law again — higher W means higher L for the same λ), which deepens the queue, and now you have a feedback loop. This is queueing collapse.

Worked example: connection pool sizing.

You have 10 application servers, each handling 200 RPS. Your average database query latency is 5ms (0.005s).

Per server: L = 200 × 0.005 = 1 connection on average.

But that's the average. With p99 query latency at 50ms, occasional spikes need 10+ connections per server. So size each app server's pool at, say, 20 connections (with margin). Total DB connections needed: 10 servers × 20 = 200.

If your DB has max_connections = 100, you cannot serve this load. The fix is either a connection pooler in front of the DB (PgBouncer in transaction mode), increasing max_connections (with the memory cost), or reducing per-app connection counts (which means thread-pool tuning in the app).

"Little's Law turns vague capacity questions into specific arithmetic. 'Can we handle 10K RPS?' becomes 'at 200ms latency, we need 2000 concurrent slots — do we have them?' Always reach for the formula first."

Pause and think. Your service handles 1000 RPS. Latency averages 100ms. You add a feature that increases average latency to 500ms. Without changing traffic, what happens to in-flight concurrency?

Answer: L was 1000 × 0.1 = 100 in-flight. Now L = 1000 × 0.5 = 500 in-flight. Concurrency increased 5x with no traffic change. If your thread pool was sized for 100 with 50% margin (= 150), you've blown through it. The latency increase silently consumed your concurrency budget.

Modeling growth: from current state to future state

Capacity planning has two halves: predicting traffic growth and predicting resource consumption per unit of traffic. Both are needed.

Step 1: Project the demand curve

The demand model.

Pick the primary driver. For most consumer products: monthly active users. For B2B: customers and seats. For APIs: integrated partners. Then derive: requests per user per day → peak RPS → resource utilization at peak RPS.

Example projection for a SaaS product:

Quarter Customers DAU/Customer Total DAU Peak RPS Notes
Q1 (now) 500 200 100,000 2,000 Current state
Q2 700 220 154,000 3,200 Sales-driven growth
Q3 1,000 240 240,000 5,200 Marketing campaign
Q4 1,400 260 364,000 8,400 Year-end push
Year+1 2,500 280 700,000 17,000 8.5x current peak

Two growth multipliers compound: customer count and DAU/customer (engagement). Don't model just one.

Beware "linear projection." Real growth is rarely linear. Consumer products often follow logistic / S-curves (slow → exponential → saturation). B2B often follows step functions (big customer wins). Cyclic businesses have seasonal peaks 5-10x the baseline. Pick the model that matches your business — and plot the actuals against your projection monthly to know when you're off.

Step 2: Per-resource consumption rates

For each resource, ask: what does one unit of demand cost?

Per-resource cost decomposition.

For each request type (read, write, search, complex query): 1. CPU per request (microseconds of CPU) 2. Memory per request (bytes allocated, working set retained) 3. Disk reads per request (in IOPS) 4. Disk writes per request (bytes written, including WAL/redo) 5. Network in/out per request (bytes) 6. Cache impact per request (cache misses) 7. Database query count and average query latency

Then weighted-sum across the request mix:

Total CPU at peak = Σ (request_type_RPS × CPU_per_request)
Total IOPS at peak = Σ (request_type_RPS × IOPS_per_request)
... etc

Now you have a per-resource projection.

Concrete consumption model. A fintech API has three request types: balance lookup (90% of traffic, 5ms, 1 DB read), transaction submit (8% of traffic, 80ms, 5 DB ops), report generation (2% of traffic, 800ms, 50 DB ops).

At 5,000 RPS aggregate: - Balance lookups: 4,500 RPS × 5ms = 22.5 CPU-seconds/sec → ~23 CPU cores - Transactions: 400 RPS × 80ms = 32 CPU-seconds/sec → ~32 cores - Reports: 100 RPS × 800ms = 80 CPU-seconds/sec → ~80 cores

Total: ~135 CPU cores. Plus headroom (50%) → 200 cores. With 32-core machines, that's 7 servers.

But check the database dimension separately: - DB ops/sec: (4,500 × 1) + (400 × 5) + (100 × 50) = 11,500 ops/sec. - That probably needs a beefier DB or read replicas.

Notice: report generation is 2% of traffic but 60% of CPU. Senior insight: optimize the expensive minority, not the cheap majority. A 2x speedup on reports moves the system more than a 2x speedup on balance lookups.

Step 3: Identify the first wall

Finding the saturation point per resource.

For each resource, compute: at what RPS does this resource hit 80% utilization?

Resource Current util at 2K RPS Saturation point (extrapolated) First-wall RPS
App CPU 40% 5,000 RPS at 100% 4,000 RPS @ 80%
DB CPU 30% 6,667 RPS at 100% 5,300 RPS @ 80%
DB IOPS (writes) 50% 4,000 RPS at 100% 3,200 RPS @ 80%
Connection pool 70% 2,857 RPS at 100% 2,300 RPS @ 80% ← FIRST WALL
Network 20% 10,000 RPS at 100% 8,000 RPS @ 80%
Cache memory 60% 3,333 RPS at 100% 2,700 RPS @ 80%

At 2,300 RPS (15% above current), you exhaust the connection pool. That's the first wall. Plan that mitigation first. After that, plan for cache memory at 2,700, then DB IOPS at 3,200.

Senior insight: each wall mitigation extends runway, but only to the next wall. Map them all upfront.

The 80% threshold isn't arbitrary. Queueing theory shows that latency rises non-linearly as utilization approaches 100%. At 50% utilization, latency might be 2x the service time. At 80%, it's 5x. At 95%, it's 20x. By the time utilization hits 90%, you're already in a customer-painful regime. Plan for 80% peak utilization, not 99%, because the last 20% buys you crash space when traffic spikes unexpectedly.

Step 4: Plan the mitigations

The mitigation roadmap.

For each wall, document: 1. What's the wall? (specific resource, expected saturation point) 2. What's the mitigation? (specific architectural change) 3. What's the cost? (engineering days, infrastructure $/month) 4. What's the lead time? (how long does the change take) 5. What's the trigger? (RPS or other signal that means "start the change now")

Example:

# Wall Mitigation Eng cost $ cost Lead time Trigger
1 Conn pool @ 2.3K RPS Add PgBouncer (transaction pool mode) 5 days $200/mo 1 week 1.8K RPS
2 Cache mem @ 2.7K RPS Upgrade Redis to larger instance 1 day $500/mo 2 days 2.4K RPS
3 DB IOPS @ 3.2K RPS Migrate to gp3 or io2 EBS 3 days $800/mo 1 week 2.8K RPS
4 App CPU @ 4K RPS Auto-scaling group + larger instances 2 days $1.5K/mo Existing 3.5K RPS
5 DB CPU @ 5.3K RPS Read replicas, route reads 10 days $2K/mo 3 weeks 4K RPS

This is the senior deliverable. Not a paragraph of "we should be fine" — a concrete table you can review with leadership and execute against.

Load testing: the discipline most teams skip

You can't trust models without validation. Load testing is where you confirm — or refute — your capacity projections. Most teams do this badly. Here's how to do it well.

The four levels of load testing

Level 1 — Smoke test Send 1 RPS for 5 minutes. Confirms the system works at all under synthetic load. Catches obvious config issues. Run on every deploy.

Level 2 — Load test Send expected peak traffic (e.g., 5,000 RPS) for 15-30 minutes. Validates that expected traffic is handled within SLO. Run weekly or before major launches.

Level 3 — Stress test Ramp from 0 to 2-5x expected peak. Find where things start breaking. Latency degrades? Errors appear? Critical for capacity planning.

Level 4 — Soak test Send moderate load (e.g., 70% of peak) for 12-24 hours. Catches memory leaks, file descriptor leaks, connection leaks, log/disk fill. Run before major releases.

The level senior engineers care most about: stress testing. Load tests confirm what you already think. Stress tests reveal what you don't. Always include a stress test phase that goes 2-3x your expected peak — that's where you discover the connection pool exhaustion at 1.4x, the GC pause at 2.1x, the cascading timeout at 2.7x. These are the things that ruin Black Friday.

Tooling

Load testing tools by use case:

  • k6 (Grafana) — modern, JavaScript-based, excellent for HTTP/REST/GraphQL. Best general-purpose choice today.
  • Locust — Python-based, great for complex user-journey simulation, write scripted scenarios easily.
  • vegeta — Go-based, simple, perfect for raw HTTP throughput tests.
  • wrk / wrk2 — extremely high throughput, low overhead, harder to script.
  • JMeter — heavyweight, complex, but battle-tested for enterprise (legacy choice in many orgs).
  • Gatling — Scala-based, code-as-config, strong reporting.
  • Artillery — Node.js, easy to start with, decent for moderate loads.

For database-specific load: sysbench, pgbench, mysqlslap, YCSB.

For API contract testing under load: Tavern, Karate, Postman (with collection runner).

Run load tests against a realistic environment. A load test against a 1-instance dev environment tells you about that 1-instance setup. The senior pattern: load test against production-shaped infrastructure (same instance types, same DB tier, same caching tier) — usually a "staging" environment that mirrors prod. Even better: replay production traffic in shadow mode to a candidate environment.

What to measure during a load test

Load test instrumentation checklist:

  1. Throughput: RPS achieved (vs RPS attempted). If you said "send 5K RPS" but the tool says "achieved 4.2K RPS," you've already found a bottleneck — the tool couldn't push that much.
  2. Latency distribution: p50, p95, p99, p99.9, max. Plot over time, not as point summaries.
  3. Error rate by type: timeouts, 5xx, connection refused, parse errors.
  4. Resource utilization on every tier: app CPU/mem, DB CPU/mem/IOPS, cache hit rate, network bandwidth.
  5. Saturation indicators: thread pool utilization, queue depths, connection pool usage.
  6. External dependencies: latency and error rate of every downstream service.
  7. Cost signals: cloud auto-scaling actions, throttling events, rate-limited responses.

Capture a baseline run before changes, then a candidate run after. Compare distributions, not point values.

Common load testing mistakes

Gotcha: closed-loop vs open-loop testing.

Most load tools default to closed-loop: a fixed number of virtual users, each one waits for a response before issuing the next request. This underestimates real load — when latency increases, virtual users naturally throttle themselves.

Real production traffic is open-loop: arrivals are independent of completions. If responses get slow, more requests pile up. Open-loop generates more pain. Most modern tools (k6, vegeta with -rate) support open-loop. Use it for capacity planning. Closed-loop is only realistic for fixed-user-count systems (like internal tools).

Gotcha: the cache-warming bias.

A 10-minute load test gives the cache 10 minutes to warm. Real traffic might never let the cache warm if the working set is too large. Senior pattern: run a cold-cache load test by clearing caches before starting, and a warm-cache test for steady state. Both numbers matter.

Gotcha: synthetic data vs real data shapes.

Loading 1M synthetic users with user_id 1-1000000 is not the same as loading 1M real users with skewed activity. Real users have hot accounts (Pareto distribution). Real queries have hot keys. Senior load tests use anonymized production traffic samples or zipfian-distributed synthetic loads, not uniform-random.

Vertical vs horizontal scaling: when to do which

The senior progression from Module 17 was: single → vertical → replicas → caching → horizontal → multi-region. Capacity planning is when you decide which step to take next. Here's the framework.

Vertical first, horizontal when forced. Vertical scaling (bigger machine) is operationally simpler, has fewer failure modes, and avoids distributed-systems complexity. Senior teams scale vertically until they hit a wall (single-machine limit, single-AZ failure domain, or per-instance limits like Postgres connections). Then they go horizontal — but only because they have to.

When vertical scaling is the right answer

Reach for vertical scaling when:

  1. Current instance has more headroom available. AWS RDS goes up to 24XL (96 vCPU, 768GB RAM). GCP and Azure have similar tiers. Most workloads can be served by a single beefy machine well into the millions of users.
  2. The workload is single-master or doesn't shard cleanly. A relational database with complex multi-table transactions is hard to shard. Buying a bigger box is the right answer for years.
  3. Operational simplicity is worth more than cost optimization. A 4xlarge costing 8x a small instance might be 2x more expensive but 100x easier to operate. For a Series-A startup, that's the right tradeoff.
  4. Compliance / data residency makes single-region single-instance preferred. Healthcare, finance, government workloads sometimes can't easily distribute.

When horizontal scaling is forced

You must scale horizontally when:

  1. You've hit the largest available instance. When the next vertical step doesn't exist, horizontal is the only path.
  2. Single-machine failure is too painful. If a 30-second restart costs you $500K, you need redundancy independent of vertical sizing.
  3. The workload genuinely shards cleanly. Per-tenant SaaS, per-user data, per-region data — these decompose naturally. Then horizontal scaling beats vertical because you get parallelism for free.
  4. Geographic distribution is needed. Vertical can't put compute closer to users in Tokyo. Horizontal across regions can.
  5. Cost crosses over. At very high scale, large instances become disproportionately expensive vs many smaller ones (the "scale-up tax"). For workloads above ~$10K/month per instance, scale-out often becomes cheaper.

Real example: when not to shard. A company with 50K users and 5K writes/sec on Postgres asked "should we shard?" Answer: no. A db.r6g.4xlarge (16 vCPU, 128 GB RAM) handles that load comfortably with 50% headroom. Sharding adds: cross-shard query complexity, distributed transactions, rebalancing operations, more failure modes. The engineering cost would be 6 months of work. The vertical scaling cost is $2K/month more.

Senior call: spend $24K/year ($2K × 12) on a bigger instance, save 6 months of engineering work, defer the sharding conversation until a real signal forces it (vertical wall hit, geographic distribution needed). Most teams shard 2-3 years too early because of "what if we grow?" fears.

"The cost of premature horizontal scaling is six months of distributed-systems complexity. The cost of late horizontal scaling is six weeks of crisis migration. Senior engineers prefer the second — they can see it coming."

Auto-scaling: when it works and when it doesn't

Auto-scaling sounds magical. "Just set it and the cloud handles it." Reality is more nuanced.

When auto-scaling works well

Auto-scaling is a good fit when:

  1. Stateless services. Web servers, API gateways, processing workers — scale them up and down freely.
  2. Workloads with predictable patterns. Daily peaks, weekly cycles, traffic that takes minutes (not seconds) to ramp.
  3. You have leading indicators. CPU, request rate, queue depth — metrics that signal "more capacity needed" before the system breaks.
  4. Spin-up time is fast relative to spike duration. If a new instance takes 5 minutes to come online and your spike is 45 minutes, auto-scaling helps. If the spike is 90 seconds, it's already over.

When auto-scaling fails

Auto-scaling fails for stateful systems. Databases don't auto-scale by adding instances — that's replication setup, not scaling. Similarly: caches with sticky data, queues with consumer-group rebalancing pain, services with long-lived connections.

Auto-scaling fails for sudden spikes. A traffic spike from 1K to 50K RPS in 30 seconds gives auto-scaling no time to react. By the time new instances are up, the original ones have already failed. Mitigations: pre-provision for known spike events (Black Friday, product launches), use predictive scaling, or maintain a baseline of warm capacity higher than current need.

Auto-scaling can mask real problems. If your CPU is rising linearly because of a memory leak (more GC = more CPU), auto-scaling adds servers and hides the leak. Now you have 50 servers all leaking memory instead of 5. Always pair auto-scaling with anomaly detection on per-instance metrics.

The senior auto-scaling configuration: - Scale-out trigger: CPU > 70% for 2 consecutive minutes (lagging) OR request rate > N/server (leading). - Scale-in trigger: CPU < 30% for 15 consecutive minutes (slow scale-in to avoid flapping). - Min instances: cover your baseline + tolerate 1 AZ failure. - Max instances: cap at 3-5x baseline to prevent runaway scaling from causing runaway costs. - Cooldown: 5 minutes between scaling actions to avoid thrash.

The asymmetry — fast scale-out, slow scale-in — is intentional. Scaling out wrongly costs money. Scaling in wrongly causes outages. Bias toward keeping capacity.

Three exercises

Exercise 1: The capacity question for the VP.

Your CEO asks: "Can we handle 5x current traffic next quarter?" Current peak is 2K RPS. CPU on app servers averages 35% (peak 65%). DB CPU is 25% (peak 50%). Memory and network are well below 50%. What's your senior answer — and what specific data would you bring to back it up?

The right answer is neither "yes, we have headroom" nor "no, we'll fall over." Both are guesses. The senior answer involves a model.

Senior answer:

"I can give you a defensible answer in 48 hours. Here's what I need to do first:

  1. Run a stress test that ramps from 2K to 10K RPS over 30 minutes. This tells me empirically where things start to bend.
  2. Decompose per-resource consumption — at 2K RPS, what's the CPU/IOPS/connections/memory cost per request? Then linearly project to 10K RPS, while flagging non-linear resources (cache hit rates degrade with working-set growth).
  3. Identify the first wall — which resource saturates first when extrapolated? Based on what I see, candidates are: connection pool, DB IOPS, or app CPU during peaks. The stress test will confirm.
  4. Build a mitigation roadmap — for each wall, the architectural change, engineering cost, and lead time.

Then I can give you one of three answers: (A) 'yes, we can handle 10K with these specific changes by date X,' (B) 'we can handle 7K but not 10K without architectural change Y,' or (C) 'we have a wall at 4K we didn't know about, here's the mitigation.'

Hand-waving 'we have headroom' is how outages happen. Give me 48 hours and you'll get a real plan."

What this signals: you have a methodology, you respect the question, you're honest about uncertainty, and you're committing to a specific deliverable. That's a senior answer to a leadership question.

Exercise 2: The Black Friday plan.

You operate an e-commerce site that does 5K RPS normal, with Black Friday peaks historically 10-15x baseline. Black Friday is in 6 weeks. What's your capacity planning playbook?

6 weeks is enough time to do this well. Less than 4 weeks and you're cutting it close. Less than 2 weeks and you're hoping.

Senior playbook (week-by-week):

Week 1-2: Model and load test. - Project peak: assume 15-20x baseline (more conservative than historical, because traffic grows year-over-year). - Run stress test up to 25x baseline. Find walls. - Decompose by request type — Black Friday traffic is read-heavy on product pages, write-heavy on cart/checkout. Different mix from normal day.

Week 3: Implement mitigations. - For each wall identified: implement the change, deploy to production at low risk, validate. - Common Black Friday mitigations: pre-warm caches, increase auto-scaling max instances, raise connection pool limits, scale up DB tier for the event, add read replicas, shed non-critical features (recommendations, recently-viewed) under load.

Week 4: Game day. - Run a production load test in a controlled window (e.g., Sunday 3am). Push to expected peak. Validate the mitigations work end-to-end. - Run a chaos exercise — kill an instance, kill a cache, kill an AZ. Confirm graceful degradation.

Week 5: Pre-event prep. - Code freeze except for ops fixes. - Pre-provision capacity (don't rely on auto-scaling to react to a spike — pre-warm to expected peak). - Stage runbooks for every plausible failure mode. - Brief on-call rotation, escalation paths, war room logistics.

Week 6 (Black Friday week): Execute. - Day before: confirm provisioning, dry-run the runbooks. - During event: war room, dashboards on big screens, no deploys, on-call doubled. - After: post-event review (what scaled, what didn't, what we'd change next year).

Senior signal: specific timeline, named mitigations, game day in week 4, code freeze, pre-provision rather than rely on auto-scaling, post-event review. This is the muscle memory of someone who's done multiple Black Fridays.

Exercise 3: Vertical or horizontal?

You're at 80% CPU on a 32-vCPU PostgreSQL primary with 200GB working set. Traffic is growing 30% per quarter. Your team is debating: scale up to 96 vCPU (vertical) or shard the database (horizontal). What's your recommendation, and what data would change your answer?

This is the canonical "scale up vs scale out" decision. Senior engineers strongly default to vertical here.

Senior recommendation: vertical, with conditions.

Why vertical first: - Sharding Postgres is a major engineering investment (3-6 months of work). Vertical scaling is a maintenance window. - 96 vCPU buys you ~3x current CPU headroom. At 30% growth/quarter, that's 4-5 quarters of runway. That's significant. - Sharding adds query complexity, distributed transactions, and rebalancing operations. The operational cost continues forever. - Vertical preserves your option to shard later with more information.

The conditions where my answer would change: - Memory wall. If working set is growing toward the largest available instance's RAM, vertical hits a hard ceiling. Then horizontal is forced. - Single-AZ risk. If a 30-second outage of the primary is unacceptable (financial trading), the redundancy argument forces horizontal — though this is replication, not necessarily sharding. - Geographic distribution. If users are now in Asia and EU, vertical can't reduce their latency. Geo-sharding (or multi-region active-active) is forced. - Workload pattern change. If query patterns are becoming embarrassingly parallel (analytics workloads, high-fanout reads), horizontal reads via replicas might be cheaper than vertical primary scaling.

What I'd do this quarter: 1. Scale vertically to 96 vCPU. 2. In parallel, build the sharding capability — but don't deploy it yet. Get the partition key chosen, get the sharding proxy ready, build the migration tooling. 3. Re-evaluate next quarter with one more data point.

Senior signal: chose vertical, but built the optionality for horizontal. Identified the specific signals that would force the decision later. Treated this as a staged decision rather than a binary one.

No dumb questions

Q: What's a reasonable utilization target for production?

For latency-sensitive systems: 60-70% peak utilization. The remaining 30-40% is your crash buffer for unexpected spikes, instance failures, and the queueing-theory reality that latency rises non-linearly past 80%. For batch systems where latency doesn't matter: 85-90% is fine. The number is not 95% — that's where things break.

Q: How far ahead should I plan capacity?

The horizon depends on lead time of the slowest mitigation. If your slowest mitigation (e.g., DB sharding) takes 6 months, plan 12+ months out for that resource. Faster mitigations (auto-scaling tweaks) need only weeks of foresight. Senior teams have a rolling 12-month capacity model updated quarterly.

Q: How do I plan capacity for spiky workloads I can't predict?

Three patterns: (1) over-provision the baseline so spikes fit in headroom, (2) build aggressive auto-scaling with predictive elements (e.g., scale up at 9am every day before traffic arrives), (3) build backpressure mechanisms (rate limiting, queue-based deferral) so spikes degrade gracefully rather than catastrophically. Most teams need all three.

Q: Should I use spot/preemptible instances to save money?

For batch and async workloads: yes, spot instances can save 60-90% for tolerant workloads. For user-facing serving: only as a supplement to a baseline of on-demand capacity. AWS Spot can yank 100% of your fleet with 2 minutes notice — if your business depends on it, you need on-demand baseline plus spot supplementation, with graceful degradation when spot capacity disappears.

Q: Do I need a load testing environment that mirrors production?

Ideally yes. Practically, "production-shaped" (same instance types, same database tier, same caching architecture) is enough — even at lower scale. The goal is to validate that the architecture scales, not to recreate production scale. A 1/4-scale staging that mirrors prod's topology is far better than a single-node dev environment.

Q: What about chaos engineering? Where does it fit?

Chaos engineering is capacity testing for failures. You test "can we handle 10x traffic?" with load tests, and "can we handle losing an AZ?" with chaos experiments. Both are part of capacity planning broadly defined. Tools: Chaos Monkey (instance kills), Gremlin (network/CPU/disk faults), Litmus (Kubernetes-native), AWS Fault Injection Simulator.

Q: How do I justify capacity investments to leadership?

Frame it as risk management. "If we don't add capacity X by date Y, we have N% chance of degraded service during Z (e.g., Black Friday), which historically costs us $K in revenue plus reputation damage." Quantified risk + concrete mitigation cost makes the conversation about ROI rather than engineering wishlist.

Q: What's the difference between capacity planning and performance engineering?

Capacity planning answers "how much capacity do we need at projected demand?" Performance engineering answers "how do we make each request use less capacity?" They're complementary: better performance reduces capacity needs (cheaper to scale), and capacity planning identifies where performance work has the most leverage (the bottleneck resource).

Three myths

MYTH: "Auto-scaling means we don't need capacity planning."

Auto-scaling handles day-to-day variation. It does not handle: sudden spikes faster than instances spin up, stateful systems, dependencies that don't auto-scale (your database, third-party APIs, your CDN's per-account quotas), or runaway cost from misbehaving traffic. Auto-scaling is a tool in capacity planning, not a substitute for it.

MYTH: "We have N% headroom, so we have N% growth runway."

Headroom is per-resource, not global. If you have 40% CPU headroom but 5% connection pool headroom, your runway is 5% growth before the connection pool saturates. Senior planning identifies the minimum headroom across all resources and plans against that.

MYTH: "Once we scale to handle 10x, we're set."

Scaling 10x reveals new bottlenecks. The system that handles 10x traffic has different bottlenecks than the system that handled 1x. Network bandwidth becomes important. Replication lag becomes important. Per-tenant noisy-neighbor problems emerge. Senior teams expect each capacity plateau to expose new walls — capacity planning is continuous, not one-time.

Five gotchas

GOTCHA 1: The "noisy neighbor" effect on shared infrastructure.

You provisioned for 5K RPS. You're getting 4K. CPU shows 70%. Cool, you have headroom — except your m5.large is on a host where another tenant is hammering the network. Your steady CPU is 70%, your bursty throughput is constrained, and you have no visibility into it. Mitigations: use larger instance types (m5.2xlarge+ get dedicated cores), use bare metal or dedicated hosts for critical workloads, monitor for unexplained latency variance.

GOTCHA 2: Cache hit rate degrades non-linearly with working set growth.

Your cache holds 80% of working set, hit rate is 95%. You grow 2x — now cache holds 40% of working set. Hit rate doesn't drop to 47.5% (linear) — it might drop to 60-70% (non-linear) because the most-accessed items still fit. But the database load doesn't 2x — it might 5x because cache misses surged disproportionately.

GOTCHA 3: Connection-pooling savings can mask the real problem.

Adding PgBouncer in transaction mode multiplies your effective connection capacity by 50-100x. Great. But if your queries are slow, you're now bottlenecked on per-query throughput, not connections. PgBouncer made you blind to the real issue. Always measure query latency and DB CPU, not just connection counts.

GOTCHA 4: GC tuning can mask memory pressure.

A JVM with aggressive GC tuning can hide a memory leak — GC works harder, throughput drops, latency degrades, but no OOM. You see "high CPU" without obvious cause. The fix is heap dump analysis, not GC tuning. Heap usage trending upward over hours/days is your signal even when GC seems to be coping.

GOTCHA 5: Cost growth is non-linear with scale.

Doubling traffic does not double cost. It might 1.5x cost (efficiency gains from amortization) or 3x cost (sharding overhead, replicated data, caching layers). Cost-per-request changes at every scale plateau. Senior plans include cost projection alongside capacity projection — leadership cares about both.

Mock interview

Interviewer: "Walk me through how you'd plan capacity for a service expected to grow 5x next year."

You: "Five steps, in this order.

First, build the demand model. What's the primary driver — users, transactions, integrations? Project that driver quarter by quarter. From the driver, derive RPS at peak. Don't model just the average — peak-to-average ratio is often 3-5x for consumer products.

Second, decompose per-resource cost. For each request type, measure: CPU, memory, IOPS, network, DB queries, external calls. Then weighted-sum across the request mix at projected peak. This gives me a per-resource projection.

Third, identify saturation points. For each resource, what's the RPS at which it hits 80% utilization? List them in order. The smallest number is the first wall.

Fourth, build the mitigation roadmap. For each wall: what's the architectural change, what's the engineering cost, what's the lead time, what's the trigger. This gives leadership a concrete plan, not 'we'll figure it out.'

Fifth, validate with load testing. Run a stress test up to the predicted peak. Confirm the model. If empirical reality disagrees with the model, the model is wrong — adjust the projection.

What I'd specifically avoid: saying 'we have headroom' based on average dashboard values. Headroom is at peak, per-resource, with growth modeled forward."

What makes this senior: named a five-step methodology, distinguished demand modeling from resource modeling, called out the peak-to-average distinction, included load test validation explicitly, and explicitly named the failure mode they avoid (hand-waving from averages). The interviewer is hearing someone who's planned capacity for real systems.

Interviewer: "Your service handles 1000 RPS at 100ms p99. The product team wants to add a feature that increases p99 to 400ms. What capacity implications do you flag?"

You: "I'd reach for Little's Law immediately.

Currently: L = 1000 × 0.1 = 100 in-flight requests. The thread pool, connection pool, and any concurrency-limited resource is sized for around 100.

After the change: L = 1000 × 0.4 = 400 in-flight requests. The system needs 4x more concurrency to handle the same traffic.

That breaks several things if we don't plan for it: 1. Thread pools need to be sized to 400+ with margin (say 600). 2. Connection pools downstream — if each request holds 1 connection for its duration, we now hold 4x more connections concurrently. 3. Memory pressure — each in-flight request retains memory; 4x in-flight means 4x peak memory consumption. 4. Downstream services — they now see longer-held connections, deeper queues.

So the capacity flag is: a 4x latency increase produces a 4x concurrency increase even at constant traffic. We need to retest at the new latency profile, resize the pools, and check downstream impact. The product team likely wasn't thinking about this — it's an engineering responsibility to flag it before launch.

I'd also ask: is the latency increase fundamental, or is it from synchronous calls that could be parallelized or async? Often the right answer isn't 'absorb the latency cost' — it's 'redesign to eliminate it.'"

What makes this senior: opened with Little's Law (named the formula), applied it numerically, traced the implications across multiple resources (pools, memory, downstream), then challenged the premise by asking whether the latency was fundamental. That last move — questioning whether to accept the constraint at all — is staff-level thinking.

Interviewer: "Tell me about a time you made the wrong capacity call. What happened and what did you learn?"

You: "I'll give you one. Three years ago, we had a service growing steadily — 30% per quarter. CPU averaged 40%, memory was 50%, looked healthy. I assured leadership we had 6+ months of headroom.

What I missed: we had a connection pool sized for 100 connections, and we were averaging 70 used. I never plotted connection utilization on the capacity dashboard — I was watching CPU and memory.

Six weeks later, traffic spiked 30% during a marketing campaign. Connection pool exhausted. Cascading timeouts upstream. We had a 2-hour partial outage.

The lesson — and I bring this up with every junior engineer I work with now — is that headroom is per-resource, not global. The bottleneck is whichever resource hits its wall first, and you only know which resource that is by measuring all of them. CPU and memory aren't a complete picture; you also need connection pools, file descriptors, thread pools, lock contention, and dependency latencies.

After that, I built a 'first wall' dashboard for every service: a visual showing utilization-to-saturation distance for every concurrency-limited resource. The smallest one is the first wall. We caught the next four near-misses with that dashboard."

What makes this senior: specific story, owned the mistake without deflection ("I missed"), explained the systemic gap (only measuring CPU/memory), described the durable change (the "first wall" dashboard), and connected it to ongoing mentorship of others. Interviewers love this kind of answer because it shows learning that changed practice, not just an anecdote.

Interviewer: "How do you decide between scaling vertically vs sharding a database?"

You: "Strong default to vertical, with specific signals that force horizontal.

Vertical first because: sharding is a 3-6 month engineering investment, adds permanent operational complexity (cross-shard queries, distributed transactions, rebalancing), and is hard to undo. Vertical scaling is a maintenance window.

I'd go horizontal only when one of these signals is true: 1. Memory wall. Working set is approaching the largest available instance's RAM. Vertical hits a hard ceiling. 2. Single-AZ risk is unacceptable. Even with vertical scaling, a single primary is a single failure domain — but this might be solved by replication, not sharding. 3. The workload shards cleanly. Per-tenant SaaS, geographic data partitioning, time-series data — these decompose naturally and the sharding overhead is genuinely worth it. 4. You've hit the largest instance. When the next vertical step doesn't exist, horizontal is forced. 5. Geographic distribution matters. Latency to users in Asia can't be fixed by a bigger machine in Virginia.

I'd also distinguish read scaling from write scaling. Read scaling via replicas is much cheaper than full sharding and solves many 'we need more DB capacity' problems. Sharding is only required when write throughput exceeds single-primary capacity.

Practical playbook: when growing toward a wall, scale vertically and in parallel build the sharding capability — partition key chosen, sharding proxy implemented, migration tooling built. Deploy sharding only when forced. This way you have the option without paying the operational cost prematurely."

What makes this senior: strong opinion stated upfront, with specific signal conditions for changing the recommendation. Distinguished read scaling from write scaling — a senior nuance. Suggested building sharding as optionality in parallel with vertical scaling, which is exactly how mature teams operate. Interviewer is hearing thoughtful staging, not binary thinking.

Cheat sheet

THE CORE QUESTION - Not "do we have headroom?" but "which resource saturates first, when, and what's the plan?"

THE FOUR RESOURCES 1. CPU — busy processor 2. Memory — RAM full or thrashing 3. I/O — disk IOPS, throughput, network bandwidth 4. Concurrency — connections, threads, FDs, locks

Plus: external dependencies (rate limits on partners, CDN quotas).

LITTLE'S LAW: L = λ × W - L = concurrent items, λ = arrival rate, W = time per item - Use to size: thread pools, connection pools, in-flight buffers - Latency increase → concurrency increase (4x latency = 4x in-flight at constant traffic)

FOUR-STEP PLANNING 1. Project demand (driver → RPS, with peak-to-average ratio) 2. Decompose per-resource cost per request 3. Find saturation point per resource (80% utilization is the line) 4. Build mitigation roadmap with cost, lead time, trigger

FOUR LEVELS OF LOAD TESTING 1. Smoke (1 RPS, sanity) 2. Load (expected peak, validate SLO) 3. Stress (2-5x peak, find walls) ← most important 4. Soak (12-24h moderate, catch leaks)

Tools: k6 / Locust / vegeta / wrk2

VERTICAL VS HORIZONTAL - Default: vertical until forced - Forced when: memory wall, can't run on one instance, sharding clean, geo-distribution, hit largest instance - Read scaling via replicas ≠ sharding (much cheaper, often sufficient)

AUTO-SCALING RULES - Fast scale-out, slow scale-in (avoid flapping) - Min: cover baseline + AZ failure - Max: 3-5x baseline (cap runaway costs) - Doesn't help: sub-spin-up spikes, stateful systems

TARGET UTILIZATION - Latency-sensitive: 60-70% peak (queueing rises non-linearly past 80%) - Batch: 85-90% fine

GOTCHAS - Headroom is per-resource (smallest one wins) - Closed-loop testing under-estimates real load - Cache hit rate degrades non-linearly - Auto-scaling masks slow leaks - Cost grows non-linearly (could be 0.5x or 3x per traffic 2x)

THE SENIOR DELIVERABLE A table with: resource × current util × saturation point × first wall RPS × mitigation × eng cost × $ cost × lead time × trigger. Not a paragraph. A table.
